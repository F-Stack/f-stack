## 摘要

本文给出 issue #1078「primary-slim（S1）」正式落地的完整测试规格，覆盖 `07` 的 38 个改动点（M3 KNI 部分据 `04` 第五次修订采用 K4 首选 / K3-corrected 退备）。所有测试基建描述均**实际读代码后写**（CMocka 1.1.7+、`tests/unit/` 12 个测试二进制 + 47 个 ini fixture、`tests/integration/` 2 个真EAL 集成二进制）。产出 **22 条新增单测用例（+5 条既有用例复用；表中 24 个编号，计数口径见 §2.1）+ 11 个新增 fixture + 12 条 cmocka 集成用例 + 12 条实机脚本用例 + 5 项性能用例 + 14 项回归项 + 18 项验收标准**，并诚实标注哪些改动点在单测层**不可达**、必须由集成层覆盖。K4 PoC 补丁 `_poc_kni_secondary.patch` 已落地 7 处改动（已复核 `ff_kni_is_runtime_owner()` 存在于 `lib/ff_dpdk_kni.c:100-106`、`owner_proc_id` 存在于 `lib/ff_config.h:342`），E4a 决定性实验已通过。

## 关键结论

1. **测试框架是 CMocka（≥1.1.7，Makefile 有 `$(error)` 版本门禁），不是 Unity**；新用例必须照既有模式写：`load_with_fixture()` / `load_with_proc()` 加载 fixture + `cmocka_unit_test_setup_teardown(fn, test_setup, NULL)` 注册 + `cmocka_run_group_tests()`。**不另建框架、不新增测试二进制**（除集成层的 slim 变体，见第3 节理由）。
2. **`07` 的 C09（B1 放宽）在纯单测层不可达**：`init_lcore_conf()` / `init_mem_pool()` 都是 `static`，`test_ff_dpdk_if.c` 只覆盖公开getter/setter 与 RSS 辅助函数。必须靠 `tests/integration/` 的真 EAL harness（`--no-huge --no-pci --vdev=net_null0`，会真正走 `ff_dpdk_init()` → `init_lcore_conf` → `init_mem_pool` → … → `init_clock`）覆盖，这是本规格最关键的方法学判断。
3. **mbuf 池等值性有两层测法**：单测层做**算术等值性**（测试文件内独立复算旧/新公式，L=2 与 L=8，断言同构配置下相等）——诚实标注为"规格一致性测试，不覆盖 lib 实际代码路径"；集成层做**真实池规模**断言（覆盖 `07` C10 的真实代码）。两者缺一不可。
4. **最重要的一条回归保护是 UT-1078-07 + IT-1078-03**：`primary_slim=0` 且 primary 不在 `lcore_list` 时，必须保持原有 `rte_exit("lcore %u has nothing to do")` 语义——**不能让新开关意外放宽旧校验**（fail-fast 退化为 silent degradation 是运维上的负向改动）。
5. **`tests/integration/test_mtu.sh` 是"步骤打印脚本"而非自动化 harness**（52 行，只有 `echo` 与 `set -e`，无任何断言、无 `kill`/`rm`、且默认 `TARGET_IP`硬编码了一个真实内网地址）。本规格的实机脚本**必须做实**：真实执行 + 退出码汇总 + 目标地址改为必填参数/环境变量（不得写入任何真实 IP），且**所有进程终止走 `/data/workspace/kill_process.sh`、所有清理走 `/data/workspace/rm_tmp_file.sh`**。

### 4.2 对照选择的方法学要求（`06` 关键结论 6，最容易搞错的一点）

> **对照必须选"同数据面进程数"的基线**。primary-slim 下 primary 不收包 ⇒ `lcore_mask=3` + `lcore_list=1` 的**数据面进程数为 1**，正确基准是**配置 B（仅 primary、1 个数据面进程，均值 122267 QPS）**，而**不是**配置 A（2 个数据面进程，均值 135783QPS）。若误用配置 A 会得出"性能下降 10%"的错误结论。

### 4.4 噪声区间与限定说明（必须随数据一并给出）

1. **噪声区间**：配置 A（2 数据面进程）±2.1%；配置 B（1 数据面进程）**±8.8%**（`06` §2.2 实测第 3 轮明显偏低，说明单进程配置对客户端抖动更敏感）。**落在噪声区间内的差异一律判为"无回归"，不得宣称为收益**（`06` §4.3 对 P1的 +4.5% 就是这样处理的）。
2. **客户端是瓶颈**：加倍数据面进程只带来 11% 提升（122267 → 135783）⇒ 服务端未饱和，瓶颈在 `ab`（单机 8 核、单进程多线程）或虚拟化网络链路。**因此绝对值仅用于同配置前后对照，严禁用于容量规划或宣称 f-stack 吞吐能力**（`06` §2.3 与 §6 第 1 条）。
3. **TIME_WAIT 假象**：`ab` 结束后本地端口进入 TIME_WAIT，连续高频压测会出现端口耗尽假象；3 轮之间由 `ab` 自身串行执行即可（`06` §6 第 2 条）。

### 7.2 已知无害噪声（**不得据此判定失败**，`05` §1 已复核）

以下三条 EAL 报错是**预期噪声**，来源是`0000:00:05.0`（内核态网卡）被 EAL 扫描时探测失败：

```
VIRTIO_INIT: eth_virtio_pci_init(): Failed to init PCI device
PCI_BUS: Requested device 0000:00:05.0 cannot be used
ETHDEV: Device 0000:00:05.0 is not driven by the primary process
```

**正确的就绪判定依据**：`f-stack-*.log` 中出现 FreeBSD 栈初始化完成，以及（**仅对持队列的进程**）`Successed to register dpdk interface`。
**注意 slim primary 的特殊性**：slim primary **不会**打出 `Successed to register dpdk interface`（无 ifp，`02` N6 + `05` E3 实测），因此它的就绪判定**只能**依据 FreeBSD 栈初始化完成+ `07` C09/C14 新增的 slim NOTICE 日志。测试脚本若沿用旧的就绪判定会**误判 slim primary 启动失败**——这是最容易踩的坑。

另有一类**曾被误判为失败**的噪声（`05` §9.4 与 §6 的勘误）：secondary 启动时的 `Connection refused` / `bus_vdev_mp` 失败 / `vdev_scan` 失败等报错，在 primary 缺席时会出现，但重启后的 secondary 打出逐字相同的报错却能正常收包⇒ **属伴随噪声，不得作为失败判据**。

### 7.3 时序与串行约束

| 约束 | 说明 |
|---|---|
| 启动等待 | primary 需约 **25s** 完成初始化（FreeBSD 栈 + 端口配置），secondary 同样约 25s。未等待即压测会得到连接超时（`06` §6 第 4 条） |
| **固定端口探测脚本必须串行** | `_e2_probe_client.py` 绑定固定本地端口，与 `ab` 并发会产生**四元组冲突**——`05` §7 明确记录过一次因此被污染的测量。⇒ 脚本层面必须用互斥/顺序执行保证二者不重叠 |
| 每轮之间清理 | 切换配置前`kill_process.sh` 清进程 + `rm_tmp_file.sh` 清 `/var/run/dpdk/rte/` 残留 |
| 启动 secondary 用绝对路径 | `cd ... && nohup ... &` 会把 `cd` 一并放入子shell，导致后续命令 cwd 未切换而报 `No such file or directory`（`05` §14 已踩过） |
| `config.ini` 本地测试值 | 测试期间`config.ini` 会带本机 `lcore_mask` / `idle_sleep` / `[portN]` 真实地址等本地值。**这些一律不得入库**：`git add` 时不选中 `config.ini`（本地值保留在未暂存区供运行使用），也**不得**用 `git checkout config.ini` 还原|
