# 06-性能基线对照报告

## 摘要

本文档记录 issue #1078 可行性调研的性能基线数据。目的：为后续 PoC（primary-slim：primary 不占队列、数据面全部下移secondary）提供**改动前对照基准**，确认 primary 瘦身不引入数据面性能回归。本轮已完成**改动前基线**采集（未改动任何代码），并已完成 **PoC 后对照**采集。结论：PoC 无性能回归，但 slim primary 仍占满一核（需引入空闲休眠）。

## 关键结论

1. **2 数据面进程基线**：约 **135.8k QPS**（3轮均值，区间 132.9k~138.6k），0 失败请求。
2. **1 数据面进程基线**：约 **122.3k QPS**（3 轮均值，区间 115.8k~126.6k），0 失败请求。
3. **关键方法学发现**：从 1 个数据面进程增加到 2 个，QPS 仅提升约 **11%**（122.3k → 135.8k），远低于线性。这说明**瓶颈在客户端/链路侧而非服务端**（客户端 8 核跑 `ab`），因此本环境的绝对 QPS **不能用于评估 f-stack 数据面吞吐上限**，只能用于"改动前 vs 改动后**同配置**对照"。
4. **PoC 无性能回归（已实测）**：slim primary 存活时 **122.4k QPS**（相对单进程基线 +0.08%）、slim primary 崩溃后 **127.7k QPS**（+4.5%），两者均 0 失败请求，**远超**验收门槛 111.5k。
5. **负面发现：slim primary 仍占满一个 CPU 核（99.8%）**——瘦身只减少了它的"职责"，没减少它的"空转"。primary-slim 的收益是稳定性，**不包含 CPU 节省**；正式实现必须引入空闲休眠（`idle_sleep` 当前为 0）。
6. **对 PoC 的对照选择（重要）**：PoC 目标态是 `lcore_mask=3`（primary 瘦身 + 1 个 secondary 收包），其**数据面进程数为 1**，因此正确的对照基准是**1 数据面进程基线（~122.3k）**，而不是 2 进程基线。若拿 2 进程基线对照会得出"性能下降 10%"的错误结论。

### 4.3 对照结论（关键）

| 场景 | 数据面进程数 | QPS 均值 | 相对基线 B（122267） | 判定 |
| --- | --- | --- | --- | --- |
| 基线 B：未改动、单进程 | 1 | 122267 | 基准 | — |

| **P1：PoC + slim primary 已崩溃** | 1 | **127745** | **+4.5%** | **无性能回归**；略高可能因primary 不再空转竞争资源，但仍在噪声区间内，不宣称为收益 |

**验收判定**：`06` §三 设定的验收标准为 ≥ 111.5k QPS 且 `Failed requests = 0`。P1b 与 P1 均**远超**该门槛且零失败请求 ⇒ **PoC 通过性能验收，primary 瘦身不引入数据面性能回归**。

### 4.4 P2：CPU 占用（实测发现的问题）

`ps -o pid,pcpu -C helloworld`（空闲态，无压测流量）：

| 进程 | %CPU |
| --- | --- |
| slim primary（不持队列、不收包） | **99.8** |
| secondary（持队列、收包） | 100 |

**结论（重要负面发现）**：**瘦身后的 primary 仍然占满一整个 CPU 核**。原因是 `main_loop` 仍在紧密空转（跑 timer 与 msg_ring 处理），而 `config.ini` 的 `idle_sleep=0`（第 51 行）意味着无空闲休眠。

**影响**：
- primary-slim 的收益是稳定性，**不包含 CPU 资源节省**；若用户期望"瘦身 = 省一个核"，需明确纠正预期。
- 正式实现**必须**为 slim primary 引入空闲休眠（复用既有 `idle_sleep` 配置或为 slim primary 单独设下限），否则在核数紧张的部署里白烧一个核。
- 该项已登记为待补实验 E12（见 `05` §十三）。

## 六、方法学注意事项（供复现）

1. **客户端是瓶颈**：结论只做同配置前后对照；如需真实吞吐上限，需换更强的压测端或多客户端并发。
2. **每轮之间需清理**：`ab` 结束后本地端口进入 TIME_WAIT，连续高频压测会出现端口耗尽假象；本轮 3 轮之间由 `ab` 自身串行执行，未观测到失败请求。
3. **固定端口探测脚本与`ab` 不可同时跑**：`_e2_probe_client.py` 绑定固定本地端口，与 `ab` 并发会产生四元组冲突（`05` 已记录一次被污染的测量）。
4. **进程启动等待**：primary 需约 25s 完成初始化（FreeBSD 栈 + 端口配置），secondary 同样约 25s；未等待即压测会得到连接超时。
5. 所有清理操作走 `/data/workspace/kill_process.sh` 与 `/data/workspace/rm_tmp_file.sh`（规约要求，严禁直接 `kill`/`rm`）。
