## 四、我对`02` B4「不成立」结论的独立复核

**结论：我独立复核后【同意】`02` 的 B4「不成立」判定**，即「摘掉 primary 的 lcore 后不会产生孤儿 RSS 队列」。

我实际读到的代码（全部为本次`awk` 取行结果）：

```c
// lib/ff_dpdk_if.c:836
nb_queues = pconf->nb_lcores;
```

```c
// lib/ff_dpdk_if.c:487-491（init_lcore_conf 内）
for (j = 0; j < pconf->nb_lcores; j++) {
    if (pconf->lcore_list[j] == lcore_id) {
        queueid = j;
    }
}
```

```c
// lib/ff_dpdk_if.c:801（set_rss_table 内）
reta_conf[i / RTE_ETH_RETA_GROUP_SIZE].reta[i % RTE_ETH_RETA_GROUP_SIZE] = hash++ % nb_queues;
```

```c
// lib/ff_dpdk_if.c:1169-1174
if (nb_queues > 1) {
    /* set HW rss hash function to Toeplitz. */
    ...
    set_rss_table(port_id, dev_info.reta_size, nb_queues);
}
```

推理链（三个独立事实闭合）：

1. **队列总数只由 `pconf->nb_lcores` 决定**（`836`），而 `nb_lcores` 就是该 port 的 `lcore_list` 长度，**与 `nb_procs` / `proc_id` 无关**；同一 `nb_queues` 被 `rte_eth_dev_configure`（`1065`）、`rx_queue_setup`（`1078`）、`rte_eth_dev_start`（`1148`）、`set_rss_table`（`1173`）共用⇒ 网卡侧建的队列数与 reta 映射范围**天然一致收缩**。
2. **每进程的 `queueid` 是其 lcore 在 `lcore_list` 中的下标**（`487-491`），不是 `proc_id` ⇒ 摘掉 primary 的 lcore 后，剩余进程的 queueid 自动变成紧凑的 `0..N-1`，**不会留下无人 poll 的空洞**。
3. **reta 只映射到 `0..nb_queues-1`**（`801`）⇒ 不可能把流量哈希到不存在/无人 poll 的队列。

因此「primary 摘出 `lcore_list` ⇒ 出现孤儿队列」这一 issue 隐含假设在代码层面确实**不成立**，`02` 的裁定正确。

**我要补充两条`02` 的 B4 小节本身没有直接写出的适用边界**（虽在 `03` R11/R12 与 `02` 开放问题中另有覆盖，但 B4 段落内未自带限定，建议加一句交叉指向）：

- **`set_rss_table()` 整体被包在 `#if !defined(FF_FLOW_ISOLATE) && !defined(FF_FLOW_IPIP)` 内（`785`，已复核）** ⇒ 开这两个宏时 reta 一致收缩的论证走的是 `create_tcp_flow`/`create_ipip_flow` 的另一条路径，B4 的结论需另行确认（`03` R12 / `07` U3 / `08` RG-13 已登记，方向正确）。
- **`nb_queues == 1` 时 `1169` 的条件不成立 ⇒ `set_rss_table()` 被跳过**，此时靠 PMD 默认 reta 是否全指queue 0（`02` 开放问题 3 / `03` R11 / `07` U2 已登记为环境受限项，仅 virtio 有正面证据）。

这两点不改变 B4 的「不成立」判定，属适用范围限定。
