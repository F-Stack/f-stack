### 2.2 核心结论

这批文档**有明确的使用价值**，但存在**三类需要纠正的问题**：

## 3. 事实性错误

按严重程度排序。

### 3.1 Nginx 集成目录版本过时

**现状：** 仓库中实际存在的是 `app/nginx-1.28.0`。

**文档声明：** 以下位置仍引用 `nginx-1.25.2`：

- 简化L1:78 — `app/nginx-1.25.2/`
- 完整L1:118 — `app/nginx-1.25.2/         # Nginx 集成`
- 总结:619 — `app/nginx-1.25.2/src/event/modules/ngx_ff_module.c`

**影响：** 读者按文档路径找文件会找不到。这不是笔误，而是文档没有跟随版本升级同步更新。

### 3.2 ff_config.h 行数标注严重错误

**完整L2:304** 写道：

> `ff_config.h (2855 行) - 配置接口`

实际 `lib/ff_config.h` 只有 **352 行**。2855 是 `ff_dpdk_if.c` 的行数。这是一个将文件名和行数搞混的笔误，但出现在接口规范文档的头文件详解部分，容易误导开发者对配置系统规模的判断。

### 3.3 ff_api.h 行数偏差

**文档声明（多处）：** `ff_api.h (412 行)`

**实际：** `lib/ff_api.h` 为 **416 行**。

偏差 4 行，说明行数是某个时间点的快照，之后代码有少量变更但文档没有同步。

### 3.4 lib/Makefile 行数偏差

**简化L1:91** 写道：

> `Makefile (264行) # 编译系统`

**实际：** `lib/Makefile` 为 **765 行**。偏差接近 3 倍。可能当时统计的是某个精简版本或只统计了非空行。

### 3.5 README 中的总行数统计失准

**导览:30** 写道：

> `总计: 3921 行 (+ 1691 行简化版本) = 5612 行`

**实际统计：**

- 完整版三份文档：825 + 1183 + 1112 = **3120 行**（不是 3921）
- 简化版三份文档：333 + 476 + 627 = **1436 行**（不是 1691）
- 含其他文档的总计：**6292 行**（含评审文档）或约 **5839 行**（不含评审文档）

所有三个数字（3921、1691、5612）都与当前实际不符。

同样，**导览:249** 再次写道：

> `总行数: 5612 行`

**总结:597-599** 中的分项行数也不准确：

> | Layer1_System_Overview | 8200 | ...|
> | Layer2_Interface_Specification | 9500 | ...|
> | Layer3_Function_Index | 10200 | ...|

这里用的是"字数"单位而非行数，但 8200/9500/10200 这些字数没有标明统计方式，与实际行数（825/1183/1112）放在一起容易混淆。

### 3.6 EVFILT_READ 等宏定义值错误

简化L3 中 kevent 结构部分写道：

```c
#define EVFILT_READ      0     // 读就绪
#define EVFILT_WRITE     1     // 写就绪
```

完整L3 中写道：

```c
#define EVFILT_READ      1  // socket 或文件可读
#define EVFILT_WRITE     2  // socket 或文件可写
```

**实际（`lib/ff_event.h:39`）：**

```c
#define EVFILT_READ     (-1)
#define EVFILT_WRITE    (-2)
```

FreeBSD kqueue 的 EVFILT 常量全部是负值。文档中两个版本给出了两种不同的正值（0/1 和 1/2），都是错的。虽然应用开发者通常不直接使用数字常量，但作为"函数级索引"文档，这个错误破坏了参考手册的可靠性。

类似地，EVFILT_TIMER、EVFILT_SIGNAL 等的数值也不正确（实际是 -7、-6 等负值）。

### 3.7 ff_errno 值不一致

简化L3:621 写道：

> | ECONNREFUSED | 61 | 连接被拒绝 |

完整L2:408 写道：

> `#define FF_ECONNREFUSED  111  // 连接被拒绝`

**实际（`lib/ff_errno.h:100`）：**

```c
#define ff_ECONNREFUSED 61 /* Connection refused */
```

值为 61（FreeBSD 标准），不是 111（Linux 标准）。完整L2 给出了 Linux 的错误码而非 F-Stack 实际使用的值。由于 F-Stack 的 errno 映射层本身就是为了屏蔽 Linux/FreeBSD 差异，文档中给出错误的数值会直接误导调试过程。

同理，ETIMEDOUT 也存在类似问题——简化L3 写 60，完整L2 写 110，实际是 60（FreeBSD）。

### 3.8 ff_kqueue 参数个数不一致

简化L3:49 的函数索引表中写道：

> | `ff_kqueue` | BSD 事件队列 | **1** | int(kq_fd) |

**实际（`lib/ff_api.h:137`）：**

```c
int ff_kqueue(void);
```

参数个数为 0（void），不是 1。完整L3 中正确写了 `ff_kqueue(void)`，但简化版的表格搞错了。

## 4. 概念边界问题

### 4.1 API 导出层次未明确区分

当前代码中存在至少三个不同层级的"接口"：

1. **`ff_api.h` 头文件声明** — 包括 ff_init/ff_run/ff_stop_run 等，共 416 行
2. **`ff_epoll.h` 补充头文件** — epoll 兼容接口，独立于 ff_api.h
3. **`ff_api.symlist` 动态导出符号表** — 80 个函数，不含 ff_init/ff_run/ff_stop_run

这三层在文档中没有被显式区分。

**具体问题：**

- 完整L3:14 写道：`F-Stack 通过 /data/workspace/f-stack/lib/ff_api.symlist 定义所有公开符号`，紧接着列出的第一组函数就是 ff_init/ff_run/ff_stop_run — 但这三个函数**并不在 ff_api.symlist 中**
- 文档在列举"80+ 导出函数"时将 ff_api.h 中的声明和 ff_api.symlist 中的导出混为一谈
- ff_epoll_create / ff_epoll_ctl / ff_epoll_wait 声明在 ff_epoll.h 中，但文档将它们与 ff_api.h 中的函数放在同一层级描述

**影响：** 做动态链接（.so）或做语言绑定（FFI）的开发者会以为所有 80+ 函数都在 symlist 中可用。实际上 ff_init/ff_run/ff_stop_run 只能通过静态链接 libfstack.a 使用。

### 4.2 LD_PRELOAD 描述与实际不符

完整L1:748-759 和总结:215 提到了 LD_PRELOAD 方式集成：

```bash
LD_PRELOAD=libfstack.so nginx
```

**实际：** 仓库中只生成 `libfstack.a`（静态库），不生成 `libfstack.so`（共享库）。Makefile 中也没有共享库构建目标。LD_PRELOAD 需要 `.so` 文件才能工作。

F-Stack 对 Nginx 的集成实际上是通过修改 Nginx 源码中的 event module 实现的（`app/nginx-1.28.0/src/event/modules/ngx_ff_module.c`），而不是通过 LD_PRELOAD 劫持系统调用。

文档中的 LD_PRELOAD 描述在技术上是有可能实现的（如果构建 .so 并实现 hook），但与当前仓库的实际集成方式不一致，容易误导。

### 4.3 "10 亿+ 并发连接"表述

简化L1:333 写道：

> `F-Stack 能够达到 500 万+ RPS、10 亿+ 并发连接的性能水平`

其他所有位置（包括性能数据表格）都写的是 "10M 并发连接"（1000 万）。10 亿与 1000 万差两个数量级，这是一个孤立的、明显错误的数字。

### 4.4 ff_config 结构体与实际代码偏差

完整L2:306-357 和完整L3:568-621 都给出了 `struct ff_config` 的定义，但两份文档的结构体字段并不完全相同。更重要的是，两者都是文档作者根据理解重构的"概要版"，与 `lib/ff_config.h` 中的实际定义存在差异——实际结构体字段更多、嵌套更深。

作为接口规范文档，如果给出了结构体定义，就需要确保它是精确的。否则不如只列出关键字段并标注"以 ff_config.h 为准"。

## 5. 结构与内容冗余

### 5.1 三类文档之间的重复

当前 docs 中存在三种内容层级：

| 类型 | 文件 | 定位 |
|------|------|------|
| 完整版 | F-Stack_Architecture_Layer{1,2,3}_*.md | 详细技术文档 |
| 简化版 | 01/02/03-LAYER*.md | 精简版本 |
| 汇总类 | README.md, Summary.md, SUMMARY.txt | 入口和导航 |

这三类之间存在大量重复：

- **核心概念**（三大创新、性能数据）在 README、简化L1、完整L1、总结中各写了一遍
- **目录结构**在简化L1、完整L1、README 中各列了一遍
- **核心文件职责表**在简化L1、完整L1 中各写了一遍
- **kevent 结构体**在简化L2/L3、完整L2/L3 中各定义了一遍（且值不同，见 3.6 节）
- **性能数据表格**在 README、简化L1、完整L1、总结中各出现一遍

这种重复导致：

1. 一处修正需要改 4-5 处，极易遗漏
2. 不同位置之间已经开始出现事实不一致（如 EVFILT 值、errno 值、并发连接数）
3. 文档总行数膨胀但信息密度下降

### 5.2 SUMMARY.txt 与 README.md 的定位重叠

SUMMARY.txt 和 README.md 在功能上高度重叠——都是做导航和概览。SUMMARY.txt 更像是生成报告的副产物，README.md 更像是面向用户的入口。保留两者没有明确的收益。

### 5.3 简化版的定位不清

简化版（01/02/03-LAYER*.md）的内容并非完整版的"精简引用"，而是独立重写了一遍——包含独立的结构体定义、独立的代码示例、独立的数据表格。这意味着完整版和简化版实际上是两套平行文档，各自需要独立维护。

## 6. 其他问题

### 6.1 文档中给出了可能不存在的 API 签名

完整L2 和简化L2 中列出了以下函数：

```c
ff_route_ctl(unsigned int cmd, const char *ifname,
             struct linux_sockaddr *dst, struct linux_sockaddr *gateway,
             struct linux_sockaddr *netmask);
```

以及总结:434 中的用法：

```c
ff_route_ctl(ROUTE_CMD_ADD, "eth0", &dst, &gw, &mask);
```

需要确认这些函数签名是否与 ff_api.h 中的实际声明完全匹配，特别是 `ROUTE_CMD_ADD` 等常量名和参数类型。文档中这类"代码化描述"如果与实际头文件不一致，会在编译阶段造成困惑。

### 6.2 性能数据缺少测试环境说明

文档在多处引用同一组性能数据（5M RPS、10M 连接、1M CPS、10μs P99 延迟），但没有任何一处给出：

- 测试硬件配置（CPU 型号、核心数、网卡型号、内存）
- 测试工具和方法
- 报文大小
- 是单核还是多核数据
- 测试年份

作为架构知识库，这些数据如果缺少上下文，更接近"宣传材料"而非"工程基线"。

### 6.3 RACK 不是拥塞控制算法

完整L2:1123 写道：

> `# 特定场景: rack (TCP 选择性确认)`

RACK (Recent ACKnowledgment) 是一种**丢包检测机制**，不是拥塞控制算法。RACK 与 cc.algorithm 的关系是：cc.algorithm 控制的是 CUBIC/BBR 等窗口增长策略，而 RACK 控制的是丢包判定方式。两者正交。将 RACK 放在 `net.inet.tcp.cc.algorithm` 的选项列表中，会误导开发者在配置文件中写出无效配置。

### 6.4 配置示例中缺少 HPTS 相关参数

当前 `config.ini` 中包含 `net.inet.tcp.hpts.skip_swi=1`、`minsleep=250` 等 HPTS (High Precision Timer System) 参数，对 RACK/BBR 性能有直接影响。但文档的配置系统分析部分完全没有涉及 HPTS 相关配置。考虑到 HPTS 参数的修改历史（包括 issue #701/#702 涉及的 tcp_hpts.h 变更），这是一个值得补充的内容。

### 6.5 文档使用了大量 emoji

README.md 中使用了 📚🚀📖📋🎯🔧❓📞 等 emoji 作为段落标记，总结文档和 SUMMARY.txt 中也有类似用法。这在 GitHub 上渲染尚可，但在纯文本环境、终端工具、或某些 PDF 导出场景下会显示为乱码或空白。对于长期维护的工程文档，建议用纯文本标记替代。

## 9. 结论

这套文档的底子是扎实的。三层架构划分、核心模块描述、收发包流向分析、多进程模型说明——这些内容基本正确，对后续的 spec-driven development 有实际参考价值。

但**文档目前处于"首次生成后未经系统校验"的状态**，主要体现在：
