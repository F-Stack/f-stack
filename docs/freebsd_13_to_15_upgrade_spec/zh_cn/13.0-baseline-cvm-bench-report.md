### 3.2 编译事件：`ff_api.symlist` 误判

**首次 `make -j$(nproc)` 失败**：

```text
make: *** No rule to make target 'ff_api.symlist', needed by 'libfstack.a'.  Stop.
```

**根因**：preflight 阶段（Step 1）我用 `find -name '*.symlist'` 收集"产物"传给 `rm_tmp_file.sh`，但 `ff_api.symlist`（1148 字节，81 行符号导出列表）实际是**手工维护源文件**（lib/Makefile L673 把它列为 libfstack.a 前置依赖）。

**恢复**：rm_tmp_file.sh 是 mv→trash 设计（非真删），从 `/data/workspace/.trash/20260603-065813-1727226/data/workspace/f-stack-13.0-baseline/lib/ff_api.symlist` 用 `cp -p` 复原（sha256 `b70dfbca…3f5c523`，与主树和 runtime-fix-done 树完全一致），随后重编成功。

**经验教训**：`*.symlist` 不能盲目当产物清理；后续清理脚本需 whitelist 明确扩展名（仅 `.o` + `libfstack.a`）。

## 6. 关键发现

### 6.1 性能 regression 实证

**runtime-fix-done (15.0) 相比 13.0 baseline 在同硬件同配置下：**

- T2 中负载 **−7.59%** (220,691 → 203,933 req/s)
- T3 高并发 **−9.37%** (239,555 → 217,100 req/s)，p99 **+27.8%** (4.21ms → 5.38ms)
- T1 轻负载 **−2.69%**，但 p99 长尾 **+39.7%** (600us → 838us)

### 6.2 性能特征推断

| 观察 | 推断 |
|---|---|
| T1 轻负载差距小（仅吞吐 −2.7%）但 p99 长尾恶化 +40% | 单 connection 路径无新瓶颈，但偶发长尾事件（GC/锁/中断）增加 |
| T2/T3 中高并发吞吐与 p99 同步劣化，且高并发劣化更大 | 锁竞争/per-CPU 数据结构改动相关性高 |
| Avg latency 在三场景都增加 ~5% | base 路径开销系统性提升（可能 epoch/atomic 改动） |

### 6.3 怀疑根因（需 perf 进一步证实）

5 个 runtime-fix 修复 + 1 防御性 panic stub 中：

1. **P3 (kern_descrip 边界下移 + `badfileops` 恢复)** —— 涉及 `kern_accept` 错误路径，**accept(2) 是高并发 fastpath**，回退 stub 后 file descriptor 创建/销毁可能引入额外原子操作
2. **P1-2 (atomic.h `__storeload_barrier` `_KERNEL` 路径修复)** —— 修复了 SIGSEGV 但同时**启用了真正的 storeload 屏障**，在 SMP 环境每次 store-load 都有内存屏障开销，对 hot path 影响大
3. **P2 (Phase 2 route_rtentry / 11 stub)** —— 启用了真实路由查找，每包 IP 处理多一次 routing table lookup
4. **Phase 1+2+3 累计 fixes** 把"短路 stub"逐步还原为"真实 FreeBSD 路径"，性能 trade-off 是预期的（**正确性换性能**）
