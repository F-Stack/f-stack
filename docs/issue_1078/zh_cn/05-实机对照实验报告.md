# 05-实机对照实验报告（E1/E2 系列）

## 摘要

本文档记录 issue #1078 可行性调研中**最具决定性**的一组实机对照实验。核心命题：primary 异常退出后，secondary 是否还能继续收发包、已建连接是否存活、能否原地恢复。全部实验在**未改动任何代码**的当前 F-Stack 主线上完成，数据来自真实进程与真实客户端流量，非推理。

## 关键结论（决定后续所有工作的意义）

1. **E2：primary 退出后 secondary 进程存活并继续正常服务**——20 条已建连接中 9 条持续 200 OK 直到实验结束（90s+、24 个探测轮次无任何衰减），失效的 11 条是 RSS 哈希落在 primary 队列上的部分。**issue 原文「所有连接都会受到影响」不成立**。
2. **E2b：primary 退出后 secondary 仍可接受全新连接**——12 次新建连接 6 条成功建连并正常响应，失败的 6 条同样是哈希到 primary 队列的部分。
3. **RSS 队列亲和性可被精确证明**：只留primary 时可服务的连接集合与只留 secondary 时可服务的集合**完全互补**，证明每个进程只服务自己队列上的流，进程之间无相互兜底。primary 退出留下的是**无人 poll 的孤儿队列**，而不是"整体瘫痪"。
4. **E2c：primary 退出后、且进程组曾整体退出时，新起的 secondary 静默失能**——进程能启动、能完成 FreeBSD 协议栈初始化，但**完全收不到任何包（0/12）**，EAL 阶段即报 `failed to send to (mp_socket) due to Connection refused`。现象复现两次。**⚠ 但其因果归因已被 E2e 更正：根因是进程组整体退出（`/dev/uioX` refcnt 归零 → 内核态 `pci_clear_master()` 停掉设备 DMA），而非"primary 缺席"本身。**
5. **E2d：issue 的前提「secondary 崩溃可重启且不影响其他进程」成立**——杀掉 secondary 只影响其自身队列的 6 条连接，primary 的 6 条完全无感；重启 secondary 后服务能力完全恢复（12/12）。
6. **E2e（本轮最关键，修正 E2c）：只要至少一个进程持续持有 `/dev/uioX`（refcnt ≥ 1），primary 缺席时 secondary 依然可以重启成功并恢复服务**——3 进程实验中杀掉 primary 后，再杀并重启 secondary(2)（secondary(1) 全程存活），可服务连接从 5/18恢复到 10/18，**复现两次**，重启贡献与其队列份额吻合。

7. **E3（PoC 决定性验证）：primary-slim 实机跑通，且瘦身 primary 崩溃后数据面零影响**——仅 3 行代码改动（解除 B1 的 `rte_exit`、修正 B3 的 mbuf 池公式），配`[port0] lcore_list=1` 让 primary 不持队列：启动正常、12/12 全量收发包；杀掉瘦身 primary 后 **12/12 连接全程零中断（26轮）**、新建连接同样 12/12。对比改动前杀 primary 会失效 11/20（2 进程）或 8/18（3 进程），改善是质变。
8. **E10（残余边界）：primary 崩溃后无法原地重新拉起**——新 primary 在 EAL 阶段即因 `Cannot allocate memzone list` 退出（存量 secondary 仍持有 `/var/run/dpdk/rte/` 运行时配置）；但该失败尝试**不损伤存量 secondary**（服务保持 10/18）。因此控制面降级态不可就地修复，需择机全组重启。

> **综合判读（已据 E2e / E10 更新）**：issue #1078 的价值不在于"救活 secondary"（secondary 本就不随 primary 死），而在于**消除孤儿队列**——让 primary 不持有队列，其崩溃对数据面零影响。且由于 E2e 证明"只要还有别的进程活着，崩掉的 secondary 就能原地重启"，**primary-slim 目标态下 primary 崩溃后既不丢流量、也不需要立即全组重启**。但 E10 表明 primary 不能原地拉回，进程组会停留在**控制面降级态**，仍需择机做一次全组重启才能完全复原。因此该特性的准确价值是：**把"必须立刻全组重启"降级为"可以择机全组重启"**。另一个固有边界是：**所有**进程都退出时设备运行态丢失（`igb_uio` + virtio PMD 模型固有，见 `02` 的 FP-1/FP-2）。

## 二、E1 —— 基线（primary + secondary 均在线）

**步骤**：清理残留 → 启动 primary（等待 ~25s 初始化完成）→ 启动 secondary（等待 ~25s）→ 客户端建立 20 条长连接持续探测。

**原始日志（客户端，已脱敏本地端口列表）**：

```
PHASE=setup established=20/20
ROUND=1  t=0.0  ok=20 dead=0
ROUND=2  t=2.0  ok=20 dead=0
...
ROUND=10 t=18.1 ok=20 dead=0
```

**结论**：E1 基线通过，20/20 连接全部正常，10 轮无抖动。另一次独立复验为 12/12（见 E2d 收尾）。

## 三、E2 —— 决定性实验：primary 退出后已建连接的存活性

**步骤**：在 E1 基线流量持续的情况下（20 条长连接），用 `kill_process.sh` 终止 primary，随后持续观察 90s+。

**原始日志（关键转折点）**：

```
ROUND=10 t=18.1 ok=20 dead=0<- kill primary 之前
ROUND=11 t=53.1 ok=9  dead=11  dead_lports=20002,20003,20004,20005,20008,20010,20013,20015,20016,20017,20019
ROUND=12 t=55.1 ok=9  dead=11  (同一组 dead_lports)
...
ROUND=34 t=99.1 ok=9  dead=11  (同一组 dead_lports，24轮完全稳定)
PHASE=done final_ok=9/20
```

> `ROUND=10 → ROUND=11` 的时间跳变（18.1s → 53.1s）是 11 条失效连接各自 3s socket 超时串行累加所致，即 kill 发生在该间隔内，属探测脚本的时序特征，非服务端异常。

**本机侧观测**：

```
$ pgrep -a -f helloworld
<pid> ./helloworld --conf ../config.ini --proc-type=secondary --proc-id=1     <- secondary 仍在
$ ps -o pid,etime,stat -p <pid>
  ELAPSED 06:07STAT Rl                                     <- 持续存活 6 分钟以上，运行态正常
$ grep -iE "error|fail|panic|abort" <secondary stdout>
（仅有上文列出的 0000:00:05.0 无害噪声，无新增错误）
```

**结论**：

- secondary **不随 primary 退出而失效**，进程存活、运行态正常、无新增错误日志。
- 9/20 已建连接**持续正常服务**（24 轮零衰减），11/20 立即失效。
- 失效与存活的划分**与连接四元组的 RSS 哈希结果一致**，即"该连接原本由哪个进程的队列承接"决定其命运。

> **重要边界（与 `02` 的 N4 交叉确认，结论不得外推）**：本实验用 `kill_process.sh` **强杀** primary，因此 primary **没有**走 `ff_dpdk_run()` 尾部的 `ff_unload_config()` + `rte_eal_cleanup()` 路径（`lib/ff_dpdk_if.c:2879-2885`）。若 primary 为**优雅退出**（`ff_dpdk_stop()` / 信号处理 / 正常返回），`rte_eal_cleanup()` 会释放 EAL 管理的共享资源，本节的 secondary 存活性结论**很可能不成立**。issue #1078 若采用"primary 初始化完成后退出"的设计，必须先解决这一分叉；本轮实测**仅覆盖强杀场景**。

## 四、E2b —— primary 退出后能否接受全新连接

**步骤**：在 primary 已退出、secondary 存活的状态下，客户端发起 12 条**全新**连接。

**原始日志**：

```
CONNECT_FAIL lport=20005 err=timed out
CONNECT_FAIL lport=20008 err=timed out
CONNECT_FAIL lport=20010 err=timed out
（另有若干 CONNECT_FAIL，共 6条）
PHASE=setup established=6/12
ROUND=1 t=0.0 ok=6 dead=6  dead_lports=20002,20003,20004,20005,20008,20010
ROUND=3 t=4.0 ok=6 dead=6  dead_lports=（同上）
PHASE=done final_ok=6/12
```

**结论**：primary 退出后 secondary **仍具备完整的新建连接能力**（三次握手、协议栈处理、业务响应全部正常），只是哈希到 primary 队列的连接请求收不到任何响应（connect 超时）。

## 五、RSS 队列亲和性的交叉证明（互补集合）

同一组固定本地端口（20000~20011）在两种单进程状态下的可服务集合：

| 状态 | 可服务（ok）本地端口集合 | 不可服务（dead） |
| --- | --- | --- |
| 只有 primary 在线 | `20002,20003,20004,20005,20008,20010` | `20000,20001,20006,20007,20009,20011` |
| 只有 secondary 在线 | `20000,20001,20006,20007,20009,20011` | `20002,20003,20004,20005,20008,20010` |
| 两者都在线 | 全部 12 条 | 无 |

两个集合**严格互补且可重复复现**。这是"每进程只 poll 自己的队列、进程间无兜底"的直接证据，也说明 primary 退出后的损失面= 其所持队列承接的流量份额（本环境为 1/2）。

## 六、E2c —— 关键限制：primary 缺席时能否重启 secondary

**动机**：issue 提出「secondary 异常可重启」，那么primary 异常后能否靠"重启 secondary"原地恢复？

**步骤（复现两次，结果一致）**：primary 已被终止 → 终止存量 secondary → 在primary 缺席的情况下重新拉起 secondary（`--proc-type=secondary --proc-id=1`）→ 等待 ~28s → 客户端 12 条新连接探测。

**启动日志（EAL 阶段的明确报错）**：

```
EAL: Detected CPU lcores: 16
EAL: Detected static linkage of DPDK
EAL: Multi-process socket /var/run/dpdk/rte/mp_socket_<pid>_<tag>
EAL: failed to send to (/var/run/dpdk/rte/mp_socket) due to Connection refused
EAL: Fail to send request /var/run/dpdk/rte/mp_socket:bus_vdev_mp
VDEV_BUS: vdev_scan(): Failed to request vdev from primary
EAL: Selected IOVA mode 'PA'
```

**进程状态**：进程**成功启动并常驻**，`f-stack-1.log` 显示 FreeBSD 协议栈初始化完成（`tcp_bbr is now available`、`ipfw2 (+ipv6) initialized`、`Successed to register dpdk interface`），**没有 rte_exit、没有崩溃**。

**服务能力**：

```
PHASE=setup established=0/12
ROUND=1 t=0.0 ok=0 dead=12  dead_lports=20000..20011（全部 12 条）
ROUND=2 t=2.0 ok=0 dead=12
PHASE=done final_ok=0/12
```

**排除干扰的对照**（重要，避免误判为"环境已损坏"）：

1. 在 E2c 之后，完整重启进程组（primary + secondary）并复验，客户端连接恢复 **12/12 全部正常**，证明网卡与环境健康，0/12 并非环境故障。
2. E2c 复现第二次同样得到 **0/12**，确定性成立。

**结论**（⚠ **本节的因果归因已被第九节 E2e 更正，请连同E2e 一起阅读**）：

- primary 缺席**且进程组曾整体退出**时，新起的 secondary **能启动但完全不具备收发包能力**（静默失能，无显式致命错误，易被误判为"启动成功"）。
- EAL 报错指向多进程 IPC（`mp_socket`）：secondary 启动期会向 primary 发请求（此处可见的是 vdev bus 的 scan 请求失败），primary 不在则请求被拒。**但 E2e 已证实这些 EAL 报错只是伴随噪声**——refcnt ≥ 1 时打印同样报错的 secondary 收包完全正常。
- **实践含义（已更正）**：本节最初据此推断"primary 一旦异常，重启 secondary 原地恢复这条路被封死"，该推断**错误**。第九节 E2e 证明：只要至少一个进程持续持有 `/dev/uioX`（refcnt ≥ 1），primary 缺席时 secondary **可以**重启成功并恢复服务。E2c 的 0/12 真实根因是**进程组曾整体退出**（refcnt 归零 → 内核态 `pci_clear_master()` 停掉设备 DMA，见 `02` 的 FP-1）。
- 静默失能的精确机理已由 `02` 任务 E 定位（FP-1：`dpdk/kernel/linux/igb_uio/igb_uio.c:352-366`；FP-2：virtio PMD 在 secondary 早退不重新编程设备），并由 E2e 的 uio fd 计数与 3 进程对照实测印证。

## 七、E2d —— 对照组：primary 在线时杀掉并重启 secondary

**动机**：验证 issue 的前提假设 A（R3）——secondary 异常可重启、不影响其他进程。

**步骤**：primary + secondary 均在线，客户端建立 12 条长连接 → 终止 secondary → 观察 → 重启 secondary → 复验。

**原始日志**：

```
（12 条长连接建立，ok=12）
kill secondary pid=<pid> at 20:20:18
ROUND=8  t=23.0 ok=6 dead=6  dead_lports=20000,20001,20006,20007,20009,20011
ROUND=9  t=25.0 ok=6 dead=6  （同上）
...
ROUND=31 t=69.1 ok=6 dead=6  （同上，primary 的 6 条全程无感）
PHASE=done final_ok=6/12
```

`dead_lports` 恰为 secondary 队列的那6 条，primary 的 6 条**从头到尾未受任何影响**。

**重启后复验**：secondary 重启成功（无EAL 报错），待上一轮探测进程退出释放本地端口后重新探测：

```
PHASE=setup established=12/12
ROUND=1 t=0.0 ok=12 dead=0
PHASE=done final_ok=12/12
```

**结论**：issue 前提假设 A **成立**。secondary 崩溃的影响面严格限定在其自身队列/自身协议栈实例内，且可原地重启完全恢复。

### 方法学诚实说明（一次被污染的测量）

E2d 重启后的首次探测得到 `6/12`，看似"primary 侧反而失效"。经排查为**探测脚本自身的端口冲突**：上一轮70s 探测进程仍在运行并持有那6 个本地端口的活动socket，导致新连接的四元组冲突而 connect 失败——与服务端无关。等待旧探测进程退出后重测即恢复 12/12。此项如实记录，作为后续复现该实验的注意事项：**同一组固定本地端口的探测必须串行、且需等待前一轮进程完全退出**。

## 八、E5 —— 边界验证：`nb_queues == 1` 时跳过 `set_rss_table` 是否仍能全量收包

**动机**：`02` 的开放问题第3 条指出——若最终配置是"primary 不占队列 + 只有 1 个 secondary"，则 `nb_queues == 1`，`lib/ff_dpdk_if.c:1169` 的 `nb_queues > 1` 条件不成立、`set_rss_table()` 被跳过，NIC 的 reta 保持 PMD 默认值。若默认 reta 不指向该进程持有的队列，会全量丢包。

**实验设计（零改动即可验证）**：把 `lcore_mask` 改为 `1`（单进程），此时 `pconf->nb_lcores == 1` → `nb_queues == 1` → `set_rss_table()` 被跳过，且该进程的 `queueid` 为 `lcore_list` 下标 0。这与 PoC 目标态"单secondary 持queueid 0"的**队列拓扑完全同构**，可提前验证 reta 默认值问题。

**步骤**：清理残留 → `lcore_mask=1` 起单进程 → 客户端12 条新连接探测。

**原始日志**：

```
PHASE=setup established=12/12
ROUND=1 t=0.0 ok=12 dead=0
ROUND=2 t=2.0 ok=12 dead=0
PHASE=done final_ok=12/12
```

**结论**：

- `nb_queues == 1` 且 `set_rss_table()` 被跳过时，持有 queueid 0 的进程**仍能收到全部流量**（12/12），PMD 默认 reta 全指向 queue 0 与代码假设一致。
- 因此 `02` 开放问题第 3 条的风险**在本环境（virtio 系 PMD）被消解**。
- **残余风险**：本结论依赖"PMD 默认 reta 全指向 queue 0"这一常见但非标准保证的行为，其他 PMD 上仍需复验；且 PoC 目标态中持队列的是 **secondary**（本实验是 primary），需在 E3 PoC 中再次确认。

## 九、E2e —— 【最关键实验】E2c 结论的修正：refcnt ≥ 1 时 secondary 可在 primary 缺席下重启成功

### 9.1 动机（为什么必须做这个实验）

`02` 的任务 E 从代码层定位出**FP-1**：`f-stack/dpdk/kernel/linux/igb_uio/igb_uio.c:352-366`的 `igbuio_pci_release()` 中，只有**最后一个**关闭 `/dev/uioX` 的进程（`atomic_dec_and_test(&udev->refcnt)` 成立）才会执行 `igbuio_pci_disable_interrupts()` + `pci_clear_master()`（停止设备 DMA）。

而 E2c 的实验序列是：**杀 primary → 杀存量 secondary → 再拉起新 secondary**。此时进程数曾归零 ⇒ refcnt 归零 ⇒ **设备 DMA 已被内核态停掉**。因此 E2c 的 0/12 **可能只证明了"进程组全退后设备失能"，而不是"primary 缺席导致 secondary 无法重启"**。这两个结论的实践含义天差地别，必须用实验区分。

### 9.2 实验设计（3 进程，全程保持 refcnt ≥ 1）

`lcore_mask=7` → 3 个 lcore → 1 个 primary（proc-id=0）+ 2 个 secondary（proc-id=1/2），共 3 个 rx 队列。关键点：**杀 primary 与重启 secondary(2) 的整个过程中，secondary(1) 始终存活**，因此 `/dev/uioX` 的 refcnt 始终 ≥ 1，`pci_clear_master()` 永不触发。

**refcnt 机制的实测印证**（`ls -l /proc/*/fd | grep -c uio`）：

| 状态 | 持有 uio fd 的进程数 |
| --- | --- |
| primary + s1 + s2 | **3** |
| 杀 primary 后 | **2** |
| 再杀 s2 后 | **1** |
| 重启 s2 后 | **2** |

即**每个f-stack 进程各持有一个 `/dev/uioX` fd**，与 `02`任务 E 的 FP-1 推断完全一致。

### 9.3 实验步骤与数据

客户端每步都建立 18 条**全新**长连接（18 条在 3 个队列上大致均分）。

| 步骤 | 状态 | 存活进程 | uio refcnt | 可服务连接 | dead 集合 |
| --- | --- | --- | --- | --- | --- |
| 1 | 基线 | primary + s1 + s2 | 3 | **18/18** | 空 |
| 2 | 杀 primary | s1 + s2 | 2 | **10/18** | 8 条（primary 队列份额） |
| 3 | 再杀 s2 | s1 | 1 | **5/18** | 13 条 |
| 4 | **重启 s2**（primary 仍缺席） | s1 + s2(new) | 2 | **10/18** | 8 条（与步骤 2 **完全相同**的集合） |
| 5 | 再杀 s2 → 再重启 s2（复现） | s1 + s2(new2) | 2 | **10/18** | 同上 |

原始日志（步骤 3 与步骤 4/5 的对比是本实验的判据）：

```
# 步骤 3：只剩 s1
PHASE=setup established=5/18
ROUND=1 t=0.0 ok=5 dead=13

# 步骤 4：primary 仍死，重启 s2 后
ROUND=1 t=0.0 ok=10 dead=8  dead_lports=20005,20007,20008,20010,20013,20014,20015,20017
PHASE=done final_ok=10/18

# 步骤 5：第二次重启 s2，复现
ROUND=2 t=2.0 ok=10 dead=8  dead_lports=（同上，完全一致）
PHASE=done final_ok=10/18
```

重启后的 s2 启动日志与 E2c 完全相同（同样有 `failed to send to (mp_socket) due to Connection refused`、`Fail to send request...:bus_vdev_mp`、`vdev_scan(): Failed to request vdev from primary`），**说明这些 EAL 报错确实只是伴随噪声，不影响 secondary 收包**。

### 9.4 结论（修正 E2c）

1. **primary 缺席时，secondary 完全可以重启成功并恢复服务**——前提是**至少有一个进程持续持有 `/dev/uioX`**（refcnt ≥ 1），使设备运行态不被内核态 `pci_clear_master()` 破坏。重启贡献了 `10 − 5 = 5` 条连接，与其队列份额吻合，且**复现两次**。
2. **E2c 的 0/12 必须重新归因**：其根因是**进程组曾整体退出（refcnt 归零 → 设备 DMA 被停）**，而非"primary 缺席"。E2c 的现象真实、但原先的因果解释是错的，本节予以更正。
3. **对 issue #1078 的意义（决定性）**：这条修正把 #1078 的可达性大幅提升——
   - 在 primary-slim 目标态下，primary 崩溃后**所有 secondary 仍在**（refcnt ≥ 1），因此崩掉的任何 secondary 都能**原地重启恢复**，**不需要全组重启**；
   - 即 issue 原文期望的"缩小影响面"与"故障后可恢复"**两者都能达成**，其代价仅是 primary 必须常驻（不得优雅退出、不得关闭其 uio fd）。
4. **仍然成立的边界**：若**所有**进程都退出（含primary-slim 场景下最后一个 secondary 也挂掉），设备运行态丢失，必须全组重启。这是 `igb_uio` + virtio PMD 的模型固有行为（`02` 的 FP-1/FP-2），与 f-stack 无关。
5. **待补充的验证**：本实验中 primary 是**被强杀**的。若 primary 走优雅退出（`rte_eal_cleanup()`，`02` 的 N4），除EAL 共享资源被拆除外，其持有的 uio fd 也会被正常 close（refcnt −1，但仍 ≥1），两者的叠加影响需另行验证。

## 十、E10 —— 残余边界：primary 崩溃后能否原地重新拉起以恢复控制面

### 10.1 动机

E2e 证明 primary 崩溃后数据面不受影响、secondary 可原地重启，但进程组仍处于**控制面降级态**（无 IPC 服务端、无法扩堆、无中断处理——DPDK 官方三条硬约束，见 `01` §1.2）。自然的下一问：**能否在存量 secondary 继续运行的情况下把 primary 重新拉起来，就地恢复控制面？**

### 10.2 步骤与结果

状态：primary 已被强杀，2 个 secondary（proc-id=1/2）仍在运行并服务流量。此时以 `--proc-type=primary --proc-id=0` 重新拉起 primary。

```
EAL: Detected CPU lcores: 16
EAL: Multi-process socket /var/run/dpdk/rte/mp_socket
EAL: Selected IOVA mode 'PA'
EAL: Cannot allocate memzone list
EAL: Cannot init memzone
EAL: Error - exiting with code: 1
Error with EAL initialization
（进程退出，exit code = 1）
```

**失败尝试后的存量进程状态**（关键的安全性观察）：

```
$ pgrep -a -f helloworld
<pid> ... --proc-type=secondary --proc-id=1     <- 仍在
<pid> ... --proc-type=secondary --proc-id=2     <- 仍在
$ （客户端复测）ROUND=1 ok=10 dead=8   PHASE=done final_ok=10/18
```

### 10.3 结论

1. **primary 不能原地重新拉起**：新 primary 在 EAL 初始化阶段即因 `Cannot allocate memzone list` 失败退出。成因是 `/var/run/dpdk/rte/` 下的运行时配置（`config`、`fbarray_memzone` 等）仍被存量 secondary 持有/映射，新 primary 试图重新创建这些全局结构时冲突。
2. **失败是安全的（fail-fast，无副作用）**：这次失败的拉起尝试**没有**损坏存量 secondary，服务能力保持 10/18 不变。这是个好性质——误操作不会二次伤害。
3. **因此控制面降级态在当前架构下不可就地修复**：要恢复完整能力（IPC、扩堆、中断、KNI、`ff_*` 工具链），必须**停掉所有进程 + 清理 `/var/run/dpdk/rte/` 残留 + 全组重启**。
4. **对 issue #1078 的意义（诚实边界）**：primary-slim 的收益是"primary 崩溃时**数据面零损失**、且崩溃的 secondary 可原地重启"，业务可以**继续跑**，但集群处于**控制面降级态**，需要在合适的维护窗口做一次全组重启才能完全复原。这比 issue 原文设想的"影响范围小"已经好很多（原设想仍假定所有连接受影响），但**不等于"完全无需重启"**，结论中必须如实说明。
5. **运维含义**：primary-slim 让"必须立刻全组重启"从**紧急故障**降级为**计划内维护**。这正是该特性的核心价值。

## 十一、E3 —— 【PoC 决定性验证】primary-slim 实机跑通与 primary 崩溃零影响

### 11.1 PoC 补丁（最小 diff，仅作调研证据，不入库）

补丁留档：`docs/issue_1078/zh_cn/_poc_primary_slim.patch`（2 个 hunk、共 3 行变更，仅动`lib/ff_dpdk_if.c`）。

| # | 位置 | 改动 | 对应阻塞点 |
| --- | --- | --- | --- |
| 1 | `lib/ff_dpdk_if.c:508-510` | `nb_rx_queue == 0` 的 `rte_exit` 增加 `&& rte_eal_process_type() != RTE_PROC_PRIMARY` 条件，允许 primary 无队列 | **B1** |
| 2 | `lib/ff_dpdk_if.c:535` | mbuf池 RX 项由 `ff_cur_lcore_conf()->nb_rx_queue * nb_lcores` 改为 `nb_ports * nb_lcores`，去掉对**本进程**队列数的依赖 | **B3** |

PoC 采用「由 primary 不在任何 port的 `lcore_list` 中**自动推导**」而非新增显式配置开关，以最小化 diff；正式实现按 `03` 的设计使用显式 `[dpdk] primary_slim` 开关。PoC **未**实现 `03` 的改动 #3（跳过 `rte_eal_cleanup()`）与 #4（ifp 归属），因为本轮只验证"能否跑通 + primary 崩溃影响面"，且 primary 常驻不退出时改动 #3 不会被触发。

编译：按规约在 `lib/` 与 `example/` 分别 `make clean` 后完整重新编译，均 **exit 0、无 error**。

### 11.2 PoC 运行配置

```ini
[dpdk]
lcore_mask=3          # 2 个 lcore：lcore0 给 primary，lcore1 给 secondary

[port0]
lcore_list=1          # 关键：只把 lcore1 列入，primary 的 lcore0 不在列表中
```

此时 `nb_queues = pconf->nb_lcores = 1`，唯一队列（queueid 0）归secondary；primary 不持任何 rx/tx 队列。

### 11.3 E3 —— 启动与全量收发包

| 步骤 | 观测 | 结果 |
| --- | --- | --- |
| 启动瘦身 primary | 进程常驻，**没有** `lcore 0 has nothing to do` 的 `rte_exit` | **通过**（B1 已解除） |
| primary 的 `f-stack-0.log` | FreeBSD 栈初始化完成，但**没有** `Successed to register dpdk interface` | 符合设计预期：`nb_tx_port == 0` ⇒ `ff_dpdk_if_up()` 循环 0 次 ⇒ 不attach ifp（`02` 的 N6 得到实测印证） |
| 启动 secondary | 正常，`f-stack-1.log` 有 `Successed to register dpdk interface` | **通过** |
| 客户端 12 条新建长连接 | `PHASE=setup established=12/12`；`ROUND=1/2 ok=12 dead=0` | **12/12 全量收发包通过** |

> 这同时复核了 `02` 开放问题第3 条（`nb_queues == 1` 时 `set_rss_table` 被跳过）在**持队列者为 secondary** 时同样成立——E5 的结论可外推。

### 11.4 E3b —— 【核心验证】瘦身 primary 崩溃时数据面影响面

步骤：12 条长连接持续探测，在 t≈10s 用 `kill_process.sh` 杀掉**瘦身 primary**，继续观察到 t=50s。

```
（kill slim primary at t≈10s）
ROUND=13 t=24.0 ok=12 dead=0
ROUND=14 t=26.0 ok=12 dead=0
...
ROUND=25 t=48.1 ok=12 dead=0
ROUND=26 t=50.1 ok=12 dead=0
```

**结果：12/12 连接全程零中断，26 个探测轮次无一次失败。**

对比基线（未改动代码、primary 持队列时）：E2 中杀 primary 导致 **11/20 连接立即失效**；E2e 的 3 进程环境中导致 **8/18 失效**。

### 11.5 E3c —— 瘦身 primary 崩溃后的新建连接能力

primary 已死、仅 secondary 存活时，客户端发起 12 条**全新**连接：

```

ROUND=1 t=0.0 ok=12 dead=0
PHASE=done final_ok=12/12
```

**结果：12/12，新建连接能力完全不受影响。**

### 11.6 E3 系列结论

1. **PoC 跑通，issue #1078 的核心命题在实机上成立**：只需 3 行代码改动（解除 B1、修正 B3），primary 即可"只做初始化、不收包"，且数据面完全正常。
2. **子目标 (b)「缩小影响面」达成度为 100%（存量+ 新建流量）**：瘦身 primary 崩溃后，已建连接零中断、新建连接零失败。相比改动前的 11/20（2 进程）或 8/18（3 进程）失效，改善是**质变而非量变**。
3. **`02` 的 B4 结论（队列数与 queueid 随 `lcore_list` 一致收缩、不产生孤儿队列）获得实测确证**。
4. **`02` 的 N6 获得实测印证**：瘦身 primary 确实不 attach ifp（无 `register dpdk interface` 日志），且**不会崩**；但这意味着 primary 上没有 f-stack 网络接口对象，控制面能力归属需按 `04` 处置。
5. **残余问题（实测发现）**：瘦身primary 仍占满一个 CPU 核（见 `06` 的 P2：99.8%），因为主循环仍在空转跑 timer/msg_ring。这印证了 `03` 的风险项，正式实现**必须**为 slim primary 引入 idle_sleep 或阻塞式等待（当前 `config.ini` 的 `idle_sleep=0`）。
6. **未覆盖项**：KNI 开启场景（`[kni]` 段在本环境未配置、运行时关闭）；改动 #3（`rte_eal_cleanup()` 跳过）与优雅退出路径；多 secondary（`lcore_list=1,2`）的 PoC 组合。

## 十二、实验结论对 issue 诉求的映射

| issue 诉求/假设 | 实测裁定 | 依据 |
| --- | --- | --- |
| R3「secondary 异常可重启、不影响其他进程的队列和已建连接」 | **成立** | E2d |
| R4「primary 异常退出，整个进程组都得重启」 | **部分不成立（已据 E2e/E10 更正）**：primary 崩溃后其余进程继续服务自身队列，且只要还有进程存活（uio refcnt ≥ 1），崩掉的 secondary 可原地重启恢复 ⇒ **无需立即全组重启**；但 primary 不能原地拉回（E10），进程组停留在控制面降级态⇒ **仍需择机全组重启**。准确表述：从"紧急必须重启"降级为"可择机重启" | E2 + E2b + **E2e** + **E10** |
| R4「所有连接都会受到影响」 | **不成立**：仅 primary 队列承接的连接受影响（2 进程环境 ~1/2，3 进程环境 ~1/3），其余队列的连接零影响 | E2（9/20 持续 24 轮正常）+ 互补集合证明 + E2e（10/18） |
| R8「对连接的影响范围也小」（若 primary 不持队列） | **成立且强于 issue 预期**：孤儿队列消除后 primary 崩溃对数据面**零影响**，且故障后可原地重启崩溃的 secondary | E2/E2b/E2e 实测 + `02` B4（队列数来源）代码坐实；最终由 E3 PoC 复核 |
