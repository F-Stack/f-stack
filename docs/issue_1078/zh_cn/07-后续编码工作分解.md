# 07-后续编码工作分解

> 修订记录：2026-08-07 据门禁报告 R1/R6/R8 修正 C28 行号（2081→2080、2056→2055）并补文本锚点、修正 Makefile 行数引用、统一单测用例数口径。

## 摘要

本文是 issue #1078「primary 稳定性控制」在**用户决定正式落地 S1「primary-slim」**前提下的编码工作分解。方案已由 `03` 定档、`04` 补齐 KNI/控制面归属、`05` 的 E3 系列 PoC 实机跑通（3 行改动 + 1 项配置，杀 slim primary 后 12/12 连接零中断）、`06` 确认无性能回归。本文把方案拆成 **4 个里程碑、38 个可执行改动点、2 个新增配置项**，逐项给出文件:行号、改法要点、依赖、风险与回滚方式，并明确标注哪些已被 PoC 实测覆盖、哪些是全新未验证代码。

## 关键结论

1. **PoC ≠ 正式实现**。PoC 只做了 2 处（B1 放宽 + B3 池公式近似），用"primary 不在任何 `lcore_list`"**自动推导**而非显式开关；`03` 的改动 #3（跳过 `rte_eal_cleanup()`）、#4（ifp 归属日志）、idle_sleep 下限、全部校验链（V2~V6）、KNI、MTU 归属**均未实现**。正式落地的新增代码量约为 PoC 的 10 倍。
2. **M1（最小可跑集）16 个改动点、4 个文件，是唯一"必须一次做完才能跑"的批次**；其中 C09+C10 必须同批提交（C09 单独上会造成 mbuf 池欠配）。M1 完成即可复现 PoC 的全部实测结论，并额外解决 P2 的 CPU 空转问题。
3. **最强回滚点是配置级**：`primary_slim=0`（默认值）+ 恢复 `lcore_list` 注释 ⇒ 行为与改造前逐字一致。这是选显式开关而非自动推导的直接收益，任何里程碑都可用一行配置回退。
4. **两处必须写进代码注释与运维文档的高危点**：(i) 绝不能给 slim primary attach ifp，否则 `tx_queue_id[port]` 恒为 0 会与 `lcore_list[0]` 那个 secondary 并发写同一条非 MT-safe 的 tx 队列（`03` R3）；(ii) slim primary 是**常驻**控制面进程，禁止优雅退出（`rte_eal_cleanup()` 会抽走全体 secondary 的共享内存，`02` N4）。
5. **KNI（M3）是唯一改动量大、风险集中的批次**（9 个点，含新增一条 ring 与广播/多播门禁语义变更），M1/M2 阶段用配置期显式拒绝 `primary_slim=1 && kni.enable=1` 把它隔离在外。

> **输入基线声明**：本文写作时 `03`/`04` 已包含 2026-08-07 第二轮修订（据 E2e/E10 上调 S1、下调 S5 为兜底、A4 闭环、新增风险 R14）。本文引用的 `03` §5 为 7 步最小集 + 6 步完整集 + 5 项 O 级 + R0~R3 回滚点的修订版。

## 八、不做项清单（范围边界）

> 目的：防止范围膨胀。以下项**明确不在本方案范围内**，理由均有代码或实测依据。

| 编号 | 不做项 | 理由 |
|---|---|---|
| **X1** | **primary 热切换 / primary failover**（选举新primary 接管共享内存所有权） | DPDK 模型固有约束：primary 是 IPC 唯一服务端（`01` §1.2.1，`eal_common_proc.c:750-751`）、全体 secondary 的扩堆代理（§1.2.2，`malloc_heap.c:484`/`:1030`）、唯一能收中断的进程（§1.2.5）。且 `05` E10 已实测 **primary 不可原地拉回**（`Cannot init memzone`，exit 1），因为 `/var/run/dpdk/rte/` 的 `config`/`fbarray_memzone` 仍被存量 secondary 持有映射 |
| **X2** | **连接迁移 / 连接接管**（把 primary 队列上的连接迁到secondary） | S1 从根上让 primary **不持有任何队列** ⇒ 不存在需要迁移的连接（`02` B4 + D.3.2 代码坐实、`05` E3b 实测 12/12 零中断）。做迁移是解决一个已被消除的问题 |
| **X3** | **运行期队列重配 / 动态增删 secondary 并调整 `nb_queues`** | `nb_queues = pconf->nb_lcores`（引自 03）在`init_port_start()` 一次性决定；运行期改需 `dev_stop/dev_configure/dev_start`，多进程下会瞬断全体 secondary（同 `04` §3.1 对 MTU `-EBUSY` 分支的判断） |
| **X4** | **KNI 完整重写 / KNI owner failover** | `04` §2.3 已论证：K3 把 owner 留在 primary，KNI 能力的可用期恰好与控制面其他能力**同生共死**，无需为 KNI 单独设计 failover；K2（owner 迁 secondary）反而制造"控制面能力分散在两个进程"的新故障组合，`04` 判定推荐度低 |
| **X5** | **消除 `igb_uio` 的 refcnt 语义**（让"所有进程都退出"后设备仍可用） | 内核模块行为（FP-1：`igb_uio.c:352-366` 的 `atomic_dec_and_test(&udev->refcnt)` → `pci_clear_master()`，引自 02/03），f-stack 侧无法消除。这是 S1 的**固有边界**（`03` §6.1 第 3 条） |
| **X6** | **降级态自动检测与主动告警** | `03` 未决问题 10 明确"本轮不设计"，仅记录必要性（候选思路：secondary 周期性探测 `mp_socket` 可连通性或轻量 `rte_mp_request_sync()` 探活）。属后续里程碑 |
| **X7** | **运行期 link status（LSC）感知** | C22：N7 是**既有**缺陷（全库无运行期 LSC 回调），非 slim 引入；若补只能补在 slim primary 侧（`01` §1.2.5）。本轮仅登记 |
| **X8** | **in-flight msg 对象泄漏修复** | `02` 开放问题 5：primary 被强杀时其持有的 msg 对象永久泄漏（消费者才 `rte_mempool_put`）。`03` §6.2 明确 S1 不改善此项 |
| **X9** | **S3（primary 保留最小队列）与 S4（`thread_mode=1`）的落地** | S3 是 `kni.enable=1` 且不接受 KNI 改造风险时的**兜底备选**（= `04` 的 K1），本方案走 K3；S4 是与 #1078 正交的长期方向，且故障域反向放大（一挂全挂、单进程退出即 refcnt 归零） |
| **X10** | **S5（外部守护+ 分层恢复）的实现** | `03` §3.1 定位为**配套建议（兜底）**、0 个 f-stack 文件改动、纯外部编排。属运维侧工作，不在本编码分解内（但 C38 需在文档中给出它要自动化的那次"计划内全组重启"流程） |
| **X11** | **为本特性额外预留 hugepage** | `03` §2.3 改动 #2 已论证：C10 修好公式后内存占用相对现状**不增加**（同构配置等值，slim 配置略降） |
| **X12** | **修改 `tools/` 的默认 `ff_proc_id`** | `04` §4.1 候选乙已被否决：会破坏 `ff_top`/`ff_traffic`/`ff_sysctl` 等 per-proc 数据采集的向后兼容且用户不自知；改用 C21 的提示方案|
