> 所有 `文件:行号` 均由本agent 实际 `read_file` / `grep -n` 核准（探测时间：2026-08-07）。
> 修订记录：2026-08-07 据门禁报告 R5/R7 补 A.1 统计口径说明、修正 ff_memory.c 行号、为 B4 补适用边界交叉指向。

## 摘要

本文枚举 f-stack `lib/`、`tools/` 中全部 primary/secondary 分叉点，逐条坐实 issue #1078「primary 瘦身、只做初始化不收包」路线上的 8 个假设阻塞点，并给出调用链与最小改动点清单。结论是：**真正的硬阻塞只有 3 处（B1 的 `rte_exit`、B2 的 KNI 配置校验、B3 的 mbuf 池公式）**；B4 假设的「队列数/queueid 错位」在代码层面**不成立**——队列数与 RSS reta 都由 `pconf->nb_lcores`驱动，会随primary 退出 `lcore_list` 自动收缩，因此"孤儿队列"会自然消失。另发现 8 个 B1~B8 之外的新阻塞点，其中「primary 优雅退出会执行 `rte_eal_cleanup()`」和「`msg_ring` 按 proc_id 索引导致 tools 默认 proc_id=0 无消费者」两条对可用性影响最大。

## 关键结论

1. **B1 成立且是第一道硬墙**：`lib/ff_dpdk_if.c:508-510` 在 `nb_rx_queue == 0` 时 `rte_exit`，且 `init_lcore_conf()` 是 `ff_dpdk_init()` 的**第一个**子步骤（`lib/ff_dpdk_if.c:1682`），primary 一旦不在任何 port的 `lcore_list` 中会在EAL 初始化后立刻退出，后续一切都跑不到。
2. **B4 不成立（重要的好消息）**：`nb_queues` 来源是 `pconf->nb_lcores`（`lib/ff_dpdk_if.c:836`），不是 `nb_procs`；`queueid` 是 lcore 在 `lcore_list` 中的**下标**（`lib/ff_dpdk_if.c:487-491`），与 `proc_id` 完全解耦；`set_rss_table()` 也按同一个 `nb_queues` 重算 reta（`lib/ff_dpdk_if.c:1169-1174`）。所以 primary 退出 `lcore_list` 后队列总数、queueid、reta、`dispatch_ring` 数量会**一致地收缩为 secondary 数量**，不会产生"孤儿队列"。
3. **B3 部分成立**：mbuf 池公式的 RX 项 `nb_rx_queue = ff_cur_lcore_conf()->nb_rx_queue * nb_lcores`（`lib/ff_dpdk_if.c:535`）唯一依赖**本进程**的队列数，而池只由 primary 创建（`lib/ff_dpdk_if.c:571-590`）。primary 队列数变0 会让整个 RX 项归零，池对所有 secondary 严重欠配。必须改成按 port 的 `nb_lcores` 求和。
4. **KNI 是 primary 强绑定的重灾区**：`ff_kni_is_owner_thread()` 直接等价于 `proc_type == primary`（`lib/ff_dpdk_kni.c:93-97`），virtio_user 口的 hotplug、`kni_stat` 分配、`kni_ring_%u` 创建、`ff_kni_process` 调用全部挂在它上面（共 7 个调用点）。primary 瘦身必须把 KNI owner 参数化。
5. **运行期 secondary 不依赖 primary（与实测 E1/E2 一致）**：`lib/` 中不存在任何 `rte_mp_request` / `rte_mp_sendmsg`；主循环热路径只用 `rte_eth_rx_burst`/`tx_burst`/`rte_ring_dequeue_burst`/`rte_mempool_get|put`，指针全部在初始化期`lookup` 到。唯一的运行期 `rte_malloc` 在 `lib/ff_dpdk_if.c:2869`（进主循环之前）与 `3434`（初始化期）。但 **primary 优雅退出路径会调 `rte_eal_cleanup()`（`lib/ff_dpdk_if.c:2884`）**，这是与 `kill` 强杀不同的、会破坏 secondary 的路径。

## 任务 B：8 个阻塞点逐条坐实

### B1 `nb_rx_queue == 0` 触发 `rte_exit("lcore %u has nothing to do")`

**结论：成立（硬阻塞，第一道墙）。**

**位置**：`lib/ff_dpdk_if.c:459-460`（`thread_mode` 分支）、`lib/ff_dpdk_if.c:508-510`（多进程分支）。预读行号准确。

```c
// lib/ff_dpdk_if.c:485-513
        int queueid = -1;
        int i;
        for (i = 0; i < pconf->nb_lcores; i++) {
            if (pconf->lcore_list[i] == lcore_id) {
                queueid = i;
            }
        }
        if (queueid < 0) {
            continue;
        }
        ...
    if (ff_cur_lcore_conf()->nb_rx_queue == 0) {
        rte_exit(EXIT_FAILURE, "lcore %u has nothing to do\n", lcore_id);
    }

    return 0;
}
```

```c
// lib/ff_dpdk_if.c:459-460（thread_mode 分支，语义等价）
            if (lc->nb_rx_queue == 0)
                rte_exit(EXIT_FAILURE, "lcore %u has nothing to do\n", lcore_id);
```

**成因**：`init_lcore_conf()` 用「本进程 lcore 是否出现在 port 的 `lcore_list` 中」来推导队列归属。`lcore_id` 取自 `ff_global_cfg.dpdk.proc_lcore[proc_id]`（`lib/ff_dpdk_if.c:475`）。primary 若从所有 port 的 `lcore_list` 里去掉，逐 port 循环（`481-506`）每次都在 `492-494` `continue`，`nb_rx_queue` 保持 0。

**完整失败路径**（primary 不在任何 `lcore_list` 中）：
1. `ff_config.c` 侧校验先过：`1405-1414` 只检查 `lcore_list ⊆ proc_lcore`（单向），不要求 primary 在 `lcore_list` 中 → **不报错**（除非开KNI，见 B2）。
2. `ff_init()`（`lib/ff_init.c:36`）→ `ff_dpdk_init()`（`lib/ff_init.c:43`）。
3. `ff_dpdk_init()` 的 `1657-1665` `nb_procs`/`proc_id` sanity 通过（`nb_procs` 由 coremask 位数得来，与 `lcore_list` 无关）。
4. `1667` `rte_eal_init()` 成功。
5. `1682` `init_lcore_conf()` → `508-510` `rte_exit(EXIT_FAILURE)` → **进程立即死亡**。
6. 后续 `init_mem_pool()`（`1684`）、`init_port_start()`（`1718`）全部不会执行 → **secondary 也无法启动**（`mbuf_pool_0` /各 ring / eth dev 都没人创建，secondary 在 `593`/`627`/`711` 的 `lookup` 会拿到 NULL 并 `rte_exit`/`rte_panic`）。

**触发条件**：`proc_type=primary` 且 primary 的 lcore 不在任一 `[portN].lcore_list` 中（`thread_mode=0`）。

**影响面**：整个进程组无法启动。这是 #1078 路线上必须首先拆掉的门。

**绕过所需改动**：在 `508-510`（和 `459-460`）引入「initializer-only」语义开关，允许 `nb_rx_queue == 0` 时跳过 `rte_exit` 并让本进程走精简路径；同时必须处理 B3（池公式）与 N6（`nb_tx_port == 0` 导致不attach ifp）。

### B2 KNI 开启时强制 primary lcore 必须在每个 port 的 `lcore_list` 中

**结论：成立（配置期硬阻塞）。**

**位置**：`lib/ff_config.c:1415-1435`。预读行号准确。

```c
// lib/ff_config.c:1415-1435
        /*
         * only primary process process KNI, so if KNI enabled,
         * primary lcore must stay in every enabled ports' lcore_list
         */
        if (cfg->kni.enable &&
            strcmp(cfg->dpdk.proc_type, "primary") == 0) {
            int found = 0;
            int j;
            uint16_t lcore_id = cfg->dpdk.proc_lcore[cfg->dpdk.proc_id];
            for (j = 0; j < pc->nb_lcores; j++) {
                if (pc->lcore_list[j] == lcore_id) {
                    found = 1;
                }
            }
            if (! found) {
                fprintf(stderr,
                         "primary lcore %d should stay in port %d's lcore_list.\n",
                         lcore_id, pc->port_id);
                return -1;
            }
        }
```

**KNI 侧真实 primary 依赖点追踪**：

**成因**：KNI 的 exception path 用一个 virtio_user vdev 承载，vdev 的 hotplug 只能由 primary 做（DPDK 约束），历史实现把「KNI owner」直接等同于「primary」。而 `ff_kni_process()` 必须在有`rx_queue` 的主循环里被调用（`lib/ff_dpdk_if.c:2759-2768` 的 per-rx-queue 循环内），所以 primary 必须有队列。

**影响面**：`kni.enable=1` 时 primary 完全无法瘦身；即使拆掉 `ff_config.c:1419-1435` 的校验，`main_loop` 里 primary 的 rx 队列循环次数为 0 → `ff_kni_process()` 一次都不会被调用 → KNI 完全失效（内核旁路管理面丢失）。

### B3 mbuf 池规模计算依赖本进程 `nb_rx_queue`，而池只由 primary 创建

**结论：部分成立（不是启动即死，但会导致池严重欠配 → 运行期丢包/`rx_queue_setup` 失败）。**

**位置**：`lib/ff_dpdk_if.c:531-548`（公式）、`lib/ff_dpdk_if.c:571-594`（primary create / secondary lookup）。预读行号 532-545、571-601 基本准确。

```c
// lib/ff_dpdk_if.c:531-548
    uint8_t nb_ports = ff_global_cfg.dpdk.nb_ports;
    uint32_t nb_lcores = ff_global_cfg.dpdk.thread_mode
        ? ff_global_cfg.dpdk.nb_threads : ff_global_cfg.dpdk.nb_procs;
    uint32_t nb_tx_queue = nb_lcores;
    uint32_t nb_rx_queue = ff_cur_lcore_conf()->nb_rx_queue * nb_lcores;
    uint16_t max_portid = ff_global_cfg.dpdk.max_portid;

    unsigned nb_mbuf = RTE_ALIGN_CEIL (
        (nb_rx_queue * (max_portid + 1) * 2 * RX_QUEUE_SIZE+
        nb_ports * (max_portid + 1) * 2 * nb_lcores * MAX_PKT_BURST    +
        nb_ports * (max_portid + 1) * 2 * nb_tx_queue * TX_QUEUE_SIZE  +
        nb_lcores * MEMPOOL_CACHE_SIZE +
#ifdef FF_KNI
        nb_ports * KNI_MBUF_MAX +
        nb_ports * KNI_QUEUE_SIZE +
#endif
        nb_lcores * nb_ports * DISPATCH_RING_SIZE),
        (unsigned)8192);
```

**精确 pool size 公式**（令 `P = nb_ports`、`M = max_portid`、`L = nb_lcores`、`Q = ff_cur_lcore_conf()->nb_rx_queue`）：

```
nb_mbuf = align8192(
      Q*L * (M+1) * 2 * RX_QUEUE_SIZE          // RX 描述符项，唯一依赖本进程队列数
    + P   * (M+1) * 2 * L * MAX_PKT_BURST      // burst 暂存
    + P   * (M+1) * 2 * L * TX_QUEUE_SIZE      // TX 描述符项（nb_tx_queue = L，见 534）
    + L   * MEMPOOL_CACHE_SIZE                 // per-lcore cache
    [+ P * KNI_MBUF_MAX + P * KNI_QUEUE_SIZE]  // 仅 FF_KNI
    + L   * P * DISPATCH_RING_SIZE )// dispatch ring
```

**primary 无队列（Q = 0）时**：第一项整体归零，池只剩 burst / TX / cache / KNI / dispatch 项。相关宏取值：`RX_QUEUE_SIZE = TX_QUEUE_SIZE = 512`（`lib/ff_memory.h:43-44`）、`MEMPOOL_CACHE_SIZE = 256`（`lib/ff_memory.h:34`）、`DISPATCH_RING_SIZE = 2048`（`lib/ff_memory.h:36`）、`MAX_PKT_BURST = 32`（`lib/ff_config.h:55`）、`KNI_MBUF_MAX = KNI_QUEUE_SIZE = 2048`（`lib/ff_dpdk_if.c:72-73`）。以单口、`max_portid=0`、`L=2` 为例，丢失的 RX 份额为 `Q*L*(0+1)*2*512`——`Q` 从 1 变0 即丢掉 2048 个 mbuf的 RX 预算——而 primary 随后在 `1078-1100` 仍要为`nb_queues` 个 RX 队列各挂 `nb_rxd` 个描述符（`1095-1096` `rte_eth_rx_queue_setup(..., mbuf_pool)`），DPDK 会在 setup 时一次性从池里预填满每个 RX ring。

**后果**：
- 若 `rte_eth_rx_queue_setup` 时池不足 → `1097-1099` 直接 `return ret` → `ff_dpdk_init:1719-1721` `rte_exit("init_port_start failed")`；
- 若勉强够用（因为对齐到 8192 的下界兜底、且 TX/dispatch 项本身不小）→ 启动成功但运行期 mbuf 长期紧张，表现为随机丢包、`ff_traffic.rx_dropped` 上升。

**注意两个容易搞错的点（与任务描述中的表述不同，以代码为准）**：
1. 池名是 `mbuf_pool_%d`，`%d` 是 **socket id**（`lib/ff_dpdk_if.c:572`、`592`），**不是 proc_id**。因此池是「按 NUMA socket 共享」而非「每进程一个」，`556-569` 的循环遍历 `proc_lcore[i]` 只为收集出现过的 socket，`567-569` 对已建socket 直接 `continue`。
2. `nb_lcores` 取 `ff_global_cfg.dpdk.nb_procs`（`532-533`），即 **coremask 置位数**，与 `lcore_list` 无关。primary 若保留 coremask 位但退出 `lcore_list`，`nb_lcores` 会比实际收包进程数多 1 → TX/cache/dispatch 项**略微超配**（无害）；而 RX 项因`Q=0` 归零（有害）。

**绕过所需改动**：把 `lib/ff_dpdk_if.c:535` 的 RX 项改为不依赖本进程，例如按各 port 的 `pconf->nb_lcores` 求和：
`nb_rx_queue = Σ_over_ports(port_cfgs[portid].nb_lcores)`，或直接用 `Σ nb_lcores * (max_portid+1)`。同时建议把 `nb_lcores` 语义拆成「收包进程数」与「总进程数」两个变量。

**B4 结论的适用边界（据门禁R5/R7 补充，使本结论自包含）**：上面「reta 一致收缩 ⇒ 无孤儿队列」的论证，成立前提是**走`set_rss_table()` 这条 RSS reta 路径**。以下两种情形该论证**不适用**，需另行论证：

1. **编译期开启 `FF_FLOW_ISOLATE` 或 `FF_FLOW_IPIP` 时，B4 论证不成立**。`set_rss_table()` 的**函数定义**（`787`）被 `lib/ff_dpdk_if.c:785`的 `#if !defined(FF_FLOW_ISOLATE) && !defined(FF_FLOW_IPIP)` 包裹（注释 `784`：`//RSS reta update will failed when enable flow isolate`），其**唯一调用点**（`1173`）同样被 `1168` 的同一条件包裹（`#endif` 在 `1175`）。⇒ 开启任一宏后 `set_rss_table` 连编译都不存在，收包分流改由 rte_flow 规则决定：`FF_FLOW_ISOLATE` 走 `port_flow_isolate()`（`1280`，由 `1708` 在 primary 侧调用）+ `create_tcp_flow()`（`1295`，`1399` 处按tcp_port 建规则）；`FF_FLOW_IPIP` 走 `create_ipip_flow()`（`1446`，由 `1761` 在 primary 侧调用）。这两条路径把流按规则**显式定向到具体 queue**，primary 退出 `lcore_list` 后规则里的目标队列是否随之收缩**本轮未论证**，需按规则的 `queue index` 生成逻辑重新核查。→ 已在 `03` 的 **R11/R12** 与 `07` 的 **U2/U3**、`08` 的 **RG-13** 登记为待办风险项。
2. **`nb_queues == 1` 时不走 `set_rss_table`，依赖 PMD 默认 reta**。`1169` 的 `if (nb_queues > 1)` 不成立 ⇒ 跳过 reta 重写，NIC 保持 PMD 默认表。本轮**只有 virtio 有正面证据**（默认 reta 全指向 queue 0，而唯一 secondary 的 `queueid` 恰为 `lcore_list` 下标 0，故正确）；其他 PMD 的默认 reta 行为未验证。→ 详见 `05` 的 **E5**（virtio 正面证据）与 **E3**（其他 PMD 未覆盖）。

**绕过所需改动**：**无需改动**（在上述适用边界内）。B4 不是阻塞点，反而是本方案能成立的关键代码基础。唯一建议：在 `1065` 之前加一条日志打印 `nb_queues` 与 `lcore_list`，便于运维确认「primary 未占队列」。

### B7 `thread_mode` 强制 primary 且 `nb_procs = 1`

**结论：成立（与 #1078 语义互斥，但两者是"或"关系，不冲突）。**

**位置**：`lib/ff_config.c:1484-1503`。预读行号准确。

```c
// lib/ff_config.c:1484-1503
    if (cfg->dpdk.thread_mode) {
        /* Single-process multi-thread: force primary, derive nb_threads,
         * collapse to one process, and expose all lcores to EAL via a
         * full-bit proc_mask. Done after per-port lcore checks so those
         * still validate against the original nb_procs=bit-count set. */
        if (cfg->dpdk.proc_type && strcmp(cfg->dpdk.proc_type, "secondary") == 0) {
            fprintf(stderr, "thread_mode=1 is incompatible with proc_type secondary\n");
            return -1;
        }
        if (cfg->dpdk.proc_type) free(cfg->dpdk.proc_type);
        cfg->dpdk.proc_type = strdup("primary");

        cfg->dpdk.nb_threads = cfg->dpdk.nb_procs;
        cfg->dpdk.nb_procs = 1;
        cfg->dpdk.proc_id = 0;
        if (cfg->dpdk.lcore_mask) {
            if (cfg->dpdk.proc_mask) free(cfg->dpdk.proc_mask);
            cfg->dpdk.proc_mask = strdup(cfg->dpdk.lcore_mask);
        }
    }
```

**语义关系分析**：
- `thread_mode=1` 时整个 f-stack 只有**一个进程**（`nb_procs=1`、`proc_id=0`、强制 primary），全部 worker 是该进程内的线程；`init_lcore_conf()` 走 `433-463` 的 `thread_mode` 分支，按 `nb_threads` 逐 lcore 填 `lcore_conf[lcore_id]`。
- #1078 的诉求（primary 挂掉不影响业务）在 `thread_mode` 下**天然不存在**：没有独立的 primary 进程，也就没有"primary 挂掉"这个故障模式；反之，该进程一挂全挂。
- 两者**互斥但不冲突**：`thread_mode=1` 是「用线程替代多进程」的另一条稳定性路线（进程内共享内存、无 secondary 依赖）；#1078 是「多进程模式下解耦 primary」。设计时应明确：**primary 瘦身特性只在 `thread_mode=0` 下生效**，并在配置校验处加互斥检查。
- 实现约束：`thread_mode` 分支的 `459-460` 同样有 `nb_rx_queue == 0` 的 `rte_exit`，若统一改造需两处同改；但 `thread_mode` 下 KNI owner 退化为「本lcore == `proc_lcore[0]`」（`lib/ff_dpdk_kni.c:95-96`），语义与本特性无关。

**影响面**：仅设计约束，无代码阻塞。

**绕过所需改动**：在 `lib/ff_config.c:1484` 附近新增「`thread_mode=1` 与 primary-slim 开关互斥」的校验（约 5 行）。

### D.2 新发现阻塞点（B1~B8 之外）

#### N1 `msg_ring[0]` 消费者缺失 → `ff_ipc` 工具默认失效（影响：高）

**位置**：`lib/ff_dpdk_if.c:698-700`（ring 数 = `nb_procs`）、`lib/ff_dpdk_if.c:2803`（唯一消费点）、`lib/ff_dpdk_if.c:2351-2368`（`process_msg_ring`）、`tools/compat/ff_ipc.c:42`（`uint16_t ff_proc_id = 0;`）、`tools/compat/ff_ipc.c:143-146`、`170-173`。

```c
// lib/ff_dpdk_if.c:2350-2358

process_msg_ring(uint16_t proc_id, struct rte_mbuf **pkts_burst)
{
    /* read msg from ring buf and to process */
    uint16_t nb_rb;
    int i;

    nb_rb = rte_ring_dequeue_burst(msg_ring[proc_id].ring[0],
        (void **)pkts_burst, MAX_PKT_BURST, NULL);
```

**成因**：`msg_ring` 是全库唯一按 `proc_id` 索引的共享对象（B6 表），`proc_id=0` 恒为 primary。所有 f-stack 工具（`ff_ipc`、`ff_sysctl`、`ff_ifconfig`、`ff_route`、`ff_top`、`ff_ipfw`、`ff_ngctl`、`ff_knictl`）默认 `ff_proc_id = 0`。
**触发条件**：primary 瘦身后若不再运行 `main_loop`（或运行但被裁掉 `process_msg_ring`）。
**影响面**：所有不带 `-p <id>` 的运维命令挂起/超时；`ff_top` 默认看不到数据。
**绕过**：改动 #3（primary 精简循环保留 `process_msg_ring`）或改动 #8（tools 默认 proc_id 指向收包进程）。

#### N2 `nb_dev_ports` 的 primary/secondary 语义不一致（影响：中）

**位置**：`lib/ff_dpdk_if.c:79`、`421-423`。

```c
// lib/ff_dpdk_if.c:79

```
```c

        nb_dev_ports = rte_eth_dev_count_avail();

    if (nb_dev_ports == 0) {
```

**成因**：`nb_dev_ports` 在 `init_lcore_conf()`（`ff_dpdk_init` 的第一步，`1682`）用 `rte_eth_dev_count_avail()` 快照。而 KNI 的 `rte_eal_hotplug_add`（`lib/ff_dpdk_kni.c:474`）发生在 `init_kni()`（`1693`）**之后**，会让端口数增加。secondary 若在 primary 完成 hotplug 之后启动，`rte_eth_dev_count_avail()` 会把 virtio_user 口也数进去 → `nb_dev_ports` 偏大。源码注释自己承认 "secondary is not correct"。
**触发条件**：`kni.enable=1` 且 secondary 在 primary 的 hotplug 之后启动。
**影响面**：`lib/ff_dpdk_kni.c:478` `kni_stat[port_id]->port_id = port_idx + nb_dev_ports` 与 `lib/ff_dpdk_if.c:844` `u_port_id = i - nb_ports + nb_dev_ports` 都依赖它。当前"无影响"是因为这两处都在 owner（=primary）分支内，`nb_dev_ports` 恰好正确。**一旦 KNI owner 迁到 secondary（改动 #6），这个已知的语义漂移会立刻变成真bug。**
**绕过**：把 `nb_dev_ports` 改成「只统计配置里的物理口」或由 primary 通过共享内存/配置显式传递给 secondary。

#### N3 `init_flow()` / `fdir_add_tcp_flow()` 缺少 primary 门禁（影响：中）

**位置**：`lib/ff_dpdk_if.c:1745-1750`（`FF_FLOW_ISOLATE`）、`lib/ff_dpdk_if.c:1777-1783`（`FF_FDIR`）；对照组`1707`（有门禁）、`1760`（有门禁）。

#### N4 primary 优雅退出会执行 `rte_eal_cleanup()` + `ff_unload_config()`（影响：高，与实测 E2 的差异根源）

**位置**：`lib/ff_dpdk_if.c:2879-2885`。

```c

    /* FU-S2-2-CFG-UNLOAD: freeff_global_cfg before EAL cleanup so any

     * are released while the EAL is still up. Mirrors the comment block
```

**成因**：`ff_dpdk_stop()`（`2889-2891`，置 `stop_loop=1`）让 `main_loop` 正常 `break`（`2693-2695`），随后 `ff_dpdk_run()` 会走到 `2883-2884`。primary 的 `rte_eal_cleanup()` 会释放 EAL 管理的共享资源（hugepage、memseg 列表、multi-process 通道等），这与「被 `kill` 强杀」是**完全不同**的退出语义。

### D.3 与实机实测（E1/E2）的代码级对照

> 实测数据来源：leader 在本机跑出的 E1/E2（primary+secondary 正常启动 → 强杀 primary → secondary 存活继续服务，20 条长连接中 9 条持续 200 OK 90s+/34 轮无衰减、11 条立即失效；新建 12 条连接 6 成 6 败）。以下为**纯代码侧**的对应解释与推论。

#### D.3.1 为什么 secondary 不随 primary 退出而失效（代码坐实）

| 实测现象 | 代码依据 | 判断 |
|----------|----------|------|
| secondary 进程存活 | secondary 与 primary 之间无父子/watchdog 关系；`rte_eal_mp_wait_lcore()`（`lib/ff_dpdk_if.c:2875`）只等本进程内的 lcore | 符合预期 |
| 已建连接继续收发 | 热路径只用启动期已`lookup` 的指针：`rte_eth_rx_burst`（`2772`）、`send_burst`→`rte_eth_tx_burst`（`2372-2379`）、`rte_ring_dequeue_burst(dispatch_ring[...])`（`2122`）、`rte_ring_dequeue_burst(msg_ring[proc_id].ring[0])`（`2357`）、`rte_mempool_get/put`（`2346`） | 符合预期 |
| 无运行期 IPC 阻塞 | `grep -rn 'rte_mp_request\|rte_mp_sendmsg\|rte_mp_action_register' lib/ tools/` → **0 命中** | 符合预期 |
| 无运行期 DPDK 堆扩容 | 运行期 `rte_malloc`仅 `2869`（进循环前）与 `3434`（初始化期）；FreeBSD栈内存走 `ff_mmap_init()`（`1698` → `lib/ff_memory.c:228`），`lib/ff_host_interface.c:71`/`120` 的 `rte_malloc` 已注释 | 符合预期 |
| 9 条存活 / 11 条失效 | RSS reta 由 `set_rss_table()` 按 `hash++ % nb_queues`（`801`）均匀铺到 queue 0（primary）与 queue 1（secondary）；当前配置 primary **在** `lcore_list` 中，`nb_queues = 2` | 失效的 11 条 = 哈希落到 queue 0 的流 → 队列在但无人 `rte_eth_rx_burst` =孤儿队列 |
| 新连接 6 成 6 败 | 同上，新 SYN 的五元组哈希同样 50% 概率落 queue 0 | 一致 |

**代码侧唯一的运行期跨进程依赖只有 2 处**（primary 挂掉会真失效）：
1. KNI 管理面——非 owner 进程 `ff_kni_enqueue()`（`lib/ff_dpdk_kni.c:529`）入 `kni_rp[port_id]`，owner（primary）在 `main_loop:2766` `ff_kni_process()` 出队。primary 挂 → ring 填满后全部 `rte_pktmbuf_free`（`lib/ff_dpdk_kni.c:530-532`、`540`）。
2. `proc_id=0` 的 msg ring —— 工具默认 `ff_proc_id = 0`（`tools/compat/ff_ipc.c:42`）→ 请求进 `msg_ring[0]`（`tools/compat/ff_ipc.c:144-146`）无人消费。详见 N1。

**⚠️ 关键限定：E2 的乐观结论不能外推到 primary "优雅退出"**。E2 用 `kill_process.sh` 强杀，未走 `ff_dpdk_run()` 的收尾路径；而正常 `break` 出主循环（`2693-2695`）后会执行 `ff_unload_config()`（`2883`）+ **`rte_eal_cleanup()`**（`2884`），后者会拆 EAL 共享资源。详见 N4。

#### D.3.2 primary 完全不占队列后「孤儿队列」是否消失（代码级判断：是）

从 B4 的四处代码可以直接推出结论，无需运行时验证即可确定队列侧的自洽性：

1. `nb_queues = pconf->nb_lcores`（`lib/ff_dpdk_if.c:836`）—— 队列总数**只由该 port `lcore_list` 的长度决定**，与 `nb_procs` / `proc_id` 无关。primary 退出 `lcore_list` → `nb_queues` 自动减 1。
2. `rte_eth_dev_configure(port_id, nb_queues, nb_queues, ...)`（`1065`）与 `for (q = 0; q < nb_queues; q++)` 的 tx/rx `queue_setup`（`1078-1100`）都用同一个 `nb_queues` → **NIC 上只会存在 N-1 个队列，物理上不存在"多出来的那个队列"**。
3. `queueid` 是 lcore 在 `lcore_list` 中的**下标**（`487-491`：`for i<nb_lcores: if lcore_list[i]==lcore_id then queueid=i`）→ 各 secondary 拿到紧凑的 `0..N-2`，**不会错位、不会留空洞**（`proc_id` 与 `queueid` 本来就是两套独立编号）。
4. `set_rss_table(port_id, dev_info.reta_size, nb_queues)`（`1173`）内部 `reta_conf[i].reta[j] = hash++ % nb_queues`（`801`）→ **reta 的取值域就是 `0..nb_queues-1`，每一项都指向一个有人 poll 的 secondary 队列**。

因此：**primary 不进 `lcore_list`⇒ 队列总数 = secondary 数 ⇒ reta 只映射到 secondary 队列 ⇒ 不存在孤儿队列 ⇒ primary 退出对数据面零影响**。这条推论完全由代码得出，与 NIC 型号无关。

**但必须同时满足以下前置条件**（否则连启动都过不去，见 D.1）：
- 拆掉 `508-510`（+`459-460`）的 `rte_exit`（改动 #1，否则 primary 启动即死）；
- 修 `535` 的 mbuf 池 RX 项公式（改动 #2，否则 primary 建出的池对 secondary 欠配）；
- primary 需保持存活且不执行 `rte_eal_cleanup()`（改动 #3）。

**两个需要运行时复核的边界**（静态无法定论，已列入开放问题 3）：
- 若最终只剩 **1 个** secondary，`1169` 的 `if (nb_queues > 1)` 不成立 → `set_rss_table()` 被跳过，NIC 保持 PMD 默认 reta。代码上该 secondary 的 `queueid` 恰为 0（`lcore_list` 下标 0），与默认 reta 通常全指 queue 0 吻合，但需实测确认。
- `dev->data->nb_rx_queues` 是 primary/secondary 共享的，从 N 变N-1 后secondary 侧 per-process 的队列视图是否完全一致，需运行时验证（DPDK 层约束由 researcher-web 提供）。

### E.2 决定性失败点（两点耦合，均为代码坐实）

#### FP-1（触发原因，内核态kmod）：`igb_uio` 在最后一个 fd 关闭时 `pci_clear_master()`，停掉设备 DMA

```c

		return 0;

	err = igbuio_pci_enable_interrupts(udev);       // :343
	...

// igb_uio.c:352-366

igbuio_pci_release(struct uio_info *info, struct inode *inode)

	...
```

`refcnt` 初值 0（`:529`）。**谁持有 `/dev/uioX`的 fd？** virtio PMD 的 `drv_flags = 0`（`virtio_pci_ethdev.c:229`，**未置** `RTE_PCI_DRV_NEED_MAPPING`）⇒ `pci_common.c:277-288` 的 `rte_pci_map_device()` 不执行 ⇒ `pci_uio_map_resource()` / `pci_uio_alloc_resource()` 都不走。真正打开 `/dev/uioX` 的地方是 legacy virtio 的 ioport映射：

由此完整解释 E1/E2 两组实测：
| 场景 | refcnt 变化 | `pci_clear_master` | 实测 |
|---|---|---|---|
| primary + secondary 同时在| 2 | 否 | 12/12 正常（E1）|
| 强杀 primary，secondary 存活 | 2→1（`:357` 不成立）| **否** | secondary 继续收包 90s+ 无衰减（E2）✓ |

即：`pci_set_master` 只恢复了「允许 DMA」这一位，**设备自身的运行态（vring 地址、queue enable、`DRIVER_OK` 状态位）没有任何人重新编程**。

**结论（决定性失败点）**：
- **`drivers/net/virtio/virtio_ethdev.c:1951-1953`（PMD 侧 secondary 早退）+ `lib/ff_dpdk_if.c:1061-1063`（f-stack 侧 secondary 跳过设备编程）** 共同构成决定性失败点：设备一旦丢失运行态（由 `igb_uio.c:362` 的 `pci_clear_master` 触发），**纯 secondary 进程组在代码上没有任何路径能把它重新编程回可收包状态**，只能等primary 重新 `dev_configure` + `dev_start`。这与实测「完整重启进程组恢复 12/12」完全一致。

**诚实边界（本仓库内无法坐实的一环）**：`pci_clear_master`（PCI COMMAND 寄存器 BME 清零）在**宿主侧 virtio-pci 后端**是否会顺带把设备 `status` 里的 `DRIVER_OK` 清掉（从而使 vring 彻底停摆、而不仅仅是"DMA 被禁"），属于 QEMU/宿主实现语义，**不在本仓库代码范围内，未坐实**。但这一环不影响上面的判定：无论宿主是"仅禁 DMA"还是"顺带清 DRIVER_OK"，恢复动作都必须由 `virtio_init_device()` / `virtio_dev_start()` 完成，而这两者在 secondary 里均不可达。

**顺带发现的 latent 隐患（与本 bug 无关，建议记录）**：`virtio_pci_ethdev.c:88`的 `VTPCI_DEV(hw) = pci_dev;` 把**本进程私有**的 `struct rte_pci_device *` 写进了**共享**的 `dev_private`（`struct virtio_pci_dev`）。每个 secondary attach 都会覆盖primary 写入的指针；primary 后续若通过 `VTPCI_DEV(hw)` 访问（如 `dev_stop`/`dev_close`/中断路径）将解引用另一个进程的地址。多进程 virtio 场景下这是真实的跨进程指针污染风险。

### E.3 为什么失败是「静默」的：调用链上每一步都 `return 0`

| PMD secondary 初始化 | `virtio_ethdev.c:1951-1953` | **`return 0`（什么都没做）** |
| probing finish | `ethdev_driver.c:211-226` | `eth_dev_fp_ops_setup()`（`:221-222`，装好 secondary 的快路径函数指针）+ `dev->state = RTE_ETH_DEV_ATTACHED`（`:226`）|
| f-stack 端口数健康检查 | `ff_dpdk_if.c:422-426` | `count_avail() = 1` → **不 `rte_exit`** |
| 收包 | `ff_dpdk_if.c:2772` `rte_eth_rx_burst()` | **恒返回 0**，语义上等价于"当前无包"，无错误码可查 |

`rte_eth_rx_burst()` 没有错误返回值，f-stack 主循环把0 视为正常空轮询；`dev->data->rx_queue_state[]`、`hw->started` 都在**共享内存**里且仍是 `STARTED`/`1`（强杀 primary 不会复位），所以连"队列没启动"这种自检也查不出来。**整条链上没有任何一处返回错误** —— 这就是静默失能的机制。

### E.4 `rte_eth_dev_count_avail()` 矛盾的解释（本次最关键的一条）

**答案：在失能的 secondary 里它返回 1（>0），所以 `ff_dpdk_if.c:422-426` 的 `rte_exit("No probed ethernet devices")` 不会触发。** 代码链：

```c
// lib/ethdev/rte_ethdev.c:674-687
uint16_t rte_eth_dev_count_avail(void)
{
	uint16_t p, count = 0;
	RTE_ETH_FOREACH_DEV(p)      // 遍历 rte_eth_find_next()
		count++;
	return count;
}

// lib/ethdev/rte_ethdev.c:349-361
uint16_t rte_eth_find_next(uint16_t port_id)
{
	while (port_id < RTE_MAX_ETHPORTS &&
			rte_eth_devices[port_id].state == RTE_ETH_DEV_UNUSED)   // :352
		port_id++;
	...
}
```
1. `count_avail()` 的统计口径是 **本进程私有数组 `rte_eth_devices[]` 的 `state != RTE_ETH_DEV_UNUSED`**，而 `state` 是 `struct rte_eth_dev` 的字段（per-process），**不是**共享 `rte_eth_dev_data` 的字段。
2. 新 secondary 的 `state` 是这样变成 `ATTACHED` 的：`rte_eth_dev_pci_allocate()`（`ethdev_pci.h:80-135`）secondary 分支 → `rte_eth_dev_attach_secondary(name)`（`ethdev_driver.c:152-180`）在**共享 memzone**（`eth_dev_shared_data->data[]`，由 primary 创建）里按 name 命中 → `eth_dev_get(i)` 把本进程 `rte_eth_devices[i].data` 指向共享 data → `dev_init` 返回 0 → `rte_eth_dev_probing_finish()`（`ethdev_pci.h:154`）→ **`dev->state = RTE_ETH_DEV_ATTACHED`（`ethdev_driver.c:226`）**。
3. **共享 `eth_dev_shared_data` 在 primary 被强杀后完好无损**：`eth_dev_release_port()` / `rte_eal_cleanup()` 都没执行（强杀），memzone 与其中的 `name`、`dev_private`、`rx_queues[]` 全部原样留在 hugepage 共享内存里。所以名字照样查得到。

**⇒ 矛盾的本质**：`count_avail()` 回答的问题是「**本进程有没有成功 attach 上共享的 ethdev 描述符**」，而不是「设备硬件是否真的能收发包」，更不是「primary 是否存活」。f-stack 唯一的端口健康检查（`422-426`）问错了问题，因此对这类"描述符在、硬件死"的状态完全免疫。这正是「静默失能」在f-stack 侧无法被现有代码发现的直接原因。

（同理，`rte_eth_dev_count_total()`、`rte_eth_link_get_nowait()` 也不可靠：virtio 的 link 状态在 secondary 里由 `dev_ops` 读共享 data，同样是陈旧值。）

### E.5 可修复性判断：分三层，结论「已发生的失能不可在 secondary 内恢复，但可检测、可预防」

**(a) 已发生的失能—— 不可恢复，属DPDK/PMD 模型固有。** 依据：
- 恢复设备必须走 `virtio_init_device()`（写 `DRIVER_OK`）或 `virtio_dev_start()`（重填 vring、置 queue_state），其可达入口只有 `eth_virtio_dev_init()` 的 primary 段（被 `virtio_ethdev.c:1951-1953`挡住）与 `virtio_dev_configure()`（f-stack 在 `ff_dpdk_if.c:1061-1063` 明确跳过）。
- 即便强行让 secondary 调用 `rte_eth_dev_configure()` / `rte_eth_dev_start()`，也会：① 改写 primary 拥有的共享 `rte_eth_dev_data`（ethdev 的 primary-only 所有权语义，与 01 的 1.2/1.4 一致）；② 队列 setup 需要 `rte_zmalloc` 分配 vring/队列结构，而 DPDK 堆扩容在 secondary 侧需 **primary 代理**（`malloc_mp.c` 的 mp 请求，01 的 1.3）—— primary 缺席时必然失败。
- DPDK **没有** primary failover / primary 重新接管机制（01 的 1.4，与代码一致：`eal_common_proc.c` 的 IPC 只有 secondary→primary 单播+ primary→all 广播，无角色切换）。

**(b) 可检测 → f-stack 层面可修（建议改动 #13，本章新增）：secondary 启动时探测 primary 是否在线，缺席则 fail-fast `rte_exit`，把"静默失能"变成"启动即报错"。** 可用手段（均已代码核实可行）：
- 最直接：secondary 在 `ff_dpdk_init()` 早期发一次 `rte_mp_request_sync()`（任意自定义 action name）；primary 缺席时 `/var/run/dpdk/rte/mp_socket` 无监听者 → `connect()`/`sendmsg()` 返回 `ECONNREFUSED`（正是实测日志里那条 `failed to send to (...) due to Connection refused`，出自 `eal_common_proc.c` 的 `send_msg()`）→ 判定 primary 不在线。
- 辅助但**不可单独使用**：`dev->data->dev_started` / `hw->started` / `rx_queue_state[]` 在 primary 被强杀后仍是"已启动"，**不能**作为判据（这正是静默的原因之一）。
- 该改动只加检测、不改数据面，风险低；建议与改动 #3（primary 常驻）配套落地。

**(c) 可预防 —— 本issue 的目标形态天然规避。** 只要 primary 常驻（不退出、且**不执行** `rte_eal_cleanup()`，见 N4 / 改动 #3），`igb_uio` 的 `refcnt` 永远 ≥ 1 ⇒ `igb_uio.c:357` 的 `atomic_dec_and_test` 永不成立 ⇒ `pci_clear_master()` 永不执行 ⇒ 设备运行态永不丢失。**这条把 N4 从「建议」升级为「必须」**：primary 不但要活着，还必须避免任何路径走到 `ff_dpdk_if.c:2884` 的 `rte_eal_cleanup()`；同时 primary 也**不应关闭它持有的 `/dev/uioX` fd**（该 fd 由 `pci_uio.c:446` 打开并保存在 `intr_handle` 中，正常运行期不会关闭）。

### E.6 与 01（外网调研）的交叉引用与冲突标注

- 与 01 的 1.2（IPC 只支持 secondary→primary 单播）、1.3（扩堆需 primary 代理）、1.4（无 primary failover）**一致**，本章 E.5(a) 直接引用并用源码复核通过。
- **需标注的差异**：若01 表述为「primary 缺席时 secondary 会因 IPC 失败而**启动失败**」，则与代码不符 —— `vdev.c:502` 明确 fall through、`rte_bus_scan()` 只打日志，**secondary 会带着失败的 mp 请求正常完成 `rte_eal_init()`**。实测（能启动、栈初始化完成、无 `rte_exit`）也支持代码侧结论。**以代码为准。**
- 本章不与 01 的任何结论冲突；B4（队列映射语义）的裁决保持不变。
