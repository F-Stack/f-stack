## 摘要

#1078 的诉求是「把 primary 独立出来只做初始化、数据面下移secondary」，以降低 primary 异常对整组进程的冲击。本轮调研的结论是：**"primary 瘦身为控制面"在 DPDK 模型内可行（primary 可以不持有任何 rx/tx 队列、不收包）**；而 primary 退出后的行为，经第二轮实机对照实验（E2e）后精确化为：**primary 退出后，其余进程继续服务、且崩溃的 secondary 可原地重启（无需全组重启）；但进程组进入控制面降级态（无 IPC 服务端、无法扩堆、无中断处理），且若所有进程都退出则设备运行态丢失、必须全组重启**。这一精确化推翻了初稿"primary 缺席则 secondary 无法重启"的判断：真正的前提条件不是"primary 在线"，而是**至少一个进程持续持有 `/dev/uioX`（内核态 uio refcnt ≥ 1），使设备的 bus-master/DMA 运行态不被内核清除**。同时 **E10 实测进一步坐实：primary 崩溃后无法就地重新拉起**（新 primary 在 EAL 阶段 `Cannot allocate memzone list` fail-fast，源码原因是 `fbarray_memzone` 的独占锁被存量 secondary 的共享锁挡住，`eal_common_fbarray.c:790-803`），即**控制面降级态单向不可逆**，恢复完整能力必须停全部进程 + 清理 `/var/run/dpdk/<prefix>/` + 全组重启（详见 1.3.1）。primary 必须常驻的**确定性**理由因此被强化——它支撑的是"控制面能力必须常驻且不可事后补回"，而不是"secondary 不能重启"：IPC 服务端（`eal_common_proc.c:750-751`）、动态扩堆代理（`malloc_heap.c:484`）、所有中断只在 primary 触发（`multi_proc_support.rst:174-177`）。

## 关键结论（3-5 条）

1. **DPDK 官方从未承诺 primary 退出后 secondary 可继续工作**：官方定义 secondary "cannot initialize shared memory, but can attach to pre-initialized shared memory"，且 "secondary processes can only run alongside a primary process **or after a primary process has already configured the hugepage shared memory for them**"（`dpdk/doc/guides/prog_guide/multi_proc_support.rst:19-24`）。这句"or after"给了"已初始化完成后 primary 缺席仍可跑"的**文字空间**，但没有任何保障语义。
2. **本机实测与官方文字空间一致**：primary 被 kill 后已运行的 secondary 存活、继续服务自身 RSS 队列上的老连接并能接受新连接（leader 实测：9/20 长连接24 轮无衰减、12条新建中 6 条成功）。这说明数据面（队列寄存器、mbuf 池、已 mmap 的 hugepage）不依赖 primary 在线。
3. **"primary 缺席时新拉起 secondary 静默失能"的根因已定论，且与 primary 缺席无关**：**（2026-08-07 第二次修正）** 根因是 **FP-1 + FP-2** 的组合：**FP-1** — `igb_uio` 的 `igbuio_pci_release()` 中，只有**最后一个**关闭 `/dev/uioX` 的进程（`atomic_dec_and_test(&udev->refcnt)` 成立）才执行 `igbuio_pci_disable_interrupts()` + `pci_clear_master()`（停设备 DMA），见 `f-stack/dpdk/kernel/linux/igb_uio/igb_uio.c:352-366`（对称地，`igbuio_pci_open()` 只在 `refcnt` 由 0→1 时才 `pci_set_master()`，`:330-349`）；**FP-2** — virtio PMD 的 secondary 分支在装完收发函数后**立即早退、不重新编程设备**（`drivers/net/virtio/virtio_ethdev.c:1949-1954`），而唯一写 `VIRTIO_CONFIG_STATUS_DRIVER_OK` 的 `virtio_reinit_complete()`（`drivers/net/virtio/virtio.c:57-61`）只在 `virtio_init_device()` 末尾被调用（`virtio_ethdev.c:1923`），该函数的全部调用点（`:1980` 的 primary probe 路径与 `:2162`/`:2195`/`:2202` 的 `virtio_dev_configure` 路径）**在 secondary 侧均不可达**。因此设备一旦被 `pci_clear_master()` 停掉，任何后续新起的 secondary 都无法把它重新拉回运行态。EAL 阶段的 `Connection refused` / `bus_vdev_mp` / `vdev_scan` 报错**已确证为伴随噪声**——E2e 中能正常收包的重启 secondary 打印了完全相同的报错。详见 1.4 节。
4. **f-stack 侧 primary 的额外职责使"纯控制面 primary"需要额外改造，但队列编号本身不是障碍**：**（2026-08-07 修正）** 队列数并非"进程数"，而是**该 port 的 `lcore_list` 长度** `pconf->nb_lcores`（`lib/ff_dpdk_if.c:836`）；本进程的 `queueid` 是**本进程 lcore 在该 port `lcore_list` 中的下标**（`lib/ff_dpdk_if.c:487-491`），与 `proc_id` **完全解耦**；`set_rss_table()` 也按同一个 `nb_queues` 重算 reta（`lib/ff_dpdk_if.c:801`、`1169-1174`）。因此 `queue_id == proc_id` 只是**默认配置下 lcore_list 顺序与 proc 顺序一致时的巧合**，不是代码约束——把 primary 的 lcore 从 `lcore_list` 中摘掉后，**队列数 / queueid / reta / dispatch_ring 会一致收缩，不会产生孤儿队列**。primary 真正需要额外处理的是：KNI 处理独占、`ifconfig`/`netstat`/`ipfw` 工具链（工具默认 `ff_proc_id = 0` 指向 primary，`tools/compat/ff_ipc.c:42`）以及全库唯一按 `proc_id` 索引的共享对象 `msg_ring`（`lib/ff_dpdk_if.c:698-700`）。
5. **同类项目的主流答案是"绕开多进程"**：VPP 与 DPVS 均采用单进程多线程（main/worker），根本不存在 primary/secondary 依赖问题；f-stack 自身也已有 native-mt（单进程多线程）方向的 spec。这提示 #1078 的"独立 primary"是在多进程框架内的**缓解**方案，而非根治方案。

## 第一部分：DPDK 官方多进程模型的硬约束

本部分以**本地 DPDK 源码树**为第一手来源（f-stack 当前使用 DPDK 24.11.6，路径 `/data/workspace/f-stack/dpdk/`），外网 `doc.dpdk.org` 同名章节作交叉验证。

### 1.1 primary / secondary 的官方定义与前提

| 官方表述 | 来源 |
| --- | --- |
| "primary processes, which can initialize and which have full permissions on shared memory" | `dpdk/doc/guides/prog_guide/multi_proc_support.rst:17` |
| "secondary processes, which **cannot initialize shared memory**, but can attach to pre-initialized shared memory and create objects in it" | 同上 `:19-20` |
| "secondary processes can only run alongside a primary process **or after a primary process has already configured the hugepage shared memory for them**" | 同上 `:22-24` |
| "Secondary processes should run alongside primary process with **same DPDK version**"；"Secondary processes which requires access to **physical devices in Primary process**, must be passed with the same allow and block options" | 同上 `:26-31` |
| primary 用 `--legacy-mem` / `--single-file-segments` 时 secondary 必须用相同开关，"Otherwise, **memory corruption may occur**" | 同上 `:64-66` |
| `--proc-type=auto`：已有 primary 在跑时自动以 secondary 启动 | 同上 `:75-76` |

**对 #1078 的意义**：官方措辞把"primary 在线"降格为"primary 曾经完成初始化"，这正是本机实测中"kill primary 后老 secondary 仍工作"的依据；但官方同时把 secondary 对**物理设备**的访问描述为"physical devices in Primary process"，即设备资源的所有者仍是 primary。

### 1.2 primary 独占能力清单（源码坐实）

1. **IPC 服务端身份**：DPDK IPC 只支持"secondary → primary 单播"和"primary → 所有 secondary 广播"，**不支持 primary→单个 secondary 单播，也不支持 secondary↔secondary**（`multi_proc_support.rst:205-211`、`:253-256`）。secondary 发消息时若未指定 peer，目的地固定为 `eal_mp_socket_path()`（`lib/eal/common/eal_common_proc.c:750-751`），即 `/var/run/dpdk/<prefix>/mp_socket`。**primary 缺席 = 整个 IPC 面瘫**。
2. **动态内存分配**：secondary 需要新 hugepage 时不能自行分配，必须 `request_to_primary()` 让 primary 代为alloc/free（`lib/eal/common/malloc_heap.c:484`、`:1030`）。因此 secondary 在 primary 缺席后**只能用已有的堆**，任何触发扩堆的 `rte_malloc`/`rte_mempool_create` 都会失败。
3. **VFIO 设备 fd（注意：本机不适用，本机走 igb_uio）**：`vfio_open_group_fd()` 中primary 直接 `open("/dev/vfio/<group>")`（`lib/eal/linux/eal_vfio.c:362-392`），secondary 则"request group fd from the primary process via mp channel"，超时 5 秒（`ts = {.tv_sec = 5}`，`:356`、`:394-419`）；IOMMU type 也走 `SOCKET_REQ_IOMMU_TYPE`（`:674-714`）。`vfio_setup_device()` 拿不到 group fd 直接失败（`:765-805`），进而 `rte_pci_map_device()` 失败（`drivers/bus/pci/linux/pci.c:57-62`）。**该条仅在部署使用 vfio-pci 时构成 primary 硬依赖**；本机实测绑定 igb_uio，故不在本次失败路径上（见 1.4.1）。
4. **vdev 设备列表**：secondary 的 vdev bus scan 通过 `VDEV_SCAN_REQ` 向 primary 索取设备清单（`drivers/bus/vdev/vdev.c:388-395` 定义协议、`:403-407` 三步注释、`:408-463` primary 侧 `vdev_action` 应答、`:466-503` secondary 侧请求）。
5. **中断线程**：官方明确 "The delivery of interrupts, such as Ethernet device link status interrupts, **do not work in secondary processes**. All interrupts are triggered inside the primary process only."（`multi_proc_support.rst:174-177`）。**这条对 #1078 是硬约束**：即使 primary 瘦身为控制面，link status / LSC / rxq 中断仍只能由 primary 处理——反过来说，这也正好是"primary 作为控制面常驻"的合理职责。
6. **核绑定互斥**：所有进程必须使用**互不相同**的 coremask/corelist，"Attempting to do so can cause corruption of memory pool caches"（`:169-172`）。这正是 f-stack `lcore_list` 机制要解决的问题，也是 #1078 中"复用 lcore_list 让 primary 不参与数据面"设想的前提基础设施。
7. **ethdev 侧**：`rte_ethdev.c` 中大量 dev_ops 的调用以 `dev->data->dev_started` 等**共享**状态为条件；`rte_eth_dev_configure`/`rx_queue_setup`/`dev_start` 在 secondary 中通常不被重复执行（f-stack 也是这样组织的，见第四部分），secondary 走 `rte_eth_dev_attach_secondary` 复用共享 `dev->data`。示例约束点：`lib/ethdev/rte_ethdev.c:1962-1963` 以 `rte_eal_process_type() == RTE_PROC_PRIMARY && dev->data->dev_started` 为分支条件。
   *诚实边界*：本轮未逐一枚举全部 primary-only dev_ops，需prober-code agent 补齐。

### 1.3 secondary 崩溃 vs primary 崩溃的语义差异

- **secondary 崩溃**：官方多进程 sample app 章节（`dpdk/doc/guides/sample_app_ug/multi_process.rst`，外网对应 `https://doc.dpdk.org/guides/sample_app_ug/multi_process.html`）描述的 client/server 模型允许 client（secondary）单独重启；EAL 侧也有配合——`send_msg()` 在向某个 secondary 的 socket 发送失败且自身是 primary 时，直接 `unlink(dst_path)` 清掉死secondary 的 socket 并**返回 0（视为非本端错误）**（`eal_common_proc.c:731-734`）。这说明 DPDK **在 EAL 层为"secondary 死掉"做了容错设计**。
- **primary 崩溃**：源码中**不存在**任何对称的容错路径——没有 secondary 接管 IPC 服务端、没有 primary 选举、没有 `mp_socket` 重建机制。`rte_eal_cleanup()` 只有 primary 才做全局清理与 socket unlink。
- **是否存在"primary 退出后 secondary 可存活"的官方支持**：**没有**。官方文档中找不到任何 primary failover / primary 重启接管的机制描述；`--proc-type=auto` 只解决"启动时判断谁是 primary"，不提供运行期 failover（`multi_proc_support.rst:75-76`）。
  *诚实边界*：本轮对 DPDK 邮件列表（`mails.dpdk.org`）关于 multi-process resilience / primary failover 的历史 patch 讨论进行了检索，但**未能取得可引用的确定性结论**（见文末开放问题 O-3），故此处不给具体 patch 编号或链接，避免编造。

### 1.3.1 primary 崩溃后的可恢复性边界（2026-08-07 由 E10 实测 + 源码坐实，原O-8 已闭环）

**问题**：primary 崩溃后，能否在存量 secondary 仍运行的情况下**重新拉起 primary**，就地补回控制面能力（IPC 服务端、扩堆代理、中断处理）？

**实测答案（E10，leader 执行）**：**不能**。primary 已被强杀、2 个 secondary 仍在运行服务流量时，以 `--proc-type=primary --proc-id=0` 重新拉起 primary，EAL 初始化即fail-fast：

```
EAL: Multi-process socket /var/run/dpdk/rte/mp_socket
EAL: Selected IOVA mode 'PA'
EAL: Cannot allocate memzone list
EAL: Cannot init memzone
EAL: Error - exiting with code: 1
Error with EAL initialization        (exit code = 1)
```

且该失败尝试**未损伤存量 secondary**（服务保持 10/18），即属**无副作用的 fail-fast**。

**源码抛出点（已定位，逐环可查）**：

| 环节 | 代码 | 位置 |
| --- | --- | --- |
| ① 抛出 `Cannot allocate memzone list` | `rte_eal_memzone_init()` 中 `if (process_type == RTE_PROC_PRIMARY && rte_fbarray_init(&mcfg->memzones, "memzone", ...)) { EAL_LOG(ERR, "Cannot allocate memzone list"); ret = -1; }`；secondary 走的是另一分支 `rte_fbarray_attach()` | `lib/eal/common/eal_common_memzone.c:444-453`（日志在 `:447`） |
| ② `rte_fbarray_init()` 失败的**确切原因** | 该函数对 `/var/run/dpdk/<prefix>/fbarray_memzone` 先`eal_file_open(EAL_OPEN_CREATE\|EAL_OPEN_READWRITE)`，随后尝试 **`EAL_FLOCK_EXCLUSIVE`** 独占锁；拿不到锁即 `rte_errno = EBUSY; goto fail;`。注释原文：*"Try to take out a lock and see if we succeed. If we don't, someone else is using it already."* | `lib/eal/common/eal_common_fbarray.c:718-796`（独占锁与 EBUSY 在 `:790-796`，`fail` 分支 `:833-842`） |
| ③ 为什么锁一定被占 | primary 首次初始化成功后会把独占锁**降级为 `EAL_FLOCK_SHARED`**，注释原文：*"take out a non-exclusive lock, so that other processes could still attach to it, but **no other process could reinitialize it**"*；而每个 `rte_fbarray_attach()` 的 secondary 也各自持一把 **SHARED** 锁且 *"keep fd until detach/destroy"* | `eal_common_fbarray.c:798-803`（primary 降级为shared）、`:899-913`（secondary attach 取 shared 锁并保留 fd） |
| ④ 上层放大为致命错误 | `rte_eal_init()` 中 `if (rte_eal_memzone_init() < 0) { rte_eal_init_alert("Cannot init memzone"); rte_errno = ENODEV; return -1; }` | `lib/eal/linux/eal.c:1128-1132` |

即：**只要还有任何一个存量 secondary 活着（持 shared 锁 + 保留 fd），新 primary 就永远拿不到 `fbarray_memzone` 的独占锁，必然 EBUSY 失败**——这正是 DPDK 的**设计意图**（`:798-801` 注释明写"不允许其他进程重新初始化它"），不是缺陷。

**可恢复性边界（结论）**：

| 场景 | 是否可恢复 | 依据 |
| --- | --- | --- |
| secondary 崩溃，**至少一个进程仍持有 `/dev/uioX`** | **可原地重启该 secondary，恢复其队列服务** | E2e 实测（复现两次），见 1.4.2 |
| 全部进程退出（uio refcnt 归零） | **不可**，必须全组重启 | FP-1 + FP-2，见 1.4.2 |
| primary 崩溃、secondary 仍在跑 → **重新拉起 primary 补回控制面** | **不可**（EBUSY fail-fast，无副作用） | E10 实测 + 上表 ①–④ |
| 恢复完整能力（含控制面） | 必须**停全部进程 + 清理 `/var/run/dpdk/<prefix>/` + 全组重启** | 由上三行推出 |

**对 #1078 的意义（对"primary 必须常驻"的论证是强化）**：primary 缺席不仅使控制面能力在缺席期间缺失（IPC / 扩堆 / 中断三条硬依赖，1.2 节），而且**缺席后无法就地补回**——降级态是**单向不可逆**的，只能靠全组重启退出。因此 #1078 的方向应当是**通过瘦身把 primary 做成"极少崩溃的常驻控制面"**，而不是"容忍 primary 崩溃"。

### 1.4 【重点】"新拉起的 secondary 能启动却收不到包"的根因（2026-08-07 已定论）

leader 本机实测现象（**E2c 场景：进程组曾整体退出后再拉起单个 secondary**）：进程能启动、FreeBSD 栈初始化完成、无 `rte_exit`，但 0/12 收包；EAL 阶段报
```
failed to send to (/var/run/dpdk/rte/mp_socket) due to Connection refused
Fail to send request ...:bus_vdev_mp
VDEV_BUS: vdev_scan(): Failed to request vdev from primary
```
**源码级解释链（每一环都可定位；注意：①–④ 解释的是"为何进程能启动而不 rte_exit"，**不是**"为何收不到包"——后者的根因见 1.4.2）**：

| 环节 | 发生了什么 | 证据 |
| --- | --- | --- |
|① IPC 底层 | secondary 把请求发往固定路径 `mp_socket`；primary 已死→ socket 文件残留但无人listen → `connect()` = `Connection refused` → 打印 `failed to send to (%s) due to %s` 并返回 -1 | `eal_common_proc.c:750-751`（peer 默认 mp_socket）、`:685-738`（`send_msg`，`:735` 即该日志） |
| ② 请求层 | `rte_mp_request_sync()`/`rte_mp_request_async()` 在 `send_msg` 失败时打印 `Fail to send request %s:%s`（日志里的 `bus_vdev_mp` 就是 `req->name`）并返回 -1 | `eal_common_proc.c:890-894`、`:944-948` |
| ③ vdev bus | `vdev_scan()` 的 `rte_mp_request_sync(...) == 0 && nb_received == 1` 不满足 → 打 `Failed to request vdev from primary`，**然后 fall through 继续扫描本地私有 vdev**（注释：`/* Fall through to allow private vdevs in secondary process */`）→ **不报错退出** | `drivers/bus/vdev/vdev.c:493-503` |
| ④ 关键：**降级而非失败** | ③ 这种"IPC 失败→仅打 ERR→继续"的模式在 bus/PMD 层普遍存在，导致 EAL 初始化整体返回成功。这就是"能启动、无 rte_exit"的直接原因 | `vdev.c:500-503`（模式示例） |
| ⑤ 【2026-08-07 修正】设备资源缺失路径 | **本机不适用**。本机 DPDK 网卡 `0000:00:09.0 'Virtio network device 1000'(0x1af4:0x1000)` 绑定的是 **igb_uio**（实测 `dpdk-devbind.py --status`，`/sys/class/uio/uio0 -> 0000:00:09.0`），**不走 VFIO**，故 `eal_vfio.c` 的 group fd / IOMMU type mp 请求**根本不在本次失败路径上** | `eal_vfio.c:349-420`（仅 VFIO 场景适用，本机不触发） |
| ⑥ 收包函数指针的真实装配机制 | `rx_pkt_burst`/`tx_pkt_burst` 确是**每进程**装配。secondary 侧由 `rte_eth_dev_probing_finish()` 调 `eth_dev_fp_ops_setup()` 写入本进程的 `rte_eth_fp_ops[port_id]`（`ethdev_driver.c:210-227`，注释原文："for secondary process, at that point we expect device to be already 'usable'…"）。**未装配时不是崩溃而是静默返回 0**：`eth_dev_fp_ops_reset()` 把 `rx_pkt_burst` 指向 `dummy_eth_rx_burst`，后者置 `rte_errno = ENOTSUP` 并 `return 0` | `ethdev_private.c:207-224`（dummy）、`:245-265`（reset）、`:267-283`（setup）；`multi_proc_support.rst:179` |

#### 1.4.1 已排除项（均有代码/实测坐实）

1. **VFIO group fd 路径 — 本机不适用**：本机走 igb_uio（见上表⑤）。原稿把它列为候选属于泛化推测，现予撤回。
2. **vdev scan 失败 = 伴随噪声，非决定性原因**：失败的收包设备是 **PCI 设备**（`0000:00:09.0`），不是 vdev；`VDEV_SCAN_REQ` 失败只影响 secondary 能否看到 primary 创建的 **virtio_user（KNI）** 口，而 KNI 口并不属于 secondary 的收包路径。且 `vdev_scan()` 失败后明确 fall through（`bus/vdev/vdev.c:493-503`），不影响 EAL 返回值。
3. **PCI bus 的 secondary probe 对 primary / IPC 的依赖 = 零**：`drivers/bus/pci/pci_common.c` 全文 grep `RTE_PROC_PRIMARY|RTE_PROC_SECONDARY` **0 命中**；`rte_pci_scan()` 完全读本地 sysfs；`pci_uio.c:273-274` 明确 `if (rte_eal_process_type() != RTE_PROC_PRIMARY) return 0;`（secondary 不参与 uio_res 记账）。**即igb_uio + PCI 的 secondary attach 全程本地化，primary 在不在线都一样。**
4. **virtio PMD 的 secondary 分支不发任何 IPC，且确实装配了 rx/tx 函数指针**：`virtio_ethdev.c:1949-1954`——
   ```c
   eth_dev->dev_ops = &virtio_eth_dev_ops;
   if (rte_eal_process_type() == RTE_PROC_SECONDARY) {
           set_rxtx_funcs(eth_dev);
           return 0;
   }
   ```
   bus 侧 `eth_virtio_pci_init()` 的 secondary 分支走 `virtio_remap_pci()`（`virtio_pci_ethdev.c:79-99`）：modern 走 `rte_pci_map_device()`（本地 mmap，唯一约束是"须映射到与 primary 相同的 VA，否则返回错误"，注释在 `:47-58`）、legacy 走 `vtpci_legacy_ioport_map()`（读本地 sysfs `resource` + x86 PIO，`pci_uio.c:381-468`）。`rte_virtio_net_pci_pmd.drv_flags = 0`（`virtio_pci_ethdev.c:229`），即 **不带 `RTE_PCI_DRV_NEED_MAPPING`**，pci_common 不代为 map（`pci_common.c:279-289`）。**结论：virtio secondary probe 也不依赖 primary 在线。**
5. **"本进程 port 未 attach / fp_ops 停留在 dummy" 这一支被 f-stack 自身的 rte_exit 反证排除**：若 secondary probe 失败 → `rte_eth_dev_release_port()` → 本进程 `rte_eth_devices[port].state = RTE_ETH_DEV_UNUSED` → `rte_eth_dev_count_avail()` 返回 0 → f-stack `init_lcore_conf()` 立刻 `rte_exit(EXIT_FAILURE, "No probed ethernet devices\n")`（`lib/ff_dpdk_if.c:421-426`）。**leader 实测明确"进程能启动、FreeBSD 栈初始化完成、无 rte_exit"**，因此可反推**attach 成功、`rte_eth_fp_ops[port]` 已装配为真实 `virtio_recv_pkts`**。

#### 1.4.2 【2026-08-07 第二次修正】根因已定论：FP-1 + FP-2，与 primary 缺席无关

**推翻初稿的关键新事实**：leader 的 E2e 三进程对照实验（`lcore_mask=7`，primary + s1 + s2，**全程至少一个进程存活**，已复现两次，详见 `05-实机对照实验报告.md` 第九节）：

| 步骤 | 存活进程 | 持有 uio fd 的进程数 | 可服务连接 |
| --- | --- | --- | --- |
| 基线 | primary + s1 + s2 | 3 | 18/18 |
| 杀 primary | s1 + s2 | 2 | 10/18 |
| 再杀 s2 | s1 | 1 | 5/18 |
| **重启 s2（primary 仍缺席）** | s1 + s2(new) | 2 | **10/18**（dead 集合与"杀 primary 后"完全相同） |
| 再杀再重启 s2（复现） | s1 + s2(new2) | 2 | **10/18** |

即：**primary 缺席时 secondary 完全可以重启成功并恢复其队列的服务能力**。初稿 E2c 观察到的 0/12 并非"primary 缺席"所致，而是那次实验中**进程组曾整体退出**（uio refcnt 归零）。

**根因（两条缺陷叠加，行号已本人 read_file 复核，与 prober-code 02 任务 E 一致）**：

| 编号 | 缺陷 | 代码证据（已复核） |
| --- | --- | --- |
| **FP-1** | `igb_uio` 只在**最后一个**持有者关闭 `/dev/uioX` 时才停设备：`igbuio_pci_release()` 中 `if (atomic_dec_and_test(&udev->refcnt)) { igbuio_pci_disable_interrupts(udev); pci_clear_master(dev); }`。一旦 refcnt 归零，设备的 bus-master/DMA 被内核态清除；对称的 `igbuio_pci_open()` 只在 `atomic_inc_return(&udev->refcnt) == 1` 时才 `pci_set_master(dev)` + 使能中断，**后续以secondary 身份打开的进程不会重新 set_master** | `f-stack/dpdk/kernel/linux/igb_uio/igb_uio.c:352-366`（release）、`:330-349`（open，`:336-337` 的 refcnt 判断+ `:340` 的 `pci_set_master`） |
| **FP-2** | virtio PMD 的 secondary 分支装完收发函数即早退，**不重新编程设备状态**：`eth_dev->dev_ops = &virtio_eth_dev_ops;`（`:1949`）→ `if (rte_eal_process_type() == RTE_PROC_SECONDARY) { set_rxtx_funcs(eth_dev); return 0; }`（`:1951-1954`）。而唯一写 `VIRTIO_CONFIG_STATUS_DRIVER_OK` 的函数是 `virtio_reinit_complete()`（其体内仅一句 `virtio_set_status(hw, VIRTIO_CONFIG_STATUS_DRIVER_OK)`），它**只**在 `virtio_init_device()` 末尾被调用；`virtio_init_device()` 的全部 4 处调用点均在 secondary 侧不可达：`:1980`（`eth_virtio_dev_init` 的 primary probe 路径，位于 `:1954` 早退之后）、`:2162`/`:2195`/`:2202`（`virtio_dev_configure` 路径，f-stack 中 `rte_eth_dev_configure` 只由 primary 执行） | `drivers/net/virtio/virtio_ethdev.c:1949-1954`（secondary 早退）、`:1923`（`virtio_reinit_complete(hw)` 唯一调用点）、`:1766-1767`（`virtio_init_device` 定义）、`:1980`/`:2162`/`:2195`/`:2202`（全部调用点）；`drivers/net/virtio/virtio.c:57-61`（`virtio_reinit_complete` 定义）；`drivers/net/virtio/virtio.h:140`（`DRIVER_OK = 0x04`）。**f-stack 内置 DPDK 与 `dpdk-stable-24.11.6` 行号完全一致**（同版本） |

**FP-1 + FP-2 的合成效应**：设备运行态（bus-master + `DRIVER_OK`）**只在"第一个打开 uio 的 primary"路径上被建立一次**；一旦全组退出使 refcnt 归零，`pci_clear_master()` 停掉 DMA，此后无论重启多少个 secondary都不可能恢复——因为 igb_uio 的 open 不会再 `pci_set_master`（refcnt 从 0→1 只对**首个**打开者成立，而新起的进程是 secondary、不走 primary 的 virtio 初始化），virtio PMD 的 secondary 分支也不会写 `DRIVER_OK`。**必须整组重启（由 primary 重新建立设备运行态）。**

#### 1.4.3 原剩余候选 R1 / R2 —— 均经 E2e 实测排除

| 原候选 | 内容 | 排除依据 |
| --- | --- | --- |
| **R1**（DPDK/virtio 侧 vring 运行时状态）|曾推测"primary 被强杀时 vq kick/notify 处于中间状态"或"rx 描述符指向的 mbuf 生命周期被打断"或"`rte_pci_map_device()` 映射到不同 VA" | **排除**。E2e 中 primary 同样是被强杀，重启的 s2 却收包正常（10/18，与杀 primary 后完全同一 dead 集合）。若 R1 成立则该场景也应失能。真正的变量是 uio refcnt 是否归零 |
| **R2**（f-stack 侧队列语义/丢包） | 曾推测队列归属（`lcore_list` 下标 → queueid）、RSS reta 与存活 lcore 集合不匹配、`dispatch_ring`/`msg_ring` 语义导致丢包 | **排除**。**同一份 f-stack 代码**在 refcnt ≥ 1 时重启 secondary 收包完全正常；队列层面已由 C8/4.3 证明与 proc_id 解耦、会一致收缩 |
| 原"EAL 报错三连"（`Connection refused` / `bus_vdev_mp` / `vdev_scan` 失败） | 曾被列为解释链前 4 环 | **确证为伴随噪声**。E2e 中**能正常收包**的重启 secondary 打印了与E2c **完全相同**的这三条报错 |

**遗留的低成本确认手段**（供后续实验复用，非未决问题）：`dummy_eth_rx_burst` 首次被调用会打印 `lcore <N> called rx_pkt_burst for not ready port <P>` 并 `rte_dump_stack()`（`ethdev_private.c:207-224`），可用于快速区分"port 在本进程未 attach"与"attach 正常但设备无流量"；`rte_eth_stats_get(port)` 的 `ipackets` 可区分"包没进 vring"与"进了 vring 但 f-stack 层丢"。

**结论（第二次修正后）**：
1. **"新起的 secondary 能启动却收不到包"的根因 = FP-1（`igb_uio.c:352-366`，refcnt 归零触发 `pci_clear_master`）+ FP-2（`virtio_ethdev.c:1949-1954` secondary 早退，`DRIVER_OK` 不可达）**，**与 primary 是否在线无关**。触发条件是"进程组曾整体退出"。
2. 1.4 表格中 ①–④ 环（IPC / 请求层 / vdev bus / 降级而非失败）是**"进程为何能启动而不 rte_exit"** 的正确解释，但**不是"收不到包"的原因**；⑤（VFIO）本机不适用；⑥（fp_ops 装配机制）为背景知识，E2e 已证实 secondary 侧装配正常。
3. **对 #1078 的推论（修正）**：secondary **可以**原地重启自愈（只要 refcnt ≥ 1），因此 #1078 的"数据面下移 secondary"具备**故障隔离价值**。但 primary 仍必须常驻，理由是 1.2 节的三条**确定性硬依赖**：IPC 服务端（`eal_common_proc.c:750-751`）、动态扩堆代理（`malloc_heap.c:484`）、所有中断只在 primary 触发（`multi_proc_support.rst:174-177`）——这三条支撑的是**"控制面能力必须常驻"**，而不是"secondary 不能重启"。此外FP-1 使 primary 额外承担了一项**隐式职责**：作为 uio 设备运行态的建立者与（若它是最后一个退出者的话）销毁者。

*诚实边界*：1.4.1 的已排除项 1-5 均有 file:line 支撑；本节 FP-1/FP-2 的行号由本 agent 独立 `read_file` 复核，与 prober-code 02 任务 E 结论一致。"primary 崩溃后能否重新拉起 primary 以恢复控制面"已由 E10 实测 + 源码坐实定论（**不能**，见 1.3.1，原 O-8 已闭环）。

## 第三部分：同类项目做法（横向对比，精简）

| 项目 | 进程/线程模型 | 是否存在 primary 依赖问题 | 代价 |
| --- | --- | --- | --- |
| **VPP (fd.io)** | **单进程多线程**：一个 main thread + N 个 worker thread，DPDK 作为 plugin 在同一进程内使用（官方 threading 文档 `https://fd.io/docs/vpp/.../threads.html`） | **不存在**。没有 primary/secondary，进程崩溃即整体崩溃，但不存在"跨进程资源依赖"这一类失效模式 | 单进程崩溃面100%；需要线程安全的全局状态 |
| **DPVS** | **单进程多线程**（master lcore + slave/worker lcore，DPDK 单primary 进程内多lcore） | 不存在 | 同上|
| **mTCP / Seastar** | 单进程 + per-core shard/线程（share-nothing） | 不存在 | 同上 |
| **f-stack 现状** | **多进程**：每进程一个独立 FreeBSD 栈实例 + 独占一条 RSS队列，proc_id 0 为 primary | **存在**，且 primary 是单点| 换来了 share-nothing 的无锁栈实例与进程级隔离 |
| **f-stack native-mt 方向（本仓库 spec）** | 单进程多线程（`docs/native_mt_spec/`、`docs/multi_thread_spec/`） | 将**彻底消除** primary/secondary 依赖 | 改造量大，需解决 FreeBSD 栈全局状态多实例化（见该spec 的并发风险清单） |

**"独立控制进程 + 多数据进程"的已知实践**：DPDK 官方 `multi_process` sample app 的 server/client 模型即是此形态——**primary 作为 load-balancer/server 收包并分发给 secondary（client）**（`multi_proc_support.rst:96-99`：a single primary process instance that acts as a load-balancer or server distributing received packets among worker or client threads, which are run as secondary processes）。注意方向：官方样例中 **primary 是收包方**，而 #1078 想要的是**反过来（primary 不收包）**。官方样例中没有"primary 不碰数据面"的形态。

**关于"primary 只做初始化后退出"**：
- **不可行**。理由（源码 + 实测）：primary 退出后 mp_socket 服务端消失，(a) 任何 secondary 的动态内存扩堆请求失败（`malloc_heap.c:484`）；(b) link status 中断无人处理（`multi_proc_support.rst:174-177`，官方硬约束）；(c) 无人做 `rte_eal_cleanup` 与 socket unlink；(d) **无法重新拉起 primary 补回控制面**——E10 实测 `Cannot allocate memzone list` / `Cannot init memzone` fail-fast，源码坐实为 `rte_fbarray_init()` 拿不到 `fbarray_memzone` 独占锁（`eal_common_fbarray.c:790-796` → `eal_common_memzone.c:447` → `eal.c:1128-1132`），详见 1.3.1；(e) 若最后一个进程也退出，设备运行态被 `pci_clear_master()` 清除且无法由 secondary 重建（FP-1 + FP-2，1.4.2）。**（2026-08-07 第二次修正）**：(a)(b)(c) 为代码/文档坐实，(d)(e) 为实测 + 源码双重坐实；已删去初稿"新 secondary 无法 attach 设备"这一**错误**理由（E2e 已证伪：refcnt ≥ 1 时新 secondary 可正常 attach 并收包）。
- **可行的是"primary 常驻但不收包"**：让 primary 保留初始化、KNI、工具链、IPC 服务端、中断处理等控制面职责，但不分配 rx/tx 队列、不进 `ff_dpdk_run` 的收发包主循环。这与 #1078 的表述基本吻合，且不违反任何 DPDK硬约束。**这是本轮认为唯一值得继续评估的方向。**

### 4.3 已闭环的原开放问题 O-5（2026-08-07 由 prober-code 回答）

原O-5 问："`queue_id == proc_id` 的静态假设在 lib 内共有多少处硬编码依赖？"
**答案（已闭环）**：**队列侧零处**。队列数、queueid、RSS reta、`dispatch_ring` 全部以该 port 的 `lcore_list` 长度与下标为准（`lib/ff_dpdk_if.c:836`、`:487-491`、`:801`、`:1169-1174`），与 `proc_id` 解耦。全库唯一按 `proc_id` 索引的共享对象是 **`msg_ring`**（`lib/ff_dpdk_if.c:698-700`），且`ifconfig`/`netstat`/`ipfw` 等工具默认 `ff_proc_id = 0`（`tools/compat/ff_ipc.c:42`）即固定指向 primary。
**对#1078 的意义**：复用 `lcore_list` 机制让 primary 不参与数据面**在队列层面无需任何改造**；primary 瘦身后真正要处理的是 `msg_ring` 与工具链的 proc_id 归属（prober-code 记为 N1，高影响），以及 KNI 报文路径（见 C5 / O-6）。
