## 摘要

围绕 issue #1078「primary 瘦身、只做初始化不收包」，本文给出主方案 **S1「primary-slim」**（新增 `[dpdk] primary_slim` 开关，primary 常驻但不持有任何 rx/tx 队列，只做设备配置/共享对象创建/控制面消息处理），并与 S0（不改）、S2（primary 退出）、S3（保留最小队列）、S4（`thread_mode=1`）、S5（外部守护 + 分层恢复，兜底全组重启）横向对比。S1 的最小可跑集为 4 处代码改动 + 1 个配置项，覆盖 KNI 与控制面完整性需 9 处。

## 关键结论

1. **S1 能达成 issue 的两个子目标（(a) 降低概率、(b) 缩小影响面，含"故障后可恢复"）**：据 `05` 第九节 E2e 实测（复现两次）——只要**至少一个进程持续持有 `/dev/uioX`**（`igb_uio` refcnt ≥ 1，`f-stack/dpdk/kernel/linux/igb_uio/igb_uio.c:352-366` 的 `atomic_dec_and_test` → `pci_clear_master()`，已复核），**primary 缺席时 secondary 依然可以原地重启并恢复服务**。在 primary-slim 目标态下 primary 崩溃时全部数据面 secondary 都还在 ⇒ ① 数据面零流量损失（孤儿队列已消除）；② 之后任何 secondary 崩溃都能原地重启恢复 ⇒ **数据面恢复不需要全组重启**。**S1 与 E2c 的关系是"规避"而非"修复"**：S1 不修复 E2c 这个现象本身（primary 缺席且赶上 refcnt 归零时，新起的 secondary 仍会静默失能），但 S1 让 E2c 的触发条件几乎不可能出现。方向亦与 `01-外网调研与交叉验证.md` §3 的独立结论一致（"可行的是primary 常驻但不收包"），交叉验证通过；`01` 的 DPDK 硬约束已逐条纳入本文第 7.0 节。**残余风险**：primary 崩溃后系统处于**控制面降级态**（IPC 服务端、扩堆代理、中断三项能力缺失，见 7.0），且 **primary 无法原地拉回**（E10 实测：`EAL: Cannot init memzone`，exit1，fail-fast 无副作用）⇒ 必须**择机（计划内维护窗口）做一次全组重启**。因此 S1 的准确价值是**把紧急故障转为计划内维护、重启时机可控**，而非"完全无需重启"（详见 R14 与 7.3）。
2. **S1 的代码基础成立**：队列数/queueid/reta/dispatch_ring 全部由 `pconf->nb_lcores` 驱动（`lib/ff_dpdk_if.c:836`、`487-491`、`801`、`651`，已复核），primary 退出 `lcore_list` 后一致收缩，孤儿队列在代码层面消失（B4，引自 02）。
3. **裁决：primary-slim 下 primary 不 attach ifp**（`ff_dpdk_if_up()` 保持 0 次循环）。本文复核发现新风险：`lcore_conf` 是零初始化的全局数组（`lib/ff_dpdk_if.c:126`，已复核），primary 的 `tx_queue_id[port]` 恒为 0，一旦 primary 持有 ifp 并发出任何报文，`send_burst()` 会执行 `rte_eth_tx_burst(port, 0, ...)`（`lib/ff_dpdk_if.c:2378-2389`，已复核）**撞进某个 secondary 正在使用的 tx 队列 0**，而 DPDK tx 队列非MT-safe。此为 `02` 未列出的新增风险（见风险 R3）。
4. **裁决：primary 精简循环保留 `rte_timer_manage()` 与 `process_msg_ring()`，去掉（自然跳过）TX drain 与 rx 队列循环**；并新增 primary 侧 idle_sleep 下限，避免瘦身后primary 空转烧满一个核。
5. **裁决：primary-slim 模式下 primary 禁止执行 `rte_eal_cleanup()`**（`lib/ff_dpdk_if.c:2883-2884`，已复核），否则会拆掉 secondary 依赖的 EAL 共享资源（N4，引自 02）。

## 一、设计目标与非目标

### 1.1 目标（对齐 `00` 的两个子目标）

| 子目标 | 内容 | S1 达成程度 | 判据 |
|---|---|---|---|
| **(a) 降低 primary 异常概率** | primary 不跑数据面、不解析报文、不进协议栈收包路径，代码路径大幅缩短 | **达成（统计意义）**。primary 主循环收缩到「timer + msg ring +用户回调」三件事，不再执行 `process_packets()`（`lib/ff_dpdk_if.c:1975`起，引自 02）、不再触碰 mbuf 与协议栈输入路径 | primary 不再是数据面参与者；但仍是"结构性单点"（此事实未改变） |
| **(b) 缩小 primary 异常后的影响面** | primary 退出时不带走任何数据面能力 | **存量/新建流量层面达成**：primary 不持队列 ⇒ `nb_queues` 收缩 ⇒ reta 只映射到 secondary 队列 ⇒ 无孤儿队列 ⇒ primary 崩溃对数据面零影响（B4 + D.3.2，引自 02）。**恢复能力层面亦达成（据 E2e 上调）**：primary 崩溃后所有 secondary 仍在 ⇒ uio refcnt ≥ 1 ⇒ 设备运行态完好 ⇒ 此后任何 secondary 崩溃都能**原地重启恢复**，**无需全组重启**（`05` 第九节，复现两次）。**唯一残余**：控制面降级（见 7.0）与"所有进程都退出"的固有边界（见第六节） | 需PoC 实测（E3）复核 |

按 `00` 的三档定义，S1 的预期定档为 **「有条件可行」**，前提条款四条：(i) `thread_mode=0`；(ii) KNI 需按 `04` 的 K1/K3 处置（`kni.enable=1` 时不能直接用 S1 最小集）；(iii) **建议**配套 S5 作为兜底（覆盖"所有进程都退出"与"控制面降级态的择机全组重启"两种残余场景；**据 E2e 已从"必须"下调为"建议"**）；(iv) **运维上必须保证 primary 常驻期间不优雅退出、且至少一个数据面进程始终存活**（否则 uio refcnt 归零、设备运行态丢失，退化到 E2c 的失能场景）。**定档理由的准确表述（据 E10）**：S1 **不是**"完全无需重启"，而是"**重启时机可控**"——primary 崩溃后业务继续跑、崩掉的 secondary 可原地重启，但控制面降级态不可就地修复（primary 无法原地拉回，E10），仍需一次计划内全组重启。最终定档由 `10` 裁定。

### 1.2 非目标（明确不做）

- **不做 primary 热切换/主备**：不实现「primary 挂掉后由某 secondary 升格为 primary」。DPDK 的 primary 身份在 `rte_eal_init()` 时确定，且 mp_socket 服务端由 primary 独占（`01` §1.2.1），运行期升格无路径。
- **不做连接迁移**：不实现把某进程的 TCP 连接迁移到其他进程（f-stack 每进程一份独立 FreeBSD 栈实例，无连接序列化机制）。
- **不做运行期队列重配**：不实现 primary 崩溃后由某 secondary 动态 `rte_eth_dev_configure` 收缩队列（secondary 无权做设备配置，`lib/ff_dpdk_if.c:1061-1063` 引自 02）。
- **不做 KNI 的完整重写**：`04` 只给出候选路径评估与推荐，不在本轮落地。
- **不落地代码**：本轮为可行性调研，S1 的代码改动清单交给 `07` 做工作分解。

## 二、主方案 S1「primary-slim」完整设计

### 2.1 配置项设计

#### 2.1.1 取舍：显式开关 vs 自动推导

两种候选语义：

- **候选甲（自动推导）**：不新增配置项，直接把「primary 的 lcore 不在任何 `[portN].lcore_list` 中」这一事实当作 slim 语义，`lib/ff_dpdk_if.c:508-510` 的 `rte_exit` 对 primary 无条件放宽。
- **候选乙（显式开关，推荐）**：新增 `[dpdk] primary_slim`，仅当其为 1 时才放宽。

**裁决：采用候选乙。理由三条**：

1. **保住 fail-fast**。现状下「primary lcore 漏写进 `lcore_list`」是一个**配置错误**，被 `508-510` 的 `rte_exit(EXIT_FAILURE, "lcore %u has nothing to do")`（已复核）明确拦住，且因`init_lcore_conf()` 是 `ff_dpdk_init()` 第一步（`lib/ff_dpdk_if.c:1682`，已复核），报错发生在启动最早期、极易定位。若改为自动推导，一个 `lcore_list` 笔误会从"启动即报错"退化为"静默少一个收包进程、吞吐掉 1/N"——把 fail-fast 变成 silent degradation，这是运维上的负向改动。
2. **需要双向交叉校验**。显式开关让配置矛盾可检测：`primary_slim=1` 但 primary lcore 仍出现在某port 的 `lcore_list` 中 → 直接报错（用户意图与配置自相矛盾）；`primary_slim=0` 且 primary 不在任何 `lcore_list` → 保持现有 `rte_exit`（零回归）。自动推导无法表达"我本来就想让 primary 收包"与"我写错了"的区别。
3. **需要一个统一门控点**。slim 语义不止影响队列分配，还联动改变：mbuf 池公式（`535`）、退出语义（`2883-2884`）、KNI owner 归属（`04`）、`msg_ring[0]` 归属（N1）、idle_sleep 下限。这些必须由同一个布尔量统一门控，才便于 `grep` 审计与一键回滚；把它散布成"从 lcore_list 反推"会让每个改动点各自重复推导，容易不一致。

#### 2.1.2 配置项定义

| 项 | 值 |
|---|---|
| section | `[dpdk]` |
| 名称 | `primary_slim` |
| 类型 / 取值 | `int`，`0` = 关闭（默认，行为与现状完全一致）；`1` = 开启 |
| 默认值 | `0`（**必须**默认关闭，保证零回归） |
| 生效范围 | 仅 `proc_type=primary` 且 `thread_mode=0` |
| 结构体字段 | `struct ff_config.dpdk` 中新增 `int primary_slim;`，建议紧邻 `thread_mode`/`nb_threads`（`lib/ff_config.h:295-296`，已复核） |
| 解析位置 | `lib/ff_config.c:1035-1036` 的 `MATCH("dpdk", "thread_mode")` 旁增加 `MATCH("dpdk", "primary_slim")`（已复核该MATCH 链的写法） |
| 默认值设置 | `ff_default_config()`（`lib/ff_config.c:1508`起，已复核入口）中不需显式置 0（结构体已memset），但为可读性建议显式写 `cfg->dpdk.primary_slim = 0;` |

#### 2.1.3 与既有 `lcore_list` 的关系

`primary_slim=1` **不改变** `lcore_list` 的语义，只是要求用户显式把 primary 的 lcore 从所有 port 的 `lcore_list` 中排除。两者是「意图声明（开关）+ 具体分配（`lcore_list`）」的关系，由校验层保证一致：

- `lcore_list` 仍是队列分配的**唯一**事实来源：`nb_queues = pconf->nb_lcores`（`lib/ff_dpdk_if.c:836`，已复核）、`queueid` = lcore 在 `lcore_list` 中的下标（`lib/ff_dpdk_if.c:487-491`，已复核）。
- 注意默认行为陷阱：`config.ini:189` 的 `lcore_list` 默认是**注释掉**的（已复核），此时 `pconf->nb_lcores = ff_global_cfg.dpdk.nb_procs`、`lcore_list` 全量继承 `proc_lcore`（`lib/ff_config.c:566-571`，引自 02）。因此 **`primary_slim=1` 必须显式配置 `lcore_list`**，否则 primary 会被自动放回 `lcore_list`，校验层应据此报错而不是静默。

#### 2.1.4 `config.ini` 示例片段

```ini
[dpdk]
# 4 lcore：lcore0 = primary（只做初始化/控制面，不收包），lcore1~3 = secondary 收包
lcore_mask=f

# primary 瘦身：primary 常驻但不分配任何 rx/tx 队列。
# 要求：thread_mode=0、nb_procs>=2、primary 的 lcore 不在任何 [portN].lcore_list 中。
primary_slim=1

# primary 不再收包，避免空转烧核（单位 us，仅对 slim primary 生效）
#primary_slim_idle_sleep=1000

[port0]
addr=<DPDK_NIC_IP>
netmask=<NETMASK>
broadcast=<BROADCAST_IP>
gateway=<GATEWAY_IP>
# 只列secondary 的 lcore，primary 的 lcore0 被排除 -> 网卡上只建 3 个队列
lcore_list=1,2,3
```

启动命令不变（每进程仍用 `--proc-type` / `--proc-id` 区分）。

### 2.3 启动路径改动（对应 `02` D.1 的 #1/#2/#3/#4）

#### 改动 #1（M）：放宽 `nb_rx_queue == 0` 的 `rte_exit`

- **位置**：`lib/ff_dpdk_if.c:508-510`（多进程分支，已复核）；`lib/ff_dpdk_if.c:459-460`（`thread_mode` 分支，已复核）。
- **改法**：把 `508-510` 改为
  「若 `ff_global_cfg.dpdk.primary_slim && rte_eal_process_type() == RTE_PROC_PRIMARY` → `ff_log(FF_LOG_NOTICE, ...)` 打印 "primary_slim: primary holds no rx/tx queue, running control-plane only" 后 `return 0`；否则保持原 `rte_exit`」。
- **`459-460` 不改**（`thread_mode` 与 slim 已由 V4 互斥），仅建议加一行注释说明互斥关系（符合最小注释规约）。
- **为什么必须这么改**：`init_lcore_conf()` 是 `ff_dpdk_init()` 的第一步（`1682`，已复核），primary 在此`rte_exit` 会导致后续 `init_mem_pool()`（`1684`）、`init_dispatch_ring()`（`1686`）、`init_msg_ring()`（`1688`）、`init_port_start()`（`1718`）全部不执行 → **所有共享对象都没人创建**，secondary 在 9 处 `rte_*_lookup`（清单见 02 B8）拿到 NULL 后 `rte_exit`/`rte_panic` → 整个进程组无法启动。这是第一道硬墙。

#### 改动 #2（M）：修正 mbuf 池 RX 项公式

- **位置**：`lib/ff_dpdk_if.c:535`（已复核：`uint32_t nb_rx_queue = ff_cur_lcore_conf()->nb_rx_queue * nb_lcores;`）。
- **改法**：改为按 port 求和，不依赖本进程队列数：
  ```
  nb_rx_queue = Σ_{j < ff_global_cfg.dpdk.nb_ports}
                    port_cfgs[ portid_list[j] ].nb_lcores
  ```
  （`thread_mode` 下`nb_lcores` 语义相同，公式通用；`portid_list`/`nb_ports` 见 `lib/ff_config.h:320-322`，已复核）
- **为什么必须这么改**：池只由 primary 创建（`571-590`，已复核），secondary 只 `lookup`（`592-593`）。primary 的 `ff_cur_lcore_conf()->nb_rx_queue` 在 slim 下为 0 → RX 项整体归零 → 池对所有 secondary 严重欠配（B3，引自 02）。
- **向后兼容性论证**：默认/同构配置下（每个进程都在每个 port 的 `lcore_list` 中）有 `Q = P`（本进程参与的 port 数 =总 port 数）、`L = N`，旧值 `Q*L = P*N`；新值 `Σ_p nb_lcores_p = P*N`，**数值完全相同 → 对既有配置零影响**。仅在异构 `lcore_list`（某进程只服务部分 port）下两者不同，此时新公式更精确（旧公式用"本进程视角 × 进程数"外推，可能偏大或偏小）。
- **内存占用量级**（宏取值引自 02：`RX_QUEUE_SIZE=TX_QUEUE_SIZE=512`、`MEMPOOL_CACHE_SIZE=256`、`DISPATCH_RING_SIZE=2048`、`MAX_PKT_BURST=32`）：
  - 例A：`P=1, max_portid=0, L=2`（1 primary + 1 secondary）。旧（非slim）RX 项 = 2048；slim 未修公式 = 0；slim 修好= 1024。合计经 `RTE_ALIGN_CEIL(..., 8192)`（`538`/`548`，已复核）后：非 slim 8832→16384；slim 未修 6784→8192；slim 修好 7808→8192。**该小配置下对齐把差异吃掉了**，这解释了为什么欠配可能不立即崩（B3 判为"部分成立"）。
  - 例 B：`P=1, max_portid=0, L=8`（1 primary + 7 secondary）。非 slim 合计 35328→40960；slim 未修 27136→**32768（少 8192 个 mbuf ≈ 19MB）**，而 7 个 RX 队列在 `rte_eth_rx_queue_setup`（`1095`，引自 02）时要一次性预填 7×512×(超配系数)，余量被吃光→ 运行期 mbuf 长期紧张；slim 修好 34304→40960，与非 slim 同档。
  - 结论：修好公式后内存占用相对现状**不增加**（同构配置等值，slim 配置略降），**不需要为本特性额外预留 hugepage**。
- **可选加固（O）**：把 `531-534` 的 `nb_lcores` 语义拆成「总进程数」（用于 TX/cache/dispatch 项）与「收包进程数」（用于 RX 项）两个局部变量。slim 下前者比后者大 1 → TX/cache/dispatch 略微超配（无害，引自 02 B3 注2），拆开后可省下这部分。本轮列为 O级，不进最小集。

- **位置**：`lib/ff_dpdk_if.c:2642`（`main_loop`，已复核）、`lib/ff_dpdk_if.c:2867-2886`（`ff_dpdk_run`，已复核）。
- **改法**：见 2.4、2.5 两节（这是本方案最关键的部分，单独展开）。

#### 改动 #4（M）：`ff_dpdk_if_up()` 的 ifp 归属裁决

- **位置**：`lib/ff_dpdk_if.c:2850-2865`（已复核）。
- **裁决：primary-slim 下primary 不 attach 任何 ifp，代码无需改动**（`qconf->nb_tx_port == 0` ⇒ 循环 0 次 ⇒ 天然 no-op），只建议加一条 NOTICE 日志说明"slim primary 无 f-stack 网络接口"。
- **裁决理由（三条，第 1 条为本文新增发现）**：
  1. **给 primary attach ifp 会引入 tx 队列并发写风险**。`ff_veth_attach(struct ff_port_cfg *cfg)`（`lib/ff_veth.c:1153-1154`，已复核）只依赖 port 配置、与队列无关，所以技术上「primary 无队列也能 attach ifp」。但 `lcore_conf` 是零初始化的全局数组（`lib/ff_dpdk_if.c:126`，已复核），slim primary 从未执行 `501` 的 `tx_queue_id[port_id] = queueid` 赋值（已复核），故其 `tx_queue_id[port]` 恒为 **0**；而 `send_burst()` 直接用它：`queueid = qconf->tx_queue_id[port]; ... rte_eth_tx_burst(port, queueid, ...)`（`lib/ff_dpdk_if.c:2378-2389`，已复核）。**队列 0 正是 `lcore_list[0]` 那个 secondary 的 tx 队列**（`487-491` 的下标语义），两进程并发写同一 tx 队列而 DPDK tx 队列非MT-safe → 队列结构损坏/丢包/崩溃。primary 一旦持ifp，任何本机发起的报文（ARP 请求、ICMP、IPv6 地址配置引发的 NS/MLD、路由/接口操作的副作用）都会走到这条路径。
  2. **重复 IP 的语义污染**。primary 与各secondary 共用同一份 `[portN]` 地址配置，多一个 ifp 就多一个持有同一 IP 的协议栈实例，但它收不到任何包，只会制造无法应答的半状态。
  3. **`02` N6 的"反向好消息"成立**：不attach ifp 恰好就是"primary 只做初始化"想要的效果，且 `main_loop:2762` 的 `ctx = veth_ctx[...][port_id]` 因rx 循环 0 次而不会被解引用（已复核 `2759-2762`）→ **不会空指针崩溃**。
- **连带确认项**：`ff_freebsd_init()`（`lib/ff_init.c:47`，已复核）**仍需执行**且在 `ff_dpdk_if_up()` 之前（`lib/ff_init.c:43-51`，已复核）。保留它的理由：primary 精简循环要处理 `msg_ring[0]` 上的 `FF_SYSCTL`/`FF_TOP`/`FF_ROUTE` 等消息（`handle_msg` 分派，`lib/ff_dpdk_if.c:2298-2340`，已复核），这些都需要一个可用的 FreeBSD 栈实例；且 `rte_timer_manage()` 驱动的 `freebsd_clock`（`init_clock()`，`lib/ff_dpdk_if.c:1197-1212`，已复核）也依赖栈已初始化。**开放问题**：`ff_freebsd_init()` 在无 ifp 情况下能否完整跑完，静态未穷尽（沿用 `02` 开放问题 4），需 PoC（E3）实测确认。
- **副作用（需在文档与运维手册中明示）**：primary 上 `ff_ifconfig` / `ff_route` 无接口对象可操作；`ff_rss_self_queue_info()` 在 primary 返回 -1（`lib/ff_dpdk_if.c:3212-3213`，已复核）。这属于**预期行为**，处置方案见 `04` 第四节。

**关于中断职责（据 `01` §1.2.5 补充）**：DPDK 官方明确"所有中断只在 primary 内触发，link status 等中断在 secondary 中不工作"（`multi_proc_support.rst:174-177`）。这对 slim primary 是**正向**的——中断由 EAL 自有的中断线程处理，**不需要 `main_loop` 参与**（与 mp 请求同理，见 7.1 假设 C 的坐实），因此 slim 后primary 仍是唯一具备中断处理能力的进程，这恰好是"primary 作为控制面常驻"的合理职责。反过来也意味着：任何"把 link status 监听迁到secondary"的想法都不可行（`04` §3.2 已据此修正）。

### 2.5 primary 退出语义设计（结合 N4）

**规则（三条，按强度排序）**：

1. **slim primary 不得执行 `rte_eal_cleanup()`**。位置 `lib/ff_dpdk_if.c:2879-2885`（已复核）。改法：把 `ff_unload_config(); rte_eal_cleanup();` 用 `if (!(ff_global_cfg.dpdk.primary_slim && rte_eal_process_type() == RTE_PROC_PRIMARY))` 包住；slim primary 只执行 `ff_log_close()`。理由：`rte_eal_cleanup()` 会释放 EAL 管理的共享资源（hugepage/memseg 列表/多进程通道），而所有 secondary 的热路径指针都指向这些共享内存（`02` B8 第2 条清单）→ 会把"primary 优雅退出"变成"全体 secondary 内存被抽走"。E2 观察到的乐观结论只覆盖 `kill_process.sh` 强杀路径（`05` 第三节的边界说明），**不能外推到优雅退出**。
   **`01` 提供的三条额外理由（进一步抬高该规则的强制性）**：slim primary 还同时是 (i) **IPC 唯一服务端**（`01` §1.2.1，`eal_common_proc.c:750-751`）、(ii) **全体 secondary 的扩堆代理**（`01` §1.2.2，`malloc_heap.c:484`、`:1030`——secondary 无法自行分配新 hugepage）、(iii) **唯一能收到中断的进程**（`01` §1.2.5，`multi_proc_support.rst:174-177`）。因此"primary 常驻"不是本方案的选择，而是 DPDK 模型的**要求**。
2. **slim primary 在收到停机请求时必须显式告警**。`ff_dpdk_stop()`（`2888-2891`，已复核）置 `stop_loop=1`后 `main_loop` 会 `break`（`2693-2695`）。改法：在 slim primary 的 break 之后（或 `ff_dpdk_run()` 的 `2876` 之前）打一条 `FF_LOG_WARNING`：说明"slim primary 退出后进入控制面降级态——mp_socket 服务端消失（IPC / 扩堆代理 / 中断能力丧失），且本进程持有的 `/dev/uioX` fd 被关闭（refcnt −1）；只要仍有数据面进程存活（refcnt ≥ 1），数据面与 secondary 原地重启不受影响（见 issue #1078 调研 E2e），但请尽快按运维流程把 primary 拉回来"。
3. **文档级规则：slim primary 是常驻控制面进程，正常运维不应退出**。它不是"初始化完就可以走"的一次性工具进程（那是 S2，已否决）。除控制面能力外，它还是 uio refcnt 的一个贡献者——在只有 1 个secondary 的极端配置下，primary 退出会让 refcnt 从 2 降到 1，此时**该 secondary 成为设备运行态的唯一持有者**，它一挂就必须全组重启。

**残余风险（诚实边界，据 E2e 修订）**：即使跳过 `rte_eal_cleanup()`，primary **进程消失**本身会导致：(i) `/var/run/dpdk/rte/mp_socket` 服务端不存在 ⇒ IPC 面瘫、secondary 无法扩堆、中断无人处理（`01` §1.2.1/§1.2.2/§1.2.5）；(ii) 该进程的 uio fd 被关闭，refcnt −1。**但 (ii) 只要 refcnt 仍 ≥ 1 就不破坏设备运行态**——E2e 实测（`05` 第九节，复现两次）证明此时**崩溃的 secondary 仍可原地重启并恢复其队列份额**。因此规则 1 保证的是「primary 优雅退出不破坏存量 secondary」，而**"能否新起 secondary"取决于 refcnt 是否 ≥ 1，而非 primary 是否在线**。详见第六节。

### 2.6 mbuf 池 sizing 公式（完整形式）

令 `P = ff_global_cfg.dpdk.nb_ports`、`M = max_portid`、`L = nb_procs`（或 `nb_threads`）、`Q_p = port_cfgs[p].nb_lcores`。

**修正后公式**（仅第一项改动，其余保持原样以最小化 diff；结构引自 02 的精确公式，已按 `lib/ff_dpdk_if.c:538-548` 复核）：

```
nb_rx_queue_total = Σ_{p ∈ portid_list} Q_p            // 【新】全局队列总数，与本进程无关

nb_mbuf = align8192(
      nb_rx_queue_total * (M+1) * 2 * RX_QUEUE_SIZE// RX 描述符项【本次唯一改动】
    + P * (M+1) * 2 * L * MAX_PKT_BURST                // burst 暂存
    + P * (M+1) * 2 * L * TX_QUEUE_SIZE                 // TX 描述符项（nb_tx_queue = L，见 534）
    + L * MEMPOOL_CACHE_SIZE                            // per-lcore cache
    [+ P * KNI_MBUF_MAX + P * KNI_QUEUE_SIZE]           // 仅 FF_KNI
    + L * P * DISPATCH_RING_SIZE )                      // dispatch ring
```

**与既有公式的差异**：旧式第一项为 `(本进程 nb_rx_queue) × L × (M+1) × 2 × RX_QUEUE_SIZE`。差异只在第一个因子：由「本进程视角 × 进程数」改为「全局队列数直接求和」。同构配置下两者恒等（见 2.3 改动 #2 的论证），slim 配置下旧式为 0（bug）、新式为 `Σ Q_p = P×(L-1)`（正确）。

**`FF_USE_PAGE_ARRAY` 的第二个池**（`lib/ff_dpdk_if.c:602-609`，已复核）：其公式只含 `nb_ports`/`nb_lcores`/`nb_tx_queue`，**不依赖本进程队列数** → slim 下无需改动。

| bond（`nb_slaves > 0`） | `rte_eth_bond_8023ad_dedicated_queues_enable()` 在 `839-841`（已复核），早于 `1061` 的 primary 门禁但只依赖 port 配置 | 无影响；`nb_queues` 仍走 `pconf->nb_lcores` |
| MTU巨帧（已交付特性） | `ff_dpdk_if_set_mtu()` 的 primary 门禁（`297-298`，已复核）+ slim primary 无 ifp ⇒ **任何进程执行 `ff_ifconfig mtu` 都不会真正调`rte_eth_dev_set_mtu()`** | 这是 N5 在 slim 下升级为**功能回归**。处置方案见 `04` 第三节（分档：P1 返回 EPERM 让失败可见；P2 经 msg ring 转发给 primary 执行） |

## 三、备选方案横向对比

### 3.1 各方案说明与否决/保留理由

#### S0：不改（现状），仅在文档中说明风险 —— **基线对照**

- 现状：默认 `lcore_list` 注释掉 ⇒ `pconf->nb_lcores = nb_procs`（`lib/ff_config.c:566-571`，引自 02）⇒ primary 天然占一个队列。primary 崩溃 ⇒ 其队列变孤儿队列 ⇒ 落到该队列的 1/N 流量黑洞（E2 实测 11/20 连接失效）。
- 保留价值：**必须作为对照基线保留在结论中**。issue 提出者的痛点在 S0 下是真实存在的（`02` D.3.1 已代码级解释）。
- 结论：**否决作为最终答复**（不响应诉求），但**保留为对比基线**。

#### S1：primary-slim，primary 常驻不占队列 —— **主方案（推荐）**

- 见第二节。核心收益：消除孤儿队列（B4 代码级坐实）+缩短 primary 代码路径 + `msg_ring[0]` 消费者不缺失 + **primary 崩溃后 secondary 仍可原地重启恢复**（E2e 实测，因primary 崩溃时数据面进程都在、uio refcnt ≥ 1）。
- 核心限制：不"修复"E2c 现象本身（只是让其触发条件几乎不出现）；primary 崩溃后处于控制面降级态，且 primary **不可原地拉回**（E10）⇒ 需一次择机的计划内全组重启；`kni.enable=1` 需额外方案。
- 结论：**推荐**（**建议**配 S5 作为兜底，非前置条件）。

#### S2：primary 初始化完成后**退出**，只留 secondary —— **否决（致命）**

五条独立的致命问题，任一即足以否决（第 2~4 条为 `01-外网调研与交叉验证.md` 提供的 **DPDK 官方硬约束**，本节据其修正了初稿的归因）：

1. **N4：优雅退出会执行 `rte_eal_cleanup()`**（`lib/ff_dpdk_if.c:2884`，已复核）→拆掉 secondary 依赖的 EAL 共享资源。虽可像 S1 那样跳过，但这只是把致命降为下面几条。
2. **DPDK 硬约束一：primary 是 IPC 的唯一服务端**。DPDK IPC 只支持"secondary → primary 单播"与"primary → 所有 secondary 广播"，不支持 secondary↔secondary；secondary 发消息的目的地固定为 `eal_mp_socket_path()`（引自 `01` §1.2.1，`lib/eal/common/eal_common_proc.c:750-751`）。**primary缺席 = 整个 IPC 面瘫**。
3. **DPDK 硬约束二：secondary 不能自行扩堆，必须由 primary 代理**。secondary 需要新 hugepage 时必须 `request_to_primary()`（引自 `01` §1.2.2，`lib/eal/common/malloc_heap.c:484`、`:1030`）⇒ primary 退出后 secondary **只能用已有的堆**，任何触发扩堆的 `rte_malloc`/`rte_mempool_create` 都会失败。这条直接否决"primary 用完即弃"。
4. **DPDK 硬约束三：所有中断只在 primary 内触发**。官方原文 "The delivery of interrupts, such as Ethernet device link status interrupts, do not work in secondary processes. All interrupts are triggered inside the primary process only."（引自 `01` §1.2.5，`doc/guides/prog_guide/multi_proc_support.rst:174-177`）⇒ primary 退出后 link status等中断永久无人处理。
5. **f-stack 侧共享对象生命周期**：secondary 的 9 处 `rte_*_lookup`（清单引自 02 B8）依赖 primary 建立的对象；`message_pool` 在 primary 被杀时 in-flight 的 msg 对象永久泄漏（引自 02 开放问题 5）。

**关于 E2c 的实测证据（归因已被 E2e 更正，S2 的否决不依赖它）**：E2c 曾观测到 primary 缺席后新起的 secondary 静默失能（`05` 第六节，复现两次）。**该现象的根因已由 leader 的 E2e 实验（`05` 第九节，复现两次）确定为"进程组曾整体退出 ⇒ uio refcnt 归零 ⇒ 内核态 `pci_clear_master()`停掉设备 DMA"**（`f-stack/dpdk/kernel/linux/igb_uio/igb_uio.c:352-366` 的 `atomic_dec_and_test(&udev->refcnt)` 分支，已复核），**而不是"primary 缺席"**。E2e 中只要保持至少一个进程持有 `/dev/uioX`，primary 缺席下重启的 secondary 能正常收包（10/18，与其队列份额吻合）。
> **两次勘误留档**：本文档初稿曾把 `vdev_scan()` 的 mp 请求失败（`drivers/bus/vdev/vdev.c:472-503`）与 `rte_dev_probe()` 的 secondary 转发分支（`lib/eal/common/eal_common_dev.c:244-259`）当作 E2c 的根因；第一次修订据 `01` §1.4.1 撤回该归因、改判"根因未收敛"。现据 E2e **第二次修订**：根因已收敛为 uio refcnt 归零（FP-1），且 E2e 逐字对比确认这些 EAL 报错（`Connection refused`、`bus_vdev_mp`、`vdev_scan` 失败）**确实只是伴随噪声**——重启后的 secondary 打出完全相同的报错却能正常收包。
>
> **对S2 的影响（诚实说明）**：E2e 意味着"primary 退出后数据面仍可工作、secondary 仍可重启"，因此 **S2 的否决理由中不能再引用 E2c**。S2 依然被否决，但依据收窄为上述第1 条（`rte_eal_cleanup()`）与第 2~4 条 DPDK 官方硬约束（IPC 服务端 / 扩堆代理 / 中断），这三条与设备运行态无关、不受 E2e 影响，**本身已足够**：一个既不能响应 IPC、不能为 secondary 扩堆、也收不到任何中断的系统不可作为交付形态。

- 结论：**否决**。若上游 issue 的原意是 S2（"只做初始化"字面理解），本轮结论必须明确告知这条路在 DPDK 多进程模型下不可行（且`01` §1.5 已确认该判断**与 23.11→24.11 的版本升级无关**），并给出 S1 作为其可实现的近似。`01` §3 的独立结论与本文一致：**"可行的是 primary 常驻但不收包"，这是唯一值得继续评估的方向**。

#### S3：primary 保留一个最小队列（"瘦身"而非"完全无队列"）—— **备选（KNI 必须开启时的首选）**

- 设计要点：primary 仍在每个 port 的 `lcore_list` 中（`nb_queues` 不收缩，B2校验无需改），但通过**把 reta 只映射到 secondary 队列**，让 primary 的队列不承接业务流量、只承接 KNI/管理面流量。实现上需改 `set_rss_table()`（`lib/ff_dpdk_if.c:787-809`，已复核）的 `reta_conf[i].reta[j] = hash++ % nb_queues`（`801`）为「跳过 primary 的 queueid」，即 `hash % (nb_queues-1) + offset` 形式，或用 `rte_flow` 把管理流量定向到 queue 0。
- 优点：KNI 完全不用动（`ff_kni_process()` 仍在 primary 的 rx 循环里、`kni_process_rx` 的 `rte_eth_tx_burst(port_id, queue_id, ...)`（`lib/ff_dpdk_kni.c:190`，已复核）仍有合法队列）；MTU/ifp/控制面全部保持现状（N5/N6 都不触发）。
- 缺点：(i) 改reta 语义的风险不低（reta 是 NIC 硬件表，`hash % (n-1) + offset` 的分布均匀性与对称RSS 的兼容性需实测；开启 `FF_FLOW_ISOLATE`/`FF_FLOW_IPIP` 时 `set_rss_table` 整体被编译掉，方案在该配置下失效）；(ii) primary 仍持有一个队列 ⇒ **孤儿队列未真正消除**，只是从"承接 1/N 业务流量"降为"承接接近 0 的管理流量"，issue 的子目标 (b) 只是近似达成；(iii) primary 仍跑 `process_packets()` 全路径（因为它有rx 队列）⇒ 子目标 (a) 的收益远小于 S1。
- 结论：**备选**。定位为「`kni.enable=1` 且不接受 KNI 改造风险时的务实折中」。

#### S4：切换到单进程多线程（`thread_mode=1`）—— **备选（长期方向，与 #1078 正交）**

- 机理：`thread_mode=1` 强制 `proc_type=primary`、`nb_procs=1`、`proc_id=0`（`lib/ff_config.c:1484-1502`，已复核），所有 worker 变成同进程内的线程，各持一份 vnet 栈实例。
- 优点：**从根上消除 primary/secondary 依赖**——没有独立 primary 进程，也就没有"primary 挂掉"这个故障模式；没有 mp_socket 依赖，E2c 不存在；共享对象都是进程内内存。
- 代价：(i) **故障域反向放大**——单进程崩溃则全部 worker 一起死，把"1/N 影响"变成"100% 影响"，与 issue 的 R8「缩小影响范围」诉求方向相反；(ii) 与 issue 的前提（"DPDK 多进程模式下"）不同，属于**换赛道**而非回答问题；(iii) 该路线在本仓库已有独立工作在推进（native-mt / CM5-B 阶段，工作区内已有相关设计与遗留并发风险清单），成熟度与本issue 无直接关系。
- 结论：**保留为并行长期方向**，在给上游的答复中应提及（"如果你的真实诉求是去掉多进程的primary 依赖，`thread_mode=1` 是另一条已在推进的路线"），但**不作为 #1078 的解**。

#### S5：外部守护/看护进程 + 快速全组重启 —— **建议配套（兜底手段，非可行性前置条件）**

- 设计：外部 supervisor 监控primary +全部 secondary 的存活。按 E2e 的结论，其职责分两层：
  - **第一层（常态，优先）**：单个 secondary 崩溃 ⇒ **原地重启该 secondary**（不动其他进程）。E2d 已验证 primary 在线时可行；**E2e 进一步验证 primary 缺席时同样可行**（只要 uio refcnt ≥ 1）。
  - **第二层（降级态收尾）**：primary 崩溃 ⇒ 进程组进入控制面降级态。**E10 已实测确认 primary 不可原地拉回**（`EAL: Cannot init memzone`，exit 1；且该失败 fail-fast、不损伤存量secondary，复测仍 10/18），因此该层的动作是：**告警 + 择机（计划内维护窗口）执行第三层的全组重启**，而不是尝试原地恢复。允许先做一次"试拉起"探测（无副作用），但不应期待成功。
  - **第三层（固有边界，唯一必须全组重启的场景）**：**所有**进程都退出 ⇒ uio refcnt 归零 ⇒ 设备运行态丢失（FP-1，`igb_uio.c:352-366`，已复核）⇒ 必须清理 `/var/run/dpdk/rte/` 残留后全组重启。
- 优点：不改 f-stack 任何代码；把上述三层恢复动作固化为可靠编排，并保证"至少一个进程始终存活"这一 S1 的运维前提（`§1.1` 前提iv）。
- 缺点：仅第三层会造成 100% 流量中断；需要外部编排能力。
- 结论：**建议配套（兜底/收尾）**。**定位据 E2e + E10 下调**：S5 不再是"唯一能应对 E2c 的手段"、也不再是 S1 可行性的前置条件；S1 自身已让primary 崩溃后的数据面零损失且 secondary 可原地重启。S5 的价值收窄为：(i) 自动化"崩掉的 secondary 原地重启"；(ii) 作为**控制面降级态的收尾手段**——自动化那一次择机的计划内全组重启（因E10 已证 primary 不可原地拉回）；(iii) 覆盖"所有进程都退出"的固有边界。

## 四、S1 风险评估

> N编号沿用 `02` D.2；`R-新` 为本文档复核新增。

| 编号 | 风险描述 | 触发条件 | 影响 | 缓解措施 | 残余风险 |
|---|---|---|---|---|---|
| **R1（N1）** | `msg_ring[0]` 无消费者 → 不带 `-p` 的运维命令挂起 | primary 不再运行 `main_loop`，或运行但裁掉 `process_msg_ring()`（`2803`） | 所有工具默认失效（`ff_proc_id = 0`，`tools/compat/ff_ipc.c:42`，已复核） | S1 设计上**primary 常驻并保留 `process_msg_ring()`**（2.4 裁决）⇒ 风险**不触发** | primary 上 `ff_ifconfig`/`ff_route` 无 ifp 可操作（不同问题，见 R6/`04` 第四节） |

## 六、诚实边界：S1 不能解决什么

### 6.1 明确判断：S1 **规避**而非**修复** E2c；真正的固有边界是"所有进程都退出"

**判断（据 leader 的 E2e/E10 实测修订）：S1 让"primary 崩溃后无法重启 secondary"这一现象的触发条件几乎不可能出现（=规避），但不修复该现象本身；同时 S1 无法消除"控制面降级态必须择机全组重启"这一固有代价。**

**理由（代码 + 实测级）**：

1. **E2c 的根因已由 E2e 更正为 uio refcnt 归零，与"primary 是否在线"无关**。`igbuio_pci_release()` 中只有**最后一个**关闭 `/dev/uioX` 的进程（`atomic_dec_and_test(&udev->refcnt)` 成立）才执行 `pci_clear_master()` 停掉设备 DMA（`f-stack/dpdk/kernel/linux/igb_uio/igb_uio.c:352-366`，已复核，即 `02` 任务 E 的 FP-1）。E2c 之所以 0/12，是因为其实验序列中**进程组曾整体退出**；E2e 在 3 进程环境下全程保持 refcnt ≥ 1，primary 缺席时重启的 secondary **正常恢复其队列份额（10/18），复现两次**（`05` 第九节）。
2. **因此 S1 在此项上是"规避"**：primary-slim 下 primary 崩溃时，**全部数据面 secondary 都还在**，refcnt ≥ 1 必然成立 ⇒ 设备运行态不被破坏 ⇒ 此后崩溃的任何 secondary 都能原地重启恢复。S1 并没有改变 `igb_uio` 的 refcnt 语义（那是内核模块行为，f-stack 侧无法消除），只是让"refcnt 归零"这一前置条件在正常运维下不出现。
3. **真正的固有边界（S1 不能解决）**：若**所有** f-stack 进程都退出（含最后一个 secondary 也挂掉），设备运行态丢失，必须清理 `/var/run/dpdk/rte/` 后全组重启（FP-1/FP-2，引自 `02` 任务 E；`05` §9.4 第 4 条）。
4. **另一条S1 不能解决的固有代价：控制面降级态不可就地修复（E10 已实测闭环）**。primary 缺席后，`01` §1.2 的三条官方硬约束使系统失去 IPC 服务端、扩堆代理与中断处理能力（`eal_common_proc.c:750-751`、`malloc_heap.c:484`/`:1030`、`multi_proc_support.rst:174-177`）；且 **primary 无法原地重新拉起**——E10 实测在"primary 已被强杀、2 个 secondary 仍在服务"的状态下以 `--proc-type=primary --proc-id=0` 拉起 primary，EAL 直接失败退出：`EAL: Cannot allocate memzone list` / `EAL: Cannot init memzone` / `Error - exiting with code: 1`，原因是 `/var/run/dpdk/rte/` 下的运行时配置（`config`、`fbarray_memzone` 等）仍被存量 secondary 持有映射，新 primary 无法重建这些全局结构。**该失败是 fail-fast 且无副作用的**（E10 复测服务能力保持 10/18 不变）。
5. **S1 的准确价值表述**：把"primary 崩溃 ⇒ **必须立刻**全组重启、所有连接受影响"降级为"primary 崩溃 ⇒ **数据面零损失、业务继续跑、崩掉的 secondary 可原地重启**，但进程组处于控制面降级态，**需择机（计划内维护窗口）做一次全组重启**"。即 **S1 把紧急故障转化为计划内维护、重启时机可控，而不是"完全无需重启"**。
6. 叠加 f-stack 侧：secondary 的 9 处 `rte_*_lookup`（`02` B8 清单）依赖 primary 创建的共享对象——这些对象在 primary 被**强杀**时仍留在 hugepage 上（E2e 中新起的 secondary 能 lookup 成功即为证据）；但若 primary **优雅退出**并执行 `rte_eal_cleanup()`，则会被拆掉（N4，故有 2.5 规则 1）。

   > **归因勘误留档（共两次）**：本文档初稿曾把 `vdev_scan()` 的 mp 请求失败（`drivers/bus/vdev/vdev.c:472-503`）与 `rte_dev_probe()` 的 secondary 转发分支（`lib/eal/common/eal_common_dev.c:244-259`）当作 E2c 根因；第一次修订据 `01` §1.4.1 撤回该归因、改判"根因未收敛"；**第二次修订（本次）**据 E2e 把根因确定为 uio refcnt 归零（FP-1），并确认那些 EAL 报错（`Connection refused`、`bus_vdev_mp` 失败、`vdev_scan` 失败）**确实只是伴随噪声**——E2e 中重启后的 secondary 打出逐字相同的报错却能正常收包。原先"S1 不解决 E2c ⇒ 故障恢复必须全组重启"的结论**已被实测推翻，本节予以上调**。
**S1 实际解决的与未解决的（据 E2e/E10 重制）**：

| 场景 | S0（现状，E2/E2e/E10 实测） | S1 预期 |
|---|---|---|
| primary 存活，正常服务 | 全部连接正常 | 全部连接正常（吞吐由 N-1 个 secondary 承担，见 `06`） |
| primary 崩溃，**存量**连接 | 1/N 失效（E2：11/20；E2e 3 进程：10/18） | **0 失效**（无孤儿队列）✅ **这是 S1 的核心收益** |

| primary 崩溃后重启单个 secondary | ✅ **可以**（**E2e** 实测 10/18，复现两次；条件是 uio refcnt ≥ 1） | ✅ 可以，且**条件必然满足**（primary 崩溃时全部数据面进程仍在）✅ |
| secondary 崩溃并重启（primary 在线） | ✅ 可以（E2d） | ✅ 可以 |
| primary 崩溃后**把 primary 拉回来** | ❌ 不可能（**E10** 实测：`Cannot init memzone`，exit 1；fail-fast、无副作用） | ❌ **同样不可能**（S1 不改变此项） |
| primary 崩溃后恢复**完整（含控制面）**能力 | 必须立刻全组重启 | **仍必须全组重启，但时机可控**（计划内维护窗口，业务期间不中断）⚠️ 建议由 S5 自动化 |
| **所有**进程都退出 | 必须全组重启（refcnt 归零，FP-1） | **同样必须全组重启**（S1 不能解决，固有边界） |

### 6.2 S1 其他不能解决的

- **不改变"primary 是结构性单点"**：primary 仍是共享内存/设备所有者与 mp 服务端。S1 只降低它异常的**概率**、并把它异常后的后果从"紧急故障"降为"计划内维护"，**不消除它的地位**。
- **不能就地修复控制面降级态**（E10 已证primary 不可原地拉起）⇒ 仍需一次择机全组重启。
- **不能让 primary 承担控制面全部能力**：因为裁决了"不attach ifp"，接口/路由类操作在 primary 上无对象（R6）。
- **不能在 `kni.enable=1` 下直接使用**（本轮 V3 显式拒绝该组合）。
- **不能保证 `FF_FLOW_ISOLATE`/`FF_FLOW_IPIP` 编译组合下的孤儿队列消除**（R12，`set_rss_table` 被编译掉）。
- **不改善primary 崩溃时in-flight msg 对象的泄漏**（`02` 开放问题 5）。
- **不能消除 `igb_uio` 的 refcnt 语义**（FP-1）：所有进程都退出时设备运行态必然丢失。

### 7.3 A4：primary 能否原地重新拉起 —— **已实测闭环（E10），不再是未决问题**

| 项 | 内容 |
|---|---|
| 原问题（A4） | primary 崩溃后，能否在存量 secondary 继续服务的情况下**单独把 primary 拉回来**，以恢复控制面（IPC 服务端 / 扩堆代理 / 中断 / KNI / `ff_*` 工具链）能力？ |
| 实验| **E10**（leader 执行）：primary 已被强杀、2 个 secondary 仍在运行并服务流量，尝试以 `--proc-type=primary --proc-id=0` 重新拉起 primary |
| 结果 | **失败退出**：`EAL: Multi-process socket /var/run/dpdk/rte/mp_socket` → `EAL: Cannot allocate memzone list` → `EAL: Cannot init memzone` → `EAL: Error - exiting with code: 1`（`Error with EAL initialization`，exit code = 1） |
| 机理 | `/var/run/dpdk/rte/` 下的运行时配置（`config`、`fbarray_memzone` 等）仍被存量 secondary 持有/映射，新 primary 试图重建这些全局结构时冲突 |
| 副作用 | **无**：该失败是 fail-fast 的，复测服务能力保持 10/18 不变（存量 secondary 未受损伤）⇒ 运维可安全地"先试一次拉起"再决定重启窗口 |
| 结论 | **① primary 不能原地重新拉起；② 控制面降级态不可就地修复**——要恢复 IPC / 扩堆 / 中断 / KNI / `ff_*` 工具链能力，必须停掉所有进程 + 清理 `/var/run/dpdk/rte/` + 全组重启；**③ 因此 S1 的准确价值是"把紧急故障转为计划内维护、重启时机可控"，而非"完全无需重启"** |
| 对方案的影响 | 已写入：§1.1 定档前提（iii）、§3.1 的 S5 分层设计（第二层）、风险 R14、§6.1 第 4/5 条与 §6.2。**S5 保留为配套建议**，定位改为"降级态的收尾手段（自动化那次择机重启）" |
| 衍生未决 | 见 7.2 第 10 条（降级态检测与主动告警） |
