# 10-可行性结论与建议

> 本文档是 issue #1078「primary稳定性控制」可行性调研的最终裁定，依据为本目录 `00`~`08` 全部文档中的代码坐实结论与实机实测数据。
> 裁定日期：2026-08-07。裁定人：调研 leader（综合）。独立审核见 `09-审核门禁报告.md`。

## 摘要

issue #1078 提议把 primary "独立/瘦身"出来只做网卡队列设置、绑定、初始化，收包及后续处理全部下移 secondary。经代码逐点坐实 + 9 组实机实验（E1/E2/E2b/E2c/E2d/E2e/E5/E10/E3）+ 一份最小 PoC 补丁实测，本轮裁定：**有条件可行，且建议采纳**。PoC 用 **3 行代码改动 + 1 项配置**即验证了核心命题：瘦身 primary 崩溃后，已建连接 **12/12 零中断**、新建连接 **12/12 正常**、性能无回归。issue 原文关于"所有连接都会受到影响"与"整个进程组都得重启"的两条判断，经实测均被证明**不准确**。

## 最终裁定

###裁定：**有条件可行（推荐采纳）**

按 `00` 定义的三档标准：

| 子目标 | 内容 | 裁定 | 核心依据 |
| --- | --- | --- | --- |
| **(a) 降低 primary 异常概率** | primary 不跑数据面、不进协议栈收包路径 | **达成（统计意义）** | PoC 实测primary 主循环收缩为 timer + msg_ring；不再触碰 mbuf 与协议栈输入路径 |
| **(b) 缩小 primary 异常后的影响面** | primary 崩溃不带走数据面能力 | **达成度100%（存量 + 新建流量）** | **E3b：杀瘦身 primary 后 12/12 连接零中断（26 轮）**；**E3c：新建连接 12/12**。对比改动前的11/20（2 进程）、8/18（3 进程）失效，是质变 |
| **(c) 故障后可恢复性**（issue 隐含期望） | 崩溃后能否原地恢复 | **部分达成** | **E2e：只要还有进程持有 `/dev/uioX`（refcnt ≥ 1），崩掉的 secondary 可原地重启恢复**；但 **E10：primary 不可原地拉回**（EAL `Cannot allocate memzone list`），进程组停留在控制面降级态 |

### 附加条件（缺一不可）

1. `thread_mode=0`（单进程多线程模式下无独立 primary 进程，本特性语义不存在，须加互斥校验）。
2. `kni.enable=1` 时必须按 `04` 的 **K4**（secondary 作运行时 KNI owner，E4a/E4b 已实测验证）或 **K3-corrected**（KNI 留 primary、物理口收发借道 secondary，退备方案）处置，不能直接套用最小改动集。
3. 运维上必须保证：**primary 常驻、不优雅退出**（避免 `rte_eal_cleanup()` 拆除共享资源）、且**至少一个数据面进程始终存活**（维持 uio refcnt ≥ 1）。
4. 必须为 slim primary 引入**空闲休眠**——实测瘦身后 primary 仍占满一个 CPU 核（99.8%），瘦身**不等于省核**。
5. 建议配套外部守护实现分层恢复（原地重启 secondary → 降级态告警 → 择机计划内全组重启）。

## 一、核心依据（按证据强度排序）

### 1.1 最强证据：PoC 实机验证（E3 系列）

**改动量（`_poc_primary_slim.patch`，2 hunk / 3 行）**：

| # | 位置 | 改动 | 解除的阻塞点 |
| --- | --- | --- | --- |
| 1 | `lib/ff_dpdk_if.c:508-510` | `rte_exit` 条件追加 `&& rte_eal_process_type() != RTE_PROC_PRIMARY` | **B1**（`lcore %u has nothing to do`） |
| 2 | `lib/ff_dpdk_if.c:535` | mbuf 池 RX 项去掉对**本进程**队列数的依赖 | **B3**（池规模归零） |

**结果**：

| 验证项 | 结果 |
| --- | --- |
| 瘦身 primary 启动 | 通过（不再 `rte_exit`） |

### 1.2 关键代码坐实：B4 假设不成立（本轮最重要的"好消息"）

原本担心"primary 退出 `lcore_list` 会导致队列数减1、queueid 错位、RSS reta 错位"，经逐行坐实**不成立**：

- `nb_queues` 来源是 `pconf->nb_lcores`（`lib/ff_dpdk_if.c:836`），即**该 port 的 `lcore_list` 长度**，不是 `nb_procs`；
- `queueid` 是本进程 lcore 在 `lcore_list` 中的**下标**（`lib/ff_dpdk_if.c:487-491`），与 `proc_id` **完全解耦**；
- `set_rss_table()` 按同一个 `nb_queues` 重算 reta（`lib/ff_dpdk_if.c:801`、`1169-1174`）。

⇒摘掉 primary 的 lcore 后，队列数 / queueid / reta / `dispatch_ring` **一致收缩**，**孤儿队列在代码层面自然消失**。这正是 issue 作者设想"复用 `lcore_list`"路线可行的根本原因。E3b 的"零中断"即此结论的实测确证。

### 1.3 issue 原文两处判断被实测修正

| issue 原文 | 实测裁定 | 依据 |
| --- | --- | --- |
| 「primary 一旦异常退出，整个进程组都得重启」 | **部分不成立**：其余进程继续服务；崩掉的 secondary 可原地重启（refcnt ≥ 1）；**无需立即全组重启**，但因primary 不可拉回（E10），仍需**择机**全组重启以复原控制面 | E2、E2e、E10 |
| 「所有连接都会受到影响」 | **不成立**：仅 primary 队列承接的连接受影响（2 进程 ~1/2，3 进程 ~1/3）；瘦身后**零影响** | E2、E2e、E3b |
| 「secondary 异常了可以重启，不影响其他进程」 | **成立** | E2d |

### 1.4 DPDK 层的硬约束（决定"primary 只能常驻、不能退出"）

`01` 从 DPDK 源码/文档坐实三条：

1. **IPC 唯一服务端**：secondary 的 mp 请求目的地硬编码为 primary 的 `mp_socket`（`lib/eal/common/eal_common_proc.c:750-751`）。
2. **动态扩堆必须由 primary 代理**：secondary 需要新 hugepage 时必须 `request_to_primary()`（`lib/eal/common/malloc_heap.c:484`）。
3. **所有中断只在 primary 内触发**（`doc/guides/prog_guide/multi_proc_support.rst:174-177`）——包括 link status/LSC。

⇒ 方案只能是 **"primary 常驻控制面、不参与数据面"**，绝不能是 **"primary 初始化完成后退出"**（`03` 的 S2 已否决）。

### 1.5 两条模型固有边界（f-stack 无法绕过）

- **FP-1**：`igb_uio` 的 `igbuio_pci_release()` 中，只有**最后一个**关闭 `/dev/uioX` 的进程才执行 `pci_clear_master()`停设备 DMA（`f-stack/dpdk/kernel/linux/igb_uio/igb_uio.c:352-366`）。⇒ **所有**进程都退出 ⇒ 设备运行态丢失 ⇒ 必须全组重启。
- **FP-2**：virtio PMD 在 secondary 早退、只装函数指针不碰设备（`drivers/net/virtio/virtio_ethdev.c:1949-1954`），唯一写 `DRIVER_OK` 的 `virtio_reinit_complete()` 在 secondary 不可达。⇒ 设备运行态只能由 primary 重建。
- **E10 的 EBUSY 是设计意图**：primary 初始化后把 `fbarray_memzone` 的独占锁降级为共享锁，注释明写"不允许其他进程重新初始化它"（`lib/eal/common/eal_common_fbarray.c:798-803`），因此存量secondary 在跑时新 primary **必然** EBUSY 失败——但该失败是 EAL 早期 fail-fast，**对存量 secondary 无副作用**（实测服务保持不变）。

## 二、该特性的准确价值表述（避免过度承诺）

> **primary-slim 把「primary 崩溃 ⇒ 必须立刻全组重启、约1/N 的连接立即中断」转变为「primary 崩溃 ⇒ 数据面零损失、业务继续跑、崩掉的 secondary 可原地重启，集群进入控制面降级态，可在计划内维护窗口择机全组重启」。**
>
> 即：**把紧急故障转化为计划内维护，重启时机由被动变为可控。**

**明确不承诺的**：

- 不承诺"完全无需重启"（控制面降级态不可就地修复，E10）。
- 不承诺"省一个 CPU 核"（slim primary 仍空转占满一核，除非实现空闲休眠）。
- 不承诺 primary 不再是结构性单点（只是概率降低、影响面缩小）。
- 不承诺连接不丢失于 secondary 崩溃场景（每进程独立 FreeBSD 栈，无连接迁移）。

## 三、建议

### 3.1 对项目的建议

| 优先级 | 建议 | 依据 |
| --- | --- | --- |
| **P0** | 采纳 S1（primary-slim），按 `07` 的里程碑推进；M1 最小集即可交付主要收益 | PoC 已验证核心命题，改动量极小（最小集 4 处、跨 1~3 个文件） |
| **P0** | 必须同时实现 slim primary 的空闲休眠| P2 实测占满一核，否则用户会认为"瘦身反而更浪费" |
| **P0** | 必须实现 `thread_mode` 与 `primary_slim` 的互斥校验 | B7 语义互斥 |
| **P1** | 处理 `msg_ring[0]` 归属（N1），否则不带 `-p` 的 `ff_*` 工具全部挂起 | N1 高影响，用户可感知 |
| **P1** | 按 `04` 的 K4 处理 KNI（secondary 作运行时 owner，E4a/E4b 已实测），含**必改的广播/多播门禁**（`lib/ff_dpdk_if.c:2080` 的 `ff_kni_is_owner_thread()` 改为 `ff_kni_is_runtime_owner()`），否则 ARP/DHCP/NS-RA 等广播报文永不进内核 | `04` K4 方案，E4a/E4b 已实测验证 |
| **P1** | 修正 MTU 在 secondary 的"假成功"（N5），避免已交付的 MTU 巨帧特性被破坏 | N5 中影响 |
| **P2** | 提供"控制面降级态检测 + 主动告警"能力，便于运维判断何时需要计划内重启 | E10 的运维含义 |
| **P2** | 补 `init_flow`/`fdir_add_tcp_flow` 的 primary 门禁（N3）、统一 `nb_dev_ports` 语义（N2）、清理 `init_kni()` 死代码（N8） | 既有缺陷，顺手加固 |

### 3.2 给上游 issue #1078 的回复建议要点

建议回复包含以下要点（**不要**直接照抄本地实测的绝对数值作为普适结论，需注明测试环境）：

1. **方向认可**：作者提出的"复用 `lcore_list` 让 primary 不分配队列"思路**技术上成立**。关键原因是 f-stack 的队列数与 queueid 由**该 port 的 `lcore_list` 长度与下标**决定（`lib/ff_dpdk_if.c:836`、`487-491`），与 `proc_id` 解耦，因此把 primary 摘出 `lcore_list` 后队列数/queueid/RSS reta 会**一致收缩**，不会产生"无人 poll 的孤儿队列"。
2. **需要的改动很小**：主要是解除 `nb_rx_queue == 0` 的 `rte_exit`（`lib/ff_dpdk_if.c:508-510`）与修正 mbuf 池规模公式对本进程队列数的依赖（`lib/ff_dpdk_if.c:535`）；另需处理 primary 精简主循环、`rte_eal_cleanup()` 跳过、ifp 归属、KNI 归属、`msg_ring` 归属。
3. **修正 issue 中的两处判断**（附实测）：primary 异常时**其余进程与其队列上的连接不受影响**；且只要还有进程持有设备（uio refcnt ≥ 1），**崩掉的 secondary 可以原地重启恢复**，不必立即全组重启。
4. **明确 primary 只能"常驻瘦身"，不能"初始化后退出"**：DPDK 官方约束——primary 是 IPC 唯一服务端、secondary 扩堆必须由 primary 代理、所有中断只在 primary 触发；且 primary 一旦退出便**无法原地拉回**（新 primary 会在 `rte_fbarray_init` 处因锁被存量进程共享持有而 EBUSY 失败），这是 DPDK 的设计意图而非缺陷。
5. **提示两个容易踩的坑**：① 瘦身后 primary 仍会空转占满一核，需要空闲休眠；② KNI 开启时既有校验强制 primary 必须在每个 port 的 `lcore_list` 中，且广播/多播入 KNI 的分支带有 owner 门禁，primary 不收包后该分支永不执行。
6. **询问作者的部署形态**（用于确认适配范围）：是否开启 KNI？secondary 数量？是否使用 `ff_*` 工具链且依赖默认 `proc_id=0`？是否用 VFIO 而非 igb_uio（VFIO 下refcnt 语义不同，本轮实测环境为 igb_uio）？

## 四、诚实边界（本轮结论的适用范围）

| 编号 | 边界 | 说明 |
| --- | --- | --- |
| L1 | **PMD/驱动局限** | 全部实测在 **virtio 设备 + igb_uio** 的虚拟化环境完成。FP-1 的 refcnt 语义是 igb_uio 特有；VFIO 下 `pci_clear_master` 时机与设备运行态保持行为**未验证**。物理网卡（ixgbe/i40e/mlx5等）行为可能不同 |
| L2 | **单端口、≤3 进程** | 实测最多 1 个 DPDK 端口、3 个进程。多端口异构 `lcore_list`、更多 secondary 的组合**未验证** |
| ~~L3~~ | ~~**KNI 未验证**~~ | **已闭环（E4a/E4b 实测验证）**。E4a 验证 secondary 通过 `VDEV_SCAN_REQ` 成功发现并 probe primary 创建的 virtio_user 口；E4b 验证 K4 PoC 补丁编译通过、两进程稳定运行、veth0 接口存在。K4 方案（secondary 作运行时 KNI owner）在代码和实机层面均已验证可行 |
| L4 | **PoC ≠ 正式实现** | PoC 用"自动推导"而非显式开关，未实现 `rte_eal_cleanup()` 跳过、ifp 归属裁决、idle_sleep、KNI 归属。正式实现须按 `07` 落地并重测 |
| L5 | **优雅退出未测** | E2/E2e/E3b 均为**强杀** primary。走 `rte_eal_cleanup()` 的优雅退出会拆 EAL 共享资源（N4），其影响**未实测**（待补实验 E8） |
| L6 | **长期稳定性未测** | 最长观测约 90s+。小时级运行、mbuf 池与 `message_pool` 水位、primary 被杀时 in-flight msg 对象的永久泄漏（`lib/ff_dpdk_if.c:706`）**未验证**（待补 E9） |
| L7 | **性能绝对值不可外推** | 压测客户端（8 核 `ab`）是瓶颈——数据面进程从 1 增到 2 仅 +11%。QPS 仅用于"同配置改动前后对照"，**不可用于容量规划** |
| L8 | **上游社区调研不完整** | issue #804/#860/#863 原文、DPDK 邮件列表 primary failover 提案**未能联网确证**，未予转述（`01` 的 O-2/O-3） |

## 五、结论一句话

> **issue #1078 的思路正确、代价很小、收益显著：3 行代码 + 1 项配置的 PoC 已实测证明"瘦身 primary 崩溃时数据面零影响"，建议采纳并按 `07` 的里程碑正式落地；但必须同时明确其边界——primary 只能常驻不能退出、瘦身不省 CPU、控制面降级态需择机全组重启。KNI 场景已通过 K4 方案（secondary 作运行时 owner）实测验证（E4a/E4b），非 igb_uio 驱动仍需进一步验证。**
