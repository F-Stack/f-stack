# 00-issue 原文与需求解析

## 摘要

F-Stack 上游 issue #1078「primary稳定性控制」提出：DPDK 多进程模式下 F-Stack 对 primary 进程的稳定性依赖过高——secondary 崩溃可单独重启且不影响其他进程，但 primary 一旦异常退出，整个进程组都要重启、所有连接受影响。提议把 primary「独立/瘦身」出来，只做网卡队列配置、绑定、初始化等控制面工作，收包及后续处理全部下移secondary，以降低 primary 异常概率、缩小故障影响面。本文档留档原文、逐条拆解诉求、给出成功判据与本轮调研边界。

## 关键结论

1. issue 的诉求可拆为**两个可独立评估的子目标**：(a) 降低 primary 异常概率（瘦身）；(b) 缩小 primary 异常后的影响面（解耦）。二者的可行性与代价截然不同，必须分开裁定，不能笼统答"可行"。
2. issue 的前提假设「secondary 异常可重启、不影响其他进程」经实机验证**成立**（见 `05-实机对照实验报告.md` E2d）。
3. issue 的隐含假设「primary 异常导致所有连接受影响」经实机验证**只部分成立**：primary 退出后 secondary 进程本身**存活并继续正常服务自身 RSS 队列上的连接**，受影响的是哈希到 primary 队列的那部分流量（见 E2/E2b）。
4. **（本条已据后续实验更正）**曾据 E2c 推断"primary 退出后无法再重启 secondary、故障后原地恢复的路径被封死"，该推断**错误**：E2e 证明只要至少一个进程持续持有 `/dev/uioX`（uio refcnt ≥ 1），primary 缺席时 secondary **可以**重启成功并恢复服务；E2c 的真实根因是进程组曾整体退出（refcnt 归零 → `pci_clear_master()` 停设备 DMA）。残余边界由 E10 给出：primary 本身**不能原地拉回**（EAL `Cannot allocate memzone list`），进程组停留在控制面降级态，需**择机**全组重启。
5. **最终裁定为「有条件可行，推荐采纳」**：PoC 实测仅需 3 行代码 + 1 项配置，杀掉瘦身 primary 后已建连接 12/12 零中断、新建连接 12/12、性能无回归（见 `05` 第十一节 E3 系列、`10-可行性结论与建议.md`）。
6. 本轮只做可行性调研，不落地正式功能改造；PoC 补丁仅作证据留档，不进入正式提交。

原文（逐字留档）：

> 想问一下你们有没有把primary 独立出来的计划？dpdk 的多进程模式下，对 primary 的稳定性依赖非常高，如果 secondary 异常了，可以重启，不影响其他进程的队列和建立的连接，但是 primary 一旦异常退出，整个进程组都得重启，所有连接都会受到影响；如果把 primary 独立出来，只做简单的网卡队列设置、绑定、初始化，在secondary 进行收包及后续操作，这样 primary 就不那么容易异常，对连接的影响范围也小。

### 两个子目标的分离

- **子目标 (a) 降低概率**：让 primary 不跑协议栈、不收发包、不承载业务，其代码路径大幅缩短，异常概率随之下降。这是**统计意义上的改善**，不改变"primary 是单点"这一结构事实。
- **子目标 (b) 缩小影响面**：让 primary 退出时不带走任何数据面能力。这要求 primary 名下**不持有任何 rx/tx 队列**，否则其队列会变成无人 poll 的「孤儿队列」，落到该队列的流量全部黑洞化。

> 这两个子目标的可达性判定分别依赖：(a) 代码改动可行性（见 `02`/`03`）；(b)孤儿队列是否可消除 + DPDK 共享内存/进程管理约束（见 `02` B4/B8、`01` 第一部分、`05` E2 系列）。

### 「可行」的三档定义

- **可行**：子目标 (a) 与 (b) 均可达，且改动量与风险可接受。
- **有条件可行**：子目标 (a) 可达；(b) 在特定配置前提下可达（例如必须关闭 KNI、必须≥2 个 secondary），需明示前提。
- **不可行**：子目标 (b) 存在不可绕过的 DPDK 层约束，且(a) 的收益不足以支撑改造成本。

## 四、本轮调研边界（诚实边界）

**本轮做**：

- 读代码坐实阻塞点；查DPDK 官方约束与上游/同类项目做法；实机对照实验；方案设计与备选对比；后续编码工作分解与测试规格；独立门禁审核。

**本轮不做**：

- 不落地正式功能改造，`lib/` 正式代码路径不做功能性改动。
- PoC 试验补丁仅作为**调研证据**留档为 patch 文件，不进入正式提交；是否转正式实现由用户在看到结论后决策。
- 不产出英文版文档（待人工审计中文版后再议）。
- 不修改 `config.ini` 入库（本地测试值仅留在工作区）。

**已知限制**：

- 实验环境为单 DPDK 端口 + 2 进程（`lcore_mask=3`）的虚拟化环境（virtio 系设备），非物理多队列高端网卡。RSS 分布、PMD 多进程行为在其他 PMD 上可能有差异，结论中凡涉及 PMD 特性者均已标注该限制。
- 实验使用 `example/helloworld`（HTTP keep-alive），不代表 nginx 等真实业务的全部行为。
