## 1. Task background

F-Stack's nginx adaptation (`app/nginx-1.28.0/`, the source-integration route) has supported a fork-protocol-based master-worker reload since 2017 (commit `406002113b143fda1fa444f0af42b97b41951882`, closing issue #12), but that implementation is a two-stage serial model of "all old workers exit, only then do new workers start", so during a reload the data plane is completely empty, with packet loss and service interruption. Issue #1036 has confirmed the root cause: under the multi-process model each worker exclusively binds a NIC hardware queue (RSS); at reload an old worker exits while the new worker has not finished DPDK/F-Stack stack initialisation, leaving a "queue with no owner" window that loses packets — **the problem is in the data plane (NIC queue ownership), not in the listening fd itself**.

**The only** scheme **seen within this search range** that was measured to reload with zero packet loss (issue #547, orange30, DPDK 18.11 + F-Stack 1.20) stopped working because DPDK 19.11's timer library moved to a shared memzone, and its **original code was not obtained within this search range (not seen as open source)** (see [03 Verification of the Legacy Community Scheme](legacy-solution.md)). **[2026-09-22 sync, A01-6]** The above means **not seen within this search range (cut-off 2026-09: publicly searchable sources plus obtained original texts)**; it does not claim "does not exist objectively"; sources not obtained are registered in the single-source declaration of [06](solution-design.md) §8.

Goal of this task: on the basis of multi-agent research plus local code verification, design and plan a lossless nginx reload scheme that can land on the current F-Stack mainline (DPDK 24.11.6 + FreeBSD 15.0 + nginx 1.28.0), and produce this Chinese specification set for human audit. Per the workspace rules this stage produces Chinese documents only (`docs/nginx_reload_spec/zh_cn/`); the English edition is produced after functional acceptance.

### 2.2 Evidence strategy

1. First-hand sources first: official documentation (nginx/Envoy/HAProxy/FDio wiki/kernel documentation), original source text (VPP raw.githubusercontent, the local f-stack repository), git log/show/blame, the gh CLI for full issue/PR text, and iwiki-cli fetching.
2. The actual code is authoritative: where documentation, external material and code disagree, the code wins; key mechanisms are re-checked against the code during solution design.
3. Honest marking: a single source is marked "this source only, not re-confirmed"; anything not found is marked "not found"; what static analysis cannot settle goes into the "unconfirmed list" together with a runtime verification method; never assert PASS without evidence.
4. Traceable evidence: each research/probing document keeps a "list of operations actually executed" section (search keywords, fetched URLs, read-only commands executed).
5. All research/verification was read-only: no git write operation and no code change.

## 3. Core conclusion summary

### 3.1 Three baseline conclusions (the two external research lines converge independently; they anchor the scheme evaluation)

1. **No precedent for migrating established TCP connections was seen within this search range** (cut-off 2026-09; no claim that none exists objectively). Envoy's official sentence "existing connections are not transferred to the new Envoy process"; in VCL mode the old worker's connections likewise close on drain rather than migrating — the two corroborate each other. The target semantics must therefore be "**seamless new connections + the old process drains**", and cross-process TCP state migration is not pursued (basis: [02](other-projects-research.md) §4 P4, [01](vpp-vcl-research.md) §4.2).
2. **Decoupling NIC queue / receive ownership from the business process lifetime is the structural precondition for a lossless reload on a user-space stack; listening fd ownership is a second-order control-plane problem.** Three independent sources point at the same conclusion: VPP's queues belong to an independent process (a no-owner window does not exist structurally), the #1078 primary_slim PoC (12/12 existing connections with zero interruption after killing the primary), and the centralised design of adapter/syscall (basis: [01](vpp-vcl-research.md) §6.2, [02](other-projects-research.md) §5).
3. **The "do not cut traffic over before ready" pattern exists isomorphically in both architectures.** Facebook's LPC 2021 "traffic keeps going to the old instance until the new one is ready" and VCL's app_listener workers bitmap (accept is not distributed to a new worker until it is registered in the bitmap) are isomorphic (basis: [02](other-projects-research.md) §2.4(a), [01](vpp-vcl-research.md) §2.2/§4.2).

### 3.2 One-line conclusion

- **Why S3 is recommended**: S3 (native multi-process evolution; **the v1.9 form M1′: resident slim primary + same queue (generation-independent `queue_id` mapping) + simultaneous takeover of rx+tx+listen after ready + G_new owning the hardware exclusively with G_old running software-parasitic + bidirectional per-generation `drain_ring` + flow_map software dispatch table + rx mutual exclusion + **both generations on the same `lcore_id`** + **same-`lcore_id` resource isolation (self-driven hardclock + per-generation mempools)** + msg_ring/KNI generation isolation + heartbeat and rx return + ARP/NDP clone**, directly continuing primary_slim #1078) is the only scheme that simultaneously satisfies the structural precondition (baseline 2), aligns with the connection semantics (baseline 1), has **zero steady-state extra cost that can only be claimed after PT-NR-09 quantifies it** (DR11 decided with M-A as the main option ⇒ `cache_size=0` carries a steady-state cost, so **"zero extra cost" must not be claimed before it is quantified**; see [06](solution-design.md) §4.1 D5) **[2026-09-22 sync, A01-8: restores the quantification condition that a deleted line had removed; the criterion is not lowered]**, has a verified PoC basis, moves in the same direction as the mainline evolution, and can be delivered incrementally ([06](solution-design.md) §4.2).
  > **Note (v1.9)**: v1.0-v1.5's "ping-pong lcore segment + atomic reta cut-over" was abandoned in v1.6 (reta is not modified and NIC RSS capability is not required); v1.6's "both generations sharing the same set of hardware queues" was in turn replaced by M1′ in v1.9 because of **TX concurrency** and **dispatch_ring's two consumers violating `RING_F_SC_DEQ`**. The abandonment notes for each form change are in [06](solution-design.md) §6.5/§6.5.1. **[2026-09-17 correction, R-12] the anchor and wording of the TX-concurrency basis**: DPDK allows lock-free concurrency on the same queue only when the PMD declares `RTE_ETH_TX_OFFLOAD_MT_LOCKFREE` (`dpdk/lib/ethdev/rte_ethdev.h:1610`); **when it is not declared, concurrent use of the same queue requires the caller to lock**. `rte_ethdev.h:6575-6576` is the **permission** statement for that capability ("If the PMD is MT_LOCKFREE capable, multiple threads **can** invoke … without SW lock"): it had been mis-cited as evidence that "concurrency is forbidden", the direction being opposite to the original, and has been corrected. Also note that the official text speaks of logical cores / threads, so this scheme's "two processes on the same lcore_id" is an **equivalent extrapolation**, not literally covered.
- **Why the legacy scheme fails**: the orange30/iWiki legacy scheme's "old and new processes coexisting on the same core" relied on DPDK 18.11's timer library being "independent static data per process"; from DPDK 19.11 the timer state moved into a shared memzone and the scheme stopped working. Its original code **was not obtained within this search range (not seen as open source)**, and the mainline has still not closed this completely (cut-off 2026-09) ([03](legacy-solution.md) §5/§6).
- **Where LD_PRELOAD sits**: S2 (the adapter/syscall LD_PRELOAD route) is a **parallel, alternative product line** — suitable for "existing applications attaching with zero changes + non-proxy scenarios + acceptable IPC performance loss"; it is not recommended as the reload solution for F-Stack nginx (the app source-integration mainline) ([06](solution-design.md) §4.2, [05](ld-preload-alternative.md)).

### 3.3 Landing path outline

The recommended S3 decomposes into M0 pre-research → M1 resident primary → M2 coexistence (**both generations on the same `lcore_id`** + self-driven hardclock + per-generation mempools + heartbeat and rx return + msg_ring/KNI generation isolation) → M3 simultaneous takeover of rx+tx+listen + TX exclusivity + flow_map software dispatch table + bidirectional drain_ring (same queue, reta unchanged, usable on both virtio and physical NICs) → M4 drain completion, the half-open connection window and closing the table back to steady state → M5 USR2 → M6 final gate (loop reload ≥100 times, checking the shared-memory state every 5 s and reloading once all G_old have exited) → M7 (optional, triggered by DR7): 8 milestones in total and **43 coding change points** ([07](milestones.md); the version is in that document's header; the counting rules are in its §0 numbering note — 308 was split into 314/315 as an index and is not counted, 311 was cancelled); throughout, `graceful_reload=0` (the default) is the configuration-level total rollback point.
