## 内核栈对比测试

### 测试方法

直接运行 `./helloworld_stack_udp`（不使用 LD_PRELOAD），程序在内核协议栈上绑定 `0.0.0.0:9000`。使用 Python 发送 UDP 测试包到 `127.0.0.1:9000`，验证回显。

### 测试步骤

```bash
# 1. 启动 UDP echo server
cd /data/workspace/f-stack/adapter/syscall
./helloworld_stack_udp &

# 2. 发送测试包
python3 -c "
import socket
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.settimeout(3)
msg = b'Hello F-Stack UDP!'
s.sendto(msg, ('127.0.0.1', 9000))
data, addr = s.recvfrom(2048)
print('RECV:', data.decode())
print('PASS' if data == msg else 'FAIL')
s.close()
"
```

### 结果

```
RECV: Hello F-Stack UDP!
RESULT: PASS - echo matches
```

**内核栈测试通过** — UDP echo server 正确接收并回显数据。

## LD_PRELOAD 模式测试

### 测试方法

1. 启动 `fstack` primary 进程（初始化 DPDK 网卡接管，接管网卡为 `[port0]` 配置的测试环境 IP，非 eth1）
2. 以 `LD_PRELOAD=./libff_syscall.so` 方式启动 `helloworld_stack_udp`
3. 从 f-stack-client 机器 ssh 发送 UDP 包到 `<DPDK网卡IP>:9000`，验证回显

### 排障记录

首次启动 primary 时报`EAL: Cannot allocate memzone list`，退出。原因是`/var/run/dpdk/rte/` 与 `/dev/hugepages/rtemap_*` 下存在此前测试遗留的共享内存/hugepage 残留文件（属于一个未被彻底清理的僵尸secondary 进程），与新 primary 初始化冲突。用 `rm_tmp_file.sh` 清理残留后重启，primary 正常完成 DPDK 网卡初始化（`Port0 Link Up`）。

日志中出现的 `VIRTIO_INIT: eth_virtio_pci_init(): Failed to init PCI device` / `Requested device 0000:00:05.0 cannot be used` 是**预期内的正常噪声**：`config.ini` 未配置 PCI allowlist，DPDK EAL 会扫描所有 PCI 设备，其中 `0000:00:05.0` 是 `eth1`（仍绑定内核 `virtio-pci` 驱动，非 DPDK 网卡），探测失败属正常；真正的 DPDK 网卡是 `0000:00:09.0`（`drv=igb_uio`），该设备已在 `f-stack-0.log` 中确认 `Port 0 Link Up`。

### 结果

- fstack primary 进程启动成功，DPDK 网卡（`0000:00:09.0`）初始化成功，`Port 0 Link Up`
- LD_PRELOAD UDP 应用启动成功，`libff_syscall.so` 正确加载并绑定 DPDK 网卡
- 从 f-stack-client 通过 ssh 向 `<DPDK网卡IP>:9000` 连续发送 3 个不同内容的 UDP 包，**全部收到正确回显**（PASS）

```
pkt0 RECV: Test-packet-0 ->  PASS
pkt1 RECV: Test-packet-1 ->  PASS
pkt2 RECV: Test-packet-2 ->  PASS
```
