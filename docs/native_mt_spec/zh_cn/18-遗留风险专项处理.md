2. 六个问题的存在性分析

2.1 P1：ipfw 动态状态 hazard pointer 的 DPCPU 槽位别名

代码依据：

- `freebsd/netpfil/ipfw/ip_fw_dynamic.c:224-226`：`DPCPU_DEFINE_STATIC(void *, dyn_hp)`，`DYNSTATE_GET(cpu)` / `DYNSTATE_PROTECT(v)` 分别经 `DPCPU_ID_PTR((cpu), dyn_hp)` / `DPCPU_PTR(dyn_hp)` 寻址。
- `freebsd/sys/pcpu.h:113-128`：`_DPCPU_PTR(b, n) = (b + (uintptr_t)&DPCPU_NAME(n))`，`DPCPU_ID_PTR(i, n)` 用 `dpcpu_off[(i)]`，`DPCPU_PTR(n)` 用 `PCPU_GET(dynamic)`。
- `freebsd/kern/subr_pcpu.c:76`：`dpcpu_off[MAXCPU]` 静态数组默认全 0；`:83-97` `pcpu_init()` 只 `bzero`，从不设 `pc_dynamic`；`:99-118` `dpcpu_init()` 是唯一写入 `pc_dynamic` / `dpcpu_off[]` 的地方。
- `lib/ff_freebsd_init.c:104-113` `ff_pcpu_thread_init()` 只调 `pcpu_init()`，从不调 `dpcpu_init()`；全 `lib/` 目录下 `dpcpu_init` 命中 0，且不编译架构 machdep 文件。

存在性结论：真实存在，且不可通过 `-DSMP` 修复。链路是：`pcpu_init()` 清零 → 所有线程 `pc_dynamic == 0`；`dpcpu_init()` 从未被调用 → `dpcpu_off[]` 恒 0；于是 `DPCPU_ID_PTR(i, dyn_hp)` 解析到同一主副本 `&dpcpu_entry_dyn_hp`，与 `i` 无关。多 worker 下所有线程读写同一个 `dyn_hp` 槽位，`dyn_free_states()`（`ip_fw_dynamic.c:2052-2143`）的 `CPU_FOREACH` 收集到同一份值，HP 机制退化为单槽位，只能保护最后一个被 `DYNSTATE_PROTECT` 写入的 state。

影响面 / 严重度：中等偏高。属正确性 bug（潜在 use-after-free），但需 ipfw `keep-state`/`check-state`/`limit` 动态规则 + 多 worker 并发 + 状态过期回收三条件叠加才触发；单线程（thread_mode=0）或不用 ipfw 动态规则时无影响。

【注1-P1】本问题已于修复轮修复（`dyn_hp` 改显式 per-cpu 数组），存在性结论不变，修复内容见 §3.5。

2.2 P2：counter(9) 去 per-cpu 化后的多线程统计竞争

代码依据：

- `lib/include/machine/counter.h:58-62` `counter_u64_add` 为 `*c += inc;`（非原子读-改-写）；`:43-47` `counter_u64_fetch_inline` 为 `return (*p);` 只读第 0 槽；`:49-53` `counter_u64_zero_inline` 为 `*c = 0;`；`:38-39` `counter_enter/exit` 为空操作。
- `freebsd/sys/counter.h:32`：`typedef uint64_t *counter_u64_t;`，counter 退化为普通指针，非 per-cpu 句柄。
- 分配侧仍是 per-cpu 数组：`freebsd/kern/subr_counter.c:63` `uma_zalloc_pcpu(pcpu_zone_8, ...)`，配合 `lib/Makefile:223` 的 `-DSMP`，实际分配 `mp_maxid+1` 槽。
- 关键不一致：分配侧 per-cpu 数组，读写侧退化只碰第 0 槽 → 其它槽白分配，且多线程写第 0 槽无原子/锁保护。

存在性结论：真实存在。多线程写同一 counter 的「丢失更新（lost update）」确凿，是「统计竞争」而非内存安全（不会越界、不崩溃，仅计数不准确）。

影响面 / 严重度：低。影响所有经 `VNET_PCPUSTAT_ADD` / `counter_u64_add` 的统计，全仓 `counter_u64_add(` 命中 ≥ 85 处，涵盖 IPv6/IPv4/TCP/pf/ipfw/vm/UMA/bpf/mp_ring 全栈（`netstat -s` / `sysctl` 读数偏低）。不涉及数据面转发、连接建立、内存分配正确性。

2.3 P3：tcp_hpts 实例数 1→N 的 callout 归属错配（R6）

代码依据：

- `freebsd/netinet/tcp_hpts.c:1872`：`tcp_pace.rp_num_hptss = ncpus;`（实例数 = CPU 数，多线程下 = N 个 worker 数）。
- `tcp_hpts.c:2008-2010`：`hpts->p_cpu = i;`；`:2047-2049` `callout_reset_sbt_on(..., hpts->p_cpu, ...)` 意图把 callout 挂到「第 i 个 CPU 的 callwheel」。
- `lib/include/sys/mutex.h:74-76`：`mtx_trylock_flags_` 等定义为常量 `1`，`mtx_lock/unlock` 为 `DO_NOTHING` → `tcp_hpts.c:216-219` 的 `HPTS_TRYLOCK` 恒返回 1、`HPTS_LOCK/HPTS_UNLOCK` 无操作，hpts 的 `p_mtx` 完全无互斥。
- `lib/ff_kern_timeout.c:183-185`：`__thread struct callout_cpu cc_cpu;`，`CC_CPU(cpu)` / `CC_SELF()` 忽略 cpu 参数返回本线程实例 → `callout_reset_sbt_on` 传入的 `cpu` 参数在 f-stack 被忽略，callout 实际挂到「执行该调用的线程」自己的 callwheel。
- `lib/ff_kern_timeout.c:1060`：`callout_init()` 里 `c->c_cpu = timeout_cpu;`（归属 = 调用线程自己的 cpuid）。
- `lib/ff_kern_intr.c:84-107`：`swi_add` 返回 0（不创建线程）、`swi_sched` 空、`intr_event_bind` 返回 `EOPNOTSUPP`。

存在性结论：真实存在。N 个 hpts 的 `co` 全部挂到主线程 callwheel（初始化在主线程上下文执行，`c_cpu = timeout_cpu` 恒为主线程 cpuid），且到期后走 `swi_sched`（no-op）永不真正触发 hpts 处理。实际驱动靠 `ff_tcp_hpts_softclock()`（`ff_kern_timeout.c:1290-1295`，main_loop 每轮经 `ff_dpdk_if.c:2934` 主动调 `__tcp_run_hpts`）旁路补偿，功能「能跑」，但存在两个设计缺陷：callout 归属错配（主 callwheel 上堆积 N 个永不生效的「死 callout」）+ `p_mtx` 无互斥下 `p_hpts_active` 的 check-then-set 非原子，可能并发重入 `tcp_hptsi()`。

影响面 / 严重度：中。pacing（RACK/BBR）精度依赖 main_loop 迭代频率而非 callout 10us 粒度；并发重入需「worker 数 != hpts 实例数、或 NUMA 分组、或多 worker 共享同一 curcpu」等额外条件，非确定故障。thread_mode=0 下 `rp_num_hptss = 1`，单实例无并发，零影响。

【注1-P3】本问题已于修复轮修复（`__tcp_run_hpts` 用原子 exchange 抢占 `p_hpts_active` 提供真实 per-instance 互斥），存在性结论不变，修复内容见 §3.6。

2.4 P4：net.isr.dispatch 必须保持 direct

代码依据：

- `freebsd/net/netisr.c:151` `NETISR_DISPATCH_POLICY_DEFAULT = NETISR_DISPATCH_DIRECT`；`:155-158` `SYSCTL_PROC` 的 `dispatch` 为 `CTLFLAG_RWTUN`（运行时可写 + loader 可写）；`:344-377` 写回时只拒绝 `NETISR_DISPATCH_DEFAULT`，不强制 direct。
- 非 RSS 下 IP 协议 `.nh_dispatch` 缺省（`ip_input.c:139-150` 只在 `#ifdef RSS` 设 HYBRID），dispatch 完全受全局 `net.isr.dispatch` 支配（`netisr_get_dispatch:787-789`）。
- hybrid 路径 `netisr.c:1172` `if (cpuid != curcpu) goto queue_fallback;` → `netisr_queue_internal`（`:1028-1052`）入队 + `NWS_SIGNAL`（`:261` = `swi_sched`）→ `lib/ff_kern_intr.c:91-95` `swi_sched` 空 stub → 无人消费 → 静默丢包。
- 注入面：`lib/ff_freebsd_init.c:357-368` 遍历 `cfg->freebsd.sysctl` 链表调 `kernel_sysctlbyname`，无名字过滤；`lib/ff_config.c:176-194` 解析 `[freebsd.sysctl]` 段同样无白名单。

存在性结论：真实存在，是确定性缺陷。f-stack 用户态无 softintr 线程、`swi_sched` 空 stub，任何走到 deferred / hybrid-fallback 的包被永久挂起在 workstream 队列形成静默丢包。运维若把 `net.isr.dispatch` 配成 hybrid/deferred（无论 config.ini 还是运行时），多 worker 下 IP 入站包静默丢弃，表现为「网络不通、无报错、计数器无异常」。

影响面 / 严重度：中偏高。多线程 native-mt 下风险最高；单线程（`nws_count==1`）时 `netisr_select_cpuid` 有 `:810-813` 短路，hybrid 下若恰好 `cpuid == curcpu` 仍可 direct，不一定立刻暴露。

2.5 P5：ff_subr_prf.c 全局无锁行缓冲（printf 并发污染）

代码依据：

- `lib/ff_subr_prf.c:86` `char bufr[PRINTF_BUFR_SIZE];`（`PRINTF_BUFR_SIZE = 256`，`:82`）全局共享、非 `__thread`、无锁。
- `lib/ff_subr_prf.c:89` `static int putbuf_done = 0;` 同样全局共享、无锁。
- `vprintf()`（`:550-581`）从 `:558` 拿 `bufr` 地址一路用到 `:577`，中间无锁；`putbuf()`（`:136-177`）逐字符写 `bufr`。

存在性结论：真实存在。多 worker 并发 `printf`/`log`/`vlog` 时同一 256 字节缓冲被并发写，导致整行丢失 / 拼接污染。注意最终输出经 `ff_log` → `rte_vlog`（DPDK 侧自身有同步），「跨线程写日志文件」不会因 bufr 竞争撕裂，但 bufr 作为行组装缓冲的竞争发生在进入 `rte_vlog` 之前，直接损害单条日志的内容正确性。

影响面 / 严重度：低到中。不影响数据面正确性、不 crash（bufr 固定 256 字节，`putbuf` 有 `KASSERT(ap->remain > 2, ...)` 且 `:154` 保证 `remain==2` 即刷，无越界），仅日志内容污染，影响可观测性/可调试性。单线程（thread_mode=0）无影响。

2.6 P6：ff_pthread_create 创建的线程不支持调用 ff_*（fail-fast 缺口）

代码依据：

- `lib/ff_thread.c:32-46` `ff_pthread_create`：`data->parent = pcurthread;`（`:44`）→ `pthread_create(thread, attr, ff_start_routine, data)`（`:45`），全程不调 `ff_pcpu_thread_init`。
- `ff_thread.c:20-30` `ff_start_routine`：`ff_set_thread(p_data->parent)`（`:26`，只继承父线程 `pcurthread`）→ `ff_free(data)` → `start_routine(arg)`，无 `pcpup` 检查。
- `lib/ff_freebsd_init.c:89` `__thread struct pcpu *pcpup;`（TLS，新线程初始 NULL）；`:104-113` `ff_pcpu_thread_init` 是唯一给 `pcpup` 赋值的路径，仅 `:191`（worker 线程）/`:317`（主线程）两处调用。
- `lib/include/sys/pcpu.h:34` `#define curcpu PCPU_GET(cpuid)`；`lib/include/amd64/include/pcpu.h:49` `PCPU_GET(member) = (pcpup->pc_ ## member)`。

存在性结论：真实存在，是 fail-fast 缺口。`ff_pthread_create` 出的线程 `pcpup == NULL`，一旦触达 `PCPU_GET(...)`（最典型 `curcpu`）即 NULL 解引用崩溃。继承 `pcurthread = parent` 只能让部分依赖 `curthread` 的路径「看起来有上下文」，无法掩盖 `pcpup==NULL`（`curcpu` 走 `pcpup` 而非 `pcurthread`），造成「有的 ff_* 能跑、有的直接崩」的隐性难排查局面。

影响面 / 严重度：中。任何 `ff_pthread_create` 起的应用线程，回调里调用触达 `PCPU_GET` 的 ff_* 接口（socket 收发、定时器、netisr 相关等）都会崩。全库唯一防御先例是 `ff_kern_synch.c:106` 的 `pcpup != NULL ? curcpu : 0`，绝大多数路径无此防御。与 P4 协同放大：应用线程 `curcpu` 语义不确定，可能把包推进 queue_fallback 丢包路径。

【注1-P6】本问题已于修复轮修复（惰性 fail-fast：`pcpu.h` 加 `ff_pcpu_get()`，触达 `curcpu/PCPU_*` 时检测 `pcpup == NULL` 并 panic），存在性结论不变，修复内容见 §3.7。

3. 修复决策与实施

3.1 P2：counter 三函数原子化

文件：`lib/include/amd64/include/counter.h`（与 `lib/include/machine/counter.h` 为同一 inode 硬链接，改一即改二）。

改动：`counter_u64_add` / `counter_u64_fetch_inline` / `counter_u64_zero_inline` 三个函数改 GCC 内建原子操作，内存序用 `__ATOMIC_RELAXED`（counter 仅统计计数、无跨线程同步语义，relaxed 足够且开销最低）：

```c
static inline uint64_t
counter_u64_fetch_inline(uint64_t *p)
{
    return (__atomic_load_n(p, __ATOMIC_RELAXED));
}

static inline void
counter_u64_zero_inline(counter_u64_t c)
{
    __atomic_store_n(c, 0, __ATOMIC_RELAXED);
}

static inline void
counter_u64_add(counter_u64_t c, int64_t inc)
{
    __atomic_fetch_add(c, inc, __ATOMIC_RELAXED);
}
```

`counter_u64_add_protected`（`:56`）是 `#define` 到 `counter_u64_add`，原子化后自动等价，未改。`counter_enter/exit`（`:38-39`）是空操作，未改。

选 `__atomic_*` 内建而非 `sys/atomic.h`：GCC 内建不依赖 libc 头，`-nostdinc` + override 头环境下完全可用，零头文件依赖。8 字节对齐由 `pcpu_zone_8`（`subr_pcpu.c:146-150`）保证。

边界：原子化消除「丢失更新」，但仍是单槽计数器（fetch/add 只读写第 0 槽），语义不变；多线程高竞争退化为单 cache line 原子热点（轻微 cache 乒乓，可接受——统计非热路径）。

3.2 P4：net.isr.dispatch 启动期防护

文件：`lib/ff_freebsd_init.c`，sysctl 注入循环（`:357-374`）。

改动：在 `kernel_sysctlbyname` 之前对 `net.isr.dispatch` 名字特判，直接拒绝注入（`continue` 跳过）并 `printf` 告警：

```c
    cur = ff_global_cfg.freebsd.sysctl;
    while (cur) {
        if (strcmp(cur->name, "net.isr.dispatch") == 0) {
            printf("net.isr.dispatch must stay direct (hybrid/deferred "
                "silently drop packets); ignoring requested value\n");
            cur = cur->next;
            continue;
        }
        error = kernel_sysctlbyname(curthread, cur->name, NULL, NULL,
            cur->value, cur->vlen, NULL, 0);
        ...
    }
```

选「拒绝注入」而非「注入后校验改回」：默认值本就是 direct（`netisr.c:151`），只要不注入非 direct 值，`netisr_dispatch_policy` 恒为 direct，连注入动作都不发生，比事后校验更彻底。

【注2】该防护堵住的是「config.ini `[freebsd.sysctl]` 注入」这一确定性入口。`net.isr.dispatch` 是 `CTLFLAG_RWTUN`，运行时理论上仍可被外部改写，但 f-stack 用户态没有 `sysctl` 命令行入口（`kernel_sysctlbyname` 只在启动注入循环用到），实际面很小。彻底封死需改 `netisr.c` 的 `sysctl_netisr_dispatch_policy`，属独立项，不在本轮最小 diff 范围。

3.3 P5：行缓冲改 `__thread`

文件：`lib/ff_subr_prf.c`，两行改动：

```c
__thread char bufr[PRINTF_BUFR_SIZE];
static __thread int putbuf_done = 0;
```

`bufr` 只作 `vprintf` 内部临时行缓冲（每次 `vprintf` 从 `:558` 重新初始化，无跨调用、跨线程共享语义），改 `__thread` 语义完全等价，仅消除并发污染。与项目既有大量 `__thread` 先例（`pcpup`/`pcurthread`/`cc_cpu`/`timeout_cpu`/`msg_iov_tmp` 等）风格一致。

3.4 P6：惰性 fail-fast

文件：`lib/include/amd64/include/pcpu.h`（核心）、`lib/ff_api.h`（契约注释）、`tests/unit/test_ff_thread.c`（新增 fail-fast 用例）、`tests/unit/Makefile`（`test_ff_thread` 链接规则新增 `-Wl,--wrap=panic`，这是 `__wrap_panic` 重定向能生效、P6 单测能跑通的关键一环）；`lib/ff_thread.c` 与 `lib/ff_api.symlist` 保持 HEAD 原样（无 diff）。

核心改动：在 `extern __thread struct pcpu *pcpup;`（`:45`）之后、`get_pcpu`（`:47`）之前，加 panic 前置声明 + 惰性检查函数 `ff_pcpu_get()`，并把 `get_pcpu` / `PCPU_GET` / `PCPU_ADD` / `PCPU_INC` / `PCPU_PTR` / `PCPU_SET` 全部改为经它取 `pcpup`：

```c
void panic(const char *fmt, ...) __attribute__((noreturn));

static __inline struct pcpu *
ff_pcpu_get(void)
{
	if (__builtin_expect(pcpup == NULL, 0))
		panic("F-Stack: NULL per-CPU context (pcpup==NULL); "
		      "curcpu/PCPU_* are unsupported in ff_pthread_create threads");
	return (pcpup);
}

#define	get_pcpu()              (ff_pcpu_get()->pc_ ## prvspace)
#define PCPU_GET(member)         (ff_pcpu_get()->pc_ ## member)
#define PCPU_ADD(member, val)    (ff_pcpu_get()->pc_ ## member += (val))
#define PCPU_INC(member)         PCPU_ADD(member, 1)
#define PCPU_PTR(member)         (&ff_pcpu_get()->pc_ ## member)
#define PCPU_SET(member, val)    (ff_pcpu_get()->pc_ ## member = (val))
```

`__builtin_expect(pcpup == NULL, 0)` 让正常路径（`pcpup` 非 NULL）几乎零开销（预测不跳转），惰性 fail-fast 只影响违规路径。

`lib/ff_api.h` 的 `ff_pthread_create` 声明上方契约注释改为如实描述惰性 fail-fast：

```c
/*
 * ff_pthread_create threads are lightweight: they inherit only the parent's
 * thread context (pcurthread), NOT its per-CPU pcpu pointer (pcpup is NULL in
 * the new thread). Calling any ff_* interface that touches curcpu/PCPU_* from
 * such a thread triggers a lazy fail-fast (panic). For a full stack instance
 * use a worker thread (ff_stack_thread_init) instead.
 */
```

`tests/unit/test_ff_thread.c` 新增 fail-fast 用例：`__thread struct pcpu *pcpup` 改零初始化（`= NULL`，与真实 f-stack 一致），`test_setup` 里主线程设 `pcpup = &g_dummy_pcpu` 模拟有 pcpu 的主线程；新增 `test_ff_pthread_create_failfast` 直接在**主线程**触发——`test_setup` 后置 `pcpup = NULL`，`sigsetjmp` 后直接调用 `curcpu`（`PCPU_GET(cpuid)` → `ff_pcpu_get()` → panic），`__wrap_panic` 设 `g_panic_fired = 1` 后 `siglongjmp` 恢复控制，断言 `g_panic_fired == 1`。

【注3】P6 采用「惰性 fail-fast」而非「入口 fail-fast」。设计阶段曾落地无条件入口 panic（`ff_start_routine` 里 `if (pcpup == NULL) panic(...)`），但经 leader 打回（bounce=1）并给出两个致命问题：(1) `pcpup` 是 `__thread`（定义于 `ff_freebsd_init.c:89`，零初始化为 NULL），POSIX 语义下 TLS 变量在新线程中的初值是其**声明时初始化器**、**不继承创建者的运行时值**，故 `ff_pthread_create` 创建的新线程 `pcpup` 恒为 NULL，入口无条件 panic 会让**所有** `ff_pthread_create` 线程（含纯计算/只依赖 pcurthread 的线程）panic、API 完全不可用；(2) 无法单测——测试里若 `pcpup` 非零初始化，新线程非 NULL、fail-fast 用例失效，若零初始化，4 个纯计算用例的新线程也 panic。故收敛为惰性 fail-fast：不在入口检查，而在**触达 `curcpu/PCPU_*` 时**检测 `pcpup == NULL`，既保留纯计算/只依赖 pcurthread 线程的可用性，又能对真正违规触达 `PCPU_GET` 的线程 fail-fast。

3.5 P1：dyn_hp 改显式 per-cpu 数组

文件：`freebsd/netpfil/ipfw/ip_fw_dynamic.c`。DPCPU 宏失效（`dpcpu_off[]` 恒 0、`pc_dynamic` 恒 0），把 `dyn_hp` 从 DPCPU 槽位改为显式 per-cpu 数组，以稠密 cpuid 索引，绕过失效的 DPCPU 宏：

改动 1（原 `:223-226`，DPCPU 定义与两个宏）：

```c
static void **dyn_hp_cache;
/* f-stack 下 dpcpu_off[] 恒 0，DPCPU 宏的 cpu 槽位别名失效，改用显式
 * per-cpu 数组，以稠密 cpuid 索引。 */
static void **dyn_hp;
#define	DYNSTATE_GET(cpu)	ck_pr_load_ptr(&dyn_hp[(cpu)])
#define	DYNSTATE_PROTECT(v)	ck_pr_store_ptr(&dyn_hp[curcpu], (v))
```

改动 2（原 `:3235-3237`，`dyn_init` 里与 `dyn_hp_cache` 一起 malloc）：

```c
	if (IS_DEFAULT_VNET(curvnet)) {
		dyn_hp_cache = malloc(mp_ncpus * sizeof(void *), M_IPFW,
		    M_WAITOK | M_ZERO);
		dyn_hp = malloc(mp_ncpus * sizeof(void *), M_IPFW,
		    M_WAITOK | M_ZERO);
	}
```

改动 3（原 `:3310-3311`，`dyn_uninit` 里与 `dyn_hp_cache` 一起 free）：

```c
	if (IS_DEFAULT_VNET(curvnet)) {
		free(dyn_hp_cache, M_IPFW);
		free(dyn_hp, M_IPFW);
	}
```

`dyn_init` / `dyn_uninit` 中 `dyn_hp` 与既有 `dyn_hp_cache` 完全对称 malloc/free，无泄漏、无双重释放。`curcpu` 在编译单元内可用（include 链含 `pcpu.h`），`DYNSTATE_PROTECT` 用 `&dyn_hp[curcpu]`；`CPU_FOREACH(i)` 的 `i` 范围 0..`mp_ncpus`-1，`&dyn_hp[i]` 不越界。多进程（thread_mode=0）下 `mp_ncpus = 1`、`curcpu = 0`，`dyn_hp[0]` 唯一槽位，等价原 DPCPU 单槽位，零回归。

3.6 P3：__tcp_run_hpts 原子互斥

文件：`freebsd/netinet/tcp_hpts.c`，仅改 `__tcp_run_hpts` 函数（原 `:1590-1660`）。f-stack 下 `p_mtx` 塌缩为无互斥（`lib/include/sys/mutex.h` 的 `HPTS_TRYLOCK` 恒返回 1、`HPTS_LOCK/UNLOCK` 无操作），用原子 exchange 抢占 `p_hpts_active` 提供真实 per-instance 互斥，消除多 worker 并发重入：

```c
	/* f-stack 下 p_mtx 塌缩为无互斥，用原子 exchange 抢占 p_hpts_active
	 * 提供真实 per-instance 互斥，避免多 worker 并发重入。 */
	if (__atomic_exchange_n(&hpts->p_hpts_active, 1, __ATOMIC_ACQUIRE)) {
		/* 已有其他 worker 在运行该实例 */
		return;
	}
	NET_EPOCH_ENTER(et);
	hpts->syscall_cnt++;
	counter_u64_add(hpts_direct_call, 1);
	ticks_ran = tcp_hptsi(hpts, false);
	...
	__atomic_store_n(&hpts->p_hpts_active, 0, __ATOMIC_RELEASE);
	NET_EPOCH_EXIT(et);
```

- 移除二次检查 `if (hpts->p_hpts_active) goto out_with_mtx;`（exchange 已原子抢占）。
- 移除 `hpts->p_hpts_active = 1;`（exchange 已置 1）。
- 移除 `out_with_mtx:` 标签与 `HPTS_UNLOCK(hpts);`。
- `p_hpts_active` 是 `uint16_t`，`__atomic_exchange_n` 返回 `uint16_t`，语义正确。
- `NET_EPOCH_ENTER/EXIT` 严格配对：抢占失败 return 时未 enter，抢占成功才 enter/exit。
- `tcp_hpts_thread`（swi 路径）在 f-stack 下是死代码（`swi_add` 返回 0 不注册、`swi_sched` 空函数），其非原子读写不会与 `__tcp_run_hpts` 的原子操作并发混合，不受影响。
