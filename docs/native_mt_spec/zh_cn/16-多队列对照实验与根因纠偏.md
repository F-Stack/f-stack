## 1. 结论摘要

### 1.1 15 号文档的结论被实测推翻

15 号文档第 5 节曾判定：

> 「2 线程吞吐受限的最终瓶颈定位为 virtio PMD 不支持 RSS/RETA（环境限制，非代码缺陷）」

**该结论错误。** 本轮补做了15 号文档缺失的关键对照实验（`thread_mode=0` + 2 进程 2 队列），证明 virtio 双队列在**完全相同的"无 RSS"代码路径**下工作正常且吞吐更高。原实验把「1 队列 vs 2 队列」的差异错误归因为「进程模式 vs 线程模式」。

### 1.2 真实根因（两个独立缺陷，均已代码坐实并修复）

| # | 缺陷 | 症状 | 修复位置 |
|---|---|---|---|
| **R1** | worker cred 挂全局 `prison0`，而 socket 的 vnet 取自 cred 的 prison（`CRED_TO_VNET`）而非 `curvnet` → worker 所有 socket / `ifioctl` 被静默重定向到 vnet0 | worker vnet 无接口地址、无默认路由（`ENETUNREACH`）；app listen PCB 全建在 vnet0，而数据面在 worker vnet 查 PCB → 收到 SYN 不回 SYN-ACK | `lib/ff_freebsd_init.c` 新增 `ff_worker_prison_init()` |
| **R2** | worker `pcpu_init()` 传`rte_lcore_id()`（=2）作 cpuid，但本 build 非 SMP（`MAXCPU==1`）、`mp_maxid==0`，UMA/SMR per-cpu 数组只按 1 CPU 分配 → `zpcpu_get()` 越界 | 修复 R1 后 worker vnet 的 PCB 表被真正使用，压测时 `in_pcblookup_mbuf` SIGSEGV | `lib/ff_freebsd_init.c` `ff_pcpu_thread_init()` 改传 0 |

附带修复 R3：`init_mem_pool()` 循环上界`nb_procs` → thread_mode 感知（跨 NUMA 才触发的条件性缺陷）。

### 1.3 修复效果

`thread_mode=1` 双线程从**完全不可用**（0 req/s，client 反复重传 SYN）恢复到 **~233k req/s**，与 2 进程模式（~234k）持平；60 秒 400 连接 soak 达**497k req/s**、2983 万请求零错误。

## 3. 根因 R1：worker socket 被静默重定向到 vnet0

### 3.1 运行时铁证（临时探针，已清除）

```
主线程 (f-stack-0.log):
DBGSOCK cret=0 so=0x7f9526f94400 so_vnet=0x37754ef0 curvnet=0x37754ef0 ioctl_ret=0
DBGVNET curvnet=0x37754ef0 ifp_vnet=0x37754ef0 ifp_fib=0 gw_ifa=0x37d1f240 self_ifa=0x37d1f240 unit_eq=1 flags=0x8803

worker (helloworld.log):
DBGSOCK cret=0 so=0x7f9526f95c00 so_vnet=0x37754ef0 curvnet=0x7f952000eb10 ioctl_ret=0
DBGVNET curvnet=0x7f952000eb10 ifp_vnet=0x7f952000eb10 ifp_fib=0 gw_ifa=0 self_ifa=0 unit_eq=1 flags=0x8802
f-stack-0: ff_veth_set_gateway failed DBGERR=51
```

判读：

| 观察 | 含义 |
|---|---|
| worker `so_vnet=0x37754ef0` **等于主线程 vnet0**，而 `curvnet=0x7f952000eb10` | socket 的 vnet 与 worker 自己的 vnet **不一致** |
| `ioctl_ret=0` 但 `self_ifa=0`、`gw_ifa=0` | `SIOCAIFADDR` "成功"了，但地址不在 worker vnet 里 |
| `unit_eq=1` | `ifunit_ref(if_name)` 与 `sc->ifp` 相同 → 接口本身在 worker vnet 的 `V_ifnet` 上，非接口错位 |
| `flags`：主线程 `0x8803` 含 `IFF_UP`(0x1)，worker `0x8802` 缺 | 地址未挂上的连带现象 |
| `DBGERR=51` = **ENETUNREACH** | `freebsd-src-releng-15.0/sys/sys/errno.h:114`；来自 `net/route.c:507` `rt_getifa_fib()` 中 `info->rti_ifa == NULL` |

### 3.2 代码链（逐条坐实）

| 步 | 位置 | 事实 |
|---|---|---|
| 1 | `freebsd/net/vnet.c:336` | `curvnet = prison0.pr_vnet = vnet0 = vnet_alloc();` — prison0 永久绑定 vnet0 |
| 2 | `lib/ff_init_main.c:586-590` | worker cred：`p->p_ucred = crget(); ... cr_prison = &prison0;` |
| 3 | `freebsd/net/vnet.h:247` | `#define CRED_TO_VNET(cr) (cr)->cr_prison->pr_vnet` → **vnet0** |
| 4 | `freebsd/kern/uipc_socket.c:948` | `so = soalloc(CRED_TO_VNET(cred));` → worker 所有 socket 的 `so_vnet` = vnet0 |
| 5 | `freebsd/kern/uipc_socket.c:829-833` | `so->so_vnet = vnet;`（来自 soalloc 参数） |
| 6 | `freebsd/net/if.c:2908` | `ifioctl()` 开头 `CURVNET_SET(so->so_vnet);` → **切到 vnet0** 执行 |
| 7 | `lib/ff_veth.c:599-601` | `ff_veth_setaddr` 用 `socreate()` + `ifioctl(so, SIOCAIFADDR, ...)` |
| 8 | 后果 | worker 的 IP 被加到 **vnet0** 的 `f-stack-0` 上（故 `ioctl_ret=0`），worker 自己 vnet 的 ifp 从未获得地址 |
| 9 | `lib/ff_veth.c:1028` → `lib/ff_veth.c:638` (`rib_action`) → `freebsd/net/route/route_ctl.c:756-757` → `freebsd/net/route.c:497,507` | `ff_veth_set_gateway` 的 `rib_action(RTM_ADD)` 直接用 `curvnet`（不经 socket）→ `ifa_ifwithroute` 找不到 on-link ifa → `ENETUNREACH` |

### 3.3 影响范围（不止路由）

凡「经 socket 进入协议栈」的 worker 操作都被静默重定向到 vnet0：
- `ff_veth_setaddr` / `ff_veth_setaddr6` / `ff_veth_setvaddr`（`ifioctl` 路径）
- `lo_set_defaultaddr()`（定义 `lib/ff_freebsd_init.c:219-263`，其 `socreate` 在 `:255`、`ifioctl` 在 `:259`；worker 调用点 `:215`，主线程调用点 `:342`）
- **app 侧 `ff_socket`/`ff_bind`/`ff_listen`**：worker 的 listen PCB 全部建在 vnet0 的 PCB 哈希表，而数据面 `ff_veth_input` 以 `ifp->if_vnet`(=worker vnet) 作 curvnet 查 PCB → 永远查不到 listen socket → 不回 SYN-ACK

这与实测「listen 成功、client 反复重传 SYN 无响应」完全吻合。

### 3.4 为何 thread_mode=0 无此问题

多进程模式每进程独立地址空间，各有一份 `prison0` 且各自 `prison0.pr_vnet = 自己的 vnet0`，故 `CRED_TO_VNET(cred) == curvnet` 恒成立。**单进程多线程共享唯一 `prison0`（`lib/ff_init_main.c:97`）才暴露该错配。**

### 3.5 修复

`lib/ff_freebsd_init.c` 新增 `ff_worker_prison_init()`：给每个 worker 分配独立 prison，`pr_vnet` 指向该 worker 的 vnet，并改写 worker cred 的 `cr_prison`。要点：
- 从 `prison0` 复制标量与字符串字段；`LIST_INIT` 三个链表头；`mtx_init` 初始化 `pr_mtx`
- **刻意不挂入** `allprison` / prison0 的 children 链表，避免全局链表并发与 jail 遍历副作用
- 调用点必须在 `vnet_alloc()` 之后、`lo_set_defaultaddr()` 之前（后者会 `socreate`）

修复后 worker 的 `ff_veth_set_gateway failed` 消失，且探针确认每线程 listen socket 落在自己的 vnet：

```
DBGAPP lcore=1 kq=1024 sockfd=1025 vnet=0x8c2fef0
DBGAPP lcore=2 kq=1024 sockfd=1025 vnet=0x7fef0000eb10
```

## 4. 根因 R2：非 SMP 视图下 per-cpu 越界导致 SIGSEGV

修复 R1 后，worker vnet 的 PCB 表首次被真正使用，压测立即暴露崩溃：

```
Thread 4 "dpdk-worker2" received signal SIGSEGV, Segmentation fault.
#0  in_pcblookup_mbuf ()
#1  tcp_input ()
#2  ip_input ()
#3  netisr_dispatch ()
#4  ether_nh_input ()
#5  netisr_dispatch ()
#6  ether_input ()
#7  process_packets ()
#8  main_loop ()
```

### 4.1 代码链

| 步 | 位置 | 事实 |
|---|---|---|
| 1 | `freebsd/amd64/include/param.h:60-66` |未定义 `SMP` → **`MAXCPU == 1`**（`lib/opt/opt_global.h` 与 `lib/Makefile` 全树无 `-DSMP`） |
| 2 | `lib/ff_glue.c:140,145` | `mp_ncpus = 1`、`mp_maxid = 0` |
| 3 | `freebsd/vm/uma_core.c:2546-2548` | `#ifndef SMP` 直接剥掉 `UMA_ZONE_PCPU` 标志 → per-cpu 分配只有1 份槽位 |
| 4 | `freebsd/kern/subr_smr.c:597-605` | SMR 只初始化 `0..mp_maxid`（即仅 CPU 0） |
| 5 | `freebsd/kern/subr_pcpu.c:96` | `pcpu_init()` 置 `pc_zpcpu_offset = zpcpu_offset_cpu(cpuid)` |
| 6 | `freebsd/sys/pcpu.h:234-236,249-252` | `zpcpu_offset_cpu(cpu) = UMA_PCPU_ALLOC_SIZE * cpu`（PAGE_SIZE）；`zpcpu_get(base) = base + zpcpu_offset()` |
| 7 | `freebsd/kern/subr_pcpu.c:88` | `KASSERT(cpuid < MAXCPU)` 因未定义 `INVARIANTS` 被**编译掉**，故cpuid=2 静默通过 |
| 8 | `freebsd/netinet/in_pcb.c:583,615-617` | PCB zone 以 `UMA_ZONE_SMR` 创建，`ipi_smr = uma_zone_get_smr(...)`；`in_pcblookup_mbuf` 走 `smr_enter/smr_exit` |
| 9 | 后果 | worker 原传 `rte_lcore_id()`=2 → offset=8192 → `smr_enter` 中 `zpcpu_get()` 读越界内存 → SIGSEGV |

### 4.2 额外坐实的连带缺陷（同一根因）

- `freebsd/netinet/ip_id.c:270` `zpcpu_get(V_ip_id)` 在 `ip_output` → `ip_fillid()`（`freebsd/netinet/ip_output.c:371`）路径中执行 → 修复前每次走到该分支即越界读。
  （精确边界：该行位于 `else` 分支，`:250` 处 `if (V_ip_rfc6864 && (ip->ip_off & htons(IP_DF)) == htons(IP_DF)) ip->ip_id = 0;` 命中时不走此行，故非"每包必达"。）
- `lib/ff_kern_timeout.c:254,730-734`：`timeout_cpu = PCPU_GET(cpuid)`，而 `if (cpu >= MAXCPU) panic("Invalid CPU in callout %d")`。修复前 worker `c_cpu = 2 >= MAXCPU(1)`。

### 4.3 修复

`ff_pcpu_thread_init()` 改为 `pcpu_init(pcpup, 0, sizeof(struct pcpu))`。

正确性依据：
- `pcpup` 是 `__thread`（`lib/ff_freebsd_init.c:85`），`lib/include/amd64/include/pcpu.h:33-53` 把 `PCPU_GET/PCPU_SET/get_pcpu` 全部重定义为经 `pcpup` 访问，**与 `cpuid_to_pcpu[]` 无关** → 每线程仍拥有独立 pcpu，隔离性不变。
- 主线程路径本就传 0（`lib/ff_freebsd_init.c:293` `ff_pcpu_thread_init(0)`）→ 对 `thread_mode=0` 是**no-op**。
- 审核建议采纳：`ff_pcpu_thread_init()` 调用点移入 `init_lock` 临界区，因 `pcpu_init()` 会写全局 `cpuid_to_pcpu[0]` 与 `cpuhead`（`freebsd/kern/subr_pcpu.c:91-92`）。仅初始化路径，数据面零影响。

## 5. 附带修复 R3：mempool 循环上界

`lib/ff_dpdk_if.c:547-551`：

```c
uint16_t nb_pools = ff_global_cfg.dpdk.thread_mode
    ? ff_global_cfg.dpdk.nb_threads : ff_global_cfg.dpdk.nb_procs;
for (i = 0; i < nb_pools; i++) {
    lcore_id = ff_global_cfg.dpdk.proc_lcore[i];
```

原上界为 `nb_procs`，而 `thread_mode=1` 时 `lib/ff_config.c:1465-1484` 把 `nb_procs` 塞成 1、真实线程数在 `nb_threads`。后果：只给 `proc_lcore[0]` 所在 NUMA socket 建 mempool，worker 若在别的 socket，`init_port_start`（`lib/ff_dpdk_if.c:1062-1086`）按队列 lcore 的 socket 取池会拿到 NULL。
`nb_mbuf` 规模计算已正确使用 `nb_threads`（`:526-527`），本次使循环与之一致。

**本机 lcore 1/2 同 socket，故该缺陷未被触发**（ff_log 仅 `create mbuf pool on socket 0`），属预防性修复。

## 7. 外网调研交叉验证（`_m1_B_external.md`，24 条可核查来源）

关键结论（与代码交叉核对，不一致处以代码为准）：

1. **无 `VIRTIO_NET_F_RSS` 时 guest 无法控制入向分发，队列由 host 单方决定。**
   - vhost-net + tap 后端走 Linux 内核 tun 的 automatic flow steering：**出方向学习、入方向查表**；表未命中时按 `txq = ((u64)__skb_get_hash_symmetric(skb) * numqueues) >> 32` 散列（**非固定进队列 0**），表项 `TUN_FLOW_EXPIRE = 3*HZ` 老化。
   - vhost-user / OVS-DPDK 后端则是「队列绑 PMD 线程」（OVS 官方文档：单 PMD → 全部流量进同一条 vhost 队列）。
   - 注：KVM wiki《Multiqueue》称「无 hash 时固定落第一个队列」属 2012 年设计稿，**以内核代码为准**。

2. **DPDK 接管不影响 host 侧 steering**（steering 在 host 内核，不感知 guest 驱动）。`VIRTIO_NET_CTRL_MQ_VQ_PAIRS_SET` 由 DPDK 在 `dev_start` 自动下发（`dpdk-stable-24.11.6/drivers/net/virtio/virtio_ethdev.c:2383-2387` → `virtio_set_multiple_queues_auto()`），应用无需干预。
   **强推论**：`virtio_cvq.c:197-200` 在 `!cvq` 时 `virtio_send_command()` 返回 -1 → `dev_start` 失败。既然 f-stack 2 队列**能启动成功**，说明 cvq 存在、`VQ_PAIRS_SET` 已成功下发、QEMU 侧 `curr_queue_pairs=2` 且对 queue 1 做了 `peer_attach()` → **「host 只启用1 条队列」可排除**。

3. **本轮 E2 结果为上述机制提供了正面实证**：2 进程各自从自己的队列发包，host tun 学到「流→队列」映射，入向随之对齐，两队列均满负荷（998k / 1060k）。

4. **f-stack 侧未找到任何在virtio 上成功跑起多队列的公开记录**（4 条公开案例全停在「virtio 不支持 RSS → 报错 → 退化单队列/改源码」）。本文档的 E2/E4 结果可作为该场景的首个可复现实证。

5. **未找到可靠来源的项**（如实标注，未编造）：DPDK「只有 queue 0 收包」的直接 bug 报告；「是否需要关 KNI」无任何来源，未作结论。

## 8. 遗留风险（明确记录，非本次引入）

### 8.1 SMR / UMA per-cpu 槽位在多 worker 间共享

修复 R2 后所有 worker 的 `pc_zpcpu_offset` 均为 0，故多 worker **共享同一份** SMR per-cpu 槽位。理论窗口：A 线程 `smr_exit` 置`SMR_SEQ_INVALID` 可能清掉 B 线程的 read section 标记 → `smr_poll` 误判无读者 → PCB 提前回收（UAF）。相关代码：`freebsd/sys/smr.h:106-160`、`freebsd/netinet/in_pcb.c:1820-1888`。

必须明确：
1. **该风险非本次改动引入**。修复前 offset 非 0 → **必然越界**（已实测 SIGSEGV）；修复后为「合法但共享」，是严格改善。
2. 彻底消除需让 f-stack 内核视图 SMP-aware（`mp_maxid > 0` + 真正按线程数分配 per-cpu 数组），远超本次修复范围，**建议独立立项**。
3. 压力验证：60 秒 / 400 连接 / 2983 万请求 soak 未观察到 UAF 症状（零socket error、零 Non-2xx、进程存活），但静态风险窗口客观存在。

### 8.2 `cpuid_to_pcpu[0]` 与 `cpuhead` 被多 worker 覆盖/串接

`pcpu_init()` 写全局 `cpuid_to_pcpu[0]`（数组仅 1 项）与 `cpuhead` 链表。已穷举确认本build 内**无任何读者**（`pcpu_find()` / `cpuhead` 遍历 / `cpuid_to_pcpu[]` 直读的全部调用点所在文件均不在 `lib/Makefile` 的 SRCS 中，或被 `#ifndef FSTACK` 关闭），故无实际错误。已按审核建议将调用移入 `init_lock` 临界区消除并发写。

### 8.3 `jailed()` 在 worker 下变为真（影响已界定，TCP/UDP 无变化）

`jailed()` 是宏而非可stub 的函数：`freebsd/sys/jail.h:449` `#define jailed(cred) (cred->cr_prison != &prison0)`（`lib/ff_glue.c:346-352` 的同名stub 整段在 `#if 0` 内，未编译）。因此 per-worker prison 使 worker cred 的 `jailed()` **为真**。

已逐条界定影响范围：
- **PCB 插入/查找顺序不受影响**：`in_pcbjailed()`（`freebsd/netinet/in_pcb.c:2743-2746`）走 `prison_flag()`，而 f-stack 的 stub（`lib/ff_glue.c:286-290`）**忽略 cred**、只返回 `(flag & PR_HOST) != 0`；调用处传 `PR_IP4`/`PR_IP6`，故恒为 false。
- **已编译集合中 `jailed()` 唯一读者是 `freebsd/netinet/raw_ip.c:500`**（`in_jail.c` / `in6_jail.c` / `kern_jail.c` / `kern_cpuset.c` 均不在 `lib/Makefile` SRCS），仅影响 raw IP + `IP_HDRINCL` 路径，且其内 `prison_local_ip4` 为 stub 返回 0（`lib/ff_glue.c:299-302`）。

结论：对 TCP/UDP 数据面与 PCB 哈希顺序**无行为改变**。若将来启用 raw IP 相关功能，需复查该路径。

### 8.4 CM5-B 既有并发风险清单

`ff_init_main.c` 中 worker cred 相关的 `uifind(0)`/`crget()` 等全局操作仍依赖初始化期串行化，见 13/14 号文档记录的 R1-R5 条目，本轮未改变其性质。

## 10. 复现步骤

```bash
# 2 线程（修复验证）
# config.ini: thread_mode=1, lcore_mask=6
cd /data/workspace/f-stack/lib && make clean && make -j8
cd ../example && make clean && make -j8
setsid nohup ./helloworld --conf ../config.ini > /tmp/run.log 2>&1 < /dev/null &
# 先用一次 curl 预热（刷新 client 侧 ARP），再压测
ssh f-stack-client "curl -s -o /dev/null http://<DPDK_NIC_IP>/"
ssh f-stack-client "/data/wrk/wrk -t5 -c100 -d10s http://<DPDK_NIC_IP>:80/"

# 2 进程对照（E2/E5-c）
# config.ini: thread_mode=0, lcore_mask=6
setsid nohup /data/workspace/f-stack/example/helloworld --conf /tmp/a.ini --proc-type=primary   --proc-id=0 > /tmp/a.log 2>&1 < /dev/null &
setsid nohup /data/workspace/f-stack/example/helloworld --conf /tmp/b.ini --proc-type=secondary --proc-id=1 > /tmp/b.log 2>&1 < /dev/null &
```

注意事项：
- 启动前须确认无残留进程（`pgrep helloworld`；清理用 `/data/workspace/kill_process.sh`）
- 必须用 `setsid` 完整脱离终端，否则父shell 退出会带走进程
