# 00 调研结论总览

> 本文档为 f-stack 原生「单进程 + 多线程 + 多协议栈实例」调研的结论先行总览。所有技术论断以 `lib/` 与 FreeBSD/DPDK 源码 file:line 为准。

## 0. 旧版结论作废声明

上一版 spec（已提交 `497e53e11`，`docs/multi_thread_spec/zh_cn/`）曾**推荐「多进程 + LD_PRELOAD adapter 多 worker」**路线并将原生多线程降级为高风险备选。**该推荐结论本轮作废。** 本版按用户明确要求，只论证并设计**库内原生（`lib/` 层）支持单进程多线程多协议栈实例**的落地方案，**不采用 adapter 路线**（adapter 仅作应用侧现状客观记录）。

## 1. 一句话结论

f-stack 当前是「一进程 = 一 lcore = 一栈实例」的多进程 share-nothing 模型。要在库内原生支持「单进程内 N 个 pthread 各跑一份独立协议栈实例」，**技术首选路径 = 启用 FreeBSD 原生的 VNET/VIMAGE（每线程 `curthread->td_vnet` 指向各自 `vnet_alloc()` 出的栈实例）+ 把非-VNET 的 f-stack 自造全局（`lcore_conf`/`pcpup`/`cc_cpu`/`thread0`/`msg_iov_tmp`）另行 per-thread 化 + 重构一次性初始化序列 + DPDK 单进程拉起 N 个 lcore 线程**。该改造**可行但工程量大**，且存在必须运行时验证的关键不确定项（VIMAGE 在 f-stack 阉割用户态能否跑通）。

## 2. 三层可行性速览

| 层面 | 结论 | 关键证据 |
|---|---|---|
| **DPDK 侧** | ✅ 基本就绪，改动小 | `rte_eal_mp_remote_launch`(`ff_dpdk_if.c:2770`) 给 N-bit coremask 即自动拉 N 线程；dispatch_ring 保 MP+SC(`:619`)、msg_ring 保 SP+SC(已数组化 `:177`)、mempool 开箱 MT-safe(`rte_mempool.h:28-32`)。唯一硬骨头 `lcore_conf` 全局单例(`:123`)需改 per-lcore 数组。 |
| **FreeBSD 网络栈全局** | ✅ 有原生解法(VNET) | 数百个 `V_ifnet/V_tcbinfo/V_rt_tables/...` 现退化为进程级全局(无 VIMAGE)。启用 VIMAGE 后按 `curvnet=curthread->td_vnet`(`vnet.h:176`) per-thread 隔离，`vnet_alloc()`(`vnet.c:239`) 每线程一份完整栈实例。 |
| **f-stack 自造全局 + init** | ⛔ 硬结论：不可 N 次初始化 | `mi_startup`/SYSINIT 跑完打勾 `SI_SUB_LAST`(`ff_init_main.c:271`)，二次调用空转；`pcpup`/`thread0`/`cc_cpu`/`msg_iov_tmp` 均全局单例，须重构初始化架构 + per-thread 化。 |

## 3. 推荐落地路径（原生，非 adapter）

**主路径（VNET-based 原生多栈实例）：**
1. 启用 VIMAGE，每线程 `vnet_alloc()` 一份 vnet 并设 `curthread->td_vnet`，复用内核 VNET 数据段虚拟化隔离数百个网络栈全局（详见 `04`、`05`）。
2. 把非-VNET 的 f-stack 自造全局逐个 per-thread 化（`lcore_conf`→数组、`pcpup`/`thread0`/`proc0`→每实例一份、`cc_cpu`→每实例 callout、`msg_iov_tmp`→恢复 `__thread`，详见 `03`）。
3. 重构初始化：`ff_init` 只调一次做 EAL + N 份 per-lcore 实例状态；每线程各自跑一遍 per-thread 的 FreeBSD 栈初始化（VNET_SYSINIT 每 vnet 一次），`rte_eal_mp_remote_launch` 在 N 个 lcore 各跑 `main_loop`（详见 `04`、`06`）。
4. 配置新增 `thread_mode` opt-in 开关 + `nb_threads`，与多进程模式互斥，保多进程零回归（详见 `07`）。
5. KNI 归单一 owner 线程；工具链 IPC 重设计（详见 `08`）。

**被否决对比（仅记录，不推荐）：** 「共享单栈 + 细粒度锁」违背 f-stack share-nothing 无锁理念、破坏 SC/SP ring 假设，仅作对比。

**非本方案：** LD_PRELOAD adapter 多 worker 是应用侧适配，不是栈侧原生多线程运行模型。

## 4. 头号改造靶点（按危险度，详见 `03`/`10`）

| 排名 | 靶点 | file:line | 成本 |
|---|---|---|---|
| 0（低垂果实） | `msg_iov_tmp/msg_iovlen_tmp` 恢复 `__thread` | `ff_syscall_wrapper.c:225-226` | 极低 |
| 1（架构卡点） | `mi_startup`/SYSINIT 一次性机制重构 | `ff_init_main.c:173-285,271` | 极大 |
| 2 | `lcore_conf` 全局单例→per-lcore | `ff_dpdk_if.c:123`(30+ 引用) | 中-大 |

| 5 | VNET 退化全局（数百个）→启 VIMAGE | `freebsd-src` 树 | 极大（VNET 原生覆盖） |
| 6 | UMA 分配器全局 MT-safe | `ff_freebsd_init.c:70-71` | 高/需运行时验证 |

## 5. 关键诚实边界（须运行时验证，不得臆断）

1. VIMAGE 在 f-stack 大量阉割的用户态环境能否完整跑通（`vnet_alloc`/`VNET_SYSINIT`/数据段重定位依赖）。
2. `mi_startup`/UMA/协议栈初始化在多线程重构后 N 次执行的实际行为。
3. mempool 多线程共池的容量与非-EAL 线程调用行为、NUMA 绑核策略。
4. callout 改多实例后与 tcp_hpts 定时器交互（`ff_kern_timeout.c:1252-1274`）。

## 7. issue #430 定位（强制调研目标第 9 项）

#430「SOCK_STREAM [SOLVED] + Multi Thread (Pthread)」属**应用侧多线程调用 API** 场景（libuv+pthread+组合 socket 标志位），当前代码 `linux2freebsd_socket_flags`(`ff_syscall_wrapper.c:672-684`)/`ff_socket`(`:943`)/`ff_accept4`(`:1679`) 已完备处理组合标志位。它是「真实用户在多线程环境用 f-stack 的一手需求佐证」，但**与本轮「栈侧原生多线程运行模型」是两个层面**，不作本轮结论落点。外网评论区因 GitHub 动态加载 + API 限流未抓到，已诚实标注、以代码为准。
