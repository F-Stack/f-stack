# 11 测试、性能基线与风险兼容

## 1. 测试策略

### 1.1 单元测试（mock 点）
| 目标 | mock/验证点 |
|---|---|
| 配置分叉 | `parse_lcore_mask`（`ff_config.c:73-142`）thread 模式：给 lcore_mask，断言 `nb_threads`/`proc_mask`/proc_type 校验正确；thread_mode=0 时输出与旧版字节一致 |
| lcore_conf 索引 | `lcore_conf[rte_lcore_id()]`（`ff_dpdk_if.c:123`）多线程下各线程取到不同实例 |
| msg_iov_tmp TLS | `ff_syscall_wrapper.c:225-226` 恢复 `__thread` 后并发 recvmsg/sendmsg 无踩踏 |
| 隔离宏 | `__thread`/`RTE_PER_LCORE`/数组三种隔离在 N 线程下各自独立 |

### 1.2 集成测试
- thread 模式启动 N 线程各起独立栈实例，各自 socket/listen/accept 正常。
- 复用既有 example（helloworld）在 thread_mode=1 下起多线程 server。
- VNET 隔离验证：不同线程绑不同 IP/路由，互不可见（`V_in_ifaddrhead`/`V_rt_tables` 隔离）。

### 1.3 端到端（本机双网卡约束）
- **DPDK 网卡**（独占，IP <DPDK_NIC_IP>）：需 `ssh f-stack-client` 从对端发起流量测 thread 模式 N 线程收发与 RSS 分流。
- **内核栈对照**：`127.0.0.1` 的 lo 走内核栈做对照基准。

### 1.4 多进程零回归（一票否决）
- thread_mode=0（默认）下，所有既有多进程用例（primary/secondary、KNI、工具链）行为**字节级不变**。任一回归即门禁失败。

## 2. 性能基线方案

### 2.1 对照组
| 组 | 配置 |
|---|---|
| G0 基准 | 现状多进程（N 进程各 1 lcore） |
| G1 目标 | thread 模式（1 进程 N 线程各 1 lcore） |

### 2.2 指标
- 吞吐（pps/bps，短连接 QPS + 长连接带宽）
- 时延（p50/p99/p999）
- CPU 利用率 / 每核 cycles
- cache miss（perf stat，验证 share-nothing cache 亲和）
- 内存占用（thread 模式共享地址空间，mempool/hugepage 可共享，预期内存优于多进程）

### 2.3 测试矩阵
- lcore 数：1/2/4/8（扩展性曲线，验证近线性）
- 报文大小：64/512/1500B
- 连接模型：短连接（accept 密集）+ 长连接（吞吐密集）

### 2.4 通过判据
- thread 模式吞吐/时延 ≥ 多进程模式的 95%（share-nothing 应无本质劣化）；
- 扩展性随 lcore 数近线性；
- 若 thread 模式出现明显锁点/劣化，回查是否有全局状态未 per-thread 化（退化为隐式共享）。

### 2.5 实测结果（2026-07-29，详见 `13-性能基线实测报告.md`）

| 配置 | median req/s | Latency | 状态 |
|---|---:|---:|---|
| thread_mode=1, 1 线程 (lcore_mask=10) | 189,044 | 497 us | ✅ PASS |
| thread_mode=0, 多进程 (lcore_mask=10) | 114,629 | 411 us | ✅ 基准 |
| thread_mode=1, 2 线程 (lcore_mask=30) | — | — | ❌ crash (R1) |
| thread_mode=1, 4 线程 (lcore_mask=f0) | — | — | ❌ crash (R1) |

- **PERF-1 PASS**：thread_mode=1 单线程吞吐 = thread_mode=0 的 **165%**（远超 95% 判据）。
- **PERF-2 BLOCKED**：2/4 线程因 VIMAGE 隔离不完整（R1 风险确认）crash，无法测扩展性曲线。

## 3. 风险清单

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| R1 | **VIMAGE 在 f-stack 用户态跑不通** | 高 | CM4 尽早 PoC；不通过转路线甲（手工 per-thread 化）；转人工决策。**实测确认（2026-07-29）**：VIMAGE 已编译（`opt_global.h:6`），1 线程正常（189k req/s），2 线程 crash 于 `kqueue_kevent`→`memset` SIGSEGV（fd 表/kqueue per-vnet 隔离不完整）。需 CM4 完整实现 kqueue/fd 表 per-vnet 隔离。 |
| R2 | **线程崩溃导致整个进程退出**（弱于多进程的进程级隔离） | 高 | spec 显著标注；建议关键部署仍保留多进程选项；线程内异常捕获/看门狗 |
| R3 | init 重构（CM5）引入初始化顺序/重复 init 缺陷 | 高 | 严格拆分一次性 vs per-thread；充分单测；回滚点 |
| R4 | 全局状态遗漏 per-thread 化 → 隐式共享踩踏 | 中-高 | `03` 清单逐项核对；工具/静态扫描辅助；压测观测 |
| R5 | callout 每实例化后与 tcp_hpts 定时器交互异常 | 中 | 运行时验证（`ff_kern_timeout.c:1252-1274`）；对照多进程行为 |
| R6 | mempool 多线程共池容量不足 | 中 | 容量公式随 nb_lcores 放大（`ff_dpdk_if.c:495`）已考虑；压测观测 `rte_mempool_avail_count` |
| R7 | 工具链不兼容（无 secondary） | 中 | C1 保留外部工具进程（`08`）；线程化列独立子项 |
| R8 | 多进程零回归被破坏 | 高 | thread_mode 默认关 + 两模式互斥 + 字节级回归门禁（一票否决） |

## 4. 兼容性

- **API 兼容**：`ff_init`/`ff_run` 签名不变（`ff_init.c:36,59`），thread 模式对应用透明（`07 §4.2`）。
- **配置兼容**：`thread_mode` 默认 0，旧 config.ini 行为不变。
- **模式互斥**：thread 模式与多进程 secondary 互斥，配置期校验。
- **向后兼容策略**：opt-in，逐里程碑可回滚。

## 5. 诚实边界分层（须运行时验证，不得臆断）
