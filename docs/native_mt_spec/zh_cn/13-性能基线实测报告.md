## 7. 2/4 线程 crash 分析（R1 风险确认）

### 7.1 症状

2 线程（lcore_mask=30, thread_mode=1）启动后立即 segfault，无需 wrk 压测。

gdb backtrace（主线程）：
```
#0  __memset_avx2_unaligned_erms () from /lib64/libc.so.6
#1  kqueue_kevent.part ()
#2  kern_kevent ()
#3  ff_kevent ()
#4  loop (arg=0x0) at main.c:147
#5  main_loop ()
#6  rte_eal_mp_remote_launch ()
#7  ff_dpdk_run ()
#8  main (argc=3, argv=...) at main.c:226
```

segfault at 0（NULL 指针写），在 `kqueue_kevent` 内部的 `memset` 中。

### 7.2 根因

**VIMAGE 隔离不完整**（spec `11` R1 风险确认）。

VIMAGE 已编译（`opt_global.h:6 #define VIMAGE 1`），`curvnet=curthread->td_vnet`（per-thread），`vnet_alloc()` 创建新 vnet。但 f-stack 用户态环境下，kqueue/fd 表的 per-vnet 隔离不完整，多线程并发调用 `ff_kevent` 导致 kqueue 内部状态竞争，`memset` 访问 NULL 指针 crash。

### 7.3 修复历程（3 次打回，bounce≤3 转人工决策）

| 次 | 问题 | 修复 | 结果 |
|---|---|---|---|
| 1 | helloworld 全局变量竞争（kq/sockfd/events 全局） | `__thread kq/sockfd/events` + `init_thread()` per-thread 初始化 | bind 冲突（EADDRINUSE） |
| 2 | `ff_bind` Address already in use（两线程 bind 同一端口） | `SO_REUSEPORT` | kqueue crash（SIGSEGV） |
| 3 | `ff_kevent` → `kqueue_kevent` → `memset` SIGSEGV | VIMAGE fd 表/kqueue per-vnet 隔离不完整 | **需 CM4 VIMAGE 完整实现，转后续工作** |

### 7.4 结论

- **R1 风险确认**：VIMAGE 在 f-stack 用户态隔离不完整，多线程下 kqueue/fd 表竞争导致 crash。
- **2/4 线程无法完成**：需 CM4 VIMAGE 完整实现（kqueue/fd 表 per-vnet 隔离）。
- **1 线程可用**：单线程无并发竞争，thread_mode=1 性能优势显著（165% of thread_mode=0）。

## 9. 关键过程发现

### 9.1 TIME_WAIT 堆积导致后续 trial 失败

thread_mode=0 Trial 1 正常（114k req/s），但 Trial 2/3 连接超时（unable to connect）。等 30 秒后 Trial 4 恢复正常（111k req/s）。

根因：wrk 100 个 keep-alive 连接断开后产生大量 TIME_WAIT，config.ini 的 `finwait2_timeout=5000` + `fast_finwait2_recycle=1` 需要数秒回收。后续 trial 需间隔 30 秒。

### 9.2 helloworld 全局变量竞争（已修复）

原 helloworld 的 `kq/sockfd/events` 是全局变量，thread_mode=1 下多 lcore 并发调用 `loop()` 导致竞争。症状：wrk Trial 1 仅 19 requests（1.9 req/s），然后 hang（`ff_kevent failed:9, Bad file descriptor`，CPU 200% 空转）。

gdb 诊断：主线程卡在 `ff_write` → `tcp_usr_send` → `ip_output` → `mb_unmapped_to_ext`（mbuf 链有环，无限循环）。

修复：改为 `__thread` + `init_thread()` per-thread 初始化。

### 9.3 config.ini lcore_mask 混淆

调试期间 config.ini 的 `lcore_mask` 在 10/30 间切换时出现混淆（以为测 1 线程实际是 2 线程），导致诊断走弯路。教训：每次修改 config.ini 后必须 `grep lcore_mask` 确认实际值。

## 11. 复现实步

```bash
# 0) 编译（make clean 后全量重编）
cd /data/workspace/f-stack/lib && make clean && make -j$(nproc)
cd /data/workspace/f-stack/example && make clean && make

# 1) thread_mode=1 单线程（lcore_mask=10）
# config.ini: lcore_mask=10, thread_mode=1, [pcap] enable=0
find /run/dpdk/rte/ -type f | xargs /data/workspace/rm_tmp_file.sh
cd /data/workspace/f-stack/example
nohup ./helloworld -c ../config.ini > /tmp/hw.log 2>&1 &
sleep 15  # 等待初始化完成
ssh f-stack-client "/data/wrk/wrk -t2 -c100 -d10s http://<DPDK_NIC_IP>:80/"
sleep 30  # TIME_WAIT 回收
ssh f-stack-client "/data/wrk/wrk -t2 -c100 -d10s http://<DPDK_NIC_IP>:80/"

# 2) thread_mode=0 对照（lcore_mask=10）
# config.ini: lcore_mask=10, #thread_mode=0
/data/workspace/kill_process.sh $(pgrep helloworld)
find /run/dpdk/rte/ -type f | xargs /data/workspace/rm_tmp_file.sh
nohup ./helloworld -c ../config.ini > /tmp/hw.log 2>&1 &
sleep 15
ssh f-stack-client "/data/wrk/wrk -t2 -c100 -d10s http://<DPDK_NIC_IP>:80/"
sleep 30
ssh f-stack-client "/data/wrk/wrk -t2 -c100 -d10s http://<DPDK_NIC_IP>:80/"

# 收尾
/data/workspace/kill_process.sh $(pgrep helloworld)
find /run/dpdk/rte/ -type f | xargs /data/workspace/rm_tmp_file.sh
```
