# GPT-5.4 评审

## 1. 评审范围

本次评审对象为 `/data/workspace/f-stack/docs/` 目录下的 F-Stack 项目文档，重点检查以下方面：

1. 文档与当前仓库代码/配置的一致性
2. 文档结构、导航与重复度
3. 术语、格式、统计信息的一致性
4. 是否缺少关键边界条件、限制说明和维护提示

本次评审是基于当前工作树对应的 F-Stack 仓库状态进行的静态审查。

---

## 2. 总体结论

这套文档整体质量较高，主体结构清晰，三层架构划分合理，对 F-Stack 的核心设计、关键模块和 API 体系做了比较完整的梳理。对于后续做 spec-driven development，这批文档已经具备较好的“架构基线”价值。

但也存在几类比较明显的问题：

1. **文档与代码版本状态不同步**，最明显的是 Nginx 集成目录版本已经变化，但文档仍写旧版本。
2. **部分 API 的“公开边界”表述不够准确**，例如 `ff_init` / `ff_run` / `ff_stop_run` 在 `ff_api.h` 中声明，但没有出现在 `ff_api.symlist` 中；`epoll` 相关接口存在于 `ff_epoll.h` / `ff_epoll.c`，但文档容易让人误以为它们和 `ff_api.h` 中的主 API 是同一层级的导出接口。
3. **文档之间重复较多**，完整版、简化版、汇总版之间存在较大面积内容重述，后续维护时很容易失步。
4. **一些统计信息已经不准确**，例如 `docs/README.md` 中的总行数和简化版行数统计都与当前实际文件不一致。
5. **关键边界条件和风险说明不够集中**，例如单线程/单 lcore 使用约束、非阻塞要求、性能数据的测试条件等，没有在一个醒目的位置统一说明。

结论很简单：

**这批文档“可用而且有价值”，但还没有达到“长期可维护、与代码强同步”的状态。**

## 4. 主要问题

下面按严重程度分级。

### 4.1 严重问题

#### 4.1.1 Nginx 集成版本已过时，文档仍引用旧目录

当前代码中实际存在的 Nginx 目录是：

- `app/nginx-1.28.0`

但文档中仍然写的是旧版本：

- `docs/01-LAYER1-ARCHITECTURE.md:78`
- `docs/F-Stack_Architecture_Layer1_System_Overview.md:118`
- `docs/F-Stack_Knowledge_Base_Summary.md:619`

这些位置仍然引用：

- `nginx-1.25.2`

这不是纯文字问题，而是**直接影响读者对代码目录和集成点的定位**。如果读者按文档去找 `app/nginx-1.25.2`，现在仓库里已经找不到。

**影响：**

1. 文档与代码定位脱节
2. 影响后续 spec 对接时的源码映射
3. 说明文档维护没有跟随版本升级同步更新

**建议：**

统一将 docs 中所有 `nginx-1.25.2` 更新为当前实际目录版本，并在文档中注明“该集成目录会随上游升级而变化，阅读时应以 `app/nginx-*` 实际目录为准”。

---

#### 4.1.2 API 导出边界表达不清，容易误导使用者

当前代码中：

- `ff_init` 定义于 `lib/ff_api.h:56`
- `ff_run` 定义于 `lib/ff_api.h:58`
- `ff_stop_run` 定义于 `lib/ff_api.h:60`

但在 `lib/ff_api.symlist` 中，并没有找到这些名字。

同样，epoll 相关接口存在于：

- `lib/ff_epoll.h:10`
- `lib/ff_epoll.h:11`
- `lib/ff_epoll.h:12`
- `lib/ff_epoll.c:25`
- `lib/ff_epoll.c:31`
- `lib/ff_epoll.c:148`

这说明当前接口体系至少分成了两层：

1. `ff_api.h` 主接口层
2. `ff_epoll.h` 补充接口层
3. `ff_api.symlist` 动态导出符号层

但文档整体上没有把这三层边界讲清楚，容易让人误以为：

- 所有在文档列出的接口都等价地位
- 所有接口都在 `ff_api.h` 中
- 所有接口都在 `ff_api.symlist` 中导出

实际上不是这样。

**影响：**

1. 做静态链接/动态链接的人容易误判
2. 做 ABI 或封装层的人可能理解错误
3. 文档在“接口定义”层面不够严谨

**建议：**

在 Layer 2 或 Layer 3 中补一个小节，明确区分：

- “头文件声明接口”
- “补充兼容接口（如 epoll）”
- “实际动态导出符号”

否则这部分会长期含混。

### 4.2 中等问题

#### 4.2.1 README 中的统计数字已经失准

`docs/README.md` 当前写的是：

- `docs/README.md:30`：总计 `3921 行 (+ 1691 行简化版本) = 5612 行`

但当前实际统计结果是：

- README.md：332 行
- 01-LAYER1-ARCHITECTURE.md：333 行
- 02-LAYER2-INTERFACES.md：476 行
- 03-LAYER3-FUNCTIONS.md：627 行
- F-Stack_Architecture_Layer1_System_Overview.md：825 行
- F-Stack_Architecture_Layer2_Interface_Specification.md：1183 行
- F-Stack_Architecture_Layer3_Function_Index.md：1112 行
- F-Stack_Knowledge_Base_Summary.md：751 行
- SUMMARY.txt：200 行
- 合计：**5839 行**

并且简化版三份文档的总行数实际是：

- `333 + 476 + 627 = 1436`

并不是 README 里写的 1691。

**影响：**

- 说明 README 中“知识库规模”信息已经过期
- 影响文档可信度
- 说明这些统计没有自动化维护

**建议：**

更新 README 中所有统计数字，或者干脆删掉这些容易过期的静态统计，改为“以当前仓库文件实际情况为准”。

---

#### 4.2.2 完整版/简化版/汇总版重复内容过多，维护风险偏高

目前 docs 里至少有三类文档：

1. 完整版：`F-Stack_Architecture_Layer*.md`
2. 简化版：`01/02/03-LAYER*.md`
3. 汇总版：`F-Stack_Knowledge_Base_Summary.md`、`README.md`、`SUMMARY.txt`

这些文档之间存在较大面积的重复：

- 核心概念重复讲多遍
- 目录结构重复列多遍
- 核心文件职责重复写多遍
- 关键版本信息重复写多遍

短期看这能提高可读性，长期看问题很明显：

1. 一处版本更新，可能要改 5 处
2. 一处目录名变化（这次 Nginx 就是）很容易漏改
3. 不同文档之间以后会慢慢长出多个“事实版本”

**建议：**

减少“完整重复”，更多采用“简版引用完整版”的方式：

- 简化版只保留结论和导航
- 细节统一落到完整版
- 汇总文档主要做入口，不重复堆细节

---

#### 4.2.3 边界条件和风险说明不够集中

现在文档确实提到了不少约束，但比较分散，不够“醒目”。

例如以下内容，对实际开发非常关键：

- socket/连接与 lcore 的绑定模型
- 单线程/事件循环约束
- 非阻塞使用要求
- 性能数据的适用前提
- KNI/多进程等配置的副作用

这些内容没有在 README 或 Layer 2 中形成一个统一的“重要限制/风险提示”章节。

**影响：**

- 新读者容易只看 API，不看约束
- 真实使用中更容易踩坑
- 文档更像知识说明，不像“工程落地说明”

**建议：**

在 `docs/README.md` 和 `docs/02-LAYER2-INTERFACES.md` 各加一个“重要约束与风险提示”小节，集中写清楚：

1. 单线程/单 lcore 模型
2. 非阻塞约束
3. 典型错误用法
4. 性能数据前提
5. 应用集成边界

---

#### 4.2.4 epoll 接口的文档表述还不够严谨

前面说过，epoll 相关接口确实存在，但它们是：

- `ff_epoll.h`
- `ff_epoll.c`

并不在 `ff_api.h` 中。

因此如果 Layer 2 / Layer 3 中把它们和主 API 放在完全同一语义层级，会让人误解为“这是同一套头文件、同一种导出方式”。

这不是“接口不存在”的问题，而是**接口归属说明不够严谨**。

**建议：**

在文档中明确一句：

- kqueue/socket 体系主要看 `ff_api.h`
- epoll 兼容接口主要看 `ff_epoll.h`

这样读者就不会去错地方找。

---

### 4.3 低优先级问题

#### 4.3.1 性能数据缺少测试条件说明

文档里多次提到类似：

- 10M 连接
- 5M RPS
- 1M CPS

但缺少足够明确的上下文：

- CPU/核数
- 网卡型号
- 报文大小
- 测试场景
- 是否是单机 benchmark 还是完整业务路径

这类数据不是不能写，但最好配套说明“测试前提”，否则它更像宣传口径，不像工程基线。

---

#### 4.3.2 术语表达存在轻微不统一

例如吞吐指标有时写：

- 5M RPS
- 500 万+ RPS

虽然意思差不多，但在长文档体系里建议统一一种写法。类似地，一些地方会混用“接口”“API”“系统调用兼容层”“封装层”等概念，虽然不至于出错，但会增加维护时的风格漂移。

---

#### 4.3.3 缺少更实战化的故障排查内容

当前文档已经有架构和 API 知识库属性，但在“怎么排查问题”方面仍然偏薄，尤其缺少：

- 常见配置错误排查路径
- 运行时日志定位建议
- 多进程/网卡/RSS 相关问题的诊断入口
- 与 DPDK 层联动排查的方法

如果未来这批文档不仅面向“阅读”，而且面向“交付/落地”，这一块迟早要补。

## 6. 结论

这批文档的最大优点不是“写得长”，而是**已经形成了比较像样的知识组织结构**。对 F-Stack 这种代码量不算小、模块边界又比较分散的项目来说，这一点本身就很重要。

但现在最大的问题也很直接：

**文档已经开始进入“维护期风险区”了。**

表现为：

- 代码升级后，文档版本点没有完全同步
- 接口边界表达开始出现模糊地带
- 多份文档之间重复较多，未来越维护越容易分叉

所以这轮评审的结论不是“这批文档不行”，恰恰相反：

**文档基础是好的，但现在需要从“内容生产”切换到“内容治理”。**

如果只做一次性交付，它已经够用；
如果要长期伴随 F-Stack 版本演进，就需要尽快解决“同步、去重、边界、维护机制”这四个问题。
