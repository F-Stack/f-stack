## 2. 网络连通性问题

### 2.1 问题描述

从 f-stack-client 向 DPDK 网卡 IP 发起 TCP 连接（curl/ab），连接超时失败。

### 2.2 诊断过程

| 步骤 | 测试 | 结果 | 分析 |
|---|---|---|---|
| 1 | f-stack-client curl DPDK 网卡 IP:80 | 超时（132s） | TCP 连接建立失败 |
| 2 | f-stack-client ping DPDK 网卡 IP | 100% 丢包 | 正常——DPDK 网卡 IP 在用户态栈，不响应 ICMP |
| 3 | `ff_ipc netstat -a` | tcp4/tcp6 LISTEN | helloworld 确实在监听 80 端口 |
| 4 | `ff_ipc netstat -i` | f-stack-0 Ipkts=0 | **DPDK 网卡未收到任何包** |
| 5 | `ff_ipc top` | sys=0% | 确认无包处理 |
| 6 | 本机 eth1 ping f-stack-client | 成功（0.3ms） | eth1 与 f-stack-client 网络连通 |
| 7 | `ff_ipc arp -a` | 无 f-stack-client 条目 | f-stack ARP 表中无客户端 MAC |
| 8 | 手动添加 ARP 条目 | 成功 | `ff_arp -s <CLIENT_IP> <CLIENT_MAC>` |
| 9 | 添加 ARP 后重新测试 | 仍然超时 | ARP 不是唯一问题 |
| 10 | `ff_ipc top` (添加 ARP 后) | sys=0%, Ipkts=0 | DPDK 网卡仍未收到包 |

### 2.3 根因分析

**DPDK 网卡（0000:00:09.0 virtio）未收到任何网络包（Ipkts=0），根因是 DPDK 网卡与 f-stack-client 不在同一个二层网络。**

证据：
- 本机 eth1（0000:00:05.0 virtio）可以 ping 通 f-stack-client — eth1 与 f-stack-client 在同一网络
- DPDK 网卡（0000:00:09.0 virtio）Ipkts=0 — DPDK 网卡未收到任何包
- f-stack-client 的 ARP 请求未到达 DPDK 网卡
- 两张 virtio 网卡可能连接到不同的虚拟交换机

### 2.4 替代方案评估

| 方案 | 可行性 | 原因 |
|---|---|---|
| 修复虚拟交换机配置 | 不可行（超出调研范围） | 需要虚拟化环境管理权限 |
| 通过 KNI 接口测试 | 不可行 | KNI 接口未在内核中创建（`ip link show` 无 kni 接口） |
| 通过 f-stack lo0 测试 | 不可行 | f-stack lo0 是用户态栈 loopback，本机 curl 走内核栈无法到达 |
| 通过 kernel_coexist 测试 | 未尝试 | config.ini 中 kernel_coexist=0，需重新编译启用 |

## 3. issue 场景复现结论

### 3.1 复现状态

**未完成。** 由于 DPDK 网卡与 f-stack-client 不在同一个二层网络，无法从 f-stack-client 生成高 CPS 压测流量到达 f-stack 的 DPDK 网卡，issue #1076 描述的 mbuf 耗尽场景无法在本环境中复现。

### 3.2 已验证的部分

虽然没有完成高 CPS 压测，但以下方面已通过实机验证：

1. **helloworld 正常启动**：DPDK 初始化、ipfw 引擎、mbuf 池创建、接口注册、80 端口监听均成功。
2. **ff_ipc 工具正常工作**：netstat/top/arp/ifconfig 均可通过 message_pool 与 f-stack 进程通信，验证了 02 报告中"ff_ipc 不受 pktmbuf_pool 耗尽影响"的结论。
3. **f-stack 协议栈初始化完整**：ipfw2 initialized、tcp_bbr available、TCP Hpts created、syncache 初始化等均正常。

### 3.3 未验证的部分

1. **高 CPS 下 mbuf 池耗尽场景**：无法从外部生成高 CPS 流量。
2. **maxsockets 达限行为**：无法生成足够连接达到 maxsockets 上限。
3. **ipfw limit 规则实机效果**：无法生成 TCP 连接验证 limit 规则。
4. **somaxconn/syncache 达限行为**：同上。

### 3.4 诚实边界

- 02 报告已代码级验证了 maxsockets/ipfw limit/somaxconn/syncache 四个原生机制在 f-stack 中的完整性，代码路径和强制执行链无断裂。
- 01 报告已交叉验证了 FreeBSD 官方文档确认这些机制的行为。
- 实机测试因环境限制未能完成，但代码级结论可靠性高（代码路径完整、UMA zone max 强制执行链验证、ipfw 动态状态跟踪非 stub）。
- 后续如需实机验证，需修复 DPDK 网卡与 f-stack-client 的二层网络连通性（虚拟交换机配置）。
