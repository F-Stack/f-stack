# 03 - 方案设计与备选对比

> f-stack issue #1076: 高 CPS 场景下的并发连接数（CC）限制方案设计
> 设计依据：00-issue原文与需求解析、01-外网调研与交叉验证、02-架构代码探测报告、04-实机测试报告
> 设计时间：2026-08-10
> 状态：方案设计（待用户审核），未落地代码改造

---

## 1. 方案概述

issue #1076 的核心问题：单核高 CPS 场景下，TCP 连接拆除速度跟不上新连接到达速度，活跃连接持续堆积，每个连接的发送/接收缓冲区消耗 mbuf，最终 mbuf 池耗尽导致整个栈无响应（含 ff_ipc 工具，因 f-stack 主循环在 mbuf 耗尽时无法正常运行，间接影响 ff_ipc 消息处理）。

02 报告已代码级确认 FreeBSD 原生的 4 个 CC 限制机制（maxsockets / ipfw limit / somaxconn / syncache）在 f-stack 中**完整可用**，代码路径无断裂。唯一缺失的是 mbuf 池水位背压机制。

基于这些发现，本方案设计三档备选：

| 档位 | 方案 | 代码改动 | 核心机制 | 适用场景 |
|------|------|----------|----------|----------|
| 零代码 | 方案 A | 无 | 调低 maxsockets + ipfw limit + syncache 调优 | 希望零改动快速部署 |
| 小改动 | 方案 B | lib 收包路径 ~20 行 | mbuf 池水位背压，低于阈值丢 SYN | 需要直接保护 mbuf 池 |
| 组合 | 方案 C | 无（或可选方案 B 的小改动） | 方案 A + 方案 B（可选） | 推荐生产部署 |

## 2. 方案 A：零代码方案（纯配置调优）

### 2.1 核心思路

利用 f-stack 已编译的 FreeBSD 原生 CC 限制机制，通过调整 `config.ini` 配置参数 + `ff_ipfw` 规则，在**不改任何代码**的前提下实现连接数限制。

三道防线：

1. **maxsockets（全局硬限）**：限制全局 socket 总数。调低到与 mbuf 池容量匹配的值，使 socket 数先于 mbuf 耗尽。
2. **ipfw limit（per-source 精细限制）**：限制每个源地址的并发连接数，防止单个客户端耗尽全局配额。
3. **syncache（半连接突发限制）**：限制 SYN 攻击/突发场景下的半连接数。

### 2.2 maxsockets 值计算依据

maxsockets 的合理值取决于 mbuf 池容量和每连接 mbuf 消耗。

**mbuf 池容量（静态公式估算）**：

f-stack mbuf 池大小由 `ff_dpdk_if.c:583-593` 的静态公式计算：

```
nb_mbuf = CEIL(
    nb_rx_queue * (max_portid+1) * 2 * RX_QUEUE_SIZE        +
    nb_ports    * (max_portid+1) * 2 * nb_lcores * MAX_PKT_BURST  +
    nb_ports    * (max_portid+1) * 2 * nb_tx_queue * TX_QUEUE_SIZE +
    nb_lcores * MEMPOOL_CACHE_SIZE                             +
    nb_lcores * nb_ports * DISPATCH_RING_SIZE
, 8192)
```

以单进程单核单端口（nb_ports=1, nb_lcores=1, nb_rx_queue=1, nb_tx_queue=1, max_portid=0, 无 KNI）为例：

| 项 | 计算 | mbuf 数 |
|----|------|---------|
| RX 队列描述符 | 1×1×2×512 | 1024 |
| 突发收包缓冲 | 1×1×2×1×32 | 64 |
| TX 队列描述符 | 1×1×2×1×512 | 1024 |
| per-lcore 缓存 | 1×256 | 256 |
| dispatch ring | 1×1×2048 | 2048 |
| **合计** | | 4416 |
| **对齐到 8192** | | **8192** |

**注意**：此 8192 是 mbuf 池的**总容量**，其中相当一部分被 RX/TX 描述符、dispatch ring 等结构性占用（约 4400 个），真正可供连接缓冲区使用的 mbuf 约 3700 个。

issue #1076 用户配置的 `dispatch_ring_size=16384`、`rx_queue_size=4096`、`tx_queue_size=4096` 会显著增大结构性占用：

| 项 | 计算 | mbuf 数 |
|----|------|---------|
| RX 队列 | 1×1×2×4096 | 8192 |
| 突发缓冲 | 1×1×2×1×32 | 64 |
| TX 队列 | 1×1×2×1×4096 | 8192 |
| per-lcore 缓存 | 256 | 256 |
| dispatch ring | 1×1×16384 | 16384 |
| **合计** | | 33088 |
| **对齐到 8192** | | **40960** |

issue 用户场景下 mbuf 池约 32768 个，结构性占用约 33088（已超池，说明用户可能增大了 hugepage 或使用了不同的对齐），但即使池为 32768，可供连接缓冲的 mbuf 也不足 16384（约一半被结构性占用）。

**每连接 mbuf 消耗**：

f-stack 的 socket 发送/接收缓冲区使用 mbuf 簇（cluster），每个 cluster 约 2KB。

| 场景 | sendspace | recvspace | 每连接 mbuf 数 |
|------|-----------|-----------|---------------|
| config.ini 默认（空闲） | 16384 | 8192 | ~12（8+4） |
| 高负载（缓冲区满载） | sendbuf_max=16MB | recvbuf_max=16MB | ~16384（8192+8192） |

**关键矛盾**：maxsockets 默认 262144（256K），但每个连接在高负载下可能消耗数千个 mbuf。256K 连接 × 即使 12 个 mbuf/连接 = 3.1M mbuf，远超 8192~32768 的池容量。

**推荐 maxsockets 计算**：

```
maxsockets = (可用 mbuf 数 × 安全系数 0.7) / 每连接 mbuf 预估值
```

以 mbuf 池 32768、可用 ~16000、每连接空闲 12 mbuf 为例：
```
maxsockets = 16000 × 0.7 / 12 ≈ 933 → 取整 1024
```

以高负载每连接 64 mbuf（含协议栈开销的保守估计）为例：
```
maxsockets = 16000 × 0.7 / 64 ≈ 175 → 取整 256
```

**注意**：maxsockets 限制的是 socket 结构体数量（UMA zone），不直接限制 mbuf 消耗。一个 socket 被创建后，其发送/接收缓冲区的 mbuf 消耗是动态的。maxsockets 作为第一道防线，确保**连接总数不会无上限增长**，但无法精确防止个别连接的缓冲区膨胀导致 mbuf 耗尽。因此需配合 ipfw limit 做 per-source 限制。

### 2.3 配置示例（config.ini 片段）

```ini
[freebsd.boot]
# 全局 socket 数上限。调低到与 mbuf 池匹配。
# 默认 262144 过大，连接先堆积 mbuf 后才触发限制。
# 建议根据 mbuf 池容量和每连接 mbuf 消耗计算（见 2.2 节）。
kern.ipc.maxsockets=4096

# syncache 桶数和桶上限。限制半连接突发。
# hashsize=1024 × bucketlimit=50 = 全局上限 51200（可按需调低）
net.inet.tcp.syncache.hashsize=1024
net.inet.tcp.syncache.bucketlimit=50

[freebsd.sysctl]
# accept 队列深度。限制全连接排队。
# 默认 32768 过大，建议降到与应用 accept 速率匹配的值。
kern.ipc.somaxconn=1024

# TCP 缓冲区。降低缓冲区上限可限制单连接 mbuf 消耗峰值。
# 注意：降低 sendbuf_max/recvbuf_max 会影响大流量传输吞吐，需权衡。
# net.inet.tcp.sendbuf_max=4194304   # 4MB，默认 16MB 的 1/4
# net.inet.tcp.recvbuf_max=4194304
```

### 2.4 ipfw limit 规则示例

```bash
# 限制每个源地址最多 100 个并发 TCP 连接
ff_ipfw add allow tcp from any to <DPDK_NIC_IP> 80 setup limit src-addr 100

# 限制每个源地址+目的端口组合最多 50 个并发连接
ff_ipfw add allow tcp from any to <DPDK_NIC_IP> 80 setup limit src-addr 50 :web_pool

# 全局并发连接数限制（使用 all 掩码，5 元组全部参与）
ff_ipfw add allow tcp from any to <DPDK_NIC_IP> setup limit all 5000
```

**规则持久化**：ff_ipfw 规则需在每次 f-stack 启动后重新加载。可通过启动脚本（如 systemd ExecStartPost 或自定义 init 脚本）自动执行 ff_ipfw 命令。

### 2.5 优点 / 缺点 / 适用场景

**优点**：
- 零代码改动，仅修改配置文件和添加 ff_ipfw 规则。
- 利用 FreeBSD 原生机制，代码路径已验证完整（02 报告）。
- 可快速部署，无需重新编译 f-stack。

**缺点**：
- maxsockets 限制的是 socket 数，不直接限制 mbuf 消耗。不同连接的 mbuf 使用量差异大（空闲 vs 满载缓冲区），难以精确匹配 mbuf 池容量。
- maxsockets 达限后 `socreate()` 返回 `ENOBUFS`，应用程序需正确处理此错误码（拒绝新连接），否则可能异常。
- ipfw limit 的 per-source 限制无法防止大量不同源地址的分布式连接堆积。
- 无法保护 mbuf 池本身——如果连接数未达 maxsockets 但个别连接缓冲区膨胀，mbuf 仍可能耗尽。

**适用场景**：
- 希望零改动快速获得基本的 CC 限制能力。
- 连接模式较均匀（每连接 mbuf 消耗可预估）。
- 应用层能正确处理 `ENOBUFS`。

## 3. 方案 B：小改动方案（mbuf 池水位背压）

### 3.1 核心思路

在 f-stack 收包路径中添加 mbuf 池水位检查。当 `pktmbuf_pool` 可用 mbuf 数低于阈值时，**主动丢弃入站 SYN 包**（不回 SYN-ACK），阻止新连接建立，保护已有连接和系统组件的 mbuf 供应。

这是 FreeBSD 原生没有的机制（FreeBSD 内核依赖 nmbclusters 的 zone max 和应急分配路径），f-stack 作为用户态栈需自行实现。

### 3.2 插入点选择

02 报告分析了 3 个候选插入点：

| 插入点 | 位置 | 优点 | 缺点 |
|--------|------|------|------|
| 1 | `process_packets()` 入口（`ff_dpdk_if.c:2024`） | 协议栈之前，不影响已有连接；粒度可控 | 检查频率高（每包） |
| 2 | `ff_veth_input()` 入口（`ff_dpdk_if.c:1839`） | 知道原始 mbuf 来源 | 与插入点 1 收益相似但更靠后 |
| 3 | TCP SYN 处理入口 | 最精确（只影响新连接） | 需深入 TCP 栈内部，改动大 |

**推荐插入点 1**（`process_packets` 入口），理由：
1. 在协议栈之前，不影响已有连接的数据包处理。
2. 可在 burst 级别检查（每个 burst 检查一次，而非每包检查），降低开销。
3. 对现有代码侵入最小。

### 3.4 阈值确定

阈值 `mbuf_low_watermark` 应满足：
- **足够高**：在 mbuf 真正耗尽前触发，留出余量给已有连接的控制报文（ACK/FIN/RST）和 ff_ipc 内部路径。
- **足够低**：不过度影响正常流量，避免误杀。

建议初始值：
```
mbuf_low_watermark = mbuf 池总容量 × 10%
```
以池 32768 为例，阈值 = 3277（取整 3276 或 4096）。

实际值需通过压测确定：逐步增大 CPS，观察 `rte_mempool_avail` 的变化曲线，找到"连接堆积加速点"对应的可用 mbuf 数。

### 3.5 配置示例

```ini
# config.ini 新增（如需方案 B）
[dpdk]
# mbuf 池低水位阈值。低于此值时丢弃新 SYN 包。
# 0 = 禁用背压（保持当前行为）。
# 推荐值为 mbuf 池总容量的 10%。
mbuf_low_watermark=3276
```

### 3.6 优点 / 缺点 / 适用场景

**优点**：
- 直接保护 mbuf 池，在最底层阻止新连接消耗 mbuf。
- 保护已有连接（只丢 SYN，不丢已建立连接的数据包）。
- 保护 ff_ipc（虽然 ff_ipc 用独立的 message_pool，但 ff_ipc 内部的 ff_mbuf_hdr 分配仍依赖 pktmbuf_pool，背压可间接保护）。
- 阈值可配置，运行时可调（如通过 sysctl 或 ff_ipc 命令）。

**缺点**：
- 需修改 `lib/ff_dpdk_if.c` 代码（约 20 行），需重新编译。
- SYN 包识别增加少量解析开销（可通过 burst 级检查 + 简单标志位优化）。
- 阈值需实测确定，不同场景（不同 mbuf 池大小、不同连接模式）可能需要不同阈值。
- 丢弃 SYN 是"静默丢弃"（不回 RST），客户端会超时重传，可能造成短暂的客户端困惑。可选优化：回 RST 拒绝（但这本身也消耗 mbuf，需权衡）。
- `rte_mempool_avail` 在多 lcore 并发访问时有轻微 cache line 竞争，但因为是只读查询，影响可忽略。

**适用场景**：
- 需要直接保护 mbuf 池，防止耗尽。
- maxsockets 等原生机制的精度不足（连接模式不均匀、个别连接缓冲区膨胀）。
- 愿意接受小量代码改动和编译。

## 4. 方案 C：组合方案（推荐）

### 4.1 核心思路

组合方案 A 和方案 B，形成多层防线：

| 防线 | 机制 | 作用 | 代码改动 |
|------|------|------|----------|
| 第一道 | ipfw limit | per-source 精细限制，防止单客户端耗尽配额 | 无 |
| 第二道 | maxsockets | 全局 socket 数硬限，兜底防止连接总数无上限增长 | 无 |
| 第三道 | syncache + somaxconn | 限制半连接突发和 accept 队列 | 无 |
| 第四道（可选） | mbuf 水位背压 | 最后防线，直接保护 mbuf 池 | 小改动（可选） |

### 4.2 配置示例

**config.ini**：

```ini
[freebsd.boot]
# === CC 限制：全局硬限 ===
# 调低到与 mbuf 池匹配。以 mbuf 池 32768、可用 ~16000、
# 每连接保守 64 mbuf 为例：16000 × 0.7 / 64 ≈ 175 → 取 256。
# 实际值需根据 mbuf 池大小和连接模式调整。
kern.ipc.maxsockets=256

# === syncache：半连接限制 ===
# hashsize=512 × bucketlimit=30 = 全局上限 15360
# （FreeBSD 默认值，对于单核场景已足够）
net.inet.tcp.syncache.hashsize=512
net.inet.tcp.syncache.bucketlimit=30

[freebsd.sysctl]
# === somaxconn：accept 队列 ===
# 降到与应用 accept 速率匹配。128 是 FreeBSD 默认值。
kern.ipc.somaxconn=128

# === TCP 缓冲区（可选，限制单连接 mbuf 峰值） ===
# 降低 sendbuf_max/recvbuf_max 可限制单连接 mbuf 消耗峰值，
# 但会降低大流量吞吐。需根据应用场景权衡。
# net.inet.tcp.sendbuf_max=4194304
# net.inet.tcp.recvbuf_max=4194304
```

**ff_ipfw 规则**（启动脚本加载）：

```bash
#!/bin/bash
# f-stack 启动后加载 ipfw limit 规则

FF_IPFW=/path/to/ff_ipfw
DPDK_NIC_IP=<DPDK_NIC_IP>

# 每个源地址最多 50 个并发连接
$FF_IPFW add allow tcp from any to $DPDK_NIC_IP 80 setup limit src-addr 50

# （可选）全局并发连接数上限
# $FF_IPFW add allow tcp from any to $DPDK_NIC_IP setup limit all 200
```

**mbuf 水位背压（可选，如需方案 B）**：

```ini
# config.ini 新增（如启用方案 B）
[dpdk]
mbuf_low_watermark=3276
```

### 4.3 防线协同逻辑

```
新 SYN 包到达
    │
    ▼
[第一道] ipfw limit 检查
    │ per-source 连接数 > N? → 是 → IP_FW_DENY（丢包）
    │ 否 ↓
[第二道] maxsockets 检查（socreate 时）
    │ 全局 socket 数 > max? → 是 → ENOBUFS（拒绝创建）
    │ 否 ↓
[第三道] syncache 检查
    │ 半连接桶满? → 是 → 丢弃最老 + syncache_pause
    │ zone 耗尽? → 是 → 降级 syncookies 或丢弃 SYN
    │ 否 ↓
[第四道，可选] mbuf 水位背压
    │ pktmbuf_pool 可用 < 阈值? → 是 → 丢弃 SYN（不回 SYN-ACK）
    │ 否 ↓
正常建立连接
```

### 4.4 优点 / 缺点

**优点**：
- 多层防线，纵深防御。任一层失效仍有后续保护。
- 前三道防线零代码改动，立即可用。
- per-source 限制（ipfw limit）+ 全局限制（maxsockets）+ mbuf 保护（背压）覆盖不同维度。
- 可根据实际需求选择性启用第四道（方案 B）。

**缺点**：
- 配置项较多，需根据实际环境调优（mbuf 池大小、连接模式、CPS 目标）。
- maxsockets 值的计算依赖 mbuf 池容量和每连接 mbuf 消耗的估算，需实测量化。
- 如启用方案 B，需代码改动和编译。

## 5. 方案对比表

| 维度 | 方案 A（零代码） | 方案 B（小改动） | 方案 C（组合，推荐） |
|------|------------------|------------------|----------------------|
| 代码改动 | 无 | ~20 行（ff_dpdk_if.c） | 无（或可选方案 B） |
| 重新编译 | 否 | 是（make clean + make） | 否（或可选） |
| 限制维度 | socket 数 + per-source | mbuf 池水位 | 全部维度 |
| 保护 mbuf 池 | 间接（限制连接数） | 直接（水位检查） | 直接 + 间接 |
| 保护已有连接 | 是（新连接被拒） | 是（只丢 SYN） | 是 |
| 保护 ff_ipc | 间接 | 是（保护 mbuf 池） | 是 |
| 精度 | 中（socket 数≠mbuf 消耗） | 高（直接查 mbuf 水位） | 高 |
| 部署难度 | 低（改配置） | 中（改代码+编译） | 低~中 |
| 可运行时调整 | 是（sysctl + ff_ipfw） | 需新增 sysctl/ff_ipc 命令 | 是 |
| 阈值依赖实测 | maxsockets 值需估算 | 水位阈值需压测 | 两者都需 |
| 防止单连接膨胀 | 否 | 是 | 是 |
| 防止分布式堆积 | 部分（maxsockets 兜底） | 是 | 是 |

## 6. 推荐方案及理由

### 6.1 推荐：方案 C（组合方案）

**推荐理由**：

1. **纵深防御**：多层防线互为补充。ipfw limit 精确控制 per-source；maxsockets 全局兜底；syncache/somaxconn 防半连接突发；mbuf 水位背压（可选）直接保护 mbuf 池。任一层失效仍有后续保护。

2. **零代码即可起步**：前三道防线（ipfw limit + maxsockets + syncache/somaxconn）零代码改动，利用 02 报告已验证完整的 FreeBSD 原生机制，可立即部署。

3. **渐进增强**：先部署零代码部分，观察效果。如仍不足，再追加方案 B 的 mbuf 水位背压。避免一次性大改动。

4. **直接对症**：方案 B 的 mbuf 水位背压直接针对 issue #1076 的根因（mbuf 耗尽），在 mbuf 真正耗尽前丢弃新 SYN，是最直接的防护。作为可选的第四道防线，弥补原生机制"限制 socket 数但不限制 mbuf 消耗"的精度不足。

5. **实机测试风险可控**：即使实机测试因环境限制未能完成（04 报告），代码级验证（02 报告）已确认机制 A-D 完整可用，方案 A/C 的前三道防线可靠性高。方案 B 的阈值需实测量化，但不影响代码框架的正确性。

### 6.2 实施建议

| 步骤 | 内容 | 前置条件 |
|------|------|----------|
| 1 | 部署方案 A（调低 maxsockets + ipfw limit + syncache 调优） | 无 |
| 2 | 压测观察效果：是否还出现 mbuf 耗尽 | 需修复测试环境网络连通性 |
| 3 | 如步骤 2 仍有 mbuf 耗尽，实现方案 B（mbuf 水位背压） | 代码评审 + clean build + 单测 |
| 4 | 压测确定 mbuf_low_watermark 阈值 | 需可从外部生成高 CPS 流量 |
| 5 | 部署方案 C 完整配置 | 步骤 1-4 完成 |

### 6.3 交用户审核事项

以下决策点需用户确认：

1. **maxsockets 目标值**：本方案给出计算方法（mbuf 池容量 × 0.7 / 每连接 mbuf 数），但具体值需用户根据实际 mbuf 池大小和连接模式确定。是否接受估算值 256（保守）或 4096（宽松）？

2. **是否启用方案 B（代码改动）**：方案 B 需修改 `lib/ff_dpdk_if.c`（约 20 行）。是否接受代码改动？还是仅用方案 A 的零代码部分？

3. **TCP 缓冲区是否调低**：降低 `sendbuf_max`/`recvbuf_max` 可限制单连接 mbuf 峰值，但影响吞吐。是否接受此权衡？

4. **ff_ipfw 规则的 per-source 限制值 N**：取决于应用的客户端连接模式。N=50？100？需用户根据业务确定。

5. **是否需修复测试环境以完成实机验证**：04 报告记录的 DPDK 网卡与 f-stack-client 二层网络不连通问题，是否需修复以完成方案验证？
