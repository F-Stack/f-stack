## 1. 调研总结

### 1.1 issue #1076 核心问题回顾

用户使用 f-stack 构建透明代理应用，单核 ~13k CPS 压测时观察到：

1. CPU 达 100%，TCP 连接拆除跟不上新连接到达速度。
2. 活跃连接持续堆积，每个连接持有发送/接收缓冲区 mbuf。
3. mbuf 池耗尽，整个栈无响应（含 ff_ipc 工具）。

用户诉求：达到性能极限时**主动丢包（优雅降级 / backpressure）**，而非整体无响应。

### 1.3 关键发现

1. **FreeBSD 原生 4 个 CC 限制机制在 f-stack 中完整可用**（02 报告代码级确认）：
   - maxsockets：UMA zone max 强制执行链完整（`uma_core.c:4461` → `zone_alloc_limit`），config.ini `[freebsd.boot]` 段可配。
   - ipfw limit：工具端编译完整、内核端 O_LIMIT 处理完整、动态状态跟踪（`ip_fw_dynamic.c`）完整非 stub。达限行为 = `IP_FW_DENY`（丢包）。
   - somaxconn：backlog 截断完整，半连接队列满丢弃最老，全连接队列 `3*qlimit/2` 检查。
   - syncache：桶满丢弃最老 + syncache_pause，zone 耗尽降级 syncookies。

2. **mbuf 池水位背压是唯一缺失项**：收包路径（`ff_dpdk_if.c process_packets`）无 `rte_mempool_avail` 检查。mbuf 池大小为静态公式计算，不考虑运行时并发连接数。

3. **ff_ipc 使用独立的 message_pool**：ff_ipc 使用独立的 `message_pool`（`FF_MSG_POOL`），不直接依赖 `pktmbuf_pool`。但 f-stack 主循环在 mbuf 耗尽时可能无法到达 ff_ipc 消息处理路径（`process_msg_ring`），间接导致 ff_ipc 工具不可用——这与 issue #1076 描述的"ff_ipc netstat 也不可用"现象一致。`ff_mbuf_gethdr()` 从 FreeBSD mbuf UMA zone 分配（`m_gethdr`），而非从 DPDK `pktmbuf_pool` 分配。

4. **issue 用户的配置矛盾**：`maxsockets=1048576`（1M）远超 mbuf 池可支撑的连接数（单进程 mbuf 池约 8K~32K）。这是 mbuf 先于 socket 耗尽的直接原因。

5. **实机测试因环境限制未完成**：DPDK 网卡与 f-stack-client 不在同一二层网络（两块 virtio 网卡连不同虚拟交换机），无法从外部生成高 CPS 流量。代码级结论可靠性高，但实机效果待验证。

## 2. FreeBSD 原生 CC 限制机制可用性结论

### 2.1 四个机制的完整性确认

| 机制 | 代码完整性 | 官方文档确认 | 实机验证 | 综合结论 |
|------|-----------|-------------|----------|----------|
| maxsockets | 完整 | 是 | 未完成 | **可用**（代码级确认） |
| ipfw limit | 完整 | 是 | 未完成 | **可用**（代码级确认） |
| somaxconn | 完整 | 是 | 未完成 | **可用**（代码级确认） |
| syncache | 完整 | 是 | 未完成 | **可用**（代码级确认） |

### 2.2 代码级验证要点

- **maxsockets**：`uma_zone_set_max(socket_zone, maxsockets)` 在 SYSINIT 阶段设置 UMA zone 上限。分配时 `zone_alloc_item()`（`uma_core.c:4461`）检查 `uz_max_items`，超限返回 NULL → `socreate()` 返回 `ENOBUFS`。config.ini `[freebsd.boot]` 段经 `kern_setenv` → `TUNABLE_INT_FETCH` → `uma_zone_set_max` 完整加载。

- **ipfw limit**：`ff_ipfw` 工具（`tools/ipfw/ipfw2.c`）编译 limit 语法完整。内核端 `O_LIMIT` 规则（`ip_fw2.c:2937`）调用 `ipfw_dyn_install_state()`。动态状态跟踪（`ip_fw_dynamic.c`）的分配（`dyn_alloc_parent/ipv4_state`）、查找、插入、aging（`dyn_tick` 每秒调用）全部完整。达限时 `DPARENT_COUNT(p) >= limit` → 返回 NULL → `IP_FW_DENY`。

- **somaxconn**：`solisten_proto()` 将 backlog 截断到 `V_somaxconn`（`uipc_socket.c:1538`）。半连接队列满时丢弃最老（`:1280-1293`）。全连接队列通过 `3 * sol_qlimit / 2` 检查限制（`:1030`）。config.ini `[freebsd.sysctl]` 段运行时设置。

- **syncache**：`syncache_init()` 通过 tunable 设置 hashsize/bucketlimit，`uma_zone_set_max(zone, hashsize * bucket_limit)` 设置全局上限。桶满时丢弃最老 + `syncache_pause`（:377-384）。zone 耗尽时丢弃最老重试 → 降级 syncookies 或丢弃 SYN（:1584-1611）。

### 2.3 实机测试的环境限制说明

实机测试未能完成高 CPS 压测和原生机制效果验证，原因：

- **DPDK 网卡（0000:00:09.0 virtio）Ipkts=0**：与 f-stack-client 不在同一二层网络，f-stack-client 的 ARP 请求和 TCP SYN 无法到达 DPDK 网卡。
- **根因**：两块 virtio 网卡连接到不同的虚拟交换机，需虚拟化环境管理权限修复。
- **替代方案均不可行**：KNI 接口未创建、f-stack lo0 无法从本机内核栈访问、kernel_coexist 需重新编译。

实机未验证的部分：
1. 高 CPS 下 mbuf 池耗尽场景复现。
2. maxsockets 达限行为（ENOBUFS）。
3. ipfw limit 规则实机效果。
4. somaxconn/syncache 达限行为。

**可靠性说明**：代码级验证已确认完整的强制执行链（UMA zone max、ipfw 动态状态、队列检查逻辑），代码路径和实现均无断裂。实机测试未完成是环境限制，而非机制本身的问题。02 报告的代码级结论可靠性高。

## 3. 推荐方案

### 3.1 推荐方案 C（组合方案）

详见 `03-方案设计与备选对比.md`。核心结构：

| 防线 | 机制 | 作用 | 代码改动 |
|------|------|------|----------|
| 第一道 | ipfw limit | per-source 精细限制 | 无 |
| 第二道 | maxsockets | 全局 socket 数硬限 | 无 |
| 第三道 | syncache + somaxconn | 半连接突发 + accept 队列 | 无 |
| 第四道（可选） | mbuf 水位背压 | 直接保护 mbuf 池 | 小改动（可选） |

推荐理由：纵深防御、零代码可起步、渐进增强、对症下药。

### 3.2 实施步骤

| 步骤 | 内容 | 前置条件 | 代码改动 |
|------|------|----------|----------|
| 1 | 部署前三道防线（调低 maxsockets + ipfw limit + syncache/somaxconn 调优） | 无 | 无 |
| 2 | 压测观察效果 | 需修复测试环境网络连通性 | 无 |
| 3 | 如仍有 mbuf 耗尽，实现方案 B（mbuf 水位背压） | 代码评审 + clean build + 单测 | ~20 行 |
| 4 | 压测确定 mbuf_low_watermark 阈值 | 可从外部生成高 CPS 流量 | 无 |
| 5 | 部署完整方案 C | 步骤 1-4 完成 | 无 |

### 3.3 配置示例

**config.ini**（前三道防线，零代码）：

```ini
[freebsd.boot]
# 全局 socket 数上限。调低到与 mbuf 池匹配。
# 计算：可用 mbuf × 0.7 / 每连接 mbuf 数。
# 示例：mbuf 池 32768、可用 ~16000、每连接 64 mbuf → 256。
kern.ipc.maxsockets=256

# syncache 半连接限制（FreeBSD 默认值，单核足够）
net.inet.tcp.syncache.hashsize=512
net.inet.tcp.syncache.bucketlimit=30

[freebsd.sysctl]
# accept 队列深度
kern.ipc.somaxconn=128
```

**ff_ipfw 规则**（启动后加载）：

```bash
# 每个源地址最多 50 个并发连接
ff_ipfw add allow tcp from any to <DPDK_NIC_IP> 80 setup limit src-addr 50
```

**mbuf 水位背压（可选，方案 B）**：

```ini
# config.ini 新增（如启用方案 B）
[dpdk]
mbuf_low_watermark=3276   # mbuf 池总容量的 10%，需实测调整
```

## 4. 诚实边界

### 4.1 实机测试未完成的部分

| 项目 | 状态 | 原因 |
|------|------|------|
| 高 CPS 下 mbuf 耗尽场景复现 | 未完成 | DPDK 网卡与 f-stack-client 二层网络不通 |
| maxsockets 达限行为验证 | 未完成 | 无法生成足够连接 |
| ipfw limit 规则实机效果 | 未完成 | 无法生成 TCP 连接 |
| somaxconn/syncache 达限行为 | 未完成 | 同上 |
| mbuf 水位背压阈值量化 | 未完成 | 需高 CPS 压测环境 |

### 4.2 方案的适用条件和局限

1. **maxsockets 值依赖估算**：maxsockets 限制的是 socket 数，不直接限制 mbuf 消耗。每连接 mbuf 消耗差异大（空闲 ~12 个 vs 满载 ~16384 个），maxsockets 值需实测量化。本方案给出计算方法但具体值需用户确认。

2. **ipfw limit 无法防止分布式连接堆积**：大量不同源地址的连接各自不超 per-source 限制，但全局总量仍可能堆积。需配合 maxsockets 全局兜底。

3. **方案 B 的阈值需实测**：`mbuf_low_watermark` 的合理值取决于 mbuf 池大小和连接模式，需压测确定。本方案给出"池容量 10%"的初始建议，但未经实机验证。

4. **代码级结论 ≠ 实机效果**：02 报告确认了代码路径完整性，但实机运行时可能受其他因素影响（如 UMA zone 在用户态的内存分配行为、ipfw 动态状态在高并发下的性能）。建议在修复测试环境后完成实机验证。

5. **ff_ipc 的 mbuf 依赖**：02 报告确认 ff_ipc 使用独立的 `message_pool`，但 ff_ipc 内部路径中 `ff_mbuf_gethdr()` 仍从 `pktmbuf_pool` 分配 `ff_mbuf_hdr`。因此 mbuf 耗尽时 ff_ipc 仍会受影响。方案 B 的 mbuf 水位背压可间接保护此路径。

## 5. 后续建议

### 5.1 如需实机验证

需修复的网络环境：

| 问题 | 修复方法 | 所需权限 |
|------|----------|----------|
| DPDK 网卡与 f-stack-client 不在同一二层网络 | 修复虚拟交换机配置，使两块 virtio 网卡连同一交换机；或将 f-stack-client 迁移到 DPDK 网卡所在网络 | 虚拟化环境管理权限 |
| KNI 接口未创建 | 启用 `kernel_coexist=1` 重新编译，或配置 KNI | 重新编译 + 配置 |

修复后可执行的验证：
1. 从 f-stack-client 用 `ab` 或 `wrk` 向 DPDK 网卡 IP 发高 CPS 流量。
2. 观察 `ff_ipc traffic` 中 mbuf 使用量随 CPS 的变化。
3. 逐步调低 maxsockets，观察连接达限时的 `ENOBUFS` 行为。
4. 添加 ipfw limit 规则，观察 per-source 限制效果。
5. 如启用方案 B，观察 mbuf 水位低于阈值时 SYN 被丢弃的行为。

### 5.3 交用户审核的事项

以下决策点需用户确认后方可推进：

1. **maxsockets 目标值**：接受保守值 256，还是宽松值 4096，还是根据实际 mbuf 池计算？需用户提供 mbuf 池实际大小（可通过 `ff_ipc traffic` 观察）。

2. **是否启用方案 B（代码改动）**：方案 B 需修改 `lib/ff_dpdk_if.c`（约 20 行）。用户是否接受代码改动？还是仅用零代码方案？

3. **TCP 缓冲区是否调低**：降低 `sendbuf_max`/`recvbuf_max` 可限制单连接 mbuf 峰值，但影响吞吐。是否接受此权衡？

4. **ipfw limit 的 per-source 限制值 N**：取决于客户端连接模式。N=50？100？需用户根据业务确定。

5. **是否修复测试环境以完成实机验证**：04 报告记录的 DPDK 网卡二层网络问题，是否需修复以验证方案效果？

6. **是否更新 issue-ana 条目**：当前 issue-ana 中 #1076 条目为初步结论（根因 mbuf 耗尽、建议水平扩展/增大内存/降低 hz/应用层限制）。本轮调研深化了结论（原生 CC 机制可用、三档方案设计），是否需更新 issue-ana？
