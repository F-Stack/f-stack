# 01 - 外网调研与交叉验证

> 本文档汇总对 issue #1076（高 CPS 下 CC 限制）的外网调研结果，交叉验证 FreeBSD 原生机制、其他用户态栈方案、DPDK backpressure 实践。
> 调研时间：2026-08-10
> 调研方式：web_search + web_fetch（FreeBSD 官方手册、nginx 调优文档、技术博客、GitHub）

## 1. FreeBSD 原生 CC 限制机制文档验证

### 1.1 maxsockets（全局 socket 数硬限制）

**官方文档/资料来源**：
- FreeBSD 手册页 / 社区文档：`kern.ipc.maxsockets` 用于设定系统最大可开启的 socket 数目。
- 站长资讯中心（FreeBSD 6.0 架设管理与应用）："这是用来设定系统最大可以开启的 socket 数目。如果您的服务器会提供大量的 FTP 服务，而且常快速地传输一些小档案，您也许会发现常传输到一半就中断。"
- 该值必须在系统一开机就设定好（`/boot/loader.conf`），对应 f-stack 的 `config.ini [freebsd.boot]` 段。

**行为**：
- 当 socket 数达 maxsockets 上限时，`socreate()` 返回 `ENOBUFS` 或 `ENFILE`。
- 这是 UMA zone 级别的硬限制（`uma_zone_set_max`）。

**与 f-stack 的对应**：
- f-stack 的 `config.ini` 支持 `kern.ipc.maxsockets` 配置（通过 `[freebsd.boot]` 段）。
- issue #1076 中用户已设 `maxsockets=1048576`（1M），这个值非常大，意味着 socket 结构体不太可能先于 mbuf 耗尽。

**关键结论**：maxsockets 是有效的全局 socket 数限制，但 issue #1076 的问题在于 maxsockets 设得太大（1M），而 mbuf 池容量远小于支撑 1M 个活跃 TCP 连接所需的 mbuf 数（每个连接 sendspace 64KB + recvspace 64KB = 128KB mbuf，1M 连接需 ~128GB mbuf）。**调低 maxsockets 到与 mbuf 池容量匹配的值**可能是最简单的原生方案。

### 1.2 ipfw limit 规则（per-source 连接数限制）

**官方文档来源**：FreeBSD 手册页 IPFW(8) — https://man.freebsd.org/cgi/man.cgi?ipfw

**语法**：
```
limit {src-addr | src-port | dst-addr | dst-port} N [:flowname]
```

**行为**（官方文档确认）：
- 防火墙只允许 N 个连接具有规则中指定的相同参数集合。
- 当已有 N 个匹配的动态规则存在时，**新的连接请求将不会创建新的动态规则**，因此不会通过状态检查（即被拒绝/丢弃）。
- `limit` 暗含了**隐式 `check-state`**，对所有数据包生效。
- 动态规则有有限生命周期（由 sysctl 变量控制），每次匹配刷新。
- 动态规则匹配相同 5 元组（协议、源/目的地址、源/目的端口）的数据包。

**`setup` 关键字**：
- 匹配 SYN=1, ACK=0 的 TCP 包（TCP 连接建立的第一个包）。
- 是 `tcpflags syn,!ack` 的简写。
- 通常与 `limit` 配合使用来控制新连接的建立。

**典型用法**：
```bash
# 限制每个源地址最多 5 个并发 TCP 连接
ipfw add allow tcp from any to any setup limit src-addr 5

# SSH 示例（限制每源地址 2 个连接）
ipfw add allow tcp from any to me 22 setup limit src-addr 2
```

**与 f-stack 的对应**：
- f-stack 已编译 ipfw（`FF_IPFW=1`），工具端为 `ff_ipfw`。
- f-stack 的 `lib/ff_dpdk_if.c` 支持 `handle_ipfw_msg()`（FF_IPFW_GET/FF_IPFW_SET 消息通道）。
- 理论上可通过 `ff_ipfw add allow tcp from any to any setup limit src-addr N` 实现 per-source 限制。
- **待验证**：动态状态跟踪（`ip_fw_dynamic.c`）在用户态栈中是否完整工作。

**关键结论**：ipfw limit 是 FreeBSD 原生的 per-source/per-dst 连接数限制机制，语法和行为有官方文档确认。f-stack 已编译 ipfw 代码，理论可用，但需实机验证动态状态跟踪在用户态的完整性。

### 1.3 somaxconn（accept 队列限制）

**官方文档来源**：
- nginx FreeBSD tuning 文档（https://nginx.org/en/docs/freebsd_tuning.html）："Here are 192 unaccepted connections and most likely new coming connections are discarding. Although the limit is 128 connections, FreeBSD allows receiving 1.5 times connections than the limit before it starts to discard the new connections."
- FreeBSD 默认 `SOMAXCONN=128`（`sys/socket.h`）。

**行为**：
- 限制 listen backlog（accept 队列深度）。
- FreeBSD 允许接收 1.5 倍 somaxconn 的连接后才开始丢弃。
- 可通过 `sysctl kern.ipc.somaxconn` 运行时修改。

**局限**：
- 仅限制 accept 队列深度（全连接排队），**不限制已 accept 的活跃连接总数**。
- 对于 issue #1076 的场景（连接已建立但拆除慢导致堆积），somaxconn 无法直接解决，因为问题出在已 accept 连接的 mbuf 消耗，而非 accept 队列。

**关键结论**：somaxconn 可作为辅助手段限制突发连接，但对 issue #1076 的核心问题（活跃连接堆积导致 mbuf 耗尽）作用有限。

### 1.4 nmbclusters（网络 mbuf 簇限制）

**官方文档/资料来源**：
- 站长资讯中心："为了增加 FreeBSD 的网络性能，可以增加 NMBCLUSTERS 的值，这个设置决定网络界面接收数据时的缓冲 mbuf 的大小。"
- CSDN（FreeBSD 系统性能调优）："kern.ipc.nmbclusters 可以调整用来增加系统愿意申请的网络 mbuf 的数量。每个 cluster 大概 2K 的内存，所以值 1024 代表保留 2M 内核内存作为网络缓冲区。"

**与 f-stack 的对应**：
- f-stack 不使用内核 nmbclusters，而是使用 DPDK 的 `rte_mempool`（`pktmbuf_pool`）。
- DPDK mbuf 池大小由 `ff_dpdk_if.c` 中的计算公式决定（基于 RX/TX queue size、burst size、dispatch ring size、KNI 等）。
- FreeBSD 内核中 nmbclusters 耗尽会导致 `m_getcl()` 返回 NULL，进而丢包或拒绝新连接；f-stack 的 DPDK mbuf 池耗尽时行为类似（`rte_pktmbuf_alloc()` 返回 NULL），但**无主动的水位检查和背压机制**。

**关键结论**：FreeBSD 内核的 nmbclusters 机制在 f-stack 中对应为 DPDK mbuf 池，但 f-stack 缺少内核态 nmbclusters 耗尽时的主动背压（在接近耗尽时丢弃新 SYN）。

## 2. 其他用户态网络栈方案

### 2.1 mTCP

**资料来源**：
- mTCP GitHub / 论文 / 技术博客
- OSCHINA（走进 mTCP）："此时用户线程在 `mtcp_epoll_wait()` 就能读取到该事件，然后调用 `mtcp_epoll_accept()` 从 Control 队列读取到连接信息，就能完成连接的建立。"
- CSDN（mTCP 性能优化秘籍）："根据应用需求调整 mbuf_size 和 mbuf_pool_size 参数。"

**mTCP 的连接管理机制**：
- 每个 CPU core 有独立的 connection pool（连接池），避免了共享 fd 空间的限制。
- 连接建立通过 `mtcp_epoll_accept()` 从 per-core Control 队列读取。
- mbuf 池大小可配置（`mbuf_pool_size`）。

**CC 限制/背压机制**：
- mTCP 的 per-core connection pool 有固定大小，达限时 `mtcp_epoll_accept()` 不再返回新连接（类似 accept 队列满）。
- 这是一种隐式的 CC 限制：连接池满 = 不再 accept 新连接 = 背压。
- 但 mTCP 论文中未明确提到 mbuf 水位检查或主动丢包机制。

**与 f-stack 的对比**：
- f-stack 使用 FreeBSD 完整协议栈，连接管理依赖 socket/UMA 机制，而非 per-core pool。
- f-stack 的 maxsockets 类似于 mTCP 的 connection pool size，但 maxsockets 是全局限制而非 per-core。
- mTCP 的架构更简单（per-core 独立栈），f-stack 的 FreeBSD 栈更完整但更复杂。

### 2.2 Seastar

**资料来源**：
- GitHub / 技术博客
- CSDN（在 Vmware 上运行 Seastar）："seastar 是目前为数不多的活跃的 DPDK user_level stack。"
- 腾讯云（千万并发连接下如何保障网络性能）："通过调研先选择了 seastar（排除了 mTCP、LwIP 等）。"

**Seastar 的连接管理机制**：
- Seastar 采用 share-nothing 架构，每个 core 独立运行一个 reactor。
- 连接由 per-core 的 TCP 栈管理，连接数受限于 per-core 内存。
- 未找到明确的 CC 限制/背压机制的文档。

**与 f-stack 的对比**：
- Seastar 的 share-nothing 架构天然隔离了 per-core 资源，单个 core 的连接耗尽不会影响其他 core。
- f-stack 的 native-mt 改造（多线程栈实例）也实现了类似的 per-thread 隔离，但共享 UMA zone（maxsockets 是全局的）。

## 3. DPDK mbuf 池 backpressure 实践

### 3.1 DPDK rte_mempool 查询能力

**资料来源**：
- DPDK 文档 / 技术博客
- CSDN（DPDK 24.11.3）："内存池结构：已分配 32，空闲 8160。"
- 知乎（DPDK mempool 和 mbuf 的理解）：rte_mempool 中每个 rte_mbuf 的大小固定，在 mempool 创建时初始化。

**可用的查询 API**：
- `rte_mempool_avail(mp)` — 返回池中可用对象数。
- `rte_mempool_in_use_count(mp)` — 返回已使用对象数。
- `rte_mempool_count(mp)` — 返回池中总对象数。

**社区实践**：
- 未找到 DPDK 社区中标准的"mbuf 池水位检查 + 主动丢包"的 backpressure 方案。
- DPDK 的设计理念是"预分配足够大的池"，而非运行时背压。
- 部分应用在应用层实现自己的水位检查（周期性检查 `rte_mempool_avail`，低于阈值时拒绝新连接）。

**与 f-stack 的对应**：
- f-stack 可在收包路径（`ff_dpdk_if.c`）中检查 `rte_mempool_avail(pktmbuf_pool)`，低于阈值时丢弃入站 SYN 包。
- 这是一个 f-stack 特有的小改动方案（需修改 lib 代码）。

### 3.2 DPDK mbuf 耗尽的现有行为

- 当 mbuf 池耗尽时，`rte_pktmbuf_alloc()` 返回 NULL。
- f-stack 收包路径中，如果 mbuf 分配失败，通常会跳过该包（丢包），但**不会主动通知 TCP 栈**。
- 这意味着 mbuf 耗尽时，新 SYN 包被静默丢弃，但**已建立的连接仍持有 mbuf**，栈可能因缺少 mbuf 而无法处理控制消息（包括 ff_ipc 通信）。

## 5. 交叉验证结论

### 5.1 FreeBSD 原生机制可用性评估

| 机制 | 官方文档确认 | f-stack 代码存在 | 预期效果 | 实机验证优先级 |
|---|---|---|---|---|
| maxsockets | ✅ | ✅（UMA zone max） | 限制全局 socket 数，调低可防 mbuf 耗尽 | 高（最简单） |
| ipfw limit | ✅（语法+行为） | ✅（FF_IPFW=1） | per-source 连接数限制，达限丢包 | 高（精确控制） |
| somaxconn | ✅ | ✅ | 仅限 accept 队列，不限制活跃连接 | 低（辅助） |
| syncache | ✅ | ✅ | 仅限半连接数 | 低（辅助） |

### 5.2 推荐方案方向

1. **零代码方案（纯配置）**：
   - 调低 `maxsockets` 到与 mbuf 池容量匹配的值（如 mbuf 池可支撑 N 个活跃连接，则 maxsockets = N × 安全系数 0.7）。
   - 配合 `ipfw limit` 做 per-source 精细限制。
   - 优点：无需改代码，仅改 config.ini + ff_ipfw 规则。
   - 风险：maxsockets 限制的是 socket 数，不直接限制 mbuf 消耗（不同连接的 mbuf 使用量不同）。

2. **小改动方案（mbuf 水位背压）**：
   - 在 `ff_dpdk_if.c` 收包路径中检查 `rte_mempool_avail(pktmbuf_pool)`。
   - 低于阈值时丢弃入站 SYN 包（不回 SYN-ACK）。
   - 优点：直接防止 mbuf 耗尽，保护所有系统组件。
   - 风险：需修改 lib 代码，需确定合理阈值。

3. **组合方案**：
   - maxsockets 作为全局硬限 + ipfw limit 作为 per-source 精细限制 + 可选 mbuf 水位背压作为最后防线。

### 5.3 诚实边界

- **ipfw limit 的动态状态跟踪在用户态栈中的完整性**：外网文档确认了语法和行为，但用户态栈是否完整实现动态状态表（`ip_fw_dynamic.c`）需代码级验证（由 02 报告确认）。
- **maxsockets 的 UMA zone max 在用户态是否真正强制执行**：需代码级验证 `uma_zone_set_max` 在 f-stack UMA 实现中的逻辑（由 02 报告确认）。
- **mbuf 水位背压的阈值确定**：需要实机测试确定合理的 mbuf 池水位阈值（由 04 报告提供数据）。
- 外网未找到 DPDK 社区标准的 backpressure 方案，说明这是一个应用层需自行解决的问题，f-stack 需自行设计。
