## 3. 发现的问题

### 3.1 [低] 文档 02 中 config.ini 行号引用偏差

文档 02 的 §1.3 表格中引用：
- `config.ini:346` → `kern.ipc.maxsockets=262144`，实际在 `config.ini:327`
- `config.ini:348-349` → `syncache.hashsize/bucketlimit`，实际在 `config.ini:329-330`

**影响**：不影响核心结论（配置值和配置段正确，仅行号偏差），但可能误导读者定位。

**建议**：将行号修正为 327 和 329-330。

### 3.2 [中] 文档 03 和 05 中关于 ff_ipc mbuf 依赖的描述不准确

**文档 03** §1 概述中写道：
> "含 ff_ipc 工具，因 ff_ipc 内部收包路径仍依赖 pktmbuf_pool 分配 ff_mbuf_hdr"

**文档 05** §1.3 关键发现第 3 点写道：
> "ff_ipc 内部路径中 ff_mbuf_gethdr() 仍从 pktmbuf_pool 分配 ff_mbuf_hdr"

**实际代码验证结果**：

`ff_mbuf_gethdr()`（`ff_veth.c:467-488`）调用 `m_gethdr(M_NOWAIT, MT_DATA)` 分配 mbuf。`m_gethdr()` 是 FreeBSD mbuf API，从 **FreeBSD UMA zone（mbuf zone）** 分配，**不是从 DPDK `pktmbuf_pool` 分配**。`m_extadd()` 只是将外部数据 buffer 挂载到 mbuf 上，也不从 `pktmbuf_pool` 分配。

ff_ipc 工具端（`tools/compat/ff_ipc.c`）仅使用 `message_pool`（`rte_mempool_lookup(FF_MSG_POOL)`），不调用 `ff_mbuf_gethdr`，不依赖 `pktmbuf_pool`。

f-stack 主进程端的 `handle_msg()`（`ff_dpdk_if.c:2347-2397`）处理 ff_ipc 消息时也不调用 `ff_mbuf_gethdr`，全程使用 `message_pool`。

**影响**：文档 02 的结论（"ff_ipc 不受 pktmbuf_pool 耗尽影响"）是**正确的**。文档 03 和 05 试图修正文档 02 的结论，但修正本身引入了新的不准确描述——声称 `ff_mbuf_gethdr` 从 `pktmbuf_pool` 分配，实际并非如此。

issue #1076 中用户报告 "ff_ipc netstat 也不可用"的现象，可能的原因是：
1. 当 mbuf 池（pktmbuf_pool）耗尽时，f-stack 主循环可能因无法收包（`rte_eth_rx_burst` 后 `ff_veth_input` 中 `ff_mbuf_gethdr` 调用 `m_gethdr` 失败）而影响整体进程运行，间接影响 ff_ipc 消息处理（主循环无法到达 `process_msg_ring` 调用点）。
2. 或者 FreeBSD mbuf UMA zone 本身耗尽（而非 DPDK pktmbuf_pool），导致 `m_gethdr` 失败。

但这与 "ff_mbuf_gethdr 从 pktmbuf_pool 分配" 是不同的因果链。

**建议**：
- 文档 03 §1 概述中删除 "因 ff_ipc 内部收包路径仍依赖 pktmbuf_pool 分配 ff_mbuf_hdr" 的说法，或改为 "因 f-stack 主循环在 mbuf 耗尽时可能无法正常运行，间接影响 ff_ipc 消息处理"。
- 文档 05 §1.3 第 3 点修正为：ff_ipc 使用独立的 `message_pool`，不直接依赖 `pktmbuf_pool`。但 f-stack 主循环在 mbuf 耗尽时可能无法到达 ff_ipc 消息处理路径（`process_msg_ring`），间接导致 ff_ipc 工具不可用。

### 3.3 [低] 文档 03 mbuf 池大小估算中的结构性占用超出池容量

文档 03 §2.2 中对 issue #1076 用户场景的估算：
- 合计 33088 个 mbuf
- 对齐到 8192 → 32768

但 33088 > 32768，文档自己也指出"已超池，说明用户可能增大了 hugepage 或使用了不同的对齐"。这个估算存在矛盾（合计已超对齐后的池大小），说明 `RTE_ALIGN_CEIL` 是向上对齐而非向下，33088 应对齐到 40960（下一个 8192 的倍数）。文档对此的处理是"即使池为 32768"的假设性叙述，但这个假设本身不成立。

**影响**：不影响方案设计核心结论（maxsockets 需调低），但估算数字可能误导。

**建议**：修正为 `RTE_ALIGN_CEIL(33088, 8192) = 40960`（向上对齐到 8192 的倍数）。

### 3.4 [信息] 实机测试未完成——已如实说明

文档 04 如实记录了实机测试因 DPDK 网卡与 f-stack-client 二层网络不连通而未能完成高 CPS 压测。这是环境限制，文档已明确标注"未完成"和"诚实边界"，处理方式合规。
