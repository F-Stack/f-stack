# Issue #631 根因分析与结论

## 1. 完整调用链追踪

### 1.1 ff_shutdown 入口

**文件**: `lib/ff_syscall_wrapper.c:1862-1891`

```c
int ff_shutdown(int s, int how) {
    struct shutdown_args sa = { .s = s, .how = how };
    if ((rc = sys_shutdown(curthread, &sa)))
        goto kern_fail;
    return (rc);
kern_fail:
    ff_os_errno(rc);
    return (-1);
}
```

`ff_shutdown` 直接调用 FreeBSD 的 `sys_shutdown`，`curthread` 是 F-Stack 用户态线程。

### 1.2 kern_shutdown

**文件**: `freebsd/kern/uipc_syscalls.c:1328-1355`

```c
int kern_shutdown(struct thread *td, int s, int how) {
    error = getsock(td, s, &cap_shutdown_rights, &fp);
    if (error == 0) {
        so = fp->f_data;
        error = soshutdown(so, how);
        if (error == ENOTCONN &&
            td->td_proc->p_osrel < P_OSREL_SHUTDOWN_ENOTCONN)
            error = 0;                    // ← ENOTCONN 被转为 0
        fdrop(fp, td);
    }
    return (error);
}
```

**关键**: `p_osrel` 在 F-Stack 用户态为 0（`lib/ff_init_main.c` 的 `proc0_init()` 中 `p->p_osrel = osreldate` 被 `#if 0` 禁用，导致 `proc0.p_osrel` 保持零初始化值 0），而 `P_OSREL_SHUTDOWN_ENOTCONN = 1100077`（`freebsd/sys/param.h:100`）。因此 `0 < 1100077` 为真，`ENOTCONN` 总是被转为 0。

### 1.3 soshutdown

**文件**: `freebsd/kern/uipc_socket.c:3673-3683`

```c
int soshutdown(struct socket *so, enum shutdown_how how) {
    error = so->so_proto->pr_shutdown(so, how);  // 分派到 udp_shutdown
    return (error);
}
```

FreeBSD 15.0 的 `soshutdown` 完全委托给协议的 `pr_shutdown` 回调，不再自行处理 sorflush/socantsendmore。

### 1.4 udp_shutdown（核心函数）

**文件**: `freebsd/netinet/udp_usrreq.c:1741-1778`

```c
int udp_shutdown(struct socket *so, enum shutdown_how how) {
    SOCK_LOCK(so);
    if (!(so->so_state & SS_ISCONNECTED))
        error = ENOTCONN;        // ← 未连接 UDP 返回 ENOTCONN
    else
        error = 0;
    SOCK_UNLOCK(so);

    switch (how) {
    case SHUT_RD:
        sorflush(so);            // ← 无论是否连接，都执行 sorflush
        break;
    case SHUT_RDWR:
        sorflush(so);
        /* FALLTHROUGH */
    case SHUT_WR:
        socantsendmore(so);
    }
    return (error);              // ← 返回 ENOTCONN（但 sorflush 已执行）
}
```

**关键**: `sorflush(so)` 在 `switch` 语句中，**不受 ENOTCONN 错误影响**。即使返回 ENOTCONN，`sorflush` 仍然被执行。

### 1.5 sorflush

**文件**: `freebsd/kern/uipc_socket.c:3688-3718`

```c
void sorflush(struct socket *so) {
    socantrcvmore(so);                          // ← 设置 SBS_CANTRCVMORE
    error = SOCK_IO_RECV_LOCK(so, SBL_WAIT | SBL_NOINTR);
    sbrelease(so, SO_RCV);                      // ← 释放接收缓冲区
    SOCK_IO_RECV_UNLOCK(so);
}
```

### 1.6 socantrcvmore

**文件**: `freebsd/kern/uipc_sockbuf.c:393-414`

```c
void socantrcvmore_locked(struct socket *so) {
    so->so_rcv.sb_state |= SBS_CANTRCVMORE;    // ← 设置标志
    sorwakeup_locked(so);                       // ← 唤醒阻塞的 recv
}
```

### 1.7 soreceive_dgram（接收路径检查）

**文件**: `freebsd/kern/uipc_socket.c:3486-3545`

```c
int soreceive_dgram(struct socket *so, ...) {
    SOCKBUF_LOCK(&so->so_rcv);
    while ((m = so->so_rcv.sb_mb) == NULL) {
        if (so->so_error) { ... }
        if (so->so_rcv.sb_state & SBS_CANTRCVMORE ||  // ← 检查标志
            uio->uio_resid == 0) {
            SOCKBUF_UNLOCK(&so->so_rcv);
            return (0);                                // ← 返回 0 (EOF)
        }
        if ((so->so_state & SS_NBIO) ||
            (flags & (MSG_DONTWAIT|MSG_NBIO))) {
            SOCKBUF_UNLOCK(&so->so_rcv);
            return (EWOULDBLOCK);
        }
        // ... block waiting for data ...
    }
}
```

**关键**: 当 `SBS_CANTRCVMORE` 被设置且接收缓冲区为空时，`soreceive_dgram` 返回 0（EOF）。

## 2. 根因结论

### 2.1 为什么 issue #631 在当前版本不复现

1. `ff_shutdown(SHUT_RD)` → `udp_shutdown` 返回 `ENOTCONN`，但**仍然调用 `sorflush`**
2. `sorflush` → `socantrcvmore` 设置 `SBS_CANTRCVMORE` + `sbrelease` 释放缓冲区
3. `kern_shutdown` 将 `ENOTCONN` 转为 0（因 `p_osrel=0 < P_OSREL_SHUTDOWN_ENOTCONN`）
4. 后续 `ff_recvfrom` → `soreceive_dgram` 检查 `SBS_CANTRCVMORE` → 返回 0（EOF）

### 2.2 与 Linux 内核的差异

| 行为 | F-Stack (FreeBSD 15.0) | Linux 内核 |
|------|----------------------|-----------|
| shutdown(SHUT_RD) 返回值 | 0（ENOTCONN 被吞） | -1 (ENOTCONN) |
| sorflush 是否执行 | 是 | 无等效操作 |
| SBS_CANTRCVMORE 是否设置 | 是 | 否 |
| 后续 recvfrom 行为 | 返回 0 (EOF) | 继续接收数据 |

Linux 内核对未连接 UDP 的 `shutdown(SHUT_RD)` 返回 `ENOTCONN` 且不修改 socket 状态，因此继续接收数据。F-Stack (FreeBSD) 的 `udp_shutdown` 即使返回 `ENOTCONN` 也执行 `sorflush`，使后续接收返回 EOF。

### 2.3 与旧版 F-Stack 的可能差异

Issue #631 提交于 2021 年，当时 F-Stack 可能使用 FreeBSD 11.0（推测，未提供版本信息）。可能的原因：
1. 旧版 `soreceive_dgram` 对 `SBS_CANTRCVMORE` 的检查不完善
2. 旧版 `soshutdown` 的逻辑与 15.0 不同（15.0 完全委托给 `pr_shutdown`）
3. 旧版 F-Stack 的 `p_osrel` 处理可能不同

## 3. 修复方案

**无需修复。** 当前 F-Stack 1.26 + FreeBSD 15.0 代码库中 `ff_shutdown(SHUT_RD)` 在 UDP 套接字上工作正常。
