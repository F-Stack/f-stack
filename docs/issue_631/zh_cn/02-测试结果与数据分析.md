# Issue #631 测试结果与数据分析

## 1. T1: F-Stack UDP SHUT_RD（3 次重复测试）

### 测试条件
- 服务器: F-Stack UDP socket 绑定 <DPDK_NIC_IP>:15310
- 客户端: f-stack-client 发送 20 个 UDP 包，每 200ms 一个
- shutdown 触发: 接收 3 个包后调用 `ff_shutdown(sockfd, 0)`

### Run #1

```
[RECV] pkt #1: 58 bytes (loop=145319447)
[RECV] pkt #2: 58 bytes (loop=146766310)
[RECV] pkt #3: 58 bytes (loop=148217886)
[SHUTDOWN] calling ff_shutdown(sockfd, 0)...
[SHUTDOWN] ret=0 errno=11 (Resource temporarily unavailable)
[EOF] recvfrom returned 0 (loop=148217887 phase=1)
[RESULT] PASS: recvfrom returned 0 (EOF) after shutdown(how=0)
```

### Run #2

```
[RECV] pkt #3: 58 bytes (loop=74895251)
[SHUTDOWN] ret=0 errno=11 (Resource temporarily unavailable)
[RESULT] PASS: recvfrom returned 0 (EOF) after shutdown(how=0)
```

### Run #3

```
[RECV] pkt #3: 58 bytes (loop=75043986)
[SHUTDOWN] ret=0 errno=11 (Resource temporarily unavailable)
[RESULT] PASS: recvfrom returned 0 (EOF) after shutdown(how=0)
```

### 分析

- `ff_shutdown(sockfd, 0)` 返回 0（成功）
  - errno=11 (EAGAIN) 是前一次 recvfrom 的残留值，非 shutdown 的返回错误
- shutdown 后**下一次** `ff_recvfrom` 立即返回 0（EOF）
- 3 次测试结果完全一致
- **结论: SHUT_RD 在 F-Stack UDP 上工作正常**

## 2. T2: F-Stack UDP SHUT_WR

### 测试条件
- 同 T1，但 `--how=1` (SHUT_WR)

### 结果

```
[RECV] pkt #1: 58 bytes (loop=72049292)
[RECV] pkt #2: 58 bytes (loop=73492851)
[RECV] pkt #3: 58 bytes (loop=74935717)
[SHUTDOWN] calling ff_shutdown(sockfd, 1)...
[SHUTDOWN] ret=0 errno=11 (Resource temporarily unavailable)
[SEND-POST-SHUTDOWN] sendto ret=-1 errno=32 (Broken pipe)
[RESULT] PASS: no data received after 5000 idle loops (shutdown(how=1) effective)
```

### 分析

- `ff_shutdown(sockfd, 1)` 返回 0（成功）
- `ff_sendto` 在 SHUT_WR 后返回 -1, errno=32 (EPIPE) — **send 侧正确关闭**
- **结论: SHUT_WR 在 F-Stack UDP 上工作正常**

## 3. T5: 内核栈 UDP SHUT_RD（基线对比）

### 测试条件
- 服务器: Linux kernel UDP socket 绑定 0.0.0.0:15310
- 客户端: 本机 Python 发送 20 个 UDP 包到 127.0.0.1:15310，每 200ms 一个

### 结果

```
[MAIN] kernel-stack test, shutdown_how=0
[MAIN] bound to 0.0.0.0:15310
[RECV] pkt #1: 58 bytes
[RECV] pkt #2: 58 bytes
[RECV] pkt #3: 58 bytes
[SHUTDOWN] calling shutdown(sockfd, 0)...
[SHUTDOWN] ret=-1 errno=107 (Transport endpoint is not connected)
[POST-SHUTDOWN] received 58 bytes after shutdown (post=1)
[POST-SHUTDOWN] received 58 bytes after shutdown (post=2)
[POST-SHUTDOWN] received 58 bytes after shutdown (post=3)
[POST-SHUTDOWN] received 58 bytes after shutdown (post=4)
[POST-SHUTDOWN] received 58 bytes after shutdown (post=5)
[RESULT] FAIL: still receiving data after shutdown(how=0)
```

### 分析

- `shutdown(sockfd, 0)` 返回 -1, errno=107 (ENOTCONN)
- shutdown 后**继续接收** 5 个数据包
- **结论: Linux 内核栈对未连接 UDP 的 SHUT_RD 不生效（返回 ENOTCONN 并继续接收）**

## 4. 对比总结

| 测试 | shutdown 返回值 | 后续 recvfrom 行为 | 结论 |
|------|----------------|-------------------|------|
| F-Stack UDP SHUT_RD | 0 (成功) | 返回 0 (EOF) | ✅ 正确 |
| F-Stack UDP SHUT_WR | 0 (成功) | sendto 返回 EPIPE | ✅ 正确 |
| Linux kernel UDP SHUT_RD | -1 (ENOTCONN) | 继续接收数据 | ❌ 不生效 |

**关键差异**: F-Stack (FreeBSD 15.0) 的 `udp_shutdown` 即使返回 `ENOTCONN`，仍然调用 `sorflush` 设置 `SBS_CANTRCVMORE`，使后续 `recvfrom` 返回 EOF。而 Linux 内核返回 `ENOTCONN` 后不修改 socket 状态，继续接收数据。

F-Stack 的行为实际上比 Linux 内核更符合用户预期（shutdown 后不再接收），且 `ff_shutdown` 返回 0（成功）而非 ENOTCONN。
