# 02 · 线程基础设施现状与差距

> 本文基于代码事实素材 `_material_code.md` 第 2 节，所有关键论断带 `file:line` 证据。外网与代码冲突以代码为准。

---

## 0. 结论先行

- f-stack 语境下"多线程"目前有两条现实基础：
  1. **LD_PRELOAD adapter 层多 worker**（`adapter/syscall/`）—— 通过 `FF_THREAD_SOCKET`（RTC per-thread `sc`）与 `FF_MULTI_SC`（类 `SO_REUSEPORT`）两个编译宏，把 N 个用户线程/进程映射到 N 个后端 f-stack 进程实例。**底层协议栈仍是多进程**，这是**推荐路线**的基础。
  2. **`lib/ff_thread.c` 的 `ff_pthread_create`** —— 只把父线程 `struct thread` 直接赋给子线程 TLS（共享同一 `td`），**隐患大、非独立上下文**。
- **唯一已被 per-thread 化的核心内核状态是 `curthread`（TLS `pcurthread`）**（`lib/ff_compat.c:59`）。其余进程级单例（`pcpup`、`msg_iov_tmp`、`lcore_conf` 等）**未 per-thread 化**，是"一进程多线程共栈"的硬缺口。
- "每线程独立 struct thread 上下文"的正确姿势已存在：`ff_adapt_user_thread_add`（`lib/ff_compat.c:96`），供 LD_PRELOAD 用。

---

## 1. TLS 当前线程指针 `pcurthread`（已 per-thread 化）

- `lib/ff_compat.c:59`：`__thread struct thread *pcurthread = NULL;` —— **TLS**，每线程独立。
- `amd64/include/pcpu.h:41`：`extern __thread struct thread *pcurthread;`；`:52-64` `__curthread_ff()` 返回 `pcurthread`，`#define curthread __curthread_ff()`（`:63`）。
- **含义**：FreeBSD 内核代码里所有 `curthread` 引用，在 f-stack 里都解析为 TLS `pcurthread`。这是**唯一**被 per-thread 化的核心内核状态。
- 符号导出：`ff_api.symlist:76 pcurthread`，`:79-82` 导出 4 个 thread 适配函数。

## 2. `lib/ff_thread.c` 全文分析（共 52 行）—— `ff_pthread_create` 隐患

| 元素 | file:line | 说明 |
|---|---|---|
| `extern __thread struct thread *pcurthread;` | `ff_thread.c:7` | 引用 TLS |
| `struct thread_data { start_routine; arg; struct thread *parent; }` | `:9-13` | 传父线程 thread 指针 |
| `ff_set_thread(other)` → `pcurthread = other` | `:15-18` | 直接覆盖 TLS |
| `ff_start_routine()` | `:20-30` | 新 pthread 里 `ff_set_thread(p_data->parent)`（`:26`） |
| `ff_pthread_create()` | `:32-46` | `data->parent = pcurthread;`（`:44`）后 `pthread_create(..., ff_start_routine, data)`（`:45`） |
| `ff_pthread_join()` | `:48-51` | 透传 `pthread_join` |

**隐患（明确）**：`ff_start_routine` 把**父线程的 `struct thread` 指针直接赋给子线程的 TLS**（`:26`），并非为子线程新建独立 `struct thread`。因此多个子线程会**共享同一个 `struct thread`（td）**，同时进协议栈时该 `td` 上的字段（如 `td_retval`、错误码、信号状态等）会互相踩踏。**结论：`ff_pthread_create` 不适合用于"多线程共栈"，仅在不并发进栈时勉强可用。**

## 3. `ff_adapt_user_thread_add`（每线程独立 thread，正确姿势）

`lib/ff_compat.c` LD_PRELOAD 模式用户线程上下文 API：

| 函数 | file:line | 说明 |
|---|---|---|
| `ff_adapt_user_thread_add(parent)` | `:96-120` | parent==NULL 时用 `&thread0`（`:102-103`）；`malloc(sizeof(struct proc))`（`:106`）+ `ff_adapt_user_proc_add`（`:111`）→ **为用户线程新建独立 struct thread** |
| `ff_adapt_user_thread_exit(td)` | `:122-128` | 释放 |
| `ff_switch_curthread(new)` | `:131-140` | 保存旧 `pcurthread`、切到 new、返回旧值 |
| `ff_restore_curthread(old)` | `:142-148` | 恢复 |
| `ff_init_thread0()` | `:156-160` | `pcurthread = &thread0;` |

**对比结论**：`ff_adapt_user_thread_add`（`:96`）是"每线程独立 thread 上下文"的正确实现（LD_PRELOAD 用）；`ff_thread.c` 的 `ff_pthread_create`（共享父 td）是老式、隐患大的做法。多线程模式若走"每线程独立栈上下文"路线，应以 `ff_adapt_user_thread_add` 为范式，而非 `ff_pthread_create`。

## 5. adapter 多 worker 结构（推荐路线的现实基础）

### 5.1 `main_stack_thread_socket.c`（kqueue 版，共 262 行）

| 元素 | file:line | 说明 |
|---|---|---|
| `#define MAX_WORKERS 128` | `:25` | worker 上限 |
| `pthread_t hworker[MAX_WORKERS]` | `:26` | worker 线程数组 |
| `pthread_spinlock_t worker_lock` | `:27` | 串行化 worker 启动 |
| `loop()` | `:75-212` | 每 worker 独立 `socket()`（`:90`）→ `bind`（`:110`）→ `listen`（`:117`）→ `kqueue`（`:125`）→ 事件循环（`:144-206`）。**每线程各自一套 fd/kq** |
| `main()` | `:214-262` | `worker_num = atoi(argv[1])`（`:224`）；`pthread_spin_lock` 串行化启动（`:229,252`）；`pthread_create(&hworker[i], NULL, loop, &i)`（`:232`）；绑核 `lcore_id = 2+i` + `pthread_setaffinity_np`（`:239-250`） |

关键注释 `/* socket will init adapter, so unlock after socket */`（`:98`）—— `socket()` 里会 `ff_adapter_init`，spinlock 保证各 worker 初始化串行。

### 5.2 `main_stack_epoll_thread_socket.c`（epoll 版）

- 结构同上（`:19-27`）。`loop()`（`:68+`）：`socket(AF_INET, SOCK_STREAM | SOCK_FSTACK, 0)`（`:79`，**显式 OR SOCK_FSTACK**）；`setsockopt(..., SO_REUSEPORT, ...)`（`:92`）；`epoll_create(512|SOCK_FSTACK)`（`:117`）。每 worker 独立 epfd/sockfd + SO_REUSEPORT 多线程 accept。

**含义**：LD_PRELOAD adapter 已提供"用户 APP 多线程/多 worker"的完整可运行示例，每 worker 通过 `SO_REUSEPORT` + `FF_PROC_ID` 映射到独立后端 f-stack 进程实例。这是本次多线程需求最低风险的落地基础。
