# 04 — 多线程架构方案与选型

> 本文由方案设计子 agent（design-writer）撰写。所有技术论断以 `_material_code.md` 的 `file:line` 代码证据为准，外网素材（`_material_web.md`）仅作交叉参考；冲突一律以代码为准。
> 关联素材：`_material_code.md` 第 1/2/3/5/7 节、`_material_web.md` 第 2/4 节。

## 0. 结论先行

1. **必须先区分两个根本不同的概念**：
   - **【概念 A：应用侧多线程调用 f-stack API】** —— 用户 APP 自己是多线程（如 pthread + libuv），在多个线程里调用 f-stack 的 socket/epoll 接口。**这是 issue #430 的真实场景，f-stack 通过 LD_PRELOAD adapter 层已经支持**（`FF_THREAD_SOCKET` / `FF_MULTI_SC` / `SO_REUSEPORT`）。
   - **【概念 B：协议栈本身的多线程运行模型】** —— 在**一个进程内开多个线程共同跑同一份 FreeBSD 用户态协议栈**（多线程共享 socket table / route table / pcpu 等）。**f-stack 原生不支持**：其原生并发模型是「多进程 run-to-completion（RTC），一进程一 lcore，share-nothing」（`ff_dpdk_if.c:123` `lcore_conf` 全局单例；`_material_code.md` 第 0.1 条）。
2. **推荐选型：优先完善「选项 (c) 多进程 + LD_PRELOAD adapter 多 worker」，慎改协议栈为共享多线程（选项 b）**。理由见第 5 节：选项 (c) 复用现有 share-nothing 无锁架构、改造量最小、多进程模式零回归、故障隔离最好；选项 (b) 需改动 FreeBSD 大量全局状态（`pcpup`/`msg_iov_tmp`/socket namespace 等），回归风险极高。
3. **选项 (a)「单进程多 lcore 线程 + 每线程独立栈实例（thread-per-core share-nothing）」是中长期可选的进阶路线**：它保留 share-nothing 免锁的核心优势，只是把「多进程」换成「单进程多线程」，可减少跨进程共享内存 attach 的复杂度，但仍需把 `lcore_conf` / ring flag / `pcpup` 等 per-thread 化（第 3 节），改造量中等，非本轮首选。

## 1. 两个概念的严格区分（避免需求错位）

| 维度 | 概念 A：应用侧多线程调用 API | 概念 B：协议栈多线程运行模型 |
|---|---|---|
| 谁是多线程 | 用户 APP（业务线程） | 协议栈内部（收发包 / TCP 状态机） |
| f-stack 现状 | **已支持**（adapter LD_PRELOAD 层） | **原生不支持** |
| 代码证据 | `adapter/syscall/main_stack_thread_socket.c`（每 worker 独立 socket/kqueue/绑核）；`ff_hook_syscall.c:226-227` `__FF_THREAD sc`；`ff_compat.c:96-120` `ff_adapt_user_thread_add` 为每线程建独立 `struct thread` | `ff_dpdk_if.c:123` `lcore_conf` 单例；`ff_freebsd_init.c:69` `pcpup` 单例；`ff_syscall_wrapper.c:225-226` `msg_iov_tmp` 故意非 `__thread` |
| issue #430 归属 | ✅ 属于此类（libuv + pthread），**已完备** | ✗ 与 #430 无关 |
| 外网印证 | mTCP「应用线程 + 独立 TCP 线程同核配对」（`_material_web.md` 4.1） | f-stack 官方资料一致指向 share-nothing 多进程，**未检索到官方「单进程多线程共享栈」设计**（`_material_web.md` 2.3） |

> **结论**：issue #430「pthread + libuv + 组合 socket 标志位」属于**概念 A**，当前代码已完备处理（`ff_syscall_wrapper.c:672-684` `linux2freebsd_socket_flags` + `ff_socket:943` + `ff_accept4:1679` 走同一转换；`ff_hook_syscall.c:363-366` 剥离标志位判领地）。因此「多线程支持」需求的主体应落在概念 A 的进一步完善，而非贸然实现概念 B。

## 2. 三种架构选项定义

### 选项 (a)：单进程多 lcore 线程 + 每线程独立栈实例（thread-per-core, share-nothing）

- 一个进程内起 N 个绑核线程（DPDK lcore 即 pthread 封装，`_material_web.md` 3），**每个线程持有自己独立的 `lcore_conf` / rx-tx queue / 协议栈实例**，线程间不共享协议栈状态，仅共享进程地址空间（少量只读全局 + DPDK mempool）。
- 本质是把现有「多进程 share-nothing」平移为「多线程 share-nothing」，RSS 仍按 queue → 线程亲和分流。
- 关键改造点：`lcore_conf`（`ff_dpdk_if.c:123`）→ per-thread；`pcpup`（`ff_freebsd_init.c:69`）→ per-thread；`msg_iov_tmp/msg_iovlen_tmp`（`ff_syscall_wrapper.c:225-226`）→ 恢复 `__thread`；ring 保持 SC/SP 但每线程独立 ring（`ff_dpdk_if.c:619`）；`ff_pthread_create`（`ff_thread.c:44`）改为每线程 `ff_adapt_user_thread_add`（`ff_compat.c:96`）建独立 `struct thread`。

### 选项 (b)：线程共享单栈 + 细粒度锁（shared-stack + fine-grained locking）

- 一个进程内多线程共享**同一份**协议栈（同一 socket table / route table / tcbinfo / callout wheel），靠 FreeBSD 原生锁（mtx/rwlock/epoch）保护并发。
- f-stack 保留了 FreeBSD 的锁原语（`ff_glue.c` 模拟），但**运行时是单线程 RTC，锁基本零竞争**（`_material_code.md` 第 3 节结论）。改成真正多线程共享会让这些锁进入真实竞争路径，且必须先修复所有非锁保护的进程级单例（`pcpup`、`msg_iov_tmp`、`lcore_conf`）。

### 选项 (c)：多进程 + LD_PRELOAD adapter 多 worker（现状可完善，推荐）

- 底层维持「多进程 share-nothing」协议栈，**应用侧多线程/多进程通过 adapter 层映射到 N 个后端 f-stack 进程实例**：
  - `FF_THREAD_SOCKET`：每线程一个 RTC per-thread `sc`（`ff_hook_syscall.c:227` `static __FF_THREAD struct ff_so_context *sc`）；
  - `FF_MULTI_SC`：类 `SO_REUSEPORT`，`scs[SOCKET_OPS_CONTEXT_MAX_NUM]`（`ff_hook_syscall.c:241`，`SOCKET_OPS_CONTEXT_MAX_NUM=32`，`ff_socket_ops.h:45`）；
  - worker → 后端进程映射：`sc = ff_attach_so_context(worker_id % nb_procs)`（`ff_hook_syscall.c:3297`）。
- 示例已存在：`main_stack_thread_socket.c`（kqueue 多 worker + `pthread_setaffinity_np` 绑核 `lcore_id=2+i`，`:239-250`）、`main_stack_epoll_thread_socket.c`（epoll + `SO_REUSEPORT` + `socket(..., SOCK_STREAM|SOCK_FSTACK, 0)` `:79-92`）。

## 3. 逐项 trade-off 对比

> 评分区间：低 / 中 / 高。改造量与回归风险越低越好；性能/隔离越高越好。

| 维度 | (a) 单进程多线程 + 独立栈实例 | (b) 共享单栈 + 细粒度锁 | (c) 多进程 + adapter 多 worker（现状） |
|---|---|---|---|
| **锁开销** | 低（share-nothing，栈内无跨线程锁竞争；DPDK ring 保持 SC/SP） | **高**（socket/route/tcbinfo/callout 全部进入真实锁竞争；FreeBSD 锁在 RTC 下本零竞争，`_material_code.md` §3 结论） | 低（各后端进程独立无锁，与现状一致） |
| **cache 亲和** | 高（每线程绑核 + queue 亲和，per-lcore 数据） | 低（共享数据结构跨核 false-sharing、cacheline 抖动） | 高（进程绑核 + RSS queue 亲和，现状即如此，`init_lcore_conf` `:415-448`） |
| **隔离性（状态）** | 高（每线程独立协议栈实例，状态互不可见） | 低（同一 socket namespace，fd 跨线程共享） | 高（每后端进程独立 FreeBSD 实例，`_material_web.md` 2.1 share-nothing） |
| **故障隔离** | 中（同进程，一线程崩溃/踩内存可能拖垮整进程） | 低（同进程 + 共享状态，一处损坏全局受影响） | **高**（进程级隔离，一个 worker/后端崩溃不影响其他进程） |
| **RSS 分发** | 直接复用（queue → 线程亲和，改 `queueid` 语义为 per-thread index，`init_lcore_conf:434-448`） | 复杂（多线程共享队列需 MC/MP ring，破坏现有 `RING_F_SC_DEQ` 前提，`ff_dpdk_if.c:619`） | 直接复用（现状 RSS queue = proc_id，`init_lcore_conf:434-448`；reta 表 `set_rss_table:750`） |
| **内存占用** | 中（每线程一份栈实例状态，但共享进程地址空间/mempool，比多进程略省共享内存 attach 开销） | 低（单份栈状态最省） | 中偏高（每后端进程一份完整栈 + 共享大页 mempool/ring，现状） |
| **改造量** | 中（`lcore_conf`/`pcpup`/`msg_iov_tmp` per-thread 化 + ring per-thread + `ff_pthread_create` 改独立 thread，见 `_material_code.md` §7.2） | **高**（除上述 per-thread 单例外，还需审计并锁化全部协议栈全局路径，风险面最大） | **低**（adapter 已有 `FF_THREAD_SOCKET`/`FF_MULTI_SC`/`SO_REUSEPORT` 与示例，主要是完善/补文档/补测试） |
| **回归风险（多进程模式）** | 中（需保证默认路径逐字节不变，per-thread 化以 opt-in 编译/配置隔离） | **高**（改动深入协议栈核心，多进程 RTC 路径极易被牵连） | **极低**（不动 lib 协议栈核心，多进程默认行为不变） |
| **issue #430 覆盖** | 覆盖（但属过度设计） | 覆盖（但属过度设计） | **已覆盖**（#430 场景即 adapter 多线程 socket，`_material_code.md` §4 已闭环） |

## 4. 业界参考模型交叉对比

### 4.1 mTCP（`_material_web.md` 4.1，NSDI 2014）
- 模型：**每个应用线程配一个独立 TCP 线程，二者绑定同一 CPU 核心（thread-per-core）**。之所以用独立 TCP 线程而非耦合，是为不破坏基于时间的操作（TCP 重传超时）。
- 隔离：所有 API 传入 `mctx`（per-thread context），各线程独立管理资源；避免共享 accept 队列（Linux 共享 accept 队列扩展性差的反面教材）。
- 对应关系：mTCP 的「应用线程 + 独立 TCP 线程同核配对」在 f-stack 语境下最接近 **选项 (a)** 的思想；而 f-stack adapter 的 `FF_THREAD_SOCKET`（每 worker 独立 `sc` + 绑核）与 mTCP 的 per-thread `mctx` 精神一致，只是 f-stack 的「TCP 线程」实体是后端进程（选项 c）。

### 4.2 Seastar（`_material_web.md` 4.3，社区常识，未深抓）
- thread-per-core + share-nothing，每核一个 reactor，核间消息传递（无锁共享）。
- 对应 **选项 (a)** 的理想形态。**诚实边界**：Seastar 官方资料本轮未深入抓取，此处仅作方向性参考，不作为强论断。

> 业界共识（mTCP/Seastar）均为 **thread-per-core + share-nothing**，**没有采用「多线程共享单栈 + 细粒度锁」（选项 b）**。这从侧面佐证选项 (b) 不是用户态高性能栈的主流方向。

## 5. 推荐选型与理由

### 5.1 推荐

- **首选（本轮 spec 落点）：选项 (c) —— 完善多进程 + LD_PRELOAD adapter 多 worker。**
- **中长期进阶（可选，非本轮实现）：选项 (a) —— 单进程多线程 + 每线程独立栈实例（thread-per-core share-nothing）。**
- **不推荐：选项 (b) —— 线程共享单栈 + 细粒度锁。**

### 5.2 理由

1. **零回归优先**：选项 (c) 完全不动 lib 协议栈核心，多进程默认行为逐字节不变，符合「多进程模式零回归」硬约束（plan.md §5.7）。选项 (b) 深入改动 `pcpup`/socket namespace/锁路径，多进程 RTC 极易被牵连（回归风险高）。
2. **issue #430 已闭环**：#430 的真实诉求（pthread + libuv 多线程调用）在选项 (c) 下已被现有代码完备支持（`_material_code.md` §4.3），无需实现选项 (b) 即可满足一手用户需求。
3. **share-nothing 是 f-stack 与业界的共同基因**：f-stack 官方（`_material_web.md` 2.1）、mTCP、Seastar 均为 share-nothing / thread-per-core。选项 (b) 的「共享 + 锁」违背这一基因，且 f-stack 现有 DPDK ring 用 `RING_F_SC_DEQ`（`ff_dpdk_if.c:619`）/`RING_F_SP_ENQ|RING_F_SC_DEQ`（`:671`）是**反多线程**的单生产单消费前提，选项 (b) 必须改 MC/MP，破坏面最大。
4. **选项 (a) 作为进阶**：若未来确需「单进程内多线程」（如减少多进程共享内存 attach 复杂度、简化部署），选项 (a) 保留 share-nothing 免锁优势，只需把 `lcore_conf`/`pcpup`/`msg_iov_tmp` per-thread 化 + ring per-thread（`_material_code.md` §7.2 最小改造清单），改造量中等且回归可控（以 opt-in 隔离），优于选项 (b)。

### 5.3 选型决策要点小结

| 决策问题 | 结论 | 依据 |
|---|---|---|
| 是否需要实现「协议栈多线程共享」满足 #430？ | **否** | #430 属概念 A，adapter 已支持（`_material_code.md` §4.3） |
| 本轮 spec 主推哪个方案？ | 选项 (c) 完善 adapter 多 worker | 零回归 + 已有基础设施 + 已闭环 #430 |
| 是否彻底排除单进程多线程？ | 否，作为选项 (a) 中长期进阶 | share-nothing 可平移，改造量中等 |
| 是否推荐共享单栈 + 锁？ | **不推荐** | 回归风险高、违背 share-nothing、破坏 SC/SP ring 前提 |
