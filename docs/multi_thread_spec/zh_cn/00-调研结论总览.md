## 1. 核心裁决（TL;DR）

1. **f-stack 原生并发模型 = 多进程 run-to-completion（RTC）、一进程一 lcore、share-nothing**，不是"单进程多线程共享协议栈"。直接证据：`lcore_conf` 全局单例（`ff_dpdk_if.c:123`）、每进程 EAL coremask 单 bit（`ff_config.c:1150-1153` proc_mask）、RSS 队列 = proc_id（`ff_dpdk_if.c:434-448`）。

2. **必须区分两个根本不同的"多线程"概念**（详见 `04`）：
   - **概念 A — 应用侧多线程调用 f-stack API**（pthread + libuv 等）：**f-stack 已通过 LD_PRELOAD adapter 层支持**（`FF_THREAD_SOCKET` / `FF_MULTI_SC` / `SO_REUSEPORT`）。
   - **概念 B — 协议栈本身多线程运行模型**（一进程多线程共享同一份 FreeBSD 栈）：**f-stack 原生不支持**，改造需动 FreeBSD 大量全局单例，回归风险极高。

3. **【issue #430 结论】** GitHub Issue #430 "SOCK_STREAM [Solved] + Multi Thread (Pthread)"（incapdns，2019-08-25，Closed）反映的是**概念 A**（libuv + pthread 多线程 + 组合 socket 标志位 `SOCK_STREAM|SOCK_NONBLOCK|SOCK_CLOEXEC`）。**当前代码已完备闭环**：
   - `linux2freebsd_socket_flags()`（`ff_syscall_wrapper.c:672-684`）统一转换 NONBLOCK/CLOEXEC；
   - `ff_socket()`（`:943`）与 `ff_accept4()`（`:1679`）走同一转换路径；
   - hook 层 `fstack_territory()`（`ff_hook_syscall.c:363-366`）先剥离 4 类标志位再判 STREAM/DGRAM。
   - 外网评论区因 GitHub 动态加载 + API 限流未抓到维护者原文（诚实标注，见 `03`），但代码侧已双向坐实该场景被支持。

4. **推荐选型**（详见 `04`/`07`）：
   - **首选（本轮 spec 落点）：选项 (c) 完善「多进程 + LD_PRELOAD adapter 多 worker」** —— 零回归、复用现有 share-nothing 无锁架构、已闭环 #430。
   - **中长期进阶（可选）：选项 (a) 单进程多线程 + 每线程独立栈实例（thread-per-core share-nothing）**。
   - **不推荐：选项 (b) 共享单栈 + 细粒度锁** —— 违背 share-nothing 基因、破坏 `RING_F_SC_DEQ`/`SP` 前提、回归风险最高。

## 3. 若要真正实现"一进程多线程跑协议栈"的最小改造清单（按危险度，详见 `05`/`07`）

| 改造点 | file:line | 危险度 |
|--------|-----------|--------|
| `msg_iov_tmp/msg_iovlen_tmp` 恢复 `__thread` | `ff_syscall_wrapper.c:225-226` | 低（注释已预留） |
| `ff_pthread_create` 改为每线程独立 `struct thread` | `ff_thread.c:44` / `ff_compat.c:96` | 中 |
| `pcpup` per-thread 化 | `ff_freebsd_init.c:69` / `pcpu.h:44-50` | 高 |
| `lcore_conf` per-thread queue 配置 | `ff_dpdk_if.c:123,400-464` | 高 |
| dispatch_ring/msg_ring SC/SP → 每线程独立 ring 或 MC/MP | `ff_dpdk_if.c:618` | 高 |
