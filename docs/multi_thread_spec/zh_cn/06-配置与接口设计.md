# 06 — 配置与接口设计

> 本文由方案设计子 agent（design-writer）撰写。所有技术论断以 `_material_code.md` 的 `file:line` 代码证据为准，外网素材仅作交叉参考；冲突以代码为准。
> 关联素材：`_material_code.md` §1.1/§1.2/§2.4/§2.5/§2.6/§7；对应架构选型见本目录 `04-多线程架构方案与选型.md`。

---

## 0. 结论先行

1. **不建议给 `proc_type` 新增 `thread` 枚举值**：`proc_type` 直接透传给 DPDK EAL（`ff_config.c:1167-1169` `--proc-type=<proc_type>`），其合法值受 DPDK 约束，现校验仅允许 `primary/secondary/auto`（`ff_config.c:1316-1321`）。塞入 `thread` 会与 DPDK 语义冲突，破坏兼容。
2. **推荐方案（对齐 04 文档首选选项 c）**：多线程能力通过 **adapter 层编译宏（`FF_THREAD_SOCKET` / `FF_MULTI_SC`）+ 环境变量（`FF_PROC_ID`）+ `config.ini` 现有多进程配置**表达，**不新增 `config.ini` 段、不改 `ff_config.h` 结构、不破坏 `ff_api.h`**，天然向后兼容、opt-in。
3. **若未来实现选项 (a)（单进程多线程独立栈）**：建议**新增独立配置项**（如 `[dpdk]` 下新增 `thread_mode` 开关 + 复用 `lcore_mask` 语义为「本进程内线程绑核集合」），而非复用 `proc_type`，并以默认关闭保证多进程零回归。此为中长期设计，非本轮落地。

## 1. 现有配置机制（改造基线，file:line）

### 1.1 `struct ff_config.dpdk` 关键字段（`ff_config.h:269-328`）
- `char *proc_type;`（`:272`）—— "primary"/"secondary"/"auto"，**直接给 DPDK EAL**。
- `char *lcore_mask;`（`:274`）—— 全部启用的 lcore 掩码（十六进制）。
- `char *proc_mask;`（`:276`）—— **当前进程**单 bit 掩码（`parse_lcore_mask` 生成，`ff_config.c:123-125`）。
- `int nb_procs;`（`:290`）—— 进程总数 = `lcore_mask` bit 数（`ff_config.c:139`）。
- `int proc_id;`（`:291`）—— 当前进程序号（0-based）。
- `uint16_t *proc_lcore;`（`:311`）—— proc_id → lcore_id 映射表。
- 常量 `DPDK_MAX_LCORE 128`（`:37`）。

### 1.2 解析与校验（`ff_config.c`）
- `parse_lcore_mask()`（`:73-142`）：逐 bit 解析 `lcore_mask`，`proc_lcore[count]=idx`（`:118`），`proc_id==count` 时生成本进程单 bit `proc_mask`（`:123-125`），`nb_procs=count`（`:139`），proc_id 越界返回（`:136-137`）。
- proc_type 解析（`:1300-1326`）：`-t` → `strdup(optarg)`（`:1303-1305`），默认 `auto`（`:1312-1314`），**合法性仅允许 primary/secondary/auto**（`:1316-1321`）。
- DPDK argv 拼接：`-c<proc_mask>`（本进程单 bit，`:1151-1153`）+ `--proc-type=<proc_type>`（`:1167-1169`）。
- 端口 lcore_list：`pconf->nb_lcores = nb_procs; memcpy(lcore_list, proc_lcore, ...)`（`:567-571`）。
- KNI primary-only 校验（`:1392-1410`）：见 `12-KNI-IPC-工具链归属方案.md`。

### 1.3 adapter 侧配置入口（`_material_code.md` §2.5/§2.6）
- 编译宏 `FF_THREAD_SOCKET`：定义 `__FF_THREAD` 为 `__thread`（`ff_socket_ops.h:27-31`），使 `sc`/`inited` 成为 per-thread（`ff_hook_syscall.c:226-227`）。
- 编译宏 `FF_MULTI_SC`：启用 `scs[SOCKET_OPS_CONTEXT_MAX_NUM]`（`ff_hook_syscall.c:241`）+ `ff_so_zones[]`（`ff_socket_ops.h:208-210`），`SOCKET_OPS_CONTEXT_MAX_NUM=32`（`ff_socket_ops.h:45`）。
- 环境变量 `FF_PROC_ID`：`ff_adapter_init` 里 `getenv("FF_PROC_ID")`（`ff_hook_syscall.c:3248`）设 `worker_id`，`sc = ff_attach_so_context(worker_id % nb_procs)`（`:3297`）。
- 示例入参：`main_stack_thread_socket.c` `worker_num = atoi(argv[1])`（`:224`），绑核 `lcore_id = 2+i`（`:239-250`）。

## 2. 配置设计方案

### 2.1 `proc_type` 是否新增 `thread` 模式 —— **不新增**

| 方案 | 结论 | 理由 |
|---|---|---|
| 给 `proc_type` 加 `thread` 枚举 | **拒绝** | `proc_type` 透传 DPDK EAL `--proc-type`（`ff_config.c:1167`），DPDK 只认 primary/secondary/auto；加 `thread` 会被 EAL 拒绝或语义错乱，且破坏现有校验（`:1316-1321`）与向后兼容 |
| 复用 `proc_type=primary` + adapter 宏 | **采纳（选项 c）** | 多线程能力在 adapter 层用编译宏 + 环境变量表达，`proc_type` 语义不变 |
| 新增独立开关（选项 a 用） | **中长期采纳** | 见 2.4 |

### 2.2 是否新增 `[thread]` 段 —— **本轮不新增**

- 选项 (c) 下多线程完全由 adapter 编译宏 + `FF_PROC_ID` + APP 自身线程数（如 `main_stack_thread_socket.c argv[1]`）驱动，**`config.ini` 无需任何新增段**，`config.ini` 本地测试值不入库的既有约束不受影响。
- **诚实边界**：`config.ini` 现有段（`[dpdk]`/`[port*]`/`[kni]` 等）中并无 `[thread]` 段的代码解析入口（`ff_config.c` 未发现 thread 段解析），新增段需同步改 `ff_config.c` 解析 + `ff_config.h` 结构，属选项 (a) 的改造范畴。

### 2.3 `lcore_mask` 语义复用 —— **选项 c 下不改；选项 a 下语义扩展**

- **选项 (c)**：`lcore_mask` 语义**完全不变**（仍是「启用哪些 lcore → 拉起哪些进程」，`parse_lcore_mask:118-139`）。adapter worker 绑核由 APP 侧 `pthread_setaffinity_np` 独立控制（`main_stack_thread_socket.c:239-250`），与 `lcore_mask` 解耦。
- **选项 (a)（中长期）**：可复用 `lcore_mask` 的 bit 集合语义为「本进程内 N 个线程分别绑到这些 lcore」，即从「一 bit 一进程」扩展为「一 bit 一线程」，但**必须以新增开关区分两种解释**（见 2.4），否则破坏多进程零回归。

### 2.4 选项 (a) 的配置扩展设计（中长期，非本轮落地）

> 仅当决定实现「单进程多线程 + 独立栈实例」时采用；默认关闭。

- 在 `struct ff_config.dpdk`（`ff_config.h:269`）新增 `int thread_mode;`（默认 0=多进程，1=单进程多线程），`config.ini` `[dpdk]` 段新增 `thread_mode=0`。
- `thread_mode=1` 时：`lcore_mask` 的 bit 集合解释为「本进程内线程绑核集合」；`nb_procs` 语义转为「本进程内线程数」（需在 `parse_lcore_mask` 分支处理，`ff_config.c:73-142`）；`proc_lcore[]` → 线程 index → lcore 映射。
- `thread_mode=0`（默认）时：所有解析路径逐字节沿用现状，保证零回归。
- **强制门禁**：`thread_mode` 默认 0；解析 `thread_mode=0` 时不得进入任何新代码分支（用 `if (thread_mode)` 包裹全部新逻辑）。

## 3. `ff_api.h` 兼容性设计（不破坏现有 API）

### 3.1 现有 API 表面（`ff_api.h`，`_material_code.md` §2.4）
- `extern __thread struct thread *pcurthread;`（`:55`）—— 已 TLS，多线程天然安全。
- `ff_pthread_create/join`（`:180-185`，`#ifndef _KERNEL`）。
- `ff_adapt_user_thread_add/exit`、`ff_switch_curthread`、`ff_restore_curthread`（`:481-487`）—— LD_PRELOAD 每线程独立 `struct thread` 上下文（`ff_compat.c:96-148`）。
- `ff_rss_self_queue_info(proc_id, queueid, nb_queues, reta_size)`（`:124-126`）—— 只读本进程 RSS 队列信息。
- 栈选择标志位（`#ifdef FF_KERNEL_COEXIST`，`:81-101`）：`SOCK_FSTACK 0x01000000`（`:96`）、`SOCK_KERNEL 0x02000000`（`:99`）。

### 3.2 兼容性设计原则

1. **所有现有 API 签名/语义保持不变**：选项 (c) 不需要新增或修改任何 `ff_api.h` 导出函数，issue #430 场景已由 `linux2freebsd_socket_flags`（`ff_syscall_wrapper.c:672-684`）+ `ff_socket`（`:943`）+ `ff_accept4`（`:1679`）完备覆盖。
2. **`ff_rss_self_queue_info` 语义在选项 (a) 下需澄清**：当前语义是「本进程 RSS 队列信息」，若实现单进程多线程，应文档化为「本线程 RSS 队列信息」（`_material_code.md` plan §0.1 已提示此点），**但不改签名**，仅在多线程模式下由调用线程各自获取自己的 queue index。
3. **新增 API（若选项 a）以增量方式**：如需暴露「本进程内起 N 个栈线程」的入口，应新增独立函数（如 `ff_run_thread_mode(...)`），不改现有 `ff_init`/`ff_run`（`ff_init.c:35-62`）签名，保证旧 APP 重编即用。

## 4. 向后兼容与 opt-in 策略

| 策略项 | 设计 | 代码依据 |
|---|---|---|
| 默认行为 | 默认多进程模式，`proc_type=auto`（`ff_config.c:1312-1314`）、无 adapter 宏时 `__FF_THREAD` 为空（`ff_socket_ops.h:27-31`）→ 单实例，行为逐字节不变 | `ff_socket_ops.h:27-31`、`ff_config.c:1312-1314` |
| opt-in 粒度（选项 c） | 编译期 opt-in：编译 adapter 时定义 `-DFF_THREAD_SOCKET` 或 `-DFF_MULTI_SC`；运行期由 `FF_PROC_ID` + APP 线程数控制 | `ff_hook_syscall.c:226-227,241,3248,3297` |
| opt-in 粒度（选项 a，中长期） | 运行期 opt-in：`config.ini` `[dpdk] thread_mode=0`（默认关），仅 `=1` 时进新分支 | 见 §2.4 |
| API 兼容 | 现有 `ff_api.h` 全部函数签名不变，新增能力以增量函数暴露 | `ff_api.h` §3.1 |
| 多进程零回归 | 不改 lib 协议栈核心（选项 c）；选项 a 全部新逻辑用 `thread_mode` 分支隔离 | 04 文档 §5.2 |

## 5. LD_PRELOAD 编译宏配置方式（选项 c 落地细节）

| 宏/变量 | 作用 | 配置方式 | 代码依据 |
|---|---|---|---|
| `FF_THREAD_SOCKET` | `sc`/`inited` per-thread（RTC 每线程独立后端上下文） | 编译 adapter 时 `-DFF_THREAD_SOCKET` | `ff_socket_ops.h:27-31`、`ff_hook_syscall.c:226-227` |
| `FF_MULTI_SC` | 类 `SO_REUSEPORT`，单进程内多 `sc` 上下文（≤32） | 编译 adapter 时 `-DFF_MULTI_SC` | `ff_hook_syscall.c:241`、`ff_socket_ops.h:45,208-210` |
| `FF_KERNEL_COEXIST` | 启用 per-socket 选栈标志位（`SOCK_FSTACK`/`SOCK_KERNEL`） | 编译时定义 | `ff_api.h:81-101` |
| `FF_PROC_ID`（环境变量） | 指定 worker 绑定的后端 f-stack 进程实例 | 运行前 `export FF_PROC_ID=<n>` | `ff_hook_syscall.c:3248,3297` |
| APP worker 数 | 决定起几个用户线程 | APP 自定（示例 `argv[1]`） | `main_stack_thread_socket.c:224` |

> **配置最小闭环（选项 c）**：`config.ini` 保持多进程配置（`lcore_mask` 决定后端进程数）→ 编译 adapter 打开所需宏 → 运行 APP 时设 `FF_PROC_ID` 并起 N 个绑核 worker。README（`adapter/syscall/README.md:122-209,342-410`）已系统描述四种模式，为权威操作参考（`_material_code.md` §7.3）。

## 6. 诚实边界

- `[thread]` 段、`thread_mode` 开关、`ff_run_thread_mode` 等均为**选项 (a) 的中长期设计建议**，当前代码库**不存在**这些配置/接口，需在实现时新增，本轮 spec 仅给出兼容性设计原则。
- 选项 (c) 的编译宏/环境变量均为**代码已存在的现实机制**（file:line 已核验），配置方式为如实描述而非新设计。
