# 完整支持 MTU 修改——需求规格

## 1. 文档目的

本文把 `00`～`06` 的调研结论转换为可实施需求，目标是让 F-Stack 在 DPDK 接管网卡后同时支持：

- 启动时按配置设置标准 MTU 或 jumbo MTU；
- 运行时通过 `SIOCSIFMTU` 修改 MTU，并同步 FreeBSD `if_mtu` 与 DPDK 端口；
- `large` 与 `scatter` 两种 mbuf 模式；
- 多进程场景下软件栈与共享物理端口保持一致；
- 标准 MTU 1500 的现有配置零回归。

本次任务只生成实现型 spec；编码、单元测试、集成测试和性能测试在后续任务执行。

## 2. 已确认决策

| ID | 决策 | 结果 |
|---|---|---|
| D-MTU-01 | mbuf 方案 | 同时实现 `large` 与 `scatter`，由配置选择 |
| D-MTU-02 | MTU 上限 | `max_mtu` 可配置；启用功能且缺省时为 9000 |
| D-MTU-03 | 本次范围 | 仅生成 spec，编码和测试另立任务 |
| D-MTU-04 | 端到端验证 | 尽力实测；链路不支持 jumbo 时必须据实登记，不得伪造通过 |
| D-MTU-05 | FreeBSD 源码策略 | 不修改 `freebsd/net/if_ethersubr.c`；在 `lib/ff_veth.c` 拦截 `SIOCSIFMTU` |
| D-MTU-06 | 兼容策略 | 新功能未启用时保持当前 1500 MTU、2048B mbuf 和既有 ioctl 行为 |

## 3. 术语

- **端口 MTU**：DPDK ethdev 的 MTU，由 `rte_eth_dev_set_mtu()` 管理。
- **协议栈 MTU**：FreeBSD `ifnet.if_mtu`，影响 MSS、分片和路由判断。
- **配置 MTU**：`[portN] mtu`，端口启动时请求的 MTU。
- **最大 MTU**：`[dpdk] max_mtu`，进程可接受的配置/运行时上限，也是 large mbuf 预分配依据。
- **large 模式**：每个 mbuf 的 data room 足以容纳 `max_mtu` 对应的完整以太帧。
- **scatter 模式**：保留标准 mbuf data room，使用多段 mbuf 接收/发送大帧。

## 4. 功能需求

### R-MTU-001 配置开关与缺省兼容

- 新增 `[dpdk] mtu_enable`，取值 `0|1`，缺省 `0`。
- `mtu_enable=0` 时不得改变现有 mbuf pool、offload、端口 MTU 和 ioctl 行为。
- `mtu_enable=1` 时启用本规格的 MTU 能力；`max_mtu` 缺省 9000，`mbuf_mode` 缺省 `large`。

> 引入 `mtu_enable` 是为解决“`max_mtu=9000` 默认值”与“旧配置零内存回归”的冲突：旧配置未显式启用时继续使用 `RTE_MBUF_DEFAULT_BUF_SIZE=2176`（含128B headroom、可用dataroom 2048），不能放大到 jumbo 大小。

### R-MTU-002 配置模型

- `[dpdk] max_mtu=N`：配置字段为 uint16，但有效上限与模式相关：
  - `large`：`max_mtu + L2_overhead + RTE_PKTMBUF_HEADROOM` 对齐后必须 `<= UINT16_MAX`，且 frame bytes/usable room 满足设备能力；超出在 `ff_check_config()` 阶段拒绝。
  - `scatter`：可配置到 65535，但仍必须满足 PMD `dev_info.max_mtu/max_rx_pktlen`。
- `[dpdk] mbuf_mode=large|scatter`：仅在 `mtu_enable=1` 时生效。
- `[portN] mtu=N`：缺省 1500；范围 `IF_MINMTU..max_mtu`。
- 统一 frame 公式：`frame_bytes = L3_MTU + Ethernet header + configured VLAN/QinQ overhead + FCS`；必须同时验证 `frame_bytes <= dev_info.max_rx_pktlen`。large 的可用 RX room 使用 `data_room_size - RTE_PKTMBUF_HEADROOM`，不得用包含 headroom/alignment 的 pool 参数直接比较 `max_rx_bufsize`。
- 任一配置非法必须在启动阶段明确报错并终止初始化，不得静默回退到 1500。

### R-MTU-003 启动时端口 MTU

- 在 `rte_eth_dev_configure()` 前设置 `port_conf.rxmode.mtu`。
- 在端口启动流程中调用并校验 `rte_eth_dev_set_mtu()`；完成后用 `rte_eth_dev_get_mtu()` 回读。
- `ff_veth_setup_interface()` 完成 `ether_ifattach()` 后，把 FreeBSD `if_mtu` 设置为相同的 `[portN] mtu`。
- 软件 MTU、硬件 MTU 或回读值任一不一致，端口初始化失败。

### R-MTU-004 large mbuf 模式

- pool API 的 `data_room_size` 必须至少为：`RTE_PKTMBUF_HEADROOM + max_mtu + L2_overhead`，并按 DPDK cache alignment 向上取整。
- `L2_overhead` 至少覆盖以太网头、双 VLAN 与 FCS 的最坏情况；具体常量统一定义，不得在多处使用裸数字。
- 创建 pool 前执行乘法/加法溢出检查与总内存上限检查。
- large 模式比较 `usable_room = data_room_size - RTE_PKTMBUF_HEADROOM` 与 `frame_bytes`，并以同一不含 headroom 的单位核对设备单RX buffer能力；pool alignment/padding不得导致误拒绝。不得自动切换 scatter。

### R-MTU-005 scatter mbuf 模式

- 保持 `RTE_MBUF_DEFAULT_BUF_SIZE`。
- 必须验证并开启 `RTE_ETH_RX_OFFLOAD_SCATTER` 和 `RTE_ETH_TX_OFFLOAD_MULTI_SEGS`。
- PMD 缺少任一能力时初始化失败并返回 `ENOTSUP` 语义；不得声称 jumbo 已启用。
- 必须验证现有 FreeBSD mbuf ↔ rte_mbuf 转换、发送释放和失败回收路径支持多段 mbuf；若现状不支持，后续实现任务必须补齐后才能通过 M2 门禁。

### R-MTU-006 运行时 SIOCSIFMTU

- `ff_veth_ioctl()` 增加 `SIOCSIFMTU` 分支，避免进入 `ether_ioctl()` 的 `ETHERMTU` 上限。
- 新 MTU 必须满足 `IF_MINMTU..configured max_mtu`、PMD `min_mtu..max_mtu` 以及当前 mbuf 模式承载能力。
- 本接口按进程角色区分（`rte_eal_process_type()`）：
  - primary：设置协议栈软 MTU（`if_setmtu`）并设置 DPDK 硬件 MTU（`rte_eth_dev_set_mtu`）；硬件变更具备本进程内事务语义：保存旧软/硬 MTU → 设硬件 → 回读确认 → 提交软件值；任一步失败回滚硬件与软件。
  - secondary：仅设置协议栈软 MTU（`if_setmtu`），绝不触达任何 DPDK 端口控制接口。
- `rte_eth_dev_set_mtu()` 对运行中端口可能返回 `-EBUSY`。实现不得在 `ff_veth_ioctl()` 中直接无同步地 stop/start 端口；primary 须在本进程内安全暂停收发（quiesce 本 primary 进程的多 lcore）后完成 stop/set/start 并恢复，或在 PMD 不支持动态变更时明确返回 `EBUSY`。完整验收要求实现 primary 内的 stop/set/start 路径。

### R-MTU-007 多进程一致性

- DPDK 物理端口 MTU 是共享状态，只允许 primary 进程执行 ethdev 控制操作；secondary 只改本进程协议栈软 MTU。
- 多进程 MTU 一致性通过“每个 f-stack 进程各自在启动/运行时各调用一次 MTU 设置”达成，进程间不通信、无事务、无 IPC 协调。
- 使用约定：应用/运维需在每个进程分别触发一次 `SIOCSIFMTU`；未在某 proc 设置时该 proc 软 MTU 视图保持旧值（属已知使用约束，本期不用 IPC 弥补）。
- `tools/sbin/ifconfig -p N ... mtu` 对 primary 会同时更新软/硬件 MTU，对 secondary 只更新该 proc 软 MTU；硬件 MTU 由 primary 唯一负责。

### R-MTU-008 查询与可观测性

- `SIOCGIFMTU` 返回协议栈有效 MTU。
- 提供 DPDK 硬件 MTU 回读日志；成功日志包含 `port_id/old_mtu/new_mtu/mbuf_mode`，失败日志包含 DPDK errno。
- 禁止打印敏感配置；MTU 日志使用现有 `ff_log()` 设施。

### R-MTU-009 IPv4/IPv6/VLAN/bond/vdev

- IPv4 与 IPv6 共用同一 ifnet MTU，均须覆盖 PMTU、MSS 和不分片测试。
- VLAN 场景按 parent port MTU 与 VLAN overhead 校验；VLAN 子接口不得请求超过父端口能力的 MTU。
- bond/vdev 必须逐成员校验最小 `max_mtu`；有成员不支持时拒绝，不得只改部分成员。
- 本期不实现 KNI/内核共存接口的 MTU 联动：检测到 `mtu_enable=1` 与 KNI/内核共存同时启用时，配置阶段必须以 `EOPNOTSUPP` 语义拒绝，并提示关闭其一；不得允许双栈 MTU 不一致。

## 5. 非功能需求

### NF-MTU-001 性能

- `mtu_enable=0` 相对基线吞吐、P99 延迟和 CPU 不得有可测回归。
- large/scatter 模式分别建立 MTU 1500 与 9000 的吞吐、P99 延迟、CPU/包、mbuf 内存基线。

### NF-MTU-002 可靠性

- 配置或运行时失败不得导致进程退出、端口永久停机、mbuf 泄漏，或单进程内软/硬件 MTU 不一致（进程内事务回滚保证）。
- stop/set/start 失败必须有恢复路径；无法恢复时端口标记为不可用并返回错误。

### NF-MTU-003 安全与边界

- 所有字符串配置使用严格解析，拒绝尾随垃圾、负数和整数溢出。
- `max_mtu` 不得绕过 PMD/设备能力上限。

## 6. 验收标准

- AC-01：旧配置不含新项，行为与当前版本一致。
- AC-02：`mtu_enable=1, mbuf_mode=large, mtu=9000` 在支持 jumbo 的链路端到端通过。
- AC-03：`mbuf_mode=scatter` 同等通过，且多段 mbuf 无泄漏/双重释放。
- AC-04：运行时 1500→9000→1500 成功，软件与硬件回读一致。
- AC-05：不支持 jumbo 的 PMD/链路返回可解释错误，不误报成功。
- AC-06：每个 proc 各自设置 MTU 后各 proc 视图一致；本期不提供跨进程自动同步（未设置的 proc 软 MTU 保持旧值，属已知约束）。
- AC-07：IPv4/IPv6、VLAN、bond/vdev 的边界测试通过或明确标记为不支持并阻止错误配置。
- AC-08：单元、集成、性能和 24 小时稳定性门禁全部满足 `11-测试与验收规格.md`。

## 7. 范围与非目标

### 7.1 范围内（In）

- 多进程各自设置 MTU（无 IPC 事务）：每个 f-stack 进程各自触发一次 `SIOCSIFMTU`，primary 设软+硬、secondary 仅设软。

### 7.2 范围外（Out）

- 多进程运行时动态 MTU 跨进程 IPC 事务协调（request/prepare/commit/ack 两阶段事务、协调器、专用消息 rings/消息池等）降级为后续独立里程碑，本期不做。
- 本次 spec 任务不修改代码、不执行测试。
- 不修改交换机、virtio backend 或 f-stack-client 的永久 MTU 配置；后续集成测试仅在获准环境中临时调整并恢复。
- 不修改 FreeBSD `ether_ioctl()` 的通用语义。
