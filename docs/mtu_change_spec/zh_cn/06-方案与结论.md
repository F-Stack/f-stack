# 方案与结论

> 本文给出最终结论，以及"若要支持增大 MTU（jumbo frame）"所需的完整改造方案（仅设计，本次调研不改代码）。

## 一、最终结论

f-stack DPDK 接管网卡后修改 MTU 属于**部分支持**：

- ✅ **减小 MTU（≤1500）**：开箱可用。可通过 `ff_ioctl(SIOCSIFMTU)` 或 `tools/sbin/ifconfig ... mtu <N≤1500>` 修改，协议栈层写入 `if_mtu` 软件值即生效；硬件承载能力（默认 1500 / mbuf 2048）≥ 新 MTU，收发无影响。
- ❌ **增大 MTU（>1500，jumbo frame）**：不支持。协议栈层 `ether_ioctl` 硬编码 `> ETHERMTU(1500)` 即 `EINVAL`；DPDK 硬件层无 `rte_eth_dev_set_mtu`、mbuf 固定 2048、`rxmode` 无 jumbo/scatter，双重阻断。F-Stack 官方 issue #720 至今 OPEN，jumbo 官方未实现。

三方证据（代码 / 运行时实测 / 官方 issue）完全一致，结论可靠。

## 二、若要支持增大 MTU（jumbo）的完整改造方案

> 目标：使 f-stack 可通过配置启用 >1500 的 MTU，并让协议栈与 DPDK 硬件联动。缺一不可。

### 改造点 1：config.ini 新增 MTU 配置项

- 在 `[port0]`（及各 `[portN]`）段新增 `mtu = <N>`（默认 1500，缺省保持现状）。
- 在 `lib/ff_config.c` / `ff_config.h` 的 `struct ff_port_cfg` 增加 `int mtu;`，解析该项。

### 改造点 2：ff_veth 初始化按配置设 if_mtu

- `lib/ff_veth.c` `ff_veth_setup_interface`（L910）在 `ether_ifattach` 之后，若 `cfg->mtu > 0` 则 `if_setmtu(ifp, cfg->mtu)`（覆盖 `ether_ifattach` 默认的 1500）。
- 因 `ether_ioctl` 对 `SIOCSIFMTU` 仍有 1500 硬校验，运行时动态改大还需改造点 3。

### 改造点 3：ff_veth_ioctl 拦截 SIOCSIFMTU（突破 1500 硬上限 + 硬件下发）

- 在 `lib/ff_veth.c` `ff_veth_ioctl`（L235）为 `SIOCSIFMTU` 增加显式 `case`，**不再无条件委托 `ether_ioctl`**：
  - 校验 `ifr_mtu` 是否 ≤ 配置允许的最大值（如 `cfg->max_mtu`）。
  - 直接 `if_setmtu(ifp, ifr_mtu)` 写入软件值（绕过 `ether_ioctl` 的 ETHERMTU 硬上限）。
  - 调用 DPDK `rte_eth_dev_set_mtu(port_id, ifr_mtu)` 把 MTU **下发硬件**。
- 保持 ≤1500 时行为与现状兼容（可继续走 `ether_ioctl`）。

### 改造点 4：DPDK 端口/mbuf 支持大帧

- `lib/ff_dpdk_if.c`：
  - mbuf 池 `data_room_size` 由 `RTE_MBUF_DEFAULT_BUF_SIZE(2048)` 放大到 `RTE_PKTMBUF_HEADROOM + max_mtu + 以太网/CRC overhead`（如 9000+ MTU 需 ~9216B）；或启用 **多段接收（scatter）** 用多个标准 mbuf 拼接大帧。
  - 端口配置设置 `port_conf.rxmode.mtu = max_mtu`，并按 PMD 能力开启 `RTE_ETH_RX_OFFLOAD_SCATTER`（若用分段）；在 `rte_eth_dev_configure` 前完成。
  - 初始化流程中调用 `rte_eth_dev_set_mtu(port_id, max_mtu)`，并检查 PMD/`dev_info` 是否支持该 `max_mtu`。

### 依赖与约束

- **PMD/链路依赖**：virtio 等 PMD 的 jumbo 能力有限，还需底层网卡/vSwitch/对端统一支持 jumbo，否则大帧会被中途丢弃/分片。
- **内存开销**：放大 mbuf 数据区会显著增加内存占用；建议 scatter 方案权衡。
- **兼容性**：默认 `mtu=1500` 时全部行为与现状一致，改造应是"可选启用"。

### 改造后建议的验证

- 单元/构建：`lib/` 重编（`-Werror`）、`tools/` 重编通过。
- 运行时：`tools/sbin/ifconfig ... mtu 9000` 成功、`rte_eth_dev_get_mtu` 返回 9000；经 ssh f-stack-client 用 `ping -s 8972 -M do <DPDK_NIC_IP>`（不分片大包）验证大帧收发；`curl` 大文件吞吐对比。

## 三、工作量与优先级评估（若立项）

| 改造点 | 复杂度 | 风险 |
|---|---|---|
| 1 config.ini + ff_config | 低 | 低 |
| 2 ff_veth 初始化设 mtu | 低 | 低 |
| 3 ff_veth_ioctl 拦截 + set_mtu 下发 | 中 | 中（需处理 ether_ioctl 兼容与错误回滚） |
| 4 DPDK mbuf/rxmode/scatter | 高 | 高（内存、PMD 兼容、性能回归） |

- 若仅需**减小 MTU**：无需改造，现状可用。
- 若需 **jumbo**：4 点全做，重点在改造点 4（DPDK 大帧 + PMD 兼容），并须物理网卡/链路支持。
