# 完整支持 MTU 修改——测试与验收规格

## 1. 测试原则

- 所有"通过"必须来自实际执行与保留的输出；不能把计划当结果。
- 先证明默认 1500 零回归，再验证 jumbo。
- large 与 scatter 必须分别验证，不允许用一种模式替代另一种。
- 本机链路若不支持 jumbo，必须区分"代码路径通过"与"链路端到端未通过"。

## 2. 单元测试

### 2.1 `test_ff_config.c`

| ID | 输入 | 预期 |
|---|---|---|
| UT-CFG-01 | 旧 fixture 无新项 | enable=0、max=9000、mode=large、port mtu=1500 |
| UT-CFG-02 | enable=1,max=9000,mode=large,mtu=9000 | 成功 |
| UT-CFG-03 | mode=scatter | 成功 |
| UT-CFG-04 | 非法 mode/空值 | 解析失败 |
| UT-CFG-05 | max_mtu 非数字/负数/溢出/尾随字符 | 解析失败 |
| UT-CFG-06 | port.mtu > max_mtu | 校验失败 |
| UT-CFG-07 | enable=0 且 port.mtu>1500 | 校验失败 |
| UT-CFG-08 | port array calloc 失败 | 无泄漏并返回失败 |

### 2.2 `test_ff_dpdk_if.c`

通过 linker wrap/stub 注入 DPDK 返回值：

- large data room：1500、9000、65535（必须在配置校验阶段返回 ERANGE，不能截断）、加法/乘法溢出、alignment；断言 legacy pool API 参数2176、可用dataroom2048的术语与值。
- capability 边界表：`frame_bytes`、large `usable_room=data_room-headroom`、设备 `max_rx_bufsize`、`max_rx_pktlen` 分别比较；证明多余 alignment/padding 不导致误拒绝；scatter 缺 RX 或 TX capability。scatter `max_mtu=65535` 不创建large room，只进入 PMD max_mtu/max_rx_pktlen 校验。
- 启动 set/get：成功、回读不一致、`ENOTSUP/EINVAL/EIO`。
- 动态：直接成功；第一次 `EBUSY` 后 stop/set/start 成功；set 失败回滚；start 失败恢复；回滚失败进入 FAILED。
- opaque context：正确 port_id；NULL context/无效端口。

### 2.3 veth/ioctl 测试

- `ff_dpdk_if_set_mtu` 成功后才更新 `if_mtu`。
- DPDK负 errno 经 helper 转为FreeBSD正 errno；上层 ioctl 返回 `-1` 且用户态 `errno` 正确，覆盖 `EBUSY/EOPNOTSUPP/EINVAL` 与未知值归一 `EIO`；失败时 `if_mtu` 保持旧值。
- legacy 未启用时 >1500 仍走 `ether_ioctl` 并返回 EINVAL。
- enabled 下 primary 的 9000→1500、9000→1400 必须先设硬件再设软件（同一进程内软/硬件同步回落），不能走 legacy 捷径。
- secondary 分支：只更新本进程 `if_mtu`，不调用 `ff_dpdk_if_set_mtu`／不触达任何 DPDK 端口控制接口。
- 成功路径由通用 `if.c` 触发一次 `if_notifymtu`，不得重复。

### 2.4 multi-seg 生命周期

针对 `ff_dpdk_if.c:1557-1588/2209-2249/2333-2364`：
- 1/2/N 段 RX 转 FreeBSD mbuf；
- 同一 9000 frame 在 large 普通 copy/raw 路径使用实际 `rte_pktmbuf_tailroom()`，断言 `nb_segs==1`；
- scatter 路径按实际 tailroom 计算 N 段，断言 `pkt_len == sum(data_len)`、`nb_segs`、链尾 `next==NULL`；
- page-array/zero-copy：PMD有TX_MULTI_SEGS时验证预期段数和capability；无该能力时验证单large-mbuf copy fallback（若实现阶段选择拒绝策略，则断言 EOPNOTSUPP，并在 spec变更中记录）；
- 第 N 段分配失败，已分配段全部释放；
- zero-copy ext mbuf 引用计数、发送失败、NIC 完成回收无双重释放。

## 3. 构建门禁

- `lib/` 在现有 `-Werror` 参数下完整编译。
- `tools/sbin/ifconfig` 与相关 tools 重编。
- 全部 `tests/unit` 执行通过；新增代码覆盖率不低于项目门槛。
- 搜索门禁：`ff_veth.c` 不得引用 `rte_eth*`；`freebsd/` 不得出现本功能 diff。

## 4. 集成测试矩阵

### 4.1 环境准备

- DPDK 端：本机 `<f-stack-v4-address>`；客户端：ssh `f-stack-client`。
- 先读取 PMD、`min_mtu/max_mtu/max_rx_bufsize/max_rx_pktlen`、scatter/multi-segs capability。
- 临时修改 f-stack-client/虚拟交换机 MTU 前记录原值；结束必须恢复。任何权限变更仍走 `chmod_modify.sh`，进程停止走 `kill_process.sh`，临时文件清理走 `rm_tmp_file.sh`。

### 4.2 静态启动测试

| 模式 | port MTU | 预期 |
|---|---:|---|
| legacy | 1500 | 行为与基线一致 |
| large | 1500 | 启动成功，pool 按 max_mtu 预留 |
| large | 9000 | 软件/硬件回读 9000 |
| scatter | 9000 | RX_SCATTER/TX_MULTI_SEGS 已启用，回读 9000 |
| 任意 | >PMD max | 启动失败，错误明确 |
| scatter | PMD 缺 offload | 启动失败 EOPNOTSUPP |

### 4.3 运行时测试

通过 `tools/sbin/ifconfig -p 0 f-stack-0 mtu N`：
- 1500→1400→1500；
- 1500→9000→1500；
- 边界 `IF_MINMTU-1/max_mtu+1`；
- 本进程内并发两个不同 MTU 请求，验证 primary 内串行化；
- 多进程一致性（无 IPC）：对每个 proc 各自 `-p N` 执行一次设置，验证各 proc 软 MTU 视图一致；
- secondary 设置：从 secondary proc 发请求，验证仅改该 proc 软 MTU、不触达 DPDK（硬件 MTU 不变）；
- 已知约束：只在部分 proc 设置时，未设置的 proc 软 MTU 保持旧值（不视为失败，须记录）；
- 注入 PMD EBUSY/stop 失败/start 失败（primary），验证进程内回滚。
- `mtu_enable=1` 与 KNI/内核共存同时配置必须在启动前被明确拒绝。

每次断言：
1. `SIOCGIFMTU`（各目标 proc）；
2. `rte_eth_dev_get_mtu`（日志或诊断接口，仅 primary 设置硬件）；
3. 已设置 proc 的 ifnet 软 MTU 与预期一致，未设置 proc 保持旧值；
4. 端口仍可收发。

### 4.4 IPv4/IPv6 大包

在链路支持时：

```text
IPv4: ping -M do -s 8972 <f-stack-v4-address>
IPv6: ping -6 -M do -s 8952 <f-stack-v6-address>
```

同时验证：
- MTU=1500 时上述大包按预期失败或触发 PMTU，不得错误发送超长帧；
- MTU=9000 时不分片成功；
- TCP curl 大文件完整性（hash 一致），双向各执行多轮；
- IPv4/IPv6 TCP MSS 与 MTU 对应。

> ping payload 需按实际工具/IP/ICMP 头计算并记录，不得照抄命令而不确认帧长。

### 4.5 VLAN、bond、vdev

- 单 VLAN/双 VLAN overhead；子接口 MTU 不超过 parent 能力。
- bond 所有成员支持/某成员不支持/中途失败回滚。
- virtio、mlx5、i40e/ice（条件允许）覆盖运行态成功与 EBUSY 两类 PMD。

## 5. 性能基线

测试矩阵：

| 模式 | MTU | 指标 |
|---|---:|---|
| legacy | 1500 | 基线 |
| large | 1500/9000 | 吞吐、P50/P99、CPU/包、内存 |
| scatter | 1500/9000 | 同上 + 平均 nb_segs |

要求：
- 固定 CPU/lcore、文件大小、并发、测试时长和预热；至少 5 轮，报告中位数与离散度。
- `mtu_enable=0` 相对旧版吞吐/延迟/CPU 回归不超过测量噪声；若超出必须分析。
- large 内存必须与理论估算对齐；scatter 需记录 segment 分布与 offload 开销。
- 不预设 jumbo 一定更快，报告实际结果。

## 6. 稳定性与故障测试

- 24 小时持续收发，large/scatter 各一轮。
- 每分钟 1500↔9000 切换（在支持的测试环境，primary 内 stop/set/start），检查死锁/mbuf 泄漏/端口失联。
- primary 回滚失败、EBUSY 反复、stop/start 失败恢复路径。
- DPDK xstats/FreeBSD netstat：错误帧、丢包、重传无异常增长。

## 7. 诚实边界与验收分层

若本机 virtio/vSwitch 不支持 jumbo：

- 可标记通过：配置解析、mbuf 模式、DPDK capability 拒绝、软件/硬件 1500 兼容、单元测试。
- 不可标记通过：9000 端到端大帧收发与性能。
- 报告必须注明实际 `dev_info`、backend MTU、失败 errno/抓包证据。
- 应转到支持 jumbo 的物理机完成最终 UAT；未完成前整体状态为"代码门禁通过，端到端待环境验证"，不是"全部验收完成"。
