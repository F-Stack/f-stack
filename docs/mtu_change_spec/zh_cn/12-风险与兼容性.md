# 完整支持 MTU 修改——风险与兼容性

## 1. 风险总览

| 风险 | 级别 | 主要控制措施 |
|---|---|---|
| large 模式内存显著增长 | 高 | feature 开关、启动估算、上限、NUMA 验证 |
| scatter 多段生命周期错误 | 高 | 双 offload、链一致性单测、失败释放审计 |
| large TX 仍按固定2048分段 | 高 | 改用实际tailroom；普通9000 frame单段断言；zero-copy能力/回退 |
| 运行态 set_mtu 返回 EBUSY | 高 | primary 内 quiesce/stop/set/start 状态机 |
| 多进程需每 proc 各自设置，漏设致该 proc 软 MTU 视图不一致 | 中 | 文档化使用约定；本期不以 IPC 弥补，属已知约束 |
| enabled下 primary MTU回落误走legacy只改软件 | 高 | primary 所有MTU都先设硬件再设软件（进程内一致） |
| PMD/虚拟交换机不支持 jumbo | 高 | capability 探测、无隐式成功、物理机 UAT |
| bond 部分成员修改成功 | 高 | prepare 全成员、逆序回滚 |
| 默认 1500 行为/内存回归 | 中 | `mtu_enable=0` 保持 legacy |
| TSO/GSO/校验和与 multi-seg 组合 | 中 | offload 组合矩阵与报文抓包 |

## 2. large 模式内存风险

### 2.1 估算方法

当前 pool 数量由 `ff_dpdk_if.c:394-430` 的 `nb_mbuf` 计算决定。近似新增内存：

```text
pool_bytes ≈ nb_mbuf × aligned(data_room + rte_mbuf/object overhead)
data_room ≈ HEADROOM + max_mtu + Ethernet/VLAN/FCS overhead
```

区分三层口径：pool API 的 `data_room_size` **包含** `RTE_PKTMBUF_HEADROOM`；可用 dataroom 为两者之差；`rte_mbuf` object/allocator overhead 另计。示例：

| max_mtu/模式 | 近似 pool API data_room | 说明 |
|---|---:|---|
| legacy | 2176B | 含128B headroom；可用 dataroom 2048B |
| large 1500 | helper对齐结果 | 须容纳frame + headroom，实际以helper输出为准 |
| large 9000 | 约9.2KB并对齐 | 相对2176B约4.2x，未含object overhead |
| large 9216 | 约9.5KB并对齐 | 相对2176B约4.4x |
| large 65535 | 不可表示 | 加headroom/overhead后超过uint16 API上限，配置确定性拒绝 |
| scatter 65535 | 2176B/segment | 不创建large room，是否可用由PMD max_mtu/max_rx_pktlen决定 |

实际值须用实现 helper 的 alignment 结果与运行时 `nb_mbuf` 计算，不得把本表作为实测。

### 2.2 控制措施

- 旧配置 `mtu_enable=0` 完全不放大 pool。
- 启动前输出每 NUMA socket 的预计内存并检查溢出。
- `max_mtu` 是uint16配置字段，但有效上限按模式判定：large 的派生 `data_room_size` 必须≤UINT16_MAX（65535确定性失败）；scatter 才继续由PMD能力判定。生产建议9000/9216。
- pool 创建失败必须终止启动，不降级为较小 pool 后继续宣称支持 max_mtu。

## 3. scatter 模式风险

- RX scatter 只解决大帧接收，TX 仍需 `RTE_ETH_TX_OFFLOAD_MULTI_SEGS`。
- PMD capability 是必要条件但非充分条件；现有 FreeBSD mbuf/rte_mbuf 桥接必须保持链字段与生命周期一致。
- 多段增加 descriptor、cache miss 和回收开销；高 PPS 小包场景可能比 large/legacy 更慢。
- TSO 与 multi-seg 组合需按 PMD 验证，不能假定 `TX_TCP_TSO` 与 `TX_MULTI_SEGS` 可任意组合。

控制：large/scatter 显式选择、能力不足直接失败、独立性能矩阵、不隐式切换。

## 4. PMD 与链路依赖

### 4.1 DPDK 24.11 已确认语义

- `rte_eth_rxmode.mtu` 存在（`rte_ethdev.h:427-430`）。
- `rte_eth_dev_set_mtu()` 可返回 `ENOTSUP/ENODEV/EIO/EINVAL/EBUSY`（L3640-3656）。
- i40e/ice 可能在 started 时返回 `EBUSY`；virtio/MLX5 的实现可能允许运行态修改。跨 PMD 不得采用同一假设。
- DPDK 要求重配置前 stop，且 MTU通常在 stop/start 间保留；仍需按 PMD 回读确认。

### 4.2 virtio

当前源码存在 `VIRTIO_NET_F_MTU`、`virtio_mtu_set()` 和 scatter/multi-segs capability，但实际 backend 是否协商该 feature、`max_mtu` 是多少只能运行时读取。源码“有实现”不等于当前虚拟链路支持 9000。

### 4.3 端到端一致

NIC、vSwitch/bridge、宿主机 tap、交换机和 f-stack-client 必须统一支持目标 MTU。任何中间节点仍为 1500 都可能造成丢包或 PMTU/分片行为。

## 5. 动态修改与并发风险

- 端口 RX/TX 正在各 lcore 轮询时直接 stop 会产生竞态、丢包或 PMD 未定义行为。
- primary 进程内多个 SIOCSIFMTU 并发可能造成 A 的回滚覆盖 B 的成功结果。

控制：primary 内 per-port 状态机、锁、本进程数据面 quiesce、TX drain、超时。本期不引入跨进程 IPC，故无 ACK 迟到/消息池竞态类风险；多进程一致性由“每进程各设一次”达成，代价是漏设 proc 视图不一致（见第 1 节使用约束风险）。

## 6. 回滚风险

理想事务（primary 进程内）：旧硬件/软件 MTU → 新硬件 → 新软件。失败处理：

1. 新硬件 set 失败：软件不变，直接返回原 errno。
2. 新硬件成功、本进程软件提交失败：恢复旧硬件。
3. restart 失败：尝试旧 MTU + restart。
4. 回滚仍失败：port 标为 FAILED/interface down，禁止继续收发并返回 EIO。

禁止在 primary 硬件 9000、本进程软件 1500 的不一致状态下返回成功。

## 7. IPv4/IPv6/VLAN/bond 兼容

- IPv4/IPv6 共用 ifnet MTU，但 ICMP PMTU、MSS 与分片路径不同，必须分别验证。
- VLAN/QinQ 会增加 L2 overhead；large data room 计算须预留双 VLAN，设备 frame limit 也须考虑 overhead。
- bond 上限取所有 member 的最小能力；由 primary 在本进程内依次修改各 member，任一失败逆序回滚。
- `mtu_enable=1` 与 `kni.enable=1` 的互斥已解除（物理机实测验证，以本条为准，覆盖本 spec 集中 07/08/09/10/11 关于 KNI 互斥的历史描述）：开启 KNI 时，若 KNI 内核接口 `veth0` 的 MTU 保持默认 1500，DPDK 巨帧路径正常工作，KNI 侧由内核协议栈负责拆包收发；若通过 `ifconfig veth0 mtu 9000` 将 `veth0` MTU 设为 9000，则 KNI 通路也可正常收发巨帧数据包。`FF_KERNEL_COEXIST` 与 `mtu_enable=1` 的互斥仍保留。

## 8. 默认兼容策略

`mtu_enable=0`：
- pool data room 仍为 `RTE_MBUF_DEFAULT_BUF_SIZE`；
- 不新增 scatter/multi-segs offload；
- `port_conf.rxmode.mtu` 保持现有默认路径；
- `ff_veth_ioctl` 对 >1500 仍由 `ether_ioctl` 返回 EINVAL；
- 性能与内存必须等价于当前版本。

只有显式 `mtu_enable=1` 才承担 jumbo 的内存与控制面成本。启用后 primary 即使目标改回1500/1400，也必须先设硬件再设软件（进程内一致），禁止回落到只改软件的legacy路径。

## 9. 配置与提交风险

- `config.ini` 只提交功能相关的注释/default 示例，不得提交本机 `lcore_mask/idle_sleep/addr/addr6/gateway` 等值。
- 实测时使用 `/usr/local/nginx_fstack/conf/f-stack.conf` 或明确的测试副本，必须确认实际进程重启并加载正确配置；不能仅修改文件后假设生效。
- 停进程用 `kill_process.sh`；临时文件清理用 `rm_tmp_file.sh`；权限调整用 `chmod_modify.sh`。

## 10. 发布与回退

- 先发布 `mtu_enable=0` 的兼容版本，确认默认路径无回归。
- 再灰度 large；scatter 作为显式可选模式。
- 遇到功能问题可把 `mtu_enable=0` 回到 legacy；若端口已经以 jumbo 启动，需重启进程恢复 pool/端口配置，不能仅热改开关。
- 每里程碑独立 commit，优先 forward-fix；不改写已共享历史。
