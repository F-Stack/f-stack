### 核心代码

```c
/* lib/ff_dpdk_if.c  main_loop() */
if (unlikely(idle && idle_callback != NULL)) {
    /* the application owns the idle behaviour: no library sleep */
    uint64_t cb_tsc = rte_rdtsc();
    idle_callback(idle_callback_arg);
    idle_cb_tsc += rte_rdtsc() - cb_tsc;
    end_tsc = rte_rdtsc();
} else if (likely(idle && effective_sleep)) {
    rte_delay_us_sleep(effective_sleep);
    end_tsc = rte_rdtsc();
} else {
    end_tsc = idle_sleep_tsc;
}
...
usr_tsc = usr_cb_tsc + idle_cb_tsc;
```

## 4. 运行时测试

探针放仓库外 `/tmp/idle_cb_probe/`（由 `example/main.c` 改写：保留 HTTP 服务，`loop()` 与空闲回调各自计数并每秒向 stderr 打印频率），测完 `rm_tmp_file.sh` 清理，**`example/` 一行未动**。

| 用例 | 注册情况 | loop() 频率 | 空闲回调频率 | 判定 |
|------|----------|-------------|--------------|------|
| R1 | 未注册 | 5939 ~ 6064 /s（≈6000） | **0 /s** | 与改动前基线完全一致，零回归 |
| R2 | 注册，回调内 `usleep(20)` | 5884 ~ 6069 /s（≈6000） | 11729 ~ 12123 /s（≈12000） | 回调每空闲圈触发一次 |
| R3 | 注册，回调内不限速 | ≈9988 /s | **≈6.17M /s** | 满速空转，即文档警示的风险 |
| R4 | 注册 + `usleep(20)`，HTTP 打流 | 5960 → ≈7200 /s | ≈11500 ~ 11800 /s | 15675/15675 返回 200 |
| R5 | 先注册，运行 6 s 后注销 | 注销后回到 ≈6000 /s | 注销后 **0 /s** | 注销立即恢复库休眠行为 |

### 关键结论

- **R2 的 2:1 关系是"每空闲圈调用一次"的直接证据**：`idle_loop_interval=100 µs` + 每圈约 83 µs ⇒ `loop()` 约每 2 圈一次（6000/s），空闲回调每圈一次（12000/s）。
- **R1 vs 改动前**：上一轮实测同配置（`idle_sleep=20`、`idle_loop_interval=100`）的基线就是 ≈6000/s，本轮未注册时同为 ≈6000/s 且空闲回调计数恒为 0 —— 未注册路径零回归。
- **R3 量化了风险**：不在回调内自我限速时，空闲回调频率达 617 万次/秒。这正是需求"由用户自行处理空闲行为"所要求的自由度，但必须在 API 注释、API Reference、Release Note、知识图谱四处显著警示（已写）。
- **R4 诚实说明**：打流期间空闲回调频率只从 ≈11900/s 略降到 ≈11600/s。原因是本环境 HTTP 负载（约 780 req/s）相对 12000 圈/s 占比太小，非空闲圈比例低；`loop()` 频率由 5960/s 升到 ≈7200/s 才是"有包即绕过节流"的直接体现。业务侧 15675/15675 全部 200，无异常。

## 5. ff_top 记账变化

空闲回调耗时由新增的 per-pass `idle_cb_tsc` 累计，并入 `usr_tsc`，因此 `ff_top` 不再把它算成空闲时间（与 `loop()` 耗时计入 usr 的处理一致）。`sys_tsc`、`work_tsc`、`idle_tsc` 的公式未改。
