# F-Stack LRO/TSO 风险与兼容性分析（中文）

> 文档层级：风险与兼容性（M4/M5 阶段产出）
> 设计依据：`02-现状与差距分析.md`、`04-方案与架构设计.md`、`05-接口与配置设计.md`、`06-里程碑与工作清单.md`、`07-测试与验收规格.md`、`08-性能基线方案.md`。
> 权威版本：DPDK `dpdk-stable-24.11.6`、FreeBSD 15.0 移植（`f-stack/freebsd/`）。
> 铁律：本轮**纯文档阶段**，不写代码、不改 lib、不提交。所有风险条目均附精确 `file:line` 与控制措施；凡涉及具体 PMD 行为一律标注"**待运行时验证**"。
> 风险级别口径：**高**＝可能导致收发不通/崩溃/静默丢包/编译失败；**中**＝特定组合下功能异常或性能不达预期；**低**＝影响面小、易控、有明确回退。

## 一、LRO 风险清单（全新开发，硬件 offload 路径）

### R-LRO-01 收包语义变更（超 MTU 大段上送协议栈）【中】

- **描述**：LRO 使能后，`ff_veth_input`（`ff_dpdk_if.c:1694-1742`）上送的 mbuf `pkt_len` 会远超单帧 MTU（这是 LRO 的目的）。现状收包路径仅凭 `pkt->pkt_len`（`ff_dpdk_if.c:1708`）+ 多段遍历（`:1725-1739`）在**长度维度**搬运，未对"超 MTU 段"做任何特殊标记；FreeBSD 协议栈能否无缝接收该大段，取决于接口是否已声明 `IFCAP_LRO`（现状全 lib 命中 0，见 `ff_veth.c:941-956`）与协议栈对大段的接收逻辑。
- **影响**：若未声明 `IFCAP_LRO` 即强开 PMD LRO，协议栈可能对超 MTU TCP 段做非预期处理（丢弃/重组异常）。
- **级别**：中。
- **控制措施**：(1) 方案已要求先设 `IFCAP_LRO`（`04` 文档 1.5、`05` 文档 5.1）再启用；(2) 默认 `lro=0` 时该路径完全不触发（零回归）；(3) 端到端接收正确性列入 CM3/CM6 运行时验证（`07` 文档 IT-LRO-10/12，HB-3）。

### R-LRO-02 与 jumbo（`mtu_enable`）/ data_room / scatter 组合【中】

- **描述**：LRO 聚合大段通常超过单 mbuf `data_room`，需 mbuf 链（scatter）或足够大的 data_room 承载；`max_lro_pkt_size`（`rte_ethdev.h:432`）须与承载能力匹配。jumbo MTU 与 `max_lro_pkt_size` 是不同维度（单帧 vs 聚合段），须保证 `max_lro_pkt_size >= mtu`（`04` 文档 1.3）。
- **影响**：`max_lro_pkt_size` 取值过大而 mbuf 承载不足时，PMD 可能在 `dev_configure`/`dev_start` 报错或运行时丢段。
- **级别**：中。
- **控制措施**：(1) 取值优先采用 `dev_info.max_lro_pkt_size`（`rte_ethdev.h:1792`）宣告上限，PMD 未宣告时取保守默认（`05` 文档 4.2）；(2) 收包路径已支持多段链（`ff_dpdk_if.c:1725-1739`），承载路径存在；(3) 精确匹配值列入运行时校准（HB-2）。

### R-LRO-03 与 RX csum / RSS 组合【低】

- **描述**：LRO 大段的 L4 校验和由 PMD 在聚合时完成，收包 csum 检查（`ff_dpdk_if.c:1698-1703`，检查 `RTE_MBUF_F_RX_L4_CKSUM_BAD` 丢包）对大段依然适用；`ff_mbuf_gethdr` 在 `rx_csum` 时置 `CSUM_DATA_VALID|CSUM_PSEUDO_HDR`（`ff_veth.c:479-483`）对大段同样成立。RSS 与 LRO 正交（RSS 分流不同流、LRO 聚合同队列内同流）。
- **影响**：正常情况无额外风险；仅当 PMD 对 LRO 段 csum 语义与预期不符时，可能误丢。
- **级别**：低。
- **控制措施**：复用既有 csum 检查逻辑，不新增分支；LRO 段 csum 正确性列入运行时验证（HB-3）。

### R-LRO-04 virtio（本机）能力依赖【高（对"端到端可验证性"而言）】

- **描述**：硬件 LRO 强依赖 PMD 在 `dev_info.rx_offload_capa` 宣告 `RTE_ETH_RX_OFFLOAD_TCP_LRO`（`rte_ethdev.h:1556`）。virtio 的 LRO/TSO 能力受后端协商（`VIRTIO_NET_F_*`）限制（`03` 文档 2.3），本机 virtio 是否宣告 LRO **不可静态断言**。
- **影响**：若本机 virtio 不宣告 LRO capa，则 `lro=1` 时代码走优雅降级（记 "LRO is not supported"、`rx_lro` 保持 0），LRO 端到端聚合**在本环境无法验证**（非"无收益"，而是"不可测"）。
- **级别**：高（就"能否端到端验证"而言）；对稳定性而言为**低**（有优雅降级，不 fatal）。
- **控制措施**：(1) 能力探测门控（仅 capa 宣告才置位，对齐 `ff_dpdk_if.c:901-906`/`931-942` 范式）；(2) 不支持时优雅降级不 fatal（`05` 文档 7）；(3) CM0 先读 `dev_info` 落档（`06` 文档 CM0 步骤 4）；(4) 端到端聚合项按 HB-1 分层，禁止用"代码路径通过"冒充"端到端通过"（`07` 文档第五节）。

### R-LRO-05 协议栈接收 LRO 大段（IFCAP_LRO 后的行为）【中】

- **描述**：即使声明 `IFCAP_LRO`（方案 `04` 文档 1.5 新增），FreeBSD 15.0 协议栈对 LRO 合并段的接收路径（重组、序号、时间戳处理）能否与 f-stack 用户态栈无缝衔接，仍需运行时坐实（`02` 文档 1.5 主风险点）。
- **影响**：接收异常时可能表现为吞吐不升反降、乱序或连接异常。
- **级别**：中。
- **控制措施**：CM3/CM6 端到端验证（IT-LRO-10/12），以 `netstat`/抓包/无异常日志为证据（HB-3）；默认关闭零回归兜底。

### R-LRO-06 多进程（primary/secondary）LRO 聚合行为【中】

- **描述**：offload 能力探测与 `port_conf` 在 primary 进程完成，secondary 共享端口配置；per-queue LRO 聚合在 RSS 多队列/多进程下的实际行为需运行时坐实（`04` 文档 1.7）。
- **影响**：多进程下若 per-queue 聚合行为与单进程不一致，可能出现部分队列不聚合或聚合异常。
- **级别**：中。
- **控制措施**：per-port 能力一致设置（各进程 `ff_veth_setup` 按 `cfg->hw_features.rx_lro` 一致声明）；per-queue 行为列入运行时验证（HB-7）。

### R-LRO-07 `rx_lro` 死字段激活引入的路径变更【低】

- **描述**：`hw_features.rx_lro`（`ff_config.h:114`）现状为死字段——全 lib 仅两处命中：定义（`ff_config.h:114`）与 `#if 0` 内的死赋值（`ff_dpdk_if.c:896`），无任何生效消费点。方案将其激活为真实生产（`ff_dpdk_if.c` LRO 探测块置 1）+ 消费（`ff_veth.c` `IFCAP_LRO`）。
- **影响**：激活后 `rx_lro` 会真实影响 `IFCAP_LRO` 声明；若生产/消费不成对（如置 1 但 `ff_veth.c` 未消费）会导致能力位不一致。
- **级别**：低。
- **控制措施**：生产点（`ff_dpdk_if.c` 探测块）与消费点（`ff_veth.c:941-956` 新增）必须成对实现（CM2 + CM3）；单测覆盖探测置位（TC-LRO-CAP-01..03）。

## 二、TSO 完善风险清单（已支持，补齐完善点）

### R-TSO-01 IPv6 TSO 伪头/l3_len 修复的正确性【高】

- **描述**：现状 TSO 分支（`ff_dpdk_if.c:2455-2465`、`ff_memory.c:358-368`）**无条件**用 `rte_ipv4_phdr_cksum`（`ff_dpdk_if.c:2460`、`ff_memory.c:363`）与 IPv4 头结构强转，IPv6 大段 TSO 时伪头校验和算错、`l3_len` 基于 IPv4 IHL 计算亦错。方案改为按 `iph->version` 分流，IPv6 用 `rte_ipv6_phdr_cksum` + `l3_len=40`（`04` 文档 2.1）。
- **影响**：修复本身若 version 判断或偏移计算有误，可能把原本正确的 IPv4 TSO 也改坏（回归风险）。
- **级别**：高（触及既有 IPv4 发包主路径的公共代码）。
- **控制措施**：(1) IPv4 分支逻辑与现状逐字段等价（回归护栏 TC-TSO-FILL-01）；(2) IPv6 分支单测（TC-TSO-FILL-02）+ 对端抓包校验和（IT-TSO-21，本项目 TSO 核心验收）；(3) `tso=0` 默认零回归（TSO 分支 `if (offload.tso_seg_size)` 不进入）。

### R-TSO-02 IPv6 扩展头场景 `l3_len` 计算【中】

- **描述**：IPv6 基本头固定 40，但含扩展头（Hop-by-Hop/Routing/Fragment）时 `l3_len` 应为"以太头到 TCP 头之间的全部 IPv6 头长"。首版仅支持无扩展头（`l3_len=40`，`04` 文档 2.1 诚实边界）。
- **影响**：IPv6 含扩展头且开启 TSO 时，`l3_len` 偏小导致 TCP 头定位错、分段错。
- **级别**：中。
- **控制措施**：(1) 首版明确标注仅支持无扩展头，扩展头场景标"待增强"（需解析 `next_header` 链，HB-4）；(2) TSO 通常用于大流量 TCP，扩展头少见，风险面窄；(3) 若命中扩展头，行为退化到与现状相当（不比现状更差）。

### R-TSO-03 `if_hw_tsomax` 系列取值【中】

- **描述**：现状 lib 从不设 `if_hw_tsomax`/`tsomaxsegcount`/`tsomaxsegsize`（全 lib 命中 0）；FreeBSD `tcp_output.c:905-931` 仅当 `if_hw_tsomax != 0`（`:927`）才用上限约束分段。方案在 `ff_veth.c:951-953` TSO 块设三项非 0 上限（`04` 文档 2.3）。
- **影响**：取值偏小限制 TSO 效率；偏大可能生成超 PMD 单包/段数能力的大段被 PMD 拒绝/截断。DPDK 未在 `dev_info` 直接提供等价"TSO 段数上限"字段，精确值依 PMD（virtio/ixgbe/i40e 各异）。
- **级别**：中。
- **控制措施**：(1) 取保守默认（总长 ≤ IP_MAXPACKET 维度、segcount/segsize 保守）+ 运行时校准（HB-5）；(2) 设**非 0** 上限本身即优于现状（全 0、完全不约束）；(3) `if_sethwtsomax*` 确切 API 以 FreeBSD 15.0 `if.h`/`if_var.h` 实际导出为准（编码阶段 `read_file` 复核，`05` 文档 5.2）。

### R-TSO-04 双份重复逻辑收敛（重构）风险【中】

- **描述**：`ff_dpdk_if.c:2405-2472` 与 `ff_memory.c:331-375` offload 填充逻辑高度重复（TSO 分支 `:2455-2465` vs `:358-368` 几乎逐行相同）。方案 A 抽取公共函数收敛，方案 B 两处同步改（`04` 文档 2.4）。收敛涉及跨编译单元（`ff_dpdk_if.c`/`ff_memory.c`）依赖。
- **影响**：收敛函数放置不当可能引入循环依赖或破坏 `ff_veth.c` 不直接引用 `rte_eth*` 的既有约束（`07` 文档 BG-06）；重构本身可能引入行为差异。
- **级别**：中。
- **控制措施**：(1) 收敛函数放两处均可 include 的公共位置，避免循环依赖（`04` 文档 2.4）；(2) 收敛前后逐字段对拍（TC-TSO-CONV-01）；(3) 单独 commit 便于回滚（`06` 文档 CM5 回滚点）；(4) 方案 A 失败退方案 B（同步改 + 交叉引用注释）；(5) **改代码先 `make clean` 再完整编译**验证跨编译单元一致性（避免增量编译掩盖头依赖问题）。

### R-TSO-05 `CSUM_IP6_TSO` 宏位关系（已坐实）【低】

- **描述**：方案 `04` 文档 2.6 / `05` 文档 5.3 曾把"`ff_veth.c:304` 是否需扩展识别 `CSUM_IP6_TSO`"列为编码阶段第一项坐实。**本文档编写阶段已实测坐实**：`freebsd/sys/mbuf.h:670` `CSUM_IP6_TSO = 0x00001000`（独立位），`:735` `#define CSUM_TSO (CSUM_IP_TSO|CSUM_IP6_TSO)` —— **`CSUM_TSO` 已是复合宏、已包含 `CSUM_IP6_TSO` 位**。
- **结论**：现状 `ff_veth.c:304 if (csum_flags & CSUM_TSO)` **已能命中 IPv6 TSO 段**（因 `CSUM_TSO` 含 `CSUM_IP6_TSO` 位）。故 `04`/`05` 提出的扩展 `& (CSUM_TSO | CSUM_IP6_TSO)` 是**冗余**的（结果等价），此步可省。
- **影响**：几乎无。IPv6 TSO 断链**不在 `ff_veth.c:304` 这一层**（此层已能识别），真正断链在下游 `ff_dpdk_if.c:2455-2465`/`ff_memory.c:358-368` 的伪头计算未按 version 分流（R-TSO-01 才是核心）。
- **级别**：低。
- **控制措施**：编码阶段以本坐实结论为准，`ff_veth.c:304` 可不改；核心修复聚焦 R-TSO-01 的下游 version 分流。

### R-TSO-06 与 `tx_csum_offoad_skip` 组合不一致【中】

- **描述**：现状 TSO 使能（`ff_dpdk_if.c:931-942`）**不受** `tx_csum_offoad_skip` 约束，而 L4 csum offload 使能（`:914-926`）在 `skip==0` 时才置 `tx_csum_l4`。TSO 隐含需要 L4 csum offload（`RTE_MBUF_F_TX_TCP_SEG` 隐含 TCP CKSUM）。当 `tso=1 && tx_csum_offoad_skip=1` 时属不一致组合。
- **影响**：`tx_csum_l4=0` 时 TSO 填充分支（`ff_dpdk_if.c:2422 if (ctx->hw_features.tx_csum_l4)`）**整体不进入** → TSO 实际不生效（大段未打 TCP_SEG 标记，可能被 PMD 拒绝或退回软件路径）。
- **级别**：中。
- **控制措施**：TSO 使能处记 WARN 日志提示互斥关系（`04` 文档 2.5，首选不强改既有行为）；组合约束文档化 + 日志化；集成用例 IT-TSO-24 验证不 crash。

### R-TSO-07 TSO 与 scatter / MULTI_SEGS 组合【低】

- **描述**：TSO 前大段本就是多段场景，发包路径（`ff_dpdk_if.c:2360-2403`）已支持多段 mbuf 链；`tso_segsz` + `nb_segs` 组合的 PMD 约束由 `if_hw_tsomaxsegcount`/`tsomaxsegsize`（R-TSO-03）保护。
- **影响**：段数/段大小超 PMD 能力时被拒；由 tsomax 上限保护。
- **级别**：低。
- **控制措施**：复用既有多段发包路径；tsomax 非 0 上限约束（R-TSO-03）。

## 三、默认关闭兼容策略（零回归红线）

### C-01 LRO 默认关闭零回归【机制保证】

- `dpdk.lro` 默认 0（`config.ini` 入库值 `lro=0`；解析未命中时结构清零，`05` 文档 3.2）→ `if (ff_global_cfg.dpdk.lro)` 不进入 → LRO 探测块、`max_lro_pkt_size`、`rx_lro=1` 全不生效 → `ff_veth.c` `if (rx_lro)` 不设 `IFCAP_LRO` → 收包路径（`ff_dpdk_if.c:1694-1742`）无任何 LRO 分支变化。
- **结论**：`lro=0` 时与现状**逐字节一致**。验证：TC-LRO-CFG-06（45 个旧 fixture）+ IT-START-01。

### C-02 TSO 默认关闭零回归【机制保证】

- `dpdk.tso` 默认 0（`config.ini:22` `tso=0`）→ `if (dpdk.tso)` 不进入 → `tx_tso=0` → `ff_veth.c:951` `if (tx_tso)` 不设 `IFCAP_TSO`/`tsomax`；发包路径 `if (offload.tso_seg_size)`（`ff_dpdk_if.c:2455`）依赖 `CSUM_TSO`，`tso=0` 时协议栈不置 `CSUM_TSO` → TSO 分支（含新增 IPv6 分流）**完全不触及**。
- **结论**：`tso=0` 时 IPv6 分流/IP_CKSUM 自洽/tsomax 等新增逻辑全不生效。验证：TC-TSO-FILL-04 + IT-TSO-22。

### C-03 老 config.ini 兼容【机制保证】

- 老 config.ini 无 `lro` 项时，`MATCH("dpdk","lro")` 不命中，`dpdk.lro` 保持默认 0（`05` 文档 1.1、3.2）→ 行为与现状一致，无需用户改配置。

## 四、发布与回退策略

### D-01 分里程碑独立可回退

- 每个编码里程碑（CM1-CM5）提交前打 commit 锚点（`06` 文档回滚点），门禁失败可回滚到上一 CM；LRO 主线（CM1→CM2→CM3）与 TSO 主线（CM4→CM5）解耦，一条主线出问题不影响另一条的回退。

### D-02 特性开关即运行时回退

- LRO/TSO 均由 config 开关控制且默认关闭；即使已发布，运行现场只需将 `lro`/`tso` 置 0 即回到零回归行为，无需回滚代码——这是最快的运行时兜底。

### D-03 bounce 回退纪律

- 任一门禁失败必须打回对应里程碑修复（bounce≤3），不得搁置为"已知问题"或带病放行；同一步骤打回超 3 次转人工决策（`06` 文档三、`07` 文档一.5）。

## 五、config.ini 提交风险（强制规约）

### E-01 config.ini 本地测试值不入库【高（合规风险）】

- **描述**：`config.ini` 是随特性入库的配置文件。历史上该文件已两次误带本地测试值入库（`lcore_mask`、`vlan_filter`、`portN` 本机真实 IP 等）。
- **影响**：误提交本地测试值污染仓库默认配置，影响其他环境。
- **级别**：高（合规）。
- **控制措施**：本次 LRO 特性对 `config.ini` 的改动**只允许**新增 `lro=0`（`[dpdk]` 段，紧邻 `tso=0`），入库默认值必须为 `lro=0`；本地调试若改 `lro=1` 必须提交前回滚。`git add config.ini` 前必须 review `git diff`，逐项确认无 `lcore_mask`/`vlan_filter`/`idle_sleep`/`portN` IP 等本地残留（`06` 文档四、`05` 文档 1.1）。

### E-02 单测 fixture 不含真实环境值【低】

- 新增 LRO fixture（`valid_lro_on.ini` 等）沿用测试私有网段（如 `192.168.*`），不得写本机真实 IP（`07` 文档 2.1）。

## 七、诚实边界（本文档新增坐实项）

1. **R-TSO-05 已由本文档编写阶段实测坐实**：`freebsd/sys/mbuf.h:735 CSUM_TSO=(CSUM_IP_TSO|CSUM_IP6_TSO)`，`:670 CSUM_IP6_TSO=0x1000`。结论：`ff_veth.c:304` 现状已能识别 IPv6 TSO 段，`04`/`05` 提出的扩展为冗余。这是对 spec 中"待坐实项"的一次前置消解，纠正方向为"可省该改动"，并已回填风险表。
2. 其余 LRO/virtio、`max_lro_pkt_size` 匹配、tsomax 精确值、多进程 per-queue、IPv6 扩展头等均为**运行时/后续里程碑验证项**，本轮不实测（对齐 `04` 文档四、`07` 文档第五节 HB-1..HB-7、`08` 文档六）。
3. 测试环境：DPDK 独占网卡 IP `<DPDK_NIC_IP>`（`ssh f-stack-client` 侧发起），内核栈测试走 `127.0.0.1` 的 `lo`。

## 八、软件 LRO / 软件 TSO / 软硬对接风险（第二轮补充）

> 依据 `11-软件LRO方案.md`、`12-软件TSO与分段方案.md`、`13-软硬offload对接方案.md`。软件 TSO 无开发（协议栈固有），无新增风险；风险集中在软件 LRO 接入与软硬对接。

### R-SWLRO-01 tcp_lro.c:1261 NULL 裸调用崩溃【高】

- **描述**：`tcp_lro_flush_all`（`tcp_lro.c:1199`）结尾 `tcp_lro.c:1261` 裸调 `tcp_hpts_softclock()`，而该函数指针 = NULL（`ff_stub_14_extra.c:627`）。若软件 LRO 走**现代模式**（`tcp_lro_queue_mbuf`+`tcp_lro_flush_all`）会解引用 NULL → 崩溃。
- **影响**：接通软件 LRO 若误用现代模式 → 运行时崩溃。
- **级别**：高。
- **控制措施**：**方案 A（经典模式）从路径规避**——用 `tcp_lro_init`+`tcp_lro_rx`+`tcp_lro_flush_inactive`（均不含 1261 裸调，`11` 文档 3 节）；备选方案 B（给 `tcp_hpts_softclock` 设空 stub）；方案 C（改 `tcp_lro.c:1261` 加判空）仅最后手段。默认 `lro=0` 时软件 LRO 完全不启用（零回归）。

### R-SWLRO-02 软硬 LRO 二次聚合【中】

- **描述**：硬件 LRO 与软件 LRO 若同时生效，硬件已聚合的大段再走软件 `tcp_lro_rx`，会二次聚合、可能超 `TCP_LRO_LENGTH_MAX`（`tcp_lro.h:200`）触发异常。
- **影响**：语义混乱、无收益、可能异常。
- **级别**：中。
- **控制措施**：`13` 文档 2.2/4 节的**互斥推导**——`hw_features.rx_lro` 与 `sw_lro` 在探测块互斥赋值（硬件支持→rx_lro=1,sw_lro=0；不支持且 lro=1→sw_lro=1），任一时刻只启用其一（4.2 真值表）。

### R-SWLRO-03 拥塞控制/RTT/ECN 精度下降【中】

- **描述**：软件 LRO 合并多段丢失各段到达时间和 IP 层 ECN 位，影响 RTT 采样精度与拥塞响应（外网 FreeBSD Journal / `03` 文档 4.1）。基础 FreeBSD 栈（非 RACK/BBR）走"拼大段注入 `if_input`"路径。
- **影响**：对时延敏感/拥塞敏感业务可能负收益。
- **级别**：中。
- **控制措施**：默认 `lro=0` 关闭；文档化提示对时延敏感业务不建议开启；`tcp_lro_flush_inactive` 超时参数控制最大暂存时延（`11` 文档 5.2）。

### R-SWLRO-04 IFCAP_LRO 条件未覆盖软件 LRO【中】

- **描述**：现状 `ff_veth.c:945-947` `IFCAP_LRO` 仅由 `hw_features.rx_lro` 驱动；软件 LRO 启用（`sw_lro=1, rx_lro=0`）时不声明 `IFCAP_LRO`，协议栈可能异常处理软件聚合大段。
- **影响**：软件 LRO 大段接收异常。
- **级别**：中。
- **控制措施**：`13` 文档 3.3——`IFCAP_LRO` 条件扩展为 `rx_lro || sw_lro`；推荐 `sw_lro` 纳入 `ff_hw_features`（`ff_config.h:112-118`）使 `ff_veth.c` 消费点统一。

### R-SWLRO-05 tcp_lro_rx 保序正确性【中】

- **描述**：`tcp_lro_rx`（`tcp_lro.c:1426`）对不可聚合包 `tcp_lro_flush_active`（`:1441`）保序，但聚合流与非聚合流交织时上送顺序需运行时确认。
- **级别**：中。
- **控制措施**：经典模式 flush_active 保序机制；**待运行时验证**（`11` 文档 7 节）。

### R-SW-06 软件 TSO 无风险【机制保证】

- 软件 TSO = 协议栈 MSS 分段（`12` 文档），协议栈固有能力，**无新增代码、无新增风险**。`rte_gso` 本轮不引入，无相关风险。
