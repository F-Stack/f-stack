# 外网调研：LRO / TSO 的 DPDK 与 FreeBSD 机制

> 调研 DPDK 官方文档、FreeBSD 机制与技术资料中关于 LRO / TSO 的权威结论，并与本仓库代码交叉核对。冲突处以代码 + 运行时实测为准。
> 调研对象：DPDK 24.11.6（本仓库 `dpdk-stable-24.11.6/`）、f-stack `lib/` + `freebsd/`。

## 1. LRO（Large Receive Offload）

### 1.1 概念（TSO/LRO/GRO 关系）

- **TSO（TCP Segmentation Offload）**：发送端卸载，网卡把上层传下的大 TCP 段按 MSS 硬件分片，减少 CPU 分段开销。
- **LRO（Large Receive Offload）**：接收端卸载，网卡把同一 TCP 流的多个小包**硬件聚合**成一个大段再上送协议栈，减少中断与协议栈处理次数。
- **GRO（Generic Receive Offload）**：LRO 的软件通用版（内核软聚合），DPDK 亦有 `rte_gro` 库。本项目 Q0 选定**硬件 LRO（DPDK offload）路径**，故以 `RTE_ETH_RX_OFFLOAD_TCP_LRO` 为主。
- 来源：Linux 内核 Segmentation Offloads 文档（kernel.org）、多篇技术博客（CSDN/华为云/GitHub 笔记）一致描述 TSO 提升发送端、LRO/GRO 提升接收端性能。

### 1.2 DPDK 硬件 LRO 的启用要求（官方，与代码交叉验证）

DPDK `struct rte_eth_rxmode`（`doc.dpdk.org` API，`lib/ethdev/rte_ethdev.h`）关键字段：

| 字段 | 说明 |
|------|------|
| `mtu` | Requested MTU |
| **`max_lro_pkt_size`** | **Maximum allowed size of LRO aggregated packet**（LRO 聚合包最大长度） |
| `offloads` | 用 `RTE_ETH_RX_OFFLOAD_*` 标记，且只能设置 `dev_info.rx_offload_capa` 中已声明支持的位 |

**启用硬件 LRO 的必要条件**：
1. `dev_info.rx_offload_capa & RTE_ETH_RX_OFFLOAD_TCP_LRO` 为真（PMD/网卡支持）。
2. `port_conf.rxmode.offloads |= RTE_ETH_RX_OFFLOAD_TCP_LRO`。
3. **必须设置 `port_conf.rxmode.max_lro_pkt_size`**（否则部分 PMD 拒绝或行为未定义）——这是聚合大段的上限，须与 mbuf 承载能力（data_room / scatter）匹配。
4. LRO 聚合的大段可能超过单 mbuf，需 mbuf 链（scatter）或足够大的 data_room 承载。

> **对本仓库的直接印证**：f-stack `ff_dpdk_if.c:890-897` 的 `#if 0` LRO 代码**只置了 offloads 位与 hw_features.rx_lro，未设置 `max_lro_pkt_size`**，且用的是旧宏 `DEV_RX_OFFLOAD_TCP_LRO`。即使解除 `#if 0` 也不完整——这正是本 spec LRO 全新开发需补齐的关键点（M1 须核对 24.11.6 头文件宏名与 max_lro_pkt_size 字段）。

### 1.3 DPDK 宏名演进（须 M1 核对）

- 旧版（≤19.x）：`DEV_RX_OFFLOAD_TCP_LRO`。
- 新版（20.11+ 命名规范化）：`RTE_ETH_RX_OFFLOAD_TCP_LRO`。DPDK 24.11 应以 `RTE_ETH_*` 为准，旧宏可能有兼容别名或已移除。本仓库 `#if 0` 内仍用旧宏，M1 须核对实际头文件。

## 2. TSO（TCP Segmentation Offload）

### 2.1 DPDK 官方 TSO mbuf 元信息要求（权威，doc.dpdk.org Mbuf Library）

启用 TSO 时，发送 mbuf **必须**正确设置以下字段与 ol_flags（以内层 TCP 为例）：

**必填 mbuf 字段**：
| 字段 | 取值 | 说明 |
|------|------|------|
| `mb->l2_len` | L2 头长度（以太头，含封装时到内层以太头） | **必填** |
| `mb->l3_len` | IP 头长度 | **必填** |
| `mb->l4_len` | TCP 头长度 | **必填** |
| `mb->tso_segsz` | 分段 MSS | **必填**（分段大小） |

**必填 ol_flags**：
```c
mb->ol_flags |= RTE_MBUF_F_TX_IPV4      /* 或 RTE_MBUF_F_TX_IPV6 */
             |  RTE_MBUF_F_TX_IP_CKSUM   /* IPv4 时 */
             |  RTE_MBUF_F_TX_TCP_CKSUM
             |  RTE_MBUF_F_TX_TCP_SEG;   /* 启用 TCP 分段 */
```

**伪头校验和要求（TSO 与普通 csum 的关键区别）**：
- IP 头 checksum 置 **0**。
- TCP checksum 填**不含 IP 负载长度**的伪头校验和，用 `rte_ipv4_phdr_cksum()`（IPv6 用 `rte_ipv6_phdr_cksum()`）计算。
- 限制：外层 L4 checksum 必须为 0（封装场景）。
- 硬件能力：需 `RTE_ETH_TX_OFFLOAD_TCP_TSO`。

> **对本仓库的核对要点（M1 坐实）**：f-stack `ff_dpdk_if.c:2448-2465` / `ff_memory.c:358-368` 预读**只见填 `l4_len`/`tso_segsz`**。按 DPDK 官方要求，`l2_len`/`l3_len`/`RTE_MBUF_F_TX_TCP_SEG` 标记/csum 标记/伪头校验和也是必填。M1 须逐字段坐实是否缺失——若缺 l2_len/l3_len 或 TCP_SEG 标记，则是 TSO 的确定性完善点。

### 2.2 IPv4 vs IPv6 TSO

- IPv4 TSO：`RTE_MBUF_F_TX_IPV4 | RTE_MBUF_F_TX_IP_CKSUM | RTE_MBUF_F_TX_TCP_SEG`，伪头用 `rte_ipv4_phdr_cksum`。
- IPv6 TSO：`RTE_MBUF_F_TX_IPV6 | RTE_MBUF_F_TX_TCP_SEG`（IPv6 无 IP 头校验和），伪头用 `rte_ipv6_phdr_cksum`。
- FreeBSD 侧：`CSUM_TSO`（IPv4）与 IPv6 TSO 标记（`CSUM_IP6_TSO`）路径不同，M1 须核对 f-stack `ff_veth.c:304-306` 是否区分 v4/v6。

### 2.3 虚拟化 virtio 环境 TSO/LRO

- 知乎《qemu 虚拟化环境 dpdk 网卡 tcp offloading》：virtio 后端需在 libvirt/qemu 配置 `tso4/tso6/csum` 等 feature，且宿主网卡 checksum 需开启；guest 侧 DPDK conf 的 `txmode.offloads` 置对应 TSO 位。
- 提示：**virtio 的 TSO/LRO 能力受后端协商（VIRTIO_NET_F_*）限制**，本机 virtio 是否支持 `RTE_ETH_RX_OFFLOAD_TCP_LRO` / `RTE_ETH_TX_OFFLOAD_TCP_TSO` 须运行时读 `dev_info` 确认，不可静态臆断（诚实边界）。

## 4. 软件路径外网调研（第二轮补充：软件 LRO/TSO + rte_gso/gro + 用户态栈范式）

> 由 web-researcher 子 agent 调研，来源均为公开权威资料；与 f-stack 代码冲突处以代码为准。

### 4.1 FreeBSD 软件 LRO（tcp_lro）

- **权威来源**：FreeBSD Journal《Introduction to TCP Large Receive Offload》(Randall Stewart / Michael Tüxen，中文镜像 github.com/FreeBSD-Ask/freebsd-journal-cn)；FreeBSD commit e69573bc2bee (2025-08-12, Netflix, reviews.freebsd.org/D51772)。
- **软件为主**：FreeBSD 绝大多数驱动用**单一软件 TCP LRO**（tcp_lro.c），仅少数网卡有硬件 LRO。软件 LRO 完全在协议栈/接口层做，不依赖网卡。
- **两种模式**（与代码坐实一致）：经典 `tcp_lro_init`+`tcp_lro_rx`（直接聚合）；现代 RSS 排序 `tcp_lro_init_args`+`tcp_lro_queue_mbuf`（成对数组满时 `tcp_lro_flush_all` 先排序让同流相邻再进 `tcp_lro_rx_common` 查哈希表聚合）。均用 `tcp_lro_free` 释放。
- **演进**：2006 Gallatin(mxge)→2008 Vogel(通用化)→2012 Zeeb(IPv6)→2016 Selasky(排序路径，解决早期"仅 8 连接"限制)。
- **iflib 接入范式（用户态栈接入软件 LRO 的最标准参考）**：commit e69573bc2bee 把 iflib 改为 RSS 排序的 `tcp_lro_queue_mbuf`——收包循环前查 `lro_enabled`，启用则对每包 `tcp_lro_queue_mbuf(&rxq->ifr_lc, m)` 后 continue，一个 burst 收完 `tcp_lro_flush_all(&lc)` 统一排序+聚合+注入栈；生命周期 `init_args→queue_mbuf→flush_all→free`。**f-stack 在 DPDK 收 burst 后、交 FreeBSD 栈前插入这套调用即可，是与移植栈最契合的做法**。
- **软件 vs 硬件 LRO**：软件 LRO 有合并 CPU 开销，但通过减少 TCP 栈调用次数、降 cache miss 净收益；硬件 LRO 零 CPU 开销但网卡支持有限、灵活性差。
- **⚠ 副作用（spec 须重点提示）**：合并丢失各段接收时间和 IP 层 ECN 位，对拥塞控制/丢包恢复有负面影响。现代栈（RACK/BBR）靠 HPTS + mbuf-queueing + 压缩 ACK 保留每 ACK 信息；基础 FreeBSD TCP 栈不用 HPTS，走"拼大段注入接口层"路径。
- **tunable**：`net.inet.tcp.lro.entries`（loader 可调）；驱动侧 `ifconfig lro/-lro`。

### 4.2 软件 TSO / GSO（本质=协议栈延迟分段）

- **权威来源**：Linux kernel segmentation-offloads 文档（kernel.org）。
- **结论**：**"软件 TSO" = 协议栈延迟分段**（GSO，发送前按 MSS 分段）。网卡无 TSO 时协议栈本就自然按 MSS 拆成 MTU 大小包——协议栈固有能力，**非需额外开发**。Linux 叫 GSO，FreeBSD 在 tcp_output 按 `t_maxseg` 分段。Linux 明确："启用硬件分段 offload 前 GSO 里必须有软件 offload 兜底"——硬件 TSO 是 GSO 的加速版，软件路径永远存在。**与 f-stack 代码坐实（5.2）完全一致**。

### 4.3 DPDK GRO / GSO 库

- **权威来源**：DPDK 官方 Generic Receive/Segmentation Offload Library 文档（doc.dpdk.org）；Intel 胡嘉瑜中文文章（cloud.tencent.com）。
- **rte_gro（接收软聚合）= 硬件 LRO 软件替代**（DPDK 17.08）：轻量 `rte_gro_reassemble_burst`（栈上表，一次调用）；重量 `rte_gro_ctx_create`+`rte_gro_reassemble`（每包）+`rte_gro_timeout_flush`（取结果，**非 rte_gro_get_pkt**）。支持 TCP/IPv4、UDP/IPv4、VxLAN；**限制**：不支持 IPv4 Options/VLAN、仅单 mbuf、不重算校验和、非线程安全、调用前须手动填 l2/l3/l4_len。
- **rte_gso（发送软分段）= 硬件 TSO 软件替代**（DPDK 17.11）：`rte_gso_segment`，two-part mbuf（direct 存包头副本 + indirect 指向原负载偏移，零拷贝）。**限制**：须显式调库、不自动 fallback、不重算校验和、目前仅 IPv4、出口驱动须支持多段包。
- **DPDK 定位**：面向网卡无硬件 offload / VxLAN·GRE 隧道（硬件常不支持）/ 软件转发降每包开销场景。

### 4.4 用户态协议栈 offload + virtio 协商

- 用户态栈（f-stack/mTCP/seastar）处理 LRO/TSO 两条路：(a) 依赖硬件 offload（DPDK tx/rx offload 位）；(b) 软件实现（DPDK rte_gro/rte_gso 或移植 FreeBSD 软件 tcp_lro）。f-stack 移植 FreeBSD 栈，**具备移植软件 tcp_lro 的天然条件**（4.1 iflib 范式），发送分段本就是协议栈固有能力（4.2）。
- **virtio offload feature 协商**（virtio-net spec）：TSO=`VIRTIO_NET_F_HOST_TSO4/6`（host 对 guest 大段分段）/`VIRTIO_NET_F_GUEST_TSO4/6`（guest 收合并大段=接收端 LRO）；UFO=`HOST/GUEST_UFO`；csum=`VIRTIO_NET_F_CSUM/GUEST_CSUM`。初始化时协商取交集，DPDK virtio PMD 据结果宣告 offload capa。**本机 virtio 实测不支持 TSO/LRO（`guest_features=0x110ef8020`）与此一致**。

### 4.5 f-stack 社区（如实说明访问局限）

- 外网**未检索到 F-Stack 仓库关于软件 LRO 接入/rte_gro 集成的公开 issue/PR/wiki 专题**（搜索返回多为通用 LRO/TSO/GRO/GSO 概念文章，非 f-stack 专属）。符合预期：f-stack 的 LRO/TSO 处理在"FreeBSD 栈 + DPDK offload 位/ff_veth"层面，非独立社区专题。**结论以仓库内代码实证为权威依据**。

## 5. 小结

- **LRO**：DPDK 官方明确硬件 LRO 需 `offloads` 位 + `max_lro_pkt_size` + 大段 mbuf 承载三者齐备；f-stack 当前 `#if 0` 代码三者均不完整，需全新开发。宏名须更正为 `RTE_ETH_RX_OFFLOAD_TCP_LRO`。
- **TSO**：DPDK 官方要求 l2/l3/l4_len + tso_segsz + `RTE_MBUF_F_TX_TCP_SEG` + csum 标记 + 伪头校验和齐备；f-stack 疑缺 l2_len/l3_len 或标记（M1 坐实），且 IPv6 TSO 路径须核对——这些是 TSO 完善点。
- 所有外网结论须与 M1 实际代码交叉验证，冲突以代码为准。
