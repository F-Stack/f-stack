# F-Stack LRO/TSO 方案与架构设计（中文）

> 文档层级：方案与架构设计（M3 阶段产出之一）
> 设计依据：`01-需求规格.md`、`02-现状与差距分析.md`、`03-外网调研.md`（均为 M1 坐实结论）。
> 权威版本：DPDK `dpdk-stable-24.11.6`、FreeBSD 15.0 移植（`f-stack/freebsd/`）。
> 铁律：本轮**不写代码、不改 lib、不提交**，仅出可落地方案。所有代码引用附精确 `file:line`，凡涉及具体 PMD 行为一律标注"**待运行时验证**"。

## 0. 设计总纲

### 0.1 两条主线

- **LRO（全新开发）**：采用**硬件 LRO / DPDK offload 路径**，六层逐层打通（配置 → 能力探测 → rxmode 使能 → 收包路径 → ifnet/协议栈 → 默认关闭零回归）。软件 LRO（`tcp_lro.c`）非本轮首选。
- **TSO（完善）**：在不破坏现有 IPv4 TSO 的前提下补齐 IPv6 TSO、`RTE_MBUF_F_TX_IP_CKSUM` 自洽、`if_hw_tsomax` 上限、双份重复逻辑收敛、组合约束。

### 0.2 设计不变量（贯穿全案）

1. **默认关闭零回归**：`dpdk.lro=0`、`dpdk.tso=0`（默认值）时，代码路径与现状逐字节一致，不引入任何行为改变。所有新增逻辑都必须挂在 `if (dpdk.lro)` / `if (offload.tso_seg_size)` 等既有开关之下。
2. **能力探测门控**：任何 offload 位只有在 `dev_info.rx_offload_capa` / `tx_offload_capa` 宣告支持时才置位（沿用 `ff_dpdk_if.c:901-906`、`931-942` 的既有范式）。
3. **代码为准**：宏名以 DPDK 24.11.6 `rte_ethdev.h` 为唯一权威（LRO 宏 = `RTE_ETH_RX_OFFLOAD_TCP_LRO`，`rte_ethdev.h:1556`）。
4. **lib 最小注释**：新增代码只在契约/不直观处加简洁注释。

## 一、LRO 硬件 offload 完整方案（六层逐层设计）

### 1.1 配置层：新增 `dpdk.lro` 配置项

**设计目标**：给 LRO 一个用户可控开关，语义与 `tso` 完全对称（默认关闭）。

- **config.ini**：在 `[dpdk]` 段 `tso=0`（`config.ini:22`）附近新增（注释形式，随特性入库，本地测试值不改）：
  ```ini
  # TCP large receive offload, default: disabled.
  lro=0
  ```
- **ff_config.h（结构）**：`struct ... dpdk`（`ff_config.h:288-300`）在 `int tso;`（L295）后新增 `int lro;` 成员。`struct ff_hw_features` 的 `uint8_t rx_lro;`（L114）**已存在**，无需新增，本轮将其从"死字段"激活为真实生产/消费。
- **ff_config.c**：
  - 默认值：`ff_default_config`（若存在集中默认设置处）或初始化路径中令 `dpdk.lro = 0`（与 `tso` 默认关闭一致）。
  - 解析分支：`ini_parse_handler`（`ff_config.c:1054-1057` 附近，紧邻 `MATCH("dpdk","tso")`）新增
    ```c
    } else if (MATCH("dpdk", "lro")) {
        pconfig->dpdk.lro = atoi(value);
    }
    ```
- **语义**：`lro=0`（默认）不触碰任何 LRO 代码路径；`lro=1` 进入能力探测。

**风险**：低。纯新增开关，默认 0 无回归。

### 1.2 能力探测层：解除 `#if 0`、更正宏、按能力探测

**现状**：`ff_dpdk_if.c:891-898` LRO 块被 `#if 0` 包裹，且用**已移除的旧宏** `DEV_RX_OFFLOAD_TCP_LRO`（24.11.6 搜索 0 命中，启用即编译失败）。

**方案**（重写该块，去掉 `#if 0`，挂在 `dpdk.lro` 开关下）：

```c
if (ff_global_cfg.dpdk.lro) {
    if (dev_info.rx_offload_capa & RTE_ETH_RX_OFFLOAD_TCP_LRO) {
        ff_log(FF_LOG_INFO, FF_LOGTYPE_FSTACK_LIB, "LRO is supported\n");
        port_conf.rxmode.offloads |= RTE_ETH_RX_OFFLOAD_TCP_LRO;
        pconf->hw_features.rx_lro = 1;
        /* max_lro_pkt_size 设置见 1.3 */
    } else {
        ff_log(FF_LOG_INFO, FF_LOGTYPE_FSTACK_LIB, "LRO is not supported\n");
    }
} else {
    ff_log(FF_LOG_INFO, FF_LOGTYPE_FSTACK_LIB, "LRO is disabled\n");
}
```

- **宏更正**：`DEV_RX_OFFLOAD_TCP_LRO` → `RTE_ETH_RX_OFFLOAD_TCP_LRO`（`rte_ethdev.h:1556`，`= RTE_BIT64(4)`）。
- **范式对齐**：与相邻 RX csum 探测（L901-906）、TSO 探测（L931-942）三段一致（先判 capa、再置 offloads、再置 hw_features、否则日志）。
- **生产者激活**：`pconf->hw_features.rx_lro = 1` 是 `rx_lro` 字段的**唯一生产点**，供收包层与 ifnet 层消费。

**风险**：低（仅在 `lro=1` 且 PMD 支持时生效）。**待运行时验证**：virtio 是否在 `rx_offload_capa` 宣告 LRO 位（03 文档 2.3：virtio 能力受后端 `VIRTIO_NET_F_*` 协商限制）。

### 1.3 rxmode 使能层：`max_lro_pkt_size` 设置及与 mtu/data_room/scatter 关系

**外网结论（03 文档 1.2）**：硬件 LRO 必须设 `port_conf.rxmode.max_lro_pkt_size`（`rte_ethdev.h:432` "Maximum allowed size of LRO aggregated packet"），否则部分 PMD 拒绝/行为未定义。

**方案**：在 1.2 置 offloads 位的同时设置 `max_lro_pkt_size`：

- **上限来源**：PMD 在 `dev_info.max_lro_pkt_size`（`rte_ethdev.h:1792` "Maximum configurable size of LRO aggregated packet"）宣告可配置上限。设计取值：
  ```c
  uint32_t lro_cap = dev_info.max_lro_pkt_size;
  port_conf.rxmode.max_lro_pkt_size =
      (lro_cap != 0) ? lro_cap : <保守默认，如 64KB 内且 >= mbuf 承载能力>;
  ```
  即优先采用 PMD 宣告上限；若 PMD 未宣告（为 0），取一个保守默认（不超过 mbuf 链可承载）。
- **与 mtu（jumbo）关系**：LRO 聚合大段远超单帧 MTU（这正是 LRO 目的）。`max_lro_pkt_size` 是聚合后上限，与单帧 `mtu`/`max_rx_pktlen`（`ff_dpdk_if.c:954+` MTU 校验）是不同维度：MTU 约束单帧、`max_lro_pkt_size` 约束聚合段。二者不冲突，但需保证 `max_lro_pkt_size >= mtu`。
- **与 data_room/scatter 关系**：聚合大段通常超过单 mbuf `data_room`，PMD 会用 **mbuf 链（scatter）** 承载。因此启用 LRO 时应确保 mbuf pool 的 `data_room` 足够或 RX scatter 可用（收包路径已支持多段链，见 1.4）。**待运行时验证**：本环境 mbuf pool data_room 与 `max_lro_pkt_size` 的匹配关系。
- **与 RSS 关系**：LRO 仅聚合**同一流**报文，RSS 将不同流分散到不同队列本身与 LRO 正交、互补（同队列内同流才聚合）。无需特殊处理。
- **与 RX csum 关系**：LRO 大段的 csum 校验由 PMD 在聚合时完成并置 `RTE_MBUF_F_RX_L4_CKSUM_GOOD`/`BAD`；收包层 csum 检查逻辑（`ff_dpdk_if.c:1698-1703`）对大段同样适用（见 1.4）。
- **与时间戳关系**：LRO 大段的时间戳取聚合中某报文时间戳，`ff_veth_input:1718-1722` 逻辑不变。

**风险**：中。`max_lro_pkt_size` 取值不当可能被 PMD 拒绝；须运行时按 `dev_info` 校准。

### 1.4 收包路径层：`ff_veth_input` 处理 LRO 大段

**现状**：`ff_veth_input`（`ff_dpdk_if.c:1694-1742`）已能凭 `pkt->pkt_len`（整链总长，L1708）+ 多段遍历（L1725-1739）把大段搬进 FreeBSD mbuf 链，但**无 `RTE_MBUF_F_RX_LRO` 感知**。

**关键洞察（坐实）**：现有收包路径在"**长度搬运**"维度**已天然支持 LRO 大段**——`ff_mbuf_gethdr(pkt, pkt->pkt_len, ...)`（L1708）用整链总长建 mbuf 头，`while(pn)` 循环（L1727-1738）逐段挂链。故 LRO 大段的数据搬运不需要重构。

**方案（最小侵入）**：

1. **csum 标记透传**：LRO 大段由 PMD 完成 csum 校验。现有 `rx_csum` 检查（L1698-1703）对 `RTE_MBUF_F_RX_L4_CKSUM_BAD` 丢包的逻辑对 LRO 段依然正确（PMD 保证聚合段 csum 语义）。`ff_mbuf_gethdr` 在 `rx_csum` 时置 `CSUM_DATA_VALID|CSUM_PSEUDO_HDR`（`ff_veth.c:479-483`），对 LRO 段同样成立。
2. **LRO 标记感知（可选增强）**：若需向协议栈传递"这是 LRO 合并段"信息，可在 `ff_veth_input` 检测 `pkt->ol_flags & RTE_MBUF_F_RX_LRO`，并（在 `ff_mbuf_gethdr` 扩展入参或后续设置）给 FreeBSD mbuf 置对应语义。**但 FreeBSD 侧 LRO 段接收主要依赖 `IFCAP_LRO` 能力位（见 1.5）与 mbuf 长度**，`RTE_MBUF_F_RX_LRO` 的透传对协议栈接收非必需——**FreeBSD `if_input` 按 mbuf 长度与 TCP 头正常收取大段**。故本设计将 `RTE_MBUF_F_RX_LRO` 感知列为**可选**，首版可仅依赖长度搬运 + `IFCAP_LRO`。
3. **nb_segs/pkt_len**：无需改动。`pkt->pkt_len`（整链）与 `pkt->nb_segs`（PMD 已填）由既有多段遍历正确消费。
4. **与 `ff_mbuf_gethdr` 适配**：无需改签名；`total=pkt->pkt_len` 已是聚合总长。

**诚实边界（待运行时验证）**：LRO 大段能否被 FreeBSD 协议栈无缝接收，取决于 (a) `IFCAP_LRO` 是否已声明、(b) 协议栈对超 MTU TCP 段的接收处理。02 文档 1.5 已标注此为主要运行时风险点。

**风险**：中。数据搬运已具备，风险在协议栈接收侧（运行时验证）。

### 1.5 ifnet/协议栈层：设置 `IFCAP_LRO`

**现状**：`ff_veth.c:941-956` 设 `IFCAP_RXCSUM/TXCSUM/TSO`，**无 `IFCAP_LRO`**（全 lib 搜索 0 命中）。

**方案**：在 `ff_veth.c` 能力设置块（L941-954）新增，挂在 `rx_lro` 下：

```c
if (cfg->hw_features.rx_lro) {
    if_setcapabilitiesbit(ifp, IFCAP_LRO, 0);
}
```

- 位置：与 `IFCAP_TSO`（L951-953）并列，`if_setcapenable(ifp, if_getcapabilities(ifp))`（L956）会自动使能。
- 作用：向 FreeBSD 协议栈声明本接口支持 LRO，使协议栈按 LRO 语义接收大段（不将超 MTU 段视为异常）。
- LRO 与 TSO 不同，收方向无 `CSUM_*` hwassist 需求，仅需 `IFCAP_LRO` 能力位。

**风险**：低。仅在 `rx_lro=1` 时声明。

### 1.6 LRO 数据流图

```
[网卡硬件 LRO 聚合同流多报文]
        │  (dev_info.rx_offload_capa & RTE_ETH_RX_OFFLOAD_TCP_LRO)
        ▼
[PMD] 产出大段 rte_mbuf: pkt_len 大、可能 nb_segs>1、ol_flags |= RTE_MBUF_F_RX_LRO
        │  rxmode.offloads |= RTE_ETH_RX_OFFLOAD_TCP_LRO; max_lro_pkt_size 已设
        ▼
[ff_veth_input  ff_dpdk_if.c:1694]
   ├─ rx_csum 检查 (L1698-1703)：PMD 已校验聚合段 csum
   ├─ ff_mbuf_gethdr(pkt, pkt->pkt_len, ...) (L1708)：以聚合总长建 mbuf 头
   └─ while(pn) 遍历多段挂链 (L1725-1739)：scatter 大段逐段挂
        ▼
[FreeBSD mbuf 链]  m_pkthdr.len = 聚合总长, csum_flags 标 VALID
        ▼
[ff_veth_process_packet → if_input  ff_veth.c:510-518]
        │  接口已声明 IFCAP_LRO (ff_veth.c 新增)
        ▼
[FreeBSD TCP 协议栈]  按 LRO 语义接收大段，降低 per-packet 开销
```

### 1.7 LRO 与多进程（primary/secondary）交互

- offload 能力探测与 `port_conf` 配置在 **primary 进程**的端口初始化路径完成（`ff_dpdk_if.c` 端口 setup）；secondary 进程共享已配置端口。
- `hw_features.rx_lro` 属 per-port 配置（`pconf->hw_features`），secondary 通过共享配置读取，ifnet 能力声明在各进程 `ff_veth_setup` 时按 `cfg->hw_features.rx_lro` 一致设置。
- **待运行时验证**：多进程下 LRO 聚合是否按 per-queue 正确工作（RSS 分流到各进程队列，同队列内同流聚合）。

## 二、TSO 完善方案

### 2.1 IPv6 TSO：offload 填充按 IP version 分流

**现状（坐实）**：`ff_dpdk_if.c:2455-2465` 与 `ff_memory.c:358-368` 的 TSO 分支**无条件**用 `rte_ipv4_phdr_cksum(iph, RTE_MBUF_F_TX_TCP_SEG)`（仅 IPv4 伪头）+ IPv4 头结构强转 + `iph_len = (version_ihl & 0x0f)<<2`（IPv4 IHL），IPv6 大段 TSO 时伪头算错、`l3_len` 算错。而上游 `ff_mbuf_tx_offload`（`ff_veth.c:304-306`）对 `CSUM_TSO` 只填 `tso_seg_size`，不带 v4/v6 信息，下游只能靠 `iph->version` 判断——但下游恰恰没按 version 分流。

**方案**：TSO 分支按 `iph->version` 分流（两处同步修改）：

```c
if (offload.tso_seg_size) {
    struct rte_tcp_hdr *tcph;
    int tcph_len;

    if (iph->version == 4) {                 /* 沿用 L2415/L2426 iph_len 计算 */
        tcph = (struct rte_tcp_hdr *)((char *)iph + iph_len);
        tcph_len = (tcph->data_off & 0xf0) >> 2;
        head->ol_flags |= RTE_MBUF_F_TX_IPV4 | RTE_MBUF_F_TX_IP_CKSUM;  /* 见 2.2 */
        tcph->cksum = rte_ipv4_phdr_cksum(iph, RTE_MBUF_F_TX_TCP_SEG);
        head->l3_len = iph_len;              /* IPv4 IHL */
    } else {
        struct rte_ipv6_hdr *ip6h = (struct rte_ipv6_hdr *)iph;
        int ip6_len = sizeof(struct rte_ipv6_hdr);   /* 固定 40，扩展头见下 */
        tcph = (struct rte_tcp_hdr *)((char *)ip6h + ip6_len);
        tcph_len = (tcph->data_off & 0xf0) >> 2;
        head->ol_flags |= RTE_MBUF_F_TX_IPV6;         /* IPv6 无 IP_CKSUM */
        tcph->cksum = rte_ipv6_phdr_cksum(ip6h, RTE_MBUF_F_TX_TCP_SEG);
        head->l3_len = ip6_len;
    }

    head->ol_flags |= RTE_MBUF_F_TX_TCP_SEG;
    head->l2_len = RTE_ETHER_HDR_LEN;        /* TSO 分支自洽，不依赖前置分支 */
    head->l4_len = tcph_len;
    head->tso_segsz = offload.tso_seg_size;
}
```

- **IPv6 伪头**：`rte_ipv6_phdr_cksum`（DPDK `rte_ip.h`），03 文档 2.2 明确 IPv6 TSO 用之、无 IP 头校验和。
- **l3_len**：IPv6 基本头固定 40（`sizeof(struct rte_ipv6_hdr)`）。
- **扩展头处理（诚实边界）**：若 IPv6 报文含扩展头（Hop-by-Hop/Routing/Fragment 等），`l3_len` 应为"以太头到 TCP 头之间的全部 IPv6 头长"。首版可先支持无扩展头场景（`l3_len=40`），扩展头场景标注**待运行时验证/后续增强**（需解析 `next_header` 链）。TSO 通常用于大流量 TCP，扩展头少见，风险可控。
- **l2_len 自洽**：将 `l2_len=RTE_ETHER_HDR_LEN` 移入 TSO 分支内，避免依赖前置 `tcp_csum` 分支是否命中（现状 L2436 在 tcp_csum 分支才填 l2_len，若该分支未命中则 l2_len 缺失）。

**风险**：中。IPv6 扩展头场景为已知边界；核心无扩展头场景可落地。

### 2.2 IP_CKSUM 自洽：IPv4 TSO 分支显式置 `RTE_MBUF_F_TX_IP_CKSUM`

**现状**：TSO 分支（L2455-2465）**未显式**置 `RTE_MBUF_F_TX_IP_CKSUM`，依赖 `offload.ip_csum`（来自 `CSUM_IP`）恰好命中 `if (offload.ip_csum)` 分支（L2410-2420）才置位。DPDK 语义（03 文档 2.1/2.2）要求 IPv4 TSO 同时请求 IP 校验和卸载并把 IP 头 checksum 写 0。

**方案**：如 2.1 代码所示，IPv4 分支内**显式**置 `RTE_MBUF_F_TX_IP_CKSUM`，使 TSO 自洽、不依赖外部分支命中。IPv6 分支**不置**（IPv6 无 IP 头校验和）。

**风险**：低。IPv4 TSO 本就应带 IP_CKSUM，显式置位更符合 DPDK 契约。

### 2.3 `if_hw_tsomax` 系列上限设置

**现状（坐实）**：`ff_veth.c:951-953` 只设 `IFCAP_TSO` + `CSUM_TSO`，**从不设** `if_hw_tsomax`/`tsomaxsegcount`/`tsomaxsegsize`（全 lib 搜索 0 命中）。FreeBSD `tcp_output.c:905-931` 仅当 `if_hw_tsomax != 0`（L927）才用上限约束 `max_len`，`tcp_m_copym`（L1093-1095）据此约束分段。上限为 0 时 TSO 段长不受接口约束，可能超 PMD 单包/段数能力。

**方案**：在 `ff_veth.c` 设 `IFCAP_TSO` 附近（L951-953）新增上限设置：

```c
if (cfg->hw_features.tx_tso) {
    if_setcapabilitiesbit(ifp, IFCAP_TSO, 0);
    if_sethwassistbits(ifp, CSUM_TSO, 0);
    if_sethwtsomax(ifp, <IP_MAXPACKET 或按 max_mtu 推导>);       /* 总长上限 */
    if_sethwtsomaxsegcount(ifp, <PMD 能力，如 nb_mbuf_segs>);    /* 段数上限 */
    if_sethwtsomaxsegsize(ifp, <单段上限，如 mbuf data_room>);   /* 段大小上限 */
}
```

- **取值原则**：
  - `if_hw_tsomax`：TSO 前大段总长上限。FreeBSD 传统默认 `IP_MAXPACKET`（65535 - 头）；jumbo 场景与 `max_mtu`（`ff_config.c:1070-1072`）相关，但 TSO 段总长上限本质由 IP 长度字段（≤65535）决定，可取 `IP_MAXPACKET - sizeof(以太头)` 附近保守值。
  - `if_hw_tsomaxsegcount`：PMD 单次发送可接受的 mbuf 段数上限（与 tx 队列/PMD 能力相关）。
  - `if_hw_tsomaxsegsize`：单段字节上限（通常为 mbuf `data_room` 或页大小）。
- **诚实边界（待运行时验证）**：`tsomaxsegcount`/`tsomaxsegsize` 的精确值依赖具体 PMD（virtio/ixgbe/i40e 各异），DPDK 未在 `dev_info` 直接提供等价"TSO 段数上限"字段。首版可取保守默认（如 segcount=一个安全值、segsize=data_room），并标注运行时按 PMD 校准。设置**非 0** 上限本身即比现状（全 0、不约束）更安全。

**风险**：中。取值偏小会限制 TSO 效率、偏大可能超 PMD 能力；保守默认 + 运行时校准可控。设 API 名（`if_sethwtsomax` 等）以 FreeBSD 15.0 `if_var.h`/`if.h` 实际导出为准（编码阶段 read_file 复核）。

### 2.4 双份重复逻辑收敛方案

**现状**：`ff_dpdk_if.c:2405-2472`（`ff_dpdk_if_send` 主路径）与 `ff_memory.c:331-375`（另一发包路径）offload 填充**逻辑几乎逐行相同**，修 IPv6 需同改两处，易漏。

**收敛方案（分级）**：

- **方案 A（首选，低风险）**：抽取公共函数 `ff_fill_tx_offload(struct rte_mbuf *head, void *data, const struct ff_tx_offload *offload, uint8_t tx_csum_l4)`，把 2.1/2.2 的 version 分流逻辑集中一处，两个调用点改为调用该函数。收敛后 IPv6/IP_CKSUM 修复只需改一处。
- **方案 B（保守，本轮如时间紧）**：两处**同步修改**相同逻辑，并在两处加交叉引用注释（"与 ff_memory.c:358 逻辑一致，修改需同步"）。风险是未来仍可能分叉。

**建议**：编码里程碑优先方案 A（收敛），若收敛涉及头文件/编译单元依赖复杂，退方案 B 并显式标注同步约束。**收敛函数应放在两处都可 include 的公共 c/h**（如 `ff_dpdk_if.c` 与 `ff_memory.c` 共同依赖处），避免循环依赖。

**风险**：中（方案 A 有跨编译单元重构风险，需 clean build 验证）；低（方案 B）。

### 2.5 与 `tx_csum_offoad_skip` / scatter / jumbo 的组合约束

- **与 `tx_csum_offoad_skip`**：现状 TSO 使能（`ff_dpdk_if.c:931-942`）**不受** `tx_csum_offoad_skip` 约束，而 L4 csum offload 使能（L914-926）在 `skip=0` 时才置 `tx_csum_l4`。TSO 隐含需要 L4 csum offload（`RTE_MBUF_F_TX_TCP_SEG` 隐含 TCP CKSUM）。**约束设计**：
  - 若 `tx_csum_offoad_skip=1`（跳过 L4 csum offload）同时 `tso=1`，属**不一致组合**。方案：在 TSO 使能处（L931）增加一致性判断——当 `tx_csum_offoad_skip` 为真时，记 WARN 日志提示"TSO 依赖 L4 csum offload，当前被 skip，TSO 可能不生效"，或将 TSO 使能也纳入 `skip==0` 前提。**首选记 WARN 不强改行为**（避免改变既有默认路径），把互斥关系文档化 + 日志化。
- **与 scatter / MULTI_SEGS**：TSO 前大段本就是多段场景，发包路径（`ff_dpdk_if.c:2360-2403`）已支持多段 mbuf 链。`tso_segsz` + `nb_segs` 组合的 PMD 约束由 2.3 的 `tsomaxsegcount`/`tsomaxsegsize` 上限保护。
- **与 jumbo（`mtu_enable`）**：TSO 段总长上限（2.3 `if_hw_tsomax`）与 jumbo MTU 相互制约。TSO 段总长受 IP 长度字段（≤65535）限制，与单帧 MTU（jumbo 可到 9000+）是不同维度，二者不冲突；`if_hw_tsomax` 保证总长不越界。

**风险**：低（以日志+文档化约束为主，不强改既有路径）。

### 2.6 `ff_mbuf_tx_offload` 兼容 `CSUM_IP6_TSO`

**现状**：`ff_veth.c:304-306` 只识别 `CSUM_TSO`（`if (csum_flags & CSUM_TSO)`），FreeBSD 侧 IPv6 TSO 可能置 `CSUM_IP6_TSO`（02 文档 2.5：FreeBSD 15.0 原生支持 IPv6 TSO，`CSUM_IP6_TSO|CSUM_TSO` 在 netinet 命中 6 文件）。

**方案**：扩展识别 `CSUM_IP6_TSO`，使 IPv6 TSO 标记也能被映射为 `tso_seg_size`：

```c
if (mb->m_pkthdr.csum_flags & (CSUM_TSO | CSUM_IP6_TSO)) {
    offload->tso_seg_size = mb->m_pkthdr.tso_segsz;
}
```

- **诚实核对（编码阶段 read_file 复核）**：需确认 FreeBSD 15.0 移植中 `CSUM_TSO` 与 `CSUM_IP6_TSO` 的宏定义关系——部分 FreeBSD 版本 `CSUM_IP6_TSO` 定义即包含/等价 `CSUM_TSO` 位，若如此则现状 `CSUM_TSO` 单判可能已覆盖 v6（需坐实 `sys/mbuf.h`/`freebsd/sys/... mbuf` 宏值）。**若 `CSUM_IP6_TSO` 与 `CSUM_TSO` 是不同位，则此扩展必需**；若等价则此步可省。此点列为编码阶段第一项坐实。
- `ff_tx_offload` 为协议无关（`ff_veth.c:290-291` 注释），`tso_seg_size` 不带 v4/v6，下游靠 `iph->version` 分流（2.1 已解决）。因此本层只需保证 IPv6 TSO 请求能被识别为"需要 TSO"，version 判断交给下游。

**风险**：低。核对宏关系后为一行扩展。

## 三、方案交互矩阵与全局约束

| 特性/交互 | LRO | TSO |
| --- | --- | --- |
| 默认关闭零回归 | `lro=0` 不触碰 LRO 路径 | `tso=0` 不触碰 TSO 路径 |
| 能力探测门控 | `rx_offload_capa & RTE_ETH_RX_OFFLOAD_TCP_LRO` | `tx_offload_capa & RTE_ETH_TX_OFFLOAD_TCP_TSO`（现状已有） |
| RX/TX csum | LRO 段 csum 由 PMD 校验，收包检查逻辑复用 | TSO 隐含 L4 csum，与 `tx_csum_offoad_skip` 约束（2.5） |
| RSS | 正交（同流同队列内聚合） | 无关 |
| 时间戳 | 大段取聚合内时间戳，逻辑不变 | 无关 |
| jumbo/MTU | `max_lro_pkt_size >= mtu`；聚合超 MTU 正常 | `if_hw_tsomax` 约束总长（≤65535 维度） |
| scatter/MULTI_SEGS | 大段用 mbuf 链承载（收包已支持多段） | TSO 前大段多段（发包已支持），受 tsomaxseg* 约束 |
| 多进程 | per-port 能力、per-queue 聚合（待运行时验证） | per-port 使能，一致设置 |

## 四、诚实边界汇总（待运行时验证清单）

1. virtio（本机）是否在 `dev_info.rx_offload_capa` 宣告 `RTE_ETH_RX_OFFLOAD_TCP_LRO`（03 文档 2.3）。
2. `max_lro_pkt_size` 取值与 mbuf pool `data_room`/scatter 承载能力的匹配。
3. LRO 大段经 `IFCAP_LRO` 后被 FreeBSD 协议栈无缝接收的正确性（02 文档 1.5 主风险点）。
4. IPv6 含扩展头场景的 `l3_len` 精确计算（2.1 首版仅支持无扩展头）。
5. `if_hw_tsomaxsegcount`/`tsomaxsegsize` 与具体 PMD 能力的精确匹配（2.3）。
6. `CSUM_IP6_TSO` 与 `CSUM_TSO` 在 FreeBSD 15.0 移植中的宏位关系（2.6，编码阶段坐实）。
7. 多进程 primary/secondary 下 LRO 聚合的 per-queue 行为（1.7）。

> 以上均为运行时/后续里程碑验证项，本轮 spec 不实测。测试环境：DPDK 独占网卡 IP `<DPDK_NIC_IP>`（`ssh f-stack-client` 侧发起），内核栈测试走 `127.0.0.1` 的 `lo`。
