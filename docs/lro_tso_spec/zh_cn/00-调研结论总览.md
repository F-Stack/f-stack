> 结论先行文档。所有结论以**实际代码**（`lib/` + `freebsd/` + DPDK 24.11.6 头文件）+ **外网权威资料**交叉验证，冲突处以代码为准。
> 本轮范围：**仅产出中文 spec 文档，不写代码、不改 lib、不出英文版**。

## 一句话结论（本轮 plan mode 预读，M1 须代码复核）

- **LRO：当前不支持**。DPDK 层 LRO 启用代码被 `#if 0` 完全注释掉（`ff_dpdk_if.c:890-897`），且用旧宏 `DEV_RX_OFFLOAD_TCP_LRO`；无 `config.ini`/`ff_config.c` 配置项；收包路径 `ff_veth_input→if_input` 未接 LRO 语义。需全新开发接通「配置项 → dev_info 能力探测 → rxmode.offloads → 收包路径/IFCAP_LRO → 协议栈」完整通路。
- **TSO：已支持，有可完善点**。DPDK tx offload 启用（`ff_dpdk_if.c:931-942`）+ offload 信息填充（`ff_veth.c:304-306`、`ff_memory.c:358-368`、`ff_dpdk_if.c:2448-2465`）；但预读仅见 `l4_len`/`tso_segsz` 填充，`l2_len`/`l3_len` 是否填充、IPv6 TSO、与 csum/scatter/jumbo 组合等完善点待 M1 坐实。

## LRO 全新支持方向（硬件 offload 路径，M3 细化）

1. 新增 `config.ini` `[dpdk] lro` 配置项 + `ff_config.c` 解析（对齐 tso 写法）。
2. 解除 `ff_dpdk_if.c:890-897` `#if 0`，宏名更正为 `RTE_ETH_RX_OFFLOAD_TCP_LRO`（M1 核对 DPDK 24.11 头文件），按 `dev_info.rx_offload_capa` 探测能力，置 `rxmode.offloads` + `hw_features.rx_lro`。
3. 收包路径 `ff_veth_input`：硬件 LRO 聚合的大段 mbuf 上送，评估 `ff_mbuf_gethdr` 的 csum/包长处理、ifnet `IFCAP_LRO` 标记、与协议栈 `if_input` 的衔接。
4. 评估与 RSS、csum offload、时间戳、`mtu_enable`(jumbo)、scatter/multi-seg、多进程 primary/secondary 的组合与回归。
5. 诚实边界：本机 virtio 是否支持 `RTE_ETH_RX_OFFLOAD_TCP_LRO` 须运行时 `dev_info` 确认，spec 阶段标“待运行时验证”。

## TSO 完善方向（M3 细化，M1 先坐实）

1. 坐实 offload 填充是否缺 `l2_len`/`l3_len`（DPDK TSO 通常要求 l2/l3/l4_len 齐全 + `RTE_MBUF_F_TX_TCP_SEG` 标记）。
2. IPv4/IPv6 TSO 路径差异（`CSUM_TSO` vs IPv6 等价、伪头校验和）。
3. TSO 与 checksum offload、`tx_csum_offoad_skip`、scatter/`MULTI_SEGS`、`mtu_enable`(jumbo) 的组合正确性。
4. PMD 能力校验完整性、多进程一致性、错误回退。

## 第二轮补充结论（软件 LRO/TSO + 软硬对接）

> 第一轮已完成硬件 LRO/TSO offload（config lro 开关、`RTE_ETH_RX_OFFLOAD_TCP_LRO`、`IFCAP_LRO`、TSO IPv6 分流、`if_hw_tsomax`），运行时验证本机 virtio 不支持硬件 offload 而优雅降级。第二轮聚焦软件路径与对接（三方交叉验证：代码坐实 + explorer 探测 + 外网调研）。

- **软件 LRO：完全未接通**（`tcp_lro.c` 编译进 lib 但 lib 调用点=0）。唯一缺口=未接入 `ff_veth_input`（`ff_dpdk_if.c:1707`）。方案：仿 iflib 范式引 per-lcore `struct lro_ctrl`，**推荐经典模式**（`tcp_lro_init`+`tcp_lro_rx`+`tcp_lro_flush_inactive`）以规避 `tcp_lro.c:1261` 对 NULL `tcp_hpts_softclock`（`ff_stub_14_extra.c:627`）的裸调用崩溃风险。
- **软件 TSO：无需开发**。本质=协议栈按 MSS 正常分段（NIC 无 TSO→`TF_TSO` 不置→`tcp_output.c:558` `tso=0`→逐段发），协议栈固有能力，已工作。`rte_gso` 为可选优化，本轮不引入。
- **软硬对接：唯一实质缺口=收端软件 LRO 接入**；发端 TSO/csum 协议栈与硬件能力天然一致（`CSUM_TSO` 门控）。开关语义**推荐方案 A（单 `lro` 开关自动选优：硬件优先+软件回退）**，软件回退标志 `sw_lro` 纳入 `ff_hw_features` 且与硬件 `rx_lro` **严格互斥**（杜绝二次聚合）；`IFCAP_LRO` 条件扩展为 `rx_lro||sw_lro`；`lro=0/tso=0` 默认零回归。
- **重要校准**：探测发现现有代码已比第一轮前的旧现状文档超前（`IFCAP_LRO`/`if_hw_tsomax`/`lro=0` 已存在，系第一轮硬件 offload 实现产物），02/13 文档已如实以最新代码为准标注。
