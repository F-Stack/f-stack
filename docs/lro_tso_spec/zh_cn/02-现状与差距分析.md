# F-Stack LRO/TSO 现状与差距分析（中文）

> 文档层级：现状与差距分析（M1 阶段产出之二）
> 方法：逐层用**实际代码 file:line** 坐实现状，逐条给出差距/影响。凡与 plan mode 预读不一致处，标注"预读为 X，实际为 Y"，一律以代码为准。
> 权威版本：DPDK `dpdk-stable-24.11.6`、FreeBSD 15.0 移植（`f-stack/freebsd/`）。

---

## 一、LRO 现状逐层分析（当前不支持）

### 1.1 配置层（config.ini）

- **现状**：`config.ini` 中**无任何 `lro` 配置项**（`config.ini` 搜索 `lro` 命中 0）。仅有相邻的 `tx_csum_offoad_skip`（L19）、`tso=0`（L22）、`vlan_strip=1`（L25）。
- **差距**：缺少 `dpdk.lro` 开关，用户无法启用 LRO。
- **影响**：LRO 无入口，整条通路从起点即断。

### 1.2 解析层（ff_config.c）

- **现状**：`ff_config.c:1054-1057` 只解析 `dpdk.tso`、`dpdk.tx_csum_offoad_skip`；全文件搜索 `tso` 仅命中 L1054-1055 一处，**无 `lro` 解析分支**。
- **差距**：无 `MATCH("dpdk", "lro")` 分支，即便 config.ini 写了 `lro` 也不会被读入。
- **影响**：`hw_features.rx_lro` 永远拿不到用户配置值。

### 1.3 结构层（ff_config.h）

- **现状**：`struct ff_hw_features` **已含** `uint8_t rx_lro;`（`ff_config.h:114`），位于 `rx_csum`（L113）与 `tx_csum_ip`（L115）之间。`tx_tso` 在 L117。config 结构体内 `int tso;`（`ff_config.h:295`），**无 `int lro;`**。
- **差距**：`rx_lro` 字段存在但**无任何赋值点（生产者）与消费点（使用者）**；config 结构体缺 `lro` 成员。
- **影响**：字段是"死字段"，需补生产/消费两端。
- **纠正**：预读疑问"是否有 rx_lro" → 实际已存在。

### 1.4 DPDK 使能层（ff_dpdk_if.c）

- **现状**：`ff_dpdk_if.c:891-898` LRO 使能代码被 `#if 0 ... #endif` 完全禁用：
  ```
  891  /* FIXME: Enable TCP LRO ?*/
  892  #if 0
  893  if (dev_info.rx_offload_capa & DEV_RX_OFFLOAD_TCP_LRO) {
  894      ff_log(... "LRO is supported\n");
  895      port_conf.rxmode.offloads |= DEV_RX_OFFLOAD_TCP_LRO;
  896      pconf->hw_features.rx_lro = 1;
  897  }
  898  #endif
  ```
- **宏名核对**：使用的 `DEV_RX_OFFLOAD_TCP_LRO` 在 **DPDK 24.11.6 中不存在**（`rte_ethdev.h` 搜索 `DEV_RX_OFFLOAD_TCP_LRO` 命中 0）；正确宏为 `RTE_ETH_RX_OFFLOAD_TCP_LRO`（`dpdk-stable-24.11.6/lib/ethdev/rte_ethdev.h:1556`，`#define RTE_ETH_RX_OFFLOAD_TCP_LRO RTE_BIT64(4)`）。
- **差距**：(a) 代码被 `#if 0` 禁用；(b) 即使去掉 `#if 0`，`DEV_RX_OFFLOAD_TCP_LRO` 未定义会导致**编译失败**；(c) 未按 `dpdk.lro` 配置控制，也未设置 `max_lro_pkt_size`。
- **影响**：`port_conf.rxmode.offloads` 永不含 LRO 位，`hw_features.rx_lro` 永远为 0。
- **纠正**：预读两候选宏 → 实际只有 `RTE_ETH_RX_OFFLOAD_TCP_LRO`。

### 1.5 收包路径层（ff_dpdk_if.c / ff_veth.c）

- **现状（收包入口）**：`ff_dpdk_if.c:1694-1742 ff_veth_input`：
  - L1697-1703：若 `rx_csum` 开启，检查 `RTE_MBUF_F_RX_IP_CKSUM_BAD | RTE_MBUF_F_RX_L4_CKSUM_BAD`，坏则丢包。**无对 `RTE_MBUF_F_RX_LRO` 的任何处理**。
  - L1708：`ff_mbuf_gethdr(pkt, pkt->pkt_len, data, len, rx_csum)` 用 `pkt->pkt_len`（整链总长）建 mbuf 头。
  - L1725-1739：遍历 `pkt->next` 多段链，逐段 `ff_mbuf_get` 挂到 mbuf 链（已能处理多段/scatter）。
  - L1741：`ff_veth_process_packet` → `if_input`。
- **现状（mbuf 头构建）**：`ff_veth.c:464-485 ff_mbuf_gethdr`：`m->m_pkthdr.len = total`（=pkt_len），`rx_csum` 时置 `CSUM_IP_CHECKED|CSUM_IP_VALID|CSUM_DATA_VALID|CSUM_PSEUDO_HDR` 且 `csum_data=0xffff`。**无 LRO 相关标记/字段（如 mbuf 的 `csum_flags` LRO 语义、`tcp_lro` 段信息）**。
- **现状（上送）**：`ff_veth.c:510-519 ff_veth_process_packet`：仅设 `rcvif` 后 `if_input`，无 LRO 特殊处理。
- **差距**：收包路径**完全不感知硬件 LRO**。硬件 LRO 上送的大段（`pkt_len` 会很大、`nb_segs` 可能 >1、带 `RTE_MBUF_F_RX_LRO` 标记）虽然凭 `pkt_len` + 多段遍历在**长度上**能被搬进 FreeBSD mbuf，但：(a) 无 `RTE_MBUF_F_RX_LRO` 感知；(b) 协议栈侧未通过 `IFCAP_LRO` 声明支持，FreeBSD 可能对超 MTU 的合并段做非预期处理；(c) csum 语义对 LRO 大段是否成立需运行时确认。
- **影响**：即便强行开启 PMD LRO，上送大段能否被协议栈正确接收**待运行时验证**；缺少显式 LRO 通路适配是主要缺口。

### 1.6 软件 LRO / stub 层（ff_stub_14_extra.c / Makefile）

- **现状**：`ff_stub_14_extra.c:629-639`：`tcp_lro_hpts_init()` 返回 0、`tcp_lro_hpts_uninit()` 空体（均为空 stub）；`tcp_hpts_softclock` 置 NULL（L627）。
- **编译列表**：`lib/Makefile:513` 含 `tcp_lro.c`（软件 LRO 核心已编译）；`lib/Makefile:572` 含 `tcp_hpts.c`；**`tcp_lro_hpts.c` 未出现在 Makefile**（搜索 0 命中）。
- **F-Stack 调用**：`ff_veth.c` 搜索 `tcp_lro_init|tcp_lro_rx|tcp_lro_flush|tcp_lro` **命中 0** → 软件 LRO 有代码但**无 F-Stack 收包路径调用点**。
- **差距**：软件 LRO 处于"编译进来但无人调用"状态；HPTS LRO 相关能力被 stub 掉。
- **影响**：本轮聚焦硬件 LRO，软件 LRO 是否作为补充/回退路径留待后续评估。
- **纠正**：预读问"tcp_lro.c/tcp_lro_hpts.c 是否被编译" → `tcp_lro.c` 已编译（L513），`tcp_lro_hpts.c` **未编译**。

### 1.7 ifnet 能力层（IFCAP_LRO）

- **现状**：`ff_veth.c:941-956` 设置接口能力：`IFCAP_RXCSUM`(rx_csum)、`IFCAP_TXCSUM`+`CSUM_IP`(tx_csum_ip)、`CSUM_DELAY_DATA`(tx_csum_l4)、`IFCAP_TSO`+`CSUM_TSO`(tx_tso)，最后 `if_setcapenable(ifp, if_getcapabilities(ifp))`。全 lib 搜索 `IFCAP_LRO` **命中 0**。
- **差距**：**从不设置 `IFCAP_LRO`**，FreeBSD 协议栈不认为该接口支持 LRO。
- **影响**：协议栈层面 LRO 通路缺失，即使硬件合并了段，ifnet 能力位也未声明 LRO。

### 1.8 LRO 差距汇总表

| 层 | 现状 | 目标 | 差距 | 影响 | file:line |

## 二、TSO 现状逐层分析（已支持，找完善点）

### 2.1 配置与解析层

- **现状**：`config.ini:21-22` `# TCP segment offload, default: disabled.` + `tso=0`；`ff_config.c:1054-1055` `MATCH("dpdk","tso") → pconfig->dpdk.tso = atoi(value)`；结构 `ff_config.h:295 int tso;`、`ff_config.h:117 uint8_t tx_tso;`。
- **是否完善**：完善。默认关闭、解析正常、字段齐全。
- **差距**：无。

### 2.2 DPDK 使能层

- **现状**：`ff_dpdk_if.c:931-942`：`if (dpdk.tso)` → 若 `dev_info.tx_offload_capa & RTE_ETH_TX_OFFLOAD_TCP_TSO` 则 `port_conf.txmode.offloads |= RTE_ETH_TX_OFFLOAD_TCP_TSO` 并置 `hw_features.tx_tso = 1`，否则日志"TSO is not supported"。宏名 `RTE_ETH_TX_OFFLOAD_TCP_TSO` 为 24.11.6 正确宏。
- **是否完善**：基本完善。
- **差距**：仅按单一 TCP TSO 能力探测，未涉及 IPv6/UFO 等细分；可接受。

### 2.3 offload 字段填充层（逐字段核对）

存在**两处近乎重复**的填充实现：

**(A) `ff_dpdk_if.c:2405-2472`（`ff_dpdk_if_send` 发包主路径）**：
- L2405-2406：`ff_tx_offload offload = {0}; ff_mbuf_tx_offload(m, &offload);`
- L2410-2420 `if (offload.ip_csum)`：注释"ipv6 not supported yet"，按 IPv4 取 `iph_len`，置 `RTE_MBUF_F_TX_IP_CKSUM|RTE_MBUF_F_TX_IPV4`、`l2_len=RTE_ETHER_HDR_LEN`、`l3_len=iph_len`。
- L2422-2471 `if (ctx->hw_features.tx_csum_l4)`：按 `iph->version` 置 `RTE_MBUF_F_TX_IPV4`/`_IPV6`（L2428-2432）；
  - L2434-2438 tcp_csum：置 `TCP_CKSUM`、`l2_len`、`l3_len`；
  - **L2455-2465 TSO**：`if (offload.tso_seg_size)` → `tcph = iph + iph_len`（**按 IPv4 结构强转**）、`tcph->cksum = rte_ipv4_phdr_cksum(iph, RTE_MBUF_F_TX_TCP_SEG)`（**仅 IPv4 伪头**）、`ol_flags |= RTE_MBUF_F_TX_TCP_SEG`、`l4_len = tcph_len`、`tso_segsz = offload.tso_seg_size`。
  - L2467-2471 udp_csum：置 `UDP_CKSUM`、`l2_len`、`l3_len`。

**(B) `ff_memory.c:331-375`（另一发包路径，结构与 A 几乎逐行相同）**：
- L358-368 TSO 分支：同样 `rte_ipv4_phdr_cksum(iph, RTE_MBUF_F_TX_TCP_SEG)`（仅 IPv4）、置 `TCP_SEG`、`l4_len`、`tso_segsz`。

**逐字段结论**（TSO 分支实际填充）：

| 字段 | IPv4 是否填 | 位置 | IPv6 是否填 |
| --- | --- | --- | --- |
| `RTE_MBUF_F_TX_TCP_SEG` | 是 | `ff_dpdk_if.c:2462` / `ff_memory.c:365` | 走同分支但伪头算错 |
| `l2_len` | 是（在 tcp_csum 分支 L2436；或 ip_csum 分支 L2418） | — | 依赖前置分支 |
| `l3_len` | 是（tcp_csum 分支 L2437） | — | 依赖前置分支 |
| `l4_len` | 是 | `ff_dpdk_if.c:2463` / `ff_memory.c:366` | 是（但基于 IPv4 偏移） |
| `tso_segsz` | 是 | `ff_dpdk_if.c:2464` / `ff_memory.c:367` | 是 |
| `RTE_MBUF_F_TX_IPV4/_IPV6` | 是（L2428-2432 按 version） | — | 是 |
| `RTE_MBUF_F_TX_IP_CKSUM`（TSO IPv4 要求） | **否**（TSO 分支未显式置 IP_CKSUM，依赖 ip_csum 分支 L2417 是否命中） | — | N/A |
| 伪头校验和 | `rte_ipv4_phdr_cksum` | L2460 / L363 | **错误：IPv6 也用 IPv4 伪头** |

- **是否完善**：**IPv4 TSO 基本完善**（l2/l3/l4/segsz/TCP_SEG 齐全）。
- **差距**：
  1. **IPv6 TSO 缺失/错误**：TSO 分支无条件用 `rte_ipv4_phdr_cksum` 与 IPv4 头结构，IPv6 大段 TSO 时伪头校验和算错、`l3_len` 基于 IPv4 IHL 计算亦不适用 → IPv6 TSO 不可用。
  2. **TSO 分支未显式置 `RTE_MBUF_F_TX_IP_CKSUM`**：DPDK 语义要求 IPv4 TSO 同时请求 IP 校验和卸载；当前依赖 `offload.ip_csum`（来自 `CSUM_IP`）是否恰好置位，非 TSO 自洽。
  3. **两处重复**：`ff_dpdk_if.c` 与 `ff_memory.c` 逻辑分叉，修 IPv6 需同改两处，易漏。
- **影响**：默认 `tso=0` 无影响；一旦开启 TSO 且走 IPv6，发包异常/校验和错。
- **纠正**：预读担心"只见 l4_len/tso_segsz、l2/l3/TCP_SEG 是否填" → 实际 l2_len/l3_len 在相邻 tcp_csum 分支已填、TCP_SEG 标记已置；真正缺口是 **IPv6 与 IP_CKSUM 自洽性**。

### 2.4 offload 来源层（ff_veth.c ff_mbuf_tx_offload）

- **现状**：`ff_veth.c:282-307 ff_mbuf_tx_offload`：从 FreeBSD mbuf `csum_flags` 映射到 `ff_tx_offload`：`CSUM_IP→ip_csum`、`CSUM_TCP|CSUM_TCP_IPV6→tcp_csum`、`CSUM_UDP|CSUM_UDP_IPV6→udp_csum`、`CSUM_SCTP|CSUM_SCTP_IPV6→sctp_csum`、**`CSUM_TSO→tso_seg_size = mb->m_pkthdr.tso_segsz`**（L304-306）。
- **是否完善**：TCP/UDP csum 已做 v4/v6 合并映射；**但 TSO 只识别 `CSUM_TSO`**，未区分 IPv6 TSO 语义（FreeBSD 有 `CSUM_IP6_TSO`）。
- **差距**：`ff_tx_offload` 为协议无关（注释 L290-291），`tso_seg_size` 不带 v4/v6 信息，下游只能靠 `iph->version` 判断，而下游 TSO 分支恰恰没按 version 分流伪头计算 → IPv6 断链。

### 2.5 IPv4 vs IPv6 TSO（FreeBSD 侧交叉）

- **现状**：`freebsd/netinet` 中 `CSUM_IP6_TSO|CSUM_TSO` 命中 6 文件（`ip_output.c`×4、`tcp_subr.c`×4、`tcp_input.c`×1、`tcp_output.c`×1、`bbr.c`×2、`rack.c`×3）→ FreeBSD 15.0 **原生支持 IPv6 TSO 语义**。
- **`tcp_output.c:1404-1405`**：`m->m_pkthdr.csum_flags |= CSUM_TSO; m->m_pkthdr.tso_segsz = tp->t_maxseg - optlen - ipsec_optlen;` → 协议栈对 IPv4/IPv6 都可能置 `CSUM_TSO`（此处未区分 v6）。
- **差距**：FreeBSD 侧会给 IPv6 段打 TSO 标记并交付 lib，但 lib 下游只按 IPv4 处理 → **v6 缺口在 lib 移植层，不在 FreeBSD 侧**。

### 2.6 TSO 与其他特性的交互

- **与 checksum offload / `tx_csum_offoad_skip`**：`ff_config.c:1056` 解析 `tx_csum_offoad_skip`；`ff_dpdk_if.c:914-929` 当 skip=0 时才启用 IPv4/L4 csum offload。TSO 隐含需要 L4 csum offload，但 TSO 使能（L931-942）**不受 `tx_csum_offoad_skip` 约束**，二者可能出现"TSO 开但 L4 csum offload 被 skip"的不一致组合。
- **与 scatter / MULTI_SEGS**：`ff_dpdk_if.c:2360-2403` 发包已支持多段 mbuf 链（逐段 copy、`head->nb_segs++`）；TSO 大段本身就是多段场景，路径存在但需确认 `nb_segs`/`tso_segsz` 组合的 PMD 约束。
- **与 `mtu_enable`（jumbo）**：`ff_config.c:1068-1072` 解析 `mtu_enable`/`max_mtu`；`ff_dpdk_if.c:954+` 按 MTU 校验范围。TSO 段长与 jumbo MTU、`if_hw_tsomax` 相互制约（见 2.7）。
- **差距/影响**：上述组合的正确性需在方案设计中显式约束（如"TSO 依赖 L4 csum offload、不应与 skip 同时生效"），并留运行时验证。

### 2.7 FreeBSD 侧 TSO 分段与 tsomax

- **现状**：`freebsd/netinet/tcp_output.c:905-931` TSO 决策：`if_hw_tsomax = tp->t_tsomax`、`if_hw_tsomaxsegcount = tp->t_tsomaxsegcount`、`if_hw_tsomaxsegsize = tp->t_tsomaxsegsize`；L927 `if (if_hw_tsomax != 0)` 才计算 `max_len` 上限；L1093-1095 `tcp_m_copym(..., if_hw_tsomaxsegcount, if_hw_tsomaxsegsize, ...)` 据此约束分段。
- **lib 侧设置**：`ff_veth.c:951-953` 仅 `if_setcapabilitiesbit(ifp, IFCAP_TSO, 0)` + `if_sethwassistbits(ifp, CSUM_TSO, 0)`；全 lib 搜索 `if_hw_tsomax` **命中 0** → **lib 从不设置 `if_hw_tsomax`/`tsomaxsegcount`/`tsomaxsegsize`**。
- **差距**：`t_tsomax` 系列若为 0，`tcp_output.c:927` 分支不生效，TSO 段长不受接口上限约束，可能生成超出 PMD/jumbo 能力的大段。
- **影响**：默认关闭无影响；开启 TSO 后大段可能超过 PMD 单包/段数上限，导致发包被 PMD 拒绝或截断（待运行时验证）。
- **完善点**：在 ifnet 侧按 PMD 能力/`max_mtu` 设置 `if_hw_tsomax` 系列上限。

### 2.8 TSO 完善点汇总表

| 完善点 | 现状 | 目标 | 差距 | 影响 | file:line |
| --- | --- | --- | --- | --- | --- |
| IPv6 TSO 伪头 | 一律 `rte_ipv4_phdr_cksum` | 按 version 用 `rte_ipv6_phdr_cksum` | IPv6 伪头算错 | v6 TSO 不可用 | `ff_dpdk_if.c:2455-2465`；`ff_memory.c:358-368` |
| IPv6 TSO l3_len | 按 IPv4 IHL 计算 | IPv6 固定 40（+ 扩展头） | v6 l3_len 错 | v6 分段错 | `ff_dpdk_if.c:2415/2458` |
| IP_CKSUM 自洽 | TSO 分支不显式置 `TX_IP_CKSUM` | IPv4 TSO 显式置位 | 依赖 ip_csum 命中 | 潜在校验和缺失 | `ff_dpdk_if.c:2455-2465` |
| tsomax 上限 | lib 从不设 `if_hw_tsomax` | 按 PMD/MTU 设上限 | 上限缺失 | 段可能超 PMD 能力 | `ff_veth.c:951-953`；`tcp_output.c:905-931` |

## 四、总体结论

1. **LRO**：从配置到协议栈**六层全断**（无 config 项/无解析/字段空转/DPDK `#if 0`+失效宏/收包无 LRO 感知/无 `IFCAP_LRO`），需按硬件 offload 路径全新打通；软件 LRO（`tcp_lro.c`）已编译但无调用点，本轮不作首选。
2. **TSO**：IPv4 已基本可用，主要完善点集中在 **IPv6 TSO 断链**（下游一律按 IPv4 伪头）、**`if_hw_tsomax` 上限未设**、**双份重复逻辑**、**与 csum_skip 组合一致性**。FreeBSD 侧原生支持 IPv6 TSO，缺口在 lib 移植层。
3. 所有涉及具体 PMD 行为的结论（LRO 大段接收、TSO 段长上限、csum 正确性）均标注**待运行时验证**，本轮不实测。

## 五、软件 LRO / 软件 TSO 与软硬对接现状（第二轮补充）

> 背景：第一轮已完成硬件 offload 路径（config lro 开关、`RTE_ETH_RX_OFFLOAD_TCP_LRO` 使能、`IFCAP_LRO`、TSO IPv6 分流、`if_hw_tsomax`），运行时验证本机 virtio 不支持硬件 TSO/LRO（`guest_features=0x110ef8020`）而优雅降级。本轮聚焦**用户态协议栈软件 LRO/软件 TSO** 与 **软件路径 ↔ 硬件 offload 的对接**。以下均为实测 file:line 坐实（工作目录 `f-stack/`，DPDK `dpdk-stable-24.11.6/`），三方（leader 坐实 + sw-path-explorer 探测 + web-researcher 外网）交叉一致。

### 5.1 软件 LRO 现状（tcp_lro.c 编译进来但完全未接通）

- **调用点为 0**：全 `lib/*.c` 搜 `tcp_lro_(init|init_args|rx|flush_all|queue_mbuf|free)` **命中 0**。软件 LRO 有代码无调用，处于"编译进来但无人调用"状态。
- **API 齐全**（`freebsd/netinet/tcp_lro.c` / `tcp_lro.h`）：
  - `tcp_lro_init`(tcp_lro.c:167)、`tcp_lro_init_args`(:173)、`tcp_lro_free`(:491)、`tcp_lro_rx`(:1426)、`tcp_lro_flush_all`(:1199)、`tcp_lro_queue_mbuf`(:1448)；`tcp_lro_flush` 为 static 内部函数(:86/:1109)。声明 tcp_lro.h:215-222。
  - `struct lro_ctrl` 定义 tcp_lro.h:161-181（`ifp`/`lro_mbuf_data`/`lro_mbuf_count,max`/`lro_hash`/`lro_active,free`）。
- **两种聚合模式**（外网 FreeBSD Journal 佐证）：
  - 经典：`tcp_lro_init` + `tcp_lro_rx`（直接进 `tcp_lro_rx_common` 聚合）。
  - 现代 RSS 排序：`tcp_lro_init_args`（分配成对数组）+ `tcp_lro_queue_mbuf`（存序列号，数组满时 `tcp_lro_flush_all` 先排序让同流相邻再聚合）。
- **iflib 接入范式（黄金参考，f-stack 不用 iflib）**：`iflib.c:462` 每 rxq 一个 `struct lro_ctrl ifr_lc`；init `tcp_lro_init_args`(iflib.c:6035)；每包 `tcp_lro_queue_mbuf`(iflib.c:3000，`lro_enabled` 门控 L2999)；批末 `tcp_lro_flush_all`(iflib.c:3029)；free `tcp_lro_free`(iflib.c:6056/6079)。**`iflib.c` 未编译进 f-stack**（Makefile 搜 iflib=0），f-stack 用自研 `ff_veth` 收包，需自行仿此模式接入。
- **⚠ hpts stub 关键风险**：
  - `tcp_lro.c:73` include `tcp_hpts.h`；flush 内 `tcp_lro_flush_tcphpts` 函数指针(:92)为 NULL 时 L1114-1116 安全回退 `tcp_lro_condense`（核心聚合可脱离 hpts）。
  - **但 `tcp_lro_flush_all` 结尾 tcp_lro.c:1261 裸调 `tcp_hpts_softclock()`**，而 `ff_stub_14_extra.c:627` `tcp_hpts_softclock=NULL` → **若接通软件 LRO 走 `tcp_lro_flush_all` 会解引用 NULL 崩溃**。这是软件 LRO 接入的头号阻断风险，须在方案中处理（详见 11-软件LRO方案.md）。
  - `tcp_lro_hpts.c` 未在 Makefile（=0，符合预期）；`ff_stub_14_extra.c:629-639` `tcp_lro_hpts_init`/`uninit` 为空 stub，仅影响 hpts 侧 LRO 加速，不阻塞基础软件聚合。

### 5.2 软件 TSO 现状（本质=协议栈 MSS 分段，天然工作，无需开发）

- **逻辑链坐实**：
  - `tcp_output.c:558-565`：`if ((tp->t_flags & TF_TSO) && V_tcp_do_tso && len > tp->t_maxseg ...) tso = 1;`，L993-994 `else tso = 0`。
  - `TF_TSO` 唯一设置点：`tcp_input.c:3973-3974` `if (cap.ifcap & CSUM_TSO) tp->t_flags |= TF_TSO;`。
  - `cap.ifcap` 来源：`tcp_subr.c:3657-3660`（IPv4，需 `IFCAP_TSO4 && if_hwassist & CSUM_TSO`）/ `:3699-3701`（IPv6，`IFCAP_TSO6`）。
- **结论**：NIC 无 TSO → `ff_veth.c:955` `tx_tso=0` → 不设 `IFCAP_TSO/CSUM_TSO` → `cap.ifcap` 无 `CSUM_TSO` → `TF_TSO` 不置 → `tso=0` → `tcp_output` 按 `t_maxseg`(MSS) 逐段发小包（常规 `sendalot` 循环）。`CSUM_TSO` 仅 `tso=1` 时置（tcp_output.c:1401-1405）。**"软件 TSO" = 协议栈固有的 MSS 分段，已工作，无缺口、无需开发**（`tcp_var.h:789 TF_TSO=0x01000000`）。

### 5.3 DPDK 软件 offload 库现状（rte_gso/rte_gro 存在但 f-stack 零使用）

- `dpdk-stable-24.11.6/lib/gso/`（`rte_gso_segment` @rte_gso.h:120）、`lib/gro/`（`rte_gro_reassemble_burst` @rte_gro.h:111、`rte_gro_reassemble` :142、`rte_gro_ctx_create` :78、取结果 `rte_gro_timeout_flush`）均存在。
- **f-stack `lib/*.c` 搜 `rte_gso|rte_gro|gso_segment|gro_reassemble` 命中 0**，完全未用。
- 定位（外网 DPDK 官方）：`rte_gro`=硬件 LRO 软件替代（接收聚合）、`rte_gso`=硬件 TSO 软件替代（发送分段）；均需应用**显式调用**、非线程安全、不重算校验和、需手动填 `l2/l3/l4_len`；`rte_gso` 目前仅 IPv4。属可选软件 offload 补充路径。

### 5.4 软硬 offload 对接现状（唯一实质缺口=收端软件 LRO 未接入）

- **收包 `ff_veth_input`(ff_dpdk_if.c:1707-1748)**：`rx_csum` BAD 丢包(:1711)→`ff_mbuf_gethdr(pkt, pkt->pkt_len, ...)`(:1720) 整段上送→多段链遍历(:1737-1751)。**软件 LRO 接入缺口在此、`ff_mbuf_gethdr` 之前**（硬件不支持 LRO 时插入 `tcp_lro_rx/queue_mbuf` 聚合的天然接入点）。
- **发包 `ff_dpdk_if_send`(ff_dpdk_if.c:2360+) + tx 组装(:2434 tx_csum_l4)**：直接把协议栈给的 mbuf 交 PMD，无软件分段位置。因软件 TSO 已由协议栈完成 MSS 分段（5.2），发包端拿到即小包，**发端无缺口**（rte_gso 是可选优化，非必需）。
- **`ff_mbuf_tx_offload`(ff_veth.c:283-308)**：L305-307 仅 `csum_flags & CSUM_TSO` 时取 `tso_segsz`；NIC 无 TSO 协议栈不置 `CSUM_TSO` → `tso_seg_size` 不被设 → **协议栈与硬件能力天然一致，无冲突**。
- **`struct ff_hw_features`(ff_config.h:112-118)**：`rx_csum`(113)/`rx_lro`(114)/`tx_csum_ip`(115)/`tx_csum_l4`(116)/`tx_tso`(117)，均 uint8_t。填充 ff_dpdk_if.c:895/914/926/933/947（以 dev_info offload_capa 为门槛）；消费 ff_veth.c:942-961 + ff_dpdk_if.c:1709/2434。
- **config.ini offload 项**：`tx_csum_offoad_skip=0`(:19)、`tso=0`(:22)、`lro=0`(:24)。无独立 rx/tx csum 开关（由 NIC 能力自动使能）。

### 5.6 本轮总体结论

1. **软件 LRO**：完全未接通（0 调用点），需在 `ff_veth_input` 仿 iflib 范式接入 `struct lro_ctrl`（init/rx/flush/free），**头号阻断风险是 tcp_lro.c:1261 对 NULL `tcp_hpts_softclock` 的裸调用**，须先处理。
2. **软件 TSO**：本质是协议栈 MSS 分段，天然工作，**无需开发**；`rte_gso` 为可选优化，不在本轮范围。
3. **软硬对接**：唯一实质缺口是收端软件 LRO 接入；发端 TSO/csum 协议栈与硬件能力天然一致，无缺口。需设计软硬协同的开关语义（硬件优先 + 软件回退）与零回归保证。
4. 所有涉及具体 PMD/运行时行为的结论均标注**待运行时验证**（软件 LRO 聚合正确性、CPU/时延收益、与拥塞控制交互等）。

### 6.2 架构调整（与 spec 11/13 设计的差异）

spec 11/13 原设计在 ff_dpdk_if.c 直接 include tcp_lro.h。实现时发现 **ff_dpdk_if.c 编译命令无 `-I.../freebsd`**（DPDK 层 CFLAGS，非 FreeBSD 层），不能 include FreeBSD 头文件。架构调整：LRO 逻辑封装到 ff_veth.c（FreeBSD 层，有完整 include 路径），ff_dpdk_if.c 通过 ff_veth.h 声明调用 ff_lro_* 封装。ff_memory.h 用 `void *lro`（无需 lro_ctrl 完整类型）。这是更干净的分层（DPDK 层调用 FreeBSD 层封装）。

### 6.3 集成测试结果（本机 virtio）

| 场景 | IPv4 | IPv6 | f-stack 日志 | 崩溃 |
| --- | --- | --- | --- | --- |
| lro=1（软件回退） | HTTP 200, 1.8ms | HTTP 200, 1.3ms | "LRO is not supported, fallback to software" | **无**（1261 规避有效） |
