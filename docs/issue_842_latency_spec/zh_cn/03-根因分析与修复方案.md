# 03 - 根因分析与修复方案

## 1. delayed_ack=1 导致连接失败的根因分析

### 1.1 根因机制

`delayed_ack=1` 时，FreeBSD TCP 栈将 ACK 延迟 40ms 发送（`TCPTV_DELACK = MSEC_2_TICKS(40)`，`tcp_timer.h:119`）。在大量数据接收场景下，这导致 TCP 接收窗口耗尽：

```
Server 发送数据 → Client 接收 → 设置 TF_DELACK（延迟 ACK 40ms）
→ Client recv() 释放缓冲区 → recwin 增大
→ tcp_output 检查窗口更新，但 TF_DELACK 被设置 → 窗口更新被阻止
→ 40ms 内接收缓冲区被填满 → recwin=0 → 发送零窗口 ACK
→ Server 收到零窗口 → 停止发送 → 持续探测窗口
→ 最终连接超时或 RST
```

### 1.2 代码证据

**ACK 延迟条件** (`freebsd/netinet/tcp_input.c:511-515`):
```c
#define DELAY_ACK(tp, tlen) \
    ((!tcp_timer_active(tp, TT_DELACK) && \
      (tp->t_flags & TF_RXWIN0SENT) == 0) && \
     (tlen <= tp->t_maxseg) && \
     (V_tcp_delack_enabled || (tp->t_flags & TF_NEEDSYN)))
```

**窗口更新被阻止** (`freebsd/netinet/tcp_output.c:655-657`):
```c
if (recwin > 0 && !(tp->t_flags & TF_NEEDSYN) &&
    !(tp->t_flags & TF_DELACK) &&  // ← TF_DELACK 阻止窗口更新
    !TCPS_HAVERCVDFIN(tp->t_state)) {
```

**40ms 定时器** (`freebsd/netinet/tcp_timer.h:119`):
```c
#define TCPTV_DELACK MSEC_2_TICKS(40) // 40ms timeout
```

### 1.3 为什么内核不受影响

Linux 内核的 delayed_ack 实现有以下差异：
- Linux delayed_ack 最多延迟 200ms 但有 **quick ACK** 机制（收到第一个数据段后立即 ACK）
- Linux 的窗口更新不受 delayed_ack 阻止
- Linux 有更积极的窗口更新策略

## 2. ff_epoll EPOLLOUT 转换缺陷

### 2.1 问题现象

F-Stack 的 `ff_epoll` 在 connect 完成后不稳定返回 EPOLLOUT 事件。实测：
- kqueue 能正确返回 EVFILT_WRITE（filter=-2）
- 但 ff_epoll_wait 有时返回 EPOLLIN（0x1）而非 EPOLLOUT（0x4）

### 2.2 代码分析

`lib/ff_epoll.c:92-204` 实现了 ff_epoll_ctl 和 ff_epoll_wait：
- `ff_epoll_ctl` 将 EPOLLOUT 转换为 kqueue EVFILT_WRITE（正确）
- `ff_epoll_wait` 将 EVFILT_WRITE 转换回 EPOLLOUT（代码逻辑正确，但运行时不稳定）

问题可能在于 F-Stack 的 FreeBSD TCP 栈在 connect 完成后没有稳定触发 kqueue 的 EVFILT_WRITE 通知（`soisconnected` 调用路径中的 `KNOTE_LOCKED` 通知可能不稳定）。

### 2.3 解决方案

使用 kqueue 原生 API 替代 ff_epoll，直接注册 EVFILT_WRITE/EVFILT_READ。这是 F-Stack 原生的事件机制，最可靠。

## 3. TX drain 机制分析

### 3.1 机制

`lib/ff_dpdk_if.c:2643-2645`:
```c
if (pkt_tx_delay) {
    drain_tsc = (rte_get_tsc_hz() + US_PER_S - 1) / US_PER_S * pkt_tx_delay;
}
```

`lib/ff_dpdk_if.c:2728-2743`:
```c
if (unlikely(diff_tsc >= drain_tsc)) {
    // 刷新 TX 批量
    send_burst(qconf, qconf->tx_mbufs[port_id].len, port_id);
    qconf->tx_mbufs[port_id].len = 0;
}
```

pkt_tx_delay=100 时，TX 数据被缓冲最多 100us。62 字节的 GET 请求在 TX 缓冲区中等待 100us 后被刷新。

### 3.2 影响

在 delayed_ack=1 的场景下，TX drain 的 100us 延迟加剧了问题：GET 请求被延迟发送，server 等待更久才开始发送数据。但 TX drain 本身不是根因（pkt_tx_delay=0 但 delayed_ack=1 时 T5 仍然失败）。

## 4. 修复方案

### 4.1 配置修复（已验证有效）

在 `config.ini` 的 `[freebsd.sysctl]` 段设置：
```ini
net.inet.tcp.delayed_ack=0
```

同时建议配合：
```ini
[dpdk]
idle_sleep=0
pkt_tx_delay=0
```

### 4.2 代码修复建议（非本轮范围）

1. **ff_epoll EPOLLOUT 修复**：排查 F-Stack FreeBSD TCP 栈 `soisconnected` 调用路径中 kqueue 通知的不稳定性
2. **delayed_ack 默认值**：考虑将 F-Stack 的 `tcp_delack_enabled` 默认值改为 0（F-Stack 是用户态栈，ACK 延迟对吞吐有害无益）
3. **文档更新**：在 config.ini 注释中明确说明 delayed_ack=1 在大量数据接收场景的风险

### 4.3 不需要代码修复

核心结论是 **Issue #842 在本环境不复现**（配置优化后 F-Stack 与内核持平）。不需要修改 lib 代码。delayed_ack=1 的问题是 FreeBSD TCP 栈的既有行为（非 F-Stack 引入的 bug），通过配置即可解决。
