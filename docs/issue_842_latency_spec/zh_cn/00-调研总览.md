# 00 - 调研总览

## Issue 背景

**Issue**: [#842 Extremely Bad Latency on TCP Connection for receiving Data](https://github.com/F-Stack/f-stack/issues/842)

**状态**: Open（2024-09-23 由 winstonzhao 提交，无评论）

**问题描述**: F-Stack TCP 客户端接收大量数据时，延迟约为原生 Linux 内核的 3.75 倍（F-Stack ~7.5s vs Linux ~2s）。作者已使用优化配置（idle_sleep=0, pkt_tx_delay=0, delayed_ack=0, 大缓冲区）。

## 调研结论

### 核心结论：Issue #842 描述的性能差距在本环境不复现

在本机物理环境（F-Stack 1.26 + FreeBSD 15.0 + DPDK 24.11.6）上，使用与 issue 作者相同的优化配置：

| 测试 | 栈 | 中位耗时 | 结论 |
| --- | --- | --- | --- |
| T1 | Linux Kernel | 9.286s | 基线 |
| T3 | F-Stack 优化配置 | 9.587s | 差距 3.2%，F-Stack 与内核持平 |

**F-Stack 在正确配置下 TCP 接收性能与内核持平**，远小于 issue #842 报告的 3.75 倍差距。

### 关键发现：delayed_ack=1 是导致连接失败的关键配置

| 测试 | delayed_ack | 结果 | 说明 |
| --- | --- | --- | --- |
| T4 | 0 | ✅ 成功 (9.417s) | recvspace=8192 也能正常工作 |
| T5 | 1 | ❌ 失败 | 连接被重置/GET 请求未发送 |

`delayed_ack=1` 时，ACK 被延迟 40ms，TCP 窗口更新被阻止，大量数据接收场景下接收窗口耗尽导致连接被重置。

### 附带发现：ff_epoll EPOLLOUT 转换分析

调研初期观察到 ff_epoll 在 connect 完成后有时返回 EPOLLIN 而非 EPOLLOUT。经深入测试确认：ff_epoll 的 EPOLLOUT 转换逻辑正确（`ff_event_to_epoll` 正确将 EVFILT_WRITE 转为 EPOLLOUT），初始观察到的问题源于测试程序同时在同一 socket 上注册了 ff_epoll 和 kqueue（双重注册导致 knote 机制干扰）。正常使用 ff_epoll 时此问题不会出现。
