# Issue #331 根因分析与修复方案

## 1. 根因分析

### 1.1 Bug 1：callout 调度双重计算（精度问题）

**调用链**：
```
filt_timerstart (kern_event.c:949-959)
  kc->next = to + sbinuptime()          // 绝对 sbintime（TSC 尺度）
  → kqtimer_sched_callout (kern_event.c:787-792)
    callout_reset_sbt_on(&kc->c, kc->next, ..., C_ABSOLUTE)
    → 宏 callout_reset_sbt_on (callout.h:96-97)
      callout_reset_tick_on((c), (kc->next)/tick_sbt, ...)   // 忽略 C_ABSOLUTE，绝对 sbt 转绝对 ticks
      → callout_cc_add (ff_kern_timeout.c:391)
        c->c_time = ticks + to_ticks   // ticks(F-Stack启动后) + 绝对ticks(TSC尺度) = 双重计算
```

**数学验证**（系统 uptime 35 天，hz=100）：
- `sbinuptime()` ≈ 35 天的 sbintime（TSC 基于 CPU 上电）。
- `kc->next` = SBT_1S + SBT_35days ≈ SBT_35days。
- `to_ticks` = kc->next / tick_sbt ≈ 35days/10ms ≈ 3.024e8（绝对 ticks，TSC 尺度）。
- `ticks`（F-Stack 启动后计数）≈ 0。
- `c->c_time` = 0 + 3.024e8 → 定时器要 3.024e8 ticks（≈35 天）后才触发。

**尺度不匹配**：`sbinuptime()`/`kc->next` 基于 TSC（CPU 上电以来），`ticks` 基于 F-Stack 启动后计数。两者尺度差 = 系统 uptime。这是 #331（10s→30-100s）和 #701（since_last 6.2s/68.4s 随时间增长）的根本原因。

### 1.2 Bug 2：普通 callout 轮从不被驱动

**代码**（`lib/ff_kern_timeout.c:329-358`）：
```c
callout_tick(void)
{
    ...
    cc = CC_SELF();
    ...
    for (; (cc->cc_softticks - ticks) < 0; cc->cc_softticks++) {
        bucket = cc->cc_softticks & callwheelmask;
        if (!LIST_EMPTY(&cc->cc_callwheel[bucket])) {
            need_softclock = 1;
            break;
        }
    }
    mtx_unlock(&cc->cc_lock);
#ifndef FSTACK
    if (need_softclock)
        softclock(cc);    // ← F-Stack 编译时(-DFSTACK)为死代码！
#endif
}
```

- `callout_tick` 由 `ff_hardclock`（rte_timer 回调，每 10ms）调用。
- `softclock(cc)` 负责处理普通 callout 轮（执行到期 callout 的 handler）。
- `#ifndef FSTACK` 使该调用在 F-Stack 下永不执行 → 普通 callout 轮上的 callout（EVFILT_TIMER、sleepq 等）**从不触发**。
- F-Stack 只通过 `ff_tcp_hpts_softclock()`（`ff_dpdk_if.c:2811` 主循环）驱动 HPTS 轮，TCP 定时器经 HPTS 路径不受影响。

**调试验证**：Bug 1 修复后（to_ticks=100 正确），加 debug printf 确认 kqtimer_sched_callout 被调用且 to_ticks 正确，但 filt_timerexpire 从未被调用（无 DBG expire）→ 确认 callout 永不触发。

### 1.3 为何 TCP 定时器不受影响

- `lib/ff_stub_14_extra.c:149-153`：`callout_when` 是空函数 stub。
- `tcp_timer.c:920-923` 调 `callout_when` 后 `tp->t_timers[which]` 保持相对 sbt（stub 无操作）。
- 宏转相对 ticks → `c->c_time = ticks + 相对` = 正确（意外）。
- TCP 定时器实际由 HPTS 轮驱动（`ff_tcp_hpts_softclock`），不依赖普通 callout 轮。
- bug 只影响 kern_event.c EVFILT_TIMER（手动算绝对 + 依赖普通 callout 轮）。

### 1.4 上游对比

上游 FreeBSD 15.0 `kern_timeout.c:880-920` `callout_when`：C_ABSOLUTE 时保留绝对 sbt；否则转绝对。上游 `callout_reset_sbt_on`（:939）是真函数，用 sbt-based callout wheel（`c->c_time = to_sbt` 绝对）。F-Stack 用旧 tick-based wheel（ff_kern_timeout.c）+ 空 stub callout_when + 宏化 callout_reset_sbt_on，三者不匹配。

## 2. 修复方案

### 2.1 Bug 1 修复：kern_event.c kqtimer_sched_callout

`freebsd/kern/kern_event.c:787-797`：

```c
static void
kqtimer_sched_callout(struct kq_timer_cb_data *kc)
{
    /* F-Stack callout is tick-based; the sbt macro ignores C_ABSOLUTE,
     * so convert the absolute fire time to relative ticks here. */
    sbintime_t now = sbinuptime();
    int to_ticks = kc->next > now ? (kc->next - now) / tick_sbt + 1 : 0;

    callout_reset_tick_on(&kc->c, to_ticks, filt_timerexpire, kc->kn,
        kc->cpuid, 0);
}
```

**原理**：用 sbinuptime()（与 kc->next 同尺度）计算相对时间 `(kc->next - now)`，转相对 ticks。尺度抵消，结果与 uptime 无关。`+1` 向上取整避免提前触发（filt_timerexpire_l 检查 `now >= kc->next`）。`kc->next <= now`（已过期）时 to_ticks=0 → 下一 tick 立即触发。

**兼容性**：兼容 NOTE_ABSTIME（kc->next=to 绝对 boot 时间）和正常周期（kc->next=to+sbinuptime）。

### 2.2 Bug 2 修复：ff_kern_timeout.c callout_tick

`lib/ff_kern_timeout.c:355-357`：移除 `#ifndef FSTACK` guard：
```c
    if (need_softclock)
        softclock(cc);
```

`lib/ff_kern_timeout.c:199`：添加前向声明：
```c
static void softclock(void *arg);
```

**原理**：softclock() 仅做 cc_lock + 遍历 callout 轮 + 调 handler，无 SWI/scheduler 依赖，在 F-Stack 用户态（ff_hardclock/rte_timer 上下文）安全调用。

### 2.3 方案排除

| 方案 | 排除原因 |
|------|----------|
| 传 kc->to 相对 + 去 C_ABSOLUTE | 不兼容 NOTE_ABSTIME（kc->to=0 立即触发） |
| 修宏 + 实现 callout_when | scope 大、影响 TCP 路径、风险高 |
| `(kc->next/tick_sbt) - ticks`（Option E 原版） | sbinuptime(TSC尺度) 与 ticks(F-Stack启动尺度) 不同 → to_ticks 巨大 |

## 3. 性能考量

- Bug 1 修复仅改变 callout 调度参数计算，无运行时额外开销。
- Bug 2 修复使 softclock 每 10ms 检查一次 callout 轮（need_softclock 为 false 时 O(1) 快速返回），开销极低。
- EVFILT_TIMER 精度上限为 tick 粒度（1/hz=10ms@hz=100），设计限制非 bug。

## 4. native-mt 注意事项

native-mt（多线程）下每个 worker 有独立 callout_cpu（CC_SELF 返回 per-thread cc），ff_hardclock_worker 调 callout_tick → softclock 处理本 worker 的 callout 轮。单线程测试已验证；多线程高并发场景建议后续压测确认。
