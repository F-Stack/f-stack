# Issue #331 测试结果与数据分析

## 1. 复现测试（bug 状态）

**配置**：git stash 撤销 kern_event.c 修复，clean build，运行 evfilt_timer_test（1s 定时器，90s 超时）。

**结果**：
```
START evfilt_timer_test period=1s total=30
（90s 内无任何 TRIGGER 输出）
```

**分析**：1 秒定时器在 90 秒内**零触发**。系统 uptime 为 35 天，sbinuptime() 基于 TSC（CPU 上电以来）≈ 35 天的 sbintime。bug 状态下 `c->c_time = ticks(F-Stack启动后~0) + 绝对ticks(35天/10ms≈3e9)` → 定时器要 ~35 天后才触发。完全印证根因。

## 2. 调试数据（确认 to_ticks 正确但 callout 不触发）

在 kqtimer_sched_callout 加 debug printf（bug 1 修复已应用但 bug 2 未修时）：
```
DBG sched: next=20000431b now=1000053e2 tick_sbt=28f5c28 to_ticks=100 ticks=0 cpuid=0
```

解析（sbintime 高 32 位=秒）：
- `next=0x20000431b` ≈ 2.0s（to=1s + sbinuptime≈1s）
- `now=0x1000053e2` ≈ 1.0s（sbinuptime）
- `tick_sbt=0x28f5c28` = 42949672（SBT_1S/100 = 10ms）✓
- `to_ticks=100`（(next-now)/tick_sbt+1 = 1s/10ms+1 = 100）✓ **正确**
- `ticks=0`（F-Stack 刚启动）

**但无 DBG expire** —— callout 被正确调度（to_ticks=100）却从不触发。这揭示了 Bug 2（softclock 不被调用）。

## 3. T1 精度测试（修复后）

**配置**：两部分修复均应用，clean build，1s 定时器，30 次触发。

**结果**：
```
START evfilt_timer_test period=1s total=30
TRIGGER #1 since_last=0.000
TRIGGER #2 since_last=1.000
TRIGGER #3 since_last=1.000
TRIGGER #4 since_last=1.000
TRIGGER #5 since_last=1.000
...
TRIGGER #10 since_last=1.000
REARM TIMER
TRIGGER #11 since_last=1.020
TRIGGER #12 since_last=1.000
...
TRIGGER #20 since_last=1.000
REARM TIMER
TRIGGER #21 since_last=1.020
TRIGGER #22 since_last=1.000
...
TRIGGER #30 since_last=1.000
REARM TIMER
DONE 30 triggers
```

**分析**：
- 30 次触发全部完成，间隔稳定 1.000s。
- rearm 后首次触发有 20ms 漂移（2 tick，hz=100 粒度内），后续自纠正回 1.000s。
- 不随 uptime 增长（对比 bug 状态零触发）。
- **T1 PASS**。

## 4. T2 周期重设测试

每 10 次触发重设定时器（EV_ADD），验证 filt_timerstart → kqtimer_sched_callout reschedule 路径。
- rearm 后 #11、#21 的 since_last=1.020（20ms 漂移），#12、#22 起恢复 1.000s。
- 漂移原因：rearm 时 sbinuptime() 重新采样，callout 按 to_ticks=100 调度，tick 边界对齐误差 ≤ 1 tick。
- **T2 PASS**。

## 5. T3 TCP 回归测试

**配置**：修复后 lib，csum_test_server + f-stack-client python 客户端。

**结果**：
```
[SERVER] listening on port 15200 fd=1025
[CLIENT] connected to 9.134.214.176:15200
[CLIENT] sent 15 bytes: b'hello-csum-test'
[CLIENT] PASS: received 15 bytes echo: b'hello-csum-test'
```

**分析**：TCP echo 正常。softclock 改动（驱动普通 callout 轮）不影响 TCP（TCP 由 HPTS 驱动，普通 callout 轮启动是叠加而非冲突）。
- **T3 PASS**。

## 6. T4 默认配置回归

T3 已使用默认 config.ini（无 extra_eal_args 等测试值），TCP echo 通过。
- **T4 PASS**（T3 覆盖）。

## 7. 结论

| 测试 | 结果 | 说明 |
|------|------|------|
| 复现 | ✅ bug 确认 | 零触发，延迟 ≈ uptime（35 天） |
| T1 精度 | ✅ PASS | 1.000s 间隔，30 次触发 |
| T2 重设 | ✅ PASS | rearm 后 ~1s（20ms 漂移自纠正） |
| T3 TCP | ✅ PASS | TCP echo 正常 |
| T4 默认 | ✅ PASS | T3 覆盖 |

两部分修复（kqtimer_sched_callout to_ticks + callout_tick softclock）联合生效，EVFILT_TIMER 精度问题完全解决，且不影响 TCP。
